# Design: pandoc.wasm in hub-client ("Download as" docx / pptx / epub / typst, PDF later)

**Date:** 2026-10-01  **Status:** design settled (D1-D12, T1-T7); execution is organized as two epics.
**Epics:** [request seam (Rust)](../plans/2026-10-01-pandoc-request-epic.md) · [host and UI (browser)](../plans/2026-10-01-pandoc-host-epic.md)
**Evidence:** [`../research/2026-10-01-pandoc-wasm-evidence.md`](../research/2026-10-01-pandoc-wasm-evidence.md) (measurements, code refs, sizes); spike code in `../research/2026-10-01-pandoc-wasm-spike/`.
**Builds on:** `../plans/2026-08-20-pandoc-hybrid-epic.md` (native Pandoc-writer hybrid), esp. P4 run machinery (`crates/quarto-core/src/stage/stages/pandoc_write.rs`); for books, [`book-projects-architecture.md`](book-projects-architecture.md).

## Goal and scope

The native `q2 render --to <fmt>` path produces non-HTML formats by handing a format-neutral AST + vendored Q1 Lua to a real `pandoc`.
Make the same output available in **hub-client** (browser) by running the official `pandoc.wasm`, loaded on demand.

- **First demo: docx, pptx, epub, plus typst source (`.typ` only, no compile; D8).** A **"Download as" control** in the print button's top-bar slot renders in the chosen format and downloads the result. No in-browser viewer for these.
- **Projects and books (D10):** single documents and multi-file projects both work, landing after the docx single-document slice. For formats that consolidate a book into one file, the direction is that downloading a chapter produces the whole book (with a "this chapter only" alternative), while the preview shows the active chapter alone.
- **Code cells (D11):** the hub has no engines. Cells render unexecuted unless the cached-execution (capture) system already holds results for them, including results contributed by other peers over the CRDT; the UI reports how many cells were not executed.
- **Follow-on:** PDF via pandoc's typst writer + a typst wasm compiler, shown with a pdf.js viewer (PDF section below).
- **Trust model:** co-authors of a shared project trust one another. There is no content-origin policy for raw output blocks, `reference-doc` or filters. Hygiene that does not depend on origin stays: a hardened remote-image fetch, path rules for mounts, sanitized download names.
- **Out of scope:** latex and other long-tail formats (same machinery, add later), pushing live-preview re-render through pandoc, and native `q2 preview` rendering of these formats (it already has real pandoc and is used by the embedded hub; D7).

## Standing decisions

1. **Host:** a JS host runs pandoc.wasm in a **Web Worker**, separate from the Rust wasm (`wasm-quarto-hub-client`). The two wasm toolchains never meet; they only exchange data.
2. **Delivery:** `pandoc.wasm` is fetched on demand from our own origin, only when a non-HTML format is first requested (D6).
3. **Formats:** docx, pptx, epub and typst-source-only (D8); PDF later via typst.wasm.
4. **UI:** a "Download as" control in `DocumentTopBar`'s print-button slot; PDF later adds a pdf.js viewer.
5. **The two mechanism risks are retired first.** Whether the official wasm runs in WASI *command mode* (`_start`, real argv/env) in a browser, and whether the vendored Q1 Lua runs under wasm pandoc on real pandoc-profile inputs, are the largest unknowns. Host phase H0 settles both before the seam and the host are built; a failure is the stop/rethink point.

## What the spikes and the audit established

- Official pandoc wasm runs in Node and in Chromium and WebKit Workers; it fetches nothing until first convert; output is byte-identical to native for the same AST (docx `document.xml`).
- Rust wasm and pandoc.wasm coexist in one Chromium page; the Rust AST goes straight into `pandoc -f json`. Memory: pandoc linear memory plateaus ~105-118 MB; page RSS about +340 MB once loaded.
- `-f json` + `filters:` + nested Lua `require` + env vars work. The stock npm host is not enough (flat file map; env fixed at init), so **we write our own thin host**.
- **Version:** the wasm is pinned to the native pandoc version `PANDOC_PIN` (3.11), so hub and `q2 render` share one pandoc (D12). npm `pandoc-wasm@1.1.0` ships 3.10 and is too old. The official wasm **requires the WebAssembly exnref exception-handling proposal**: fine in Chromium and WebKit 26.4, needs `--experimental-wasm-exnref` in Node 24, Firefox 157 verified (`spike/ff/`; Playwright's own Firefox won't launch here, so it was run in the real browser).
- **Command mode works in Node.** A runtime audit replayed captured native runs through `_start` with real argv and env: typst output is byte-identical to native, pptx and epub differ only in timestamps and random UUIDs, docx only through SVG images; exit codes arrive as return values; `+RTS` options work; a nested `require` and sibling `io.open` from a user filter match native (evidence §9). The spike measurements (630 ms first docx, memory plateau) were taken in reactor mode on the preview-format AST; command-mode numbers in Node are about 0.3-0.5 s per fresh-instance render, ~250-300 ms of it Lua init. A pre-plan run of the same replay passes every H0 observable criterion in Chromium 148 and WebKit 26.4 and is byte-equal to native for docx (evidence §10); H0 repeats it on the R0 recordings for all four formats and takes the browser numbers.

## Target architecture

```
hub-client (TS)                                       wasm-quarto-hub-client (Rust wasm, main thread)
  "Download as docx"  ───────────────────────────▶   render_pandoc_request(path, format, …)
                                                      = render prelude with format_override
                                                        + HTML-pipeline prefix (ungated builder)
                                                        + remote-image prefetch stage (D5)
                                                        + PandocWriteStage::prepare()  (pure; shared with native)
                      ◀───────────────────────────   PandocRequest { writer, argv, env, files[], dirs[], resource_refs[],
                                                        output_path, post, expected_pandoc_wasm_sha256, share_tree_version }
  main thread: fetch pandoc.wasm.gz (opaque), cache the compressed bytes (Cache API),
    DecompressionStream -> SHA-check the decompressed wasm -> compile once; keeps the resident WebAssembly.Module
  pandoc worker (one short-lived worker per render; the Module is posted to it; the PDF preview alone uses persistent warm workers, D2(b))
    per render: fresh instance; mount the share tree (posted by the main thread, which re-reads it only when share_tree_version changes) + files[] + resource bytes
    at the *absolute paths* the argv names; run the module's `_start` (command mode) with argv + env;
    collect output bytes, stderr (fd 2) and exit code. Abort/timeout = terminate the worker; the Module survives. The PDF preview is the exception: a superseded render there is not terminated, and a warm worker is terminated only on the wall timeout, the adaptive grace rule for a superseded runaway, a poisoned or oversized instance, a pool reboot, or idle (H10b).
                      ──── (ok, status, stderr) ──────▶  classify_pandoc_completion() (shared, pure) -> diagnostics
  Blob -> browser download
```

The Rust side stays the single source of truth for argument construction and filter params. Native and wasm share `prepare()`; they differ only in
`execute()` (native: write files to a temp dir and `Command`; wasm: return the request to the host).

**Path anchoring.** Every argv entry is absolute (`--data-dir`, `-L`, `--resource-path <doc_dir>`, `-o`, `--reference-doc`, `--template`, epub extras). The worker mounts bytes at *identical absolute paths*, so `prepare()` takes an explicit temp root (`PrepareOptions`), which on wasm is the **deterministic share root** (one constant shared by Rust and TS, `/__q2_share__`, never at `/` where a project `filters/` would collide) rather than `ctx.temp_dir()`, whose wasm implementation is a per-call counter (`/tmp/quarto-pipeline-N`). The share root is the temp root: the share tree sits at `<share_root>/pandoc-share` (`QUARTO_SHARE_PATH`), beside the input JSON, results and dependency files. The wasm working directory is `/`, whereas native's is the q2 process cwd, so every user-facing path must be absolute (a relative `--highlight-style` file, for instance, resolves differently). Native tests make the temp root injectable (or normalize it, and Windows separators) when comparing requests.

**Snapshot.** The document is snapshotted at click time: every Rust read in a request goes through one VFS snapshot taken at the click (Automerge sync keeps mutating the live VFS while remote images are fetched), the fetch is the only await, and it only *adds* files. Resource bytes therefore come from the snapshot, not from the live VFS afterwards. The first seam phases have no await, so they are atomic without a snapshot facility; building one belongs to the remote-image phase (request epic R6). The Rust wasm runs on the main thread, so a heavy `prepare()` blocks the UI; that is accepted.

**Failure taxonomy.** Each is one diagnostic plus one UI state, each with a test:
- exnref unsupported, or wasm disabled by the browser or policy (D4; the message names the minimum browser versions);
- worker or compile blocked (CSP, extensions: `new Worker` and `WebAssembly.compile` are wrapped);
- fetch or checksum failure (the message names the URL and size, since a proxy may have corrupted it);
- offline with nothing cached;
- Cache API unavailable or rejecting (`QuotaExceededError`; `SecurityError` in Firefox private browsing): proceed uncached;
- user abort (worker terminated);
- timeout of a runaway filter: wasm cannot be interrupted, so the worker is terminated after a 120 s wall limit;
- wasm OOM, and worker crash with no stderr;
- non-zero pandoc exit (`Q-20-3`);
- pandoc warnings (`Q-11-1`): the file is still saved and the warnings are shown in the status channel.

The host `execute` takes a typed fault-injection option (OOM via `+RTS -M<n>`, which exits 251; crash by throwing from an import; hang by a `poll_oneoff` that never returns), plus a test-only page hook compiled out of release builds, so the OOM, crash and hang cases are testable deterministically in vitest and Playwright.

**Who owns what.** Rust: argv, env, file set, paths, versions, the supported-format table, format resolution, diagnostics classification. TS: fetching, caching, compiling, mounting, running, aborting, saving, UI. Shared constants live in one file, `resources/pandoc-wasm.json` (asset name, upstream zip SHA-256, decompressed-wasm SHA-256, the share-root literal, the mount size limits; the version is `PANDOC_PIN`), read by Rust (`include_str!`) and by the TS download script. TS never re-derives anything Rust owns; the loader only checks that the decompressed wasm's SHA equals `expected_pandoc_wasm_sha256` from the request. The TS host is a DOM-free package in `ts-packages` exposing `execute(request, shareTree, { module, fault? }) -> result`, with the compiled `WebAssembly.Module` and the test-only fault option in the third argument (so Node, MCP and CI can reuse it); hub-client owns the UI and the click-time policy (supersession, classification), never the host.

**Terms.** D2a = D2's fresh-instance-per-render option; T10.x = the native pandoc-transport tests (`tests/integration/pandoc_transport.rs`); P7 fixtures = the native pandoc-hybrid epic's docx golden fixtures (`quarto_output_extract::FIXTURES`); `Q-5-30`, `Q-11-1`, `Q-20-3` = q2 diagnostic codes (missing `reference-doc`/`template`, pandoc warning, pandoc non-zero exit); the pandoc-profile AST is what the Pandoc pipeline hands to pandoc, the preview-format AST is what hub's preview uses; `spike/` means `claude-notes/research/2026-10-01-pandoc-wasm-spike/` (tracked sources; binaries gitignored); R-phases and H-phases are the request epic's and host epic's phases.

**Contracts** (fixed in R0/R1 so the Rust and TS sequences can run in parallel):
- `resources/pandoc-wasm.json`, with the share-root literal `/__q2_share__`.
- The schema at `crates/quarto-core/schemas/pandoc-request.schema.json` and a golden request (`pandoc-request.golden.json`, beside it), both published by the first task of R1 and consumed by H1 (the TS type is generated from or checked against the schema). JSON cannot carry bytes, so R1's first task pins the mapping: byte fields are annotated in the schema, the golden stores them as base64, and the wire object built in R2 carries `Uint8Array`s; a vitest decodes the golden and deep-equals it with the wire object.
- All request paths are `/`-normalized absolute strings. The request carries its own bytes (`files`, `resource_refs`) as `Uint8Array`s, never base64 or number arrays, plus the whole argv (argv[0] and RTS options included) and env.
- **Mount rules** (the one place they are stated; R1 produces requests that obey them and H1 enforces them). The worker's filesystem starts empty and is built from the request alone, with no host passthrough: the share tree (held by the main thread), `files` and `resource_refs`. The host creates the parent directories of every file implicitly; `dirs` lists only directories that must exist on their own (empty ones such as `.quarto/`, the output file's parent and `/tmp` in wasm mode; pandoc's own `make_directory` creates the mediabag directory). In wasm mode (`collect_resources`) `/__q2_share__` and `/tmp` are reserved (native temp roots live under the OS temp dir, which can itself be `/tmp`, so native requests skip the prefix checks): the share tree and `files` own `/__q2_share__`, no `resource_refs` path may begin with either prefix, and no `files` path may begin with `/tmp`. `prepare()` dedupes identical entries within a list; a path present in two of the share tree, `files`, `resource_refs` and `dirs`, or both a file and a directory, is a **hard error**: `prepare()` refuses to produce the request, and the host rejects it with a diagnostic naming the path. Nothing is ever overwritten, so mount order does not matter.
- A `/tmp` directory is part of every wasm request's `dirs` (`PrepareOptions.collect_resources`, R1), because `pandoc.system.with_temporary_directory` without it is an uncatchable fatal error (callers: `modules/mediabag.lua:21`, `ast/runemulation.lua:143`).
- The request env sets `SOURCE_DATE_EPOCH` when `PrepareOptions.source_date_epoch` is `Some` (wasm requests; native passes `None` and does not set it, so request-equality tests exclude it). **Decision:** the value is the click time (so document dates are right for users); it is an input to `render_pandoc_request`, so tests and the parity net pin a fixed value for reproducible output, and any request hash excludes this one variable and never `LANG=C` (non-ASCII file names fail under it; leaving `LANG` unset is fine). Machine-specific values inside `QUARTO_FILTER_PARAMS` (temp root, `quarto-cli-path`, Typst path) are normalized by the same equality tests. `argv[0]` is the literal `pandoc` and the RTS options are fixed in R1.
- The WASI shim is created with `{debug: false}` (otherwise it logs every path open). Its `args_sizes_get` counts UTF-16 units, so a non-ASCII argv overruns the buffer; the host overrides it with UTF-8 byte lengths.
- Export names, signatures and the `render_pandoc_request` response envelope are written down in R2's first task as `.d.ts` stubs in `ts-packages/preview-runtime` and do not change afterwards, except that additive optional trailing parameters (an `options` object) and additive envelope fields are allowed (R9 adds `options` and `stats.book`) (capture inputs and `typst_available_fonts` are already in the signature). Completion classification is `(success, status, stderr)`; the request supplies `stage_name` and `json_path`, which the host passes back.

## Decisions

- **D1 — share tree embedded in the Rust wasm and exposed through an export.** The `include_dir!` statics are already ungated; embedding guarantees the Lua version matches the Rust params builder. The export returns the share tree in native's `extract_share_tree` layout (filters + datadir + `formats/docx`) as `{share_tree_version, files: [{path, bytes}]}`; the epub snippets and the typst template reach the request as `files` entries (R4, R5), and typst packages and fonts are a separate export: a hash computed lazily at runtime over the embedded `Dir`s (`include_dir` gives none; no `build.rs`, `sha2` is already a dependency). R2 measures the size delta; revisit only if unacceptable (~1.35 MB raw / 353 KB gz for filters+datadir+formats, on a ~30 MB module). Pandoc's own data files (`reference.docx`/`.pptx`, templates, `epub.css`, highlight styles, translations) are embedded in the wasm and used when `--data-dir` lacks them, so the mounted tree needs only the vendored Lua, `formats/docx/*.png` and what the request names (evidence §9).
- **D2 — compile `pandoc.wasm` once and keep the `WebAssembly.Module` resident; instantiate a fresh instance per render.** ~40 ms to create; memory stable; zero Lua changes. The `Module` is compiled and held on the **main thread** and posted to a fresh short-lived worker per render, so terminating a worker (the only way to stop a runaway filter) never discards the compile. D2(b) (persistent warm instances driven through the exported `hs_init_with_rtsopts` and `convert`, with the per-render values delivered through a Lua preamble that overrides `os.getenv`) is implemented for the PDF preview only, as a pool of two workers on a second runner, with its own serialized (never-killed) typst runner (H10a: executor; H10b: pool and preview). Downloads, parity and the book menu stay on the fresh instance per render. The warm path rebuilds `stderr` from WASI fd 2 and pandoc's `/warnings` JSON, falls back to the fresh path on argv outside a checked-in allowlist, drops an instance when it is poisoned or above 512 MB, and has its own fault-injection instances.
- **D3 — `resource_refs[]` are mounted at identical absolute VFS paths** (argv paths are absolute). A `reference-doc` outside the Automerge project is unavailable and surfaces `Q-5-30`. `resource_refs[]` is a purpose-built computation inside `prepare()`, not the `ResourceCopyFlushStage` collector: that collector returns early in vfs-root mode (`transforms/resource_collector.rs:100-102`, which the hub prelude uses) and only knows `Image` targets. It covers resource-path images (AST walk), every path-valued arg and meta key (`reference-doc`, `template`, `template-partials`, `epub-cover-image`, `epub-metadata`, `epub-embed-font`, `css`, brand logo/fonts), and user entry-point filter files, each together with its containing directory (a filter's `require`/`io.open` of siblings cannot be found from the AST). A filter in a subdirectory mounts that directory recursively, so a family of scripts and their data belong in a subdirectory (`_extensions/<name>/` is one); a filter at the project root mounts only itself, because the root holds unrelated files and recursing from it would copy the whole project on the main thread (a documented limitation). Extensions work as in Quarto: they must be installed in the project (`_extensions/<name>/`), and the project's files are what the VFS holds, so an extension's filters and the files they `require` are mounted from there. Rust copies these bytes into the request in the same synchronous step; TS mounts only what the request carries and never reads the VFS or lists it (`vfs_list_files` also returns `/__quarto_resources__` and `/.quarto`), so no binary VFS export is needed. Every path is normalized through `normalize_request_path` (R1). A ref that resolves outside the allowed root is not mounted and yields a `Q-11-1`-style diagnostic, and a ref whose file is absent from the snapshot is left to pandoc (image: `Q-11-1`; `reference-doc`/`template`: `Q-5-30`). The allowed root is the project root (the `_quarto.yml` directory, else `doc_dir`), so a legitimate `../img.png` in a chapter still mounts.
- **D4 — feature-detect exnref and show a friendly error** naming the minimum versions (Chrome/Edge 137, Firefox 131, Safari 18.4, per MDN's compat data; Firefox 157 and WebKit 26.4 were verified here). `spike/ff/` stays the manual Firefox check; a pandoc 3.10 wasm is rejected (below the native floor). Node cannot take the flag through `NODE_OPTIONS` ("not allowed in NODE_OPTIONS"); pass it via vitest `execArgv` / the `node` flag (Node 24), or use Node 25+.
- **D5 — remote images are fetched through `SystemRuntime::fetch_url`** and mounted as `<doc_dir>/_remote/<hash>.<ext>`; the AST handed to pandoc has the image `src` rewritten to that local path (original URL kept as an attribute for diagnostics; the phase where the prefetch lands checks that the vendored Lua ignores that attribute). Mounting alone would not work: pandoc would still see `https://…` and try its own absent network after the mediabag. The prefetch is an async stage (`#[async_trait(?Send)]`) before the prepare step, since it needs the AST. It walks Images including Figures and Custom-block slots plus meta image fields; ignores `data:` and protocol-relative URLs; dedupes; caps size and time; fetches in parallel; and takes the extension from MIME over URL. The fetch is hardened for hub use: https only, `credentials: 'omit'`, a hard byte cap and a timeout, and relative URLs are not resolved against the hub origin. The current `jsFetchUrl` (`ts-packages/wasm-js-bridge/src/fetch.js`) has none of these and base64s through JSON (~2.3× memory for big images, accepted), so this path needs a hardened variant. For docx/pptx/epub a failed fetch leaves the URL, giving pandoc's `Q-11-1` warning + alt text. **Typst is different:** `quarto-post/typst.lua:260` reaches `pandoc.mediabag.fetch` through `resolve_image_from_url` (`modules/mediabag.lua:30`), which in the wasm ("compiled without HTTP support") is a hard failure (exit 83), as native is when offline. A typst document with a remote image therefore fails until the prefetch exists; the first typst increment documents that limitation and the prefetch lands right after it.
- **D6 — delivery and caching.** `pandoc.wasm` ships as an **opaque gzip file** (`pandoc.wasm.gz`, served as `application/octet-stream`, ~16 MB), not as `.wasm` with `Content-Encoding`. The main thread fetches it, stores the compressed bytes in the **Cache API** (the single cache), decompresses with `DecompressionStream`, **verifies the SHA-256 of the decompressed wasm** against the shared constants, and only then compiles. The root of trust is the upstream release zip's SHA and the decompressed wasm's SHA, both recorded in the constants file; the repacked `.gz` is not a root of trust, because gzip output varies with the zlib version and level. Checking the decompressed bytes on every load also covers a stale or corrupted cache entry. The new entry is written only after its SHA check passes and old-SHA entries are evicted after that write settles; a cancel never aborts a write in flight, and a half-written entry is caught by the per-load check. Consequences:
  - the same ~16 MB on the wire and in the cache on every host, with no `Content-Encoding` negotiation (the repo has no Brotli path: `precompress-dist.mjs` is gzip-only by a 2026-08-13 decision; nginx and `vite preview` gzip only), rather than the decoded 59 MB;
  - `Content-Length` is accurate for progress;
  - the asset URL sits outside the service worker's `/assets/*.wasm` route (`hub-client/public/pandoc/` does this by construction), so no `wasm-cache` `maxEntries` change is needed;
  - `.gz` is already in `scripts/gzip-skip-extensions.txt`, so `precompress-dist.mjs` and the embed never re-gzip it; the loader sniffs the first bytes because some servers add `Content-Encoding: gzip` to `*.gz`;
  - the cache is skipped silently when `caches` is undefined (non-secure context) and the load proceeds uncached when it rejects: `QuotaExceededError`, or a `SecurityError` (Firefox private browsing rejects `caches.open`);
  - the main thread passes an absolute URL (`new URL(p, document.baseURI)`) since the app uses `base: './'`;
  - `pandoc.wasm` is never precached (`OFFLINE.md`, GH #447);
  - on first use the menu shows the download size (~16 MB) and a cancel control.
- **D7 — the embedded hub in native `q2 preview` does not carry pandoc.wasm; it uses the native pandoc that `q2 preview` already has.** In the embed, "Download as" is served by the native render rather than the browser path. How the embedded hub asks the native side to render (the preview server's existing routes, or the hub-provider execution channel in `crates/quarto-hub-provider`, which already has a beacon/request/consent flow) is chosen in H4, picking the least invasive mechanism; the menu hides or reroutes accordingly. The embed's build (`hub-client/package.json`'s `build:preview-embed`, `crates/quarto-preview`) is otherwise unaffected by this design. The format table and the classification (D8) are shared by both paths.
- **D8 — formats docx, pptx, epub, typst (typst = `.typ` source only, no compile).**
  1. **"Download as <fmt>"** renders with the format *overridden*, on click only.
  2. If the document's own format is one the preview cannot render, there is no preview, only a **"Download <type>"** button for the document's own format; it renders only when clicked, never on edits. For a document that names several formats, the label shows the first format key (as detection does today).
  3. The menu comes from one table.
  4. Three classes: preview-capable, downloadable via pandoc.wasm (docx/pptx/epub/typst), and neither (e.g. revealjs, latex, odt); for "neither" the button is disabled with an `aria-disabled` explanation naming the format.
  5. **One download in flight at a time** (memory; a click on any format supersedes it): the new click terminates the previous worker (the PDF preview pane is the exception, H10b), the main-thread `Module` survives, and the document is snapshotted at click time. A cancel control covers fetches and renders. `render_pandoc_request` is async once remote images land (R6) and cannot be cancelled from outside: hub-client tags each call with a click id and discards any response that is not the latest click's, and the prefetch's fetches take an abort signal tied to that click. The file is named `<doc-stem>.<ext>`, sanitized (no bidi or control characters or path separators). A document with errors does not download (as natively); its diagnostics are shown. Warnings still download.
  6. **Typst is in scope because it proves the architecture** (template partials, brand, params and the virtual filesystem all pass through the request; the PDF work follows soon), so its request work comes first among the increments after the docx slice. The downloaded `.typ` is one file: images and brand logos it references are not bundled (natively `ResourceCopyFlushStage` copies them next to it), so the UI and docs say it will have dangling resource references; `typst-available-fonts` is `None` (no `typst fonts`), so it can also differ from native's.
  7. **"The document's own format" needs new code.** `getQ2Format` (`getQ2Format.ts:29-41`) returns `null` for docx/pdf/extension formats, `PreviewRouter.tsx:174-186` then mounts the full-DOM HTML `Preview`, and detection is content-only (`detect_format_from_content`, ignoring `_quarto.yml`; first key of a format map). The request epic therefore exports a **project-aware format resolver** (a Rust export built on `ProjectContext::discover`) and the format table; the host epic adds a **three-class classifier** (replacing `null`'s double meaning) and a third `PreviewRouter` branch that mounts neither preview. The branch is an **enum of modes** so a later "pdf-preview" mode (T6) fits.
- **D9 — failure policy for Q1 Lua features the sandbox lacks.** The docx/pptx/epub happy path avoids all of them (evidence §6, §9); anything else surfaces pandoc's stderr through the existing diagnostics classification, with no special-casing in v1.
  - **Supported in the wasm Lua:** `os.getenv`, `os.date` (UTC), `os.time`, `io.open` read and write anywhere in the mounted tree, `pandoc.system.make_directory`, `with_working_directory`, `pandoc.read`/`write`, the mediabag (insert, lookup, fetch of a file), `lpeg`.
  - **Unsupported:** `os.tmpname`, `io.tmpfile`, `io.popen`, `pandoc.pipe`, network `mediabag.fetch`, `require 'lfs'`; `os.execute` is a stub that returns `true`, so a filter that runs a command and reads its output finds no file.
  - **Where user filters run.** Default-position user filters run in pampa's own Lua (a synthetic VFS `io`, `quarto.*` from pampa); only post-position and entry-point filters run in pandoc.wasm with Q1's vendored Lua, and only those are subject to this list.
  - **What a filter sees in pandoc.wasm.** The working directory is `/`, so a relative `io.open('data.csv')` finds nothing: files beside the document are not mounted, only the filter's directory, images and the path-valued options. `os.getenv` returns only the request env (`QUARTO_*`, `SOURCE_DATE_EPOCH`), so `HOME`, `PATH` and `TMPDIR` are nil; `quarto.project.directory` is nil, as natively. A Lua error exits 83 and the user sees pandoc's stderr in the `Q-20-3` error; on success only warning lines are surfaced, so a filter's `print` output is not shown. A short user-facing note lives with the H5 docs.
  - **SVG images in docx/pptx:** pandoc calls `rsvg-convert`, which does not exist, and emits a warning plus an empty `<a:blip>` with no `r:embed` (native with `rsvg-convert` embeds a PNG); epub and typst keep the SVG. **Now rasterized** (`2026-10-05-metafile-svg-media.md`): in the browser, `RasterizeSvgImagesStage` asks a main-thread canvas hook (`wasm-js-bridge/rasterize.js`) for a PNG of each local SVG image before pandoc runs, at 2x intrinsic size and 192 dpi so pandoc sizes it as the SVG. If the canvas refuses (e.g. `<foreignObject>` in Chromium/WebKit) the SVG is left and warned about, giving alt text as before.
  - **Typst's one OS call** was `juice`; PR #766 (merged on `origin/main`; this branch is rebased onto it in R0) replaces it with `pandoc.pipe(quarto.config.cli_path(), {'inline-css'}, html)`. `cli_path` is set only by the native CLI and `pandoc.pipe` is unsupported here, so on wasm the Lua `inline_css` returns the HTML unchanged. R8 closed the gap with a Rust-side `inline-table-css` stage (last stage of the pandoc prefix, so native and wasm share it; the `css-inline` crate is pure Rust). The Lua pipe and the `inline-css` subcommand stay, as harmless no-ops once the stage has run.
- **D10 — projects and books.** Multi-file projects take a different path (`render_project_active_page_to_response`, `lib.rs:1699`, `ProjectPipeline` + `Pass2Renderer`, which re-detects the format; renderers today are HTML and preview-AST only), so R7 adds a pandoc `Pass2Renderer`/payload variant. Image targets: the wasm prelude's vfs-root mode leaves `Image.target` doc-relative (`link_rewrite.rs:~285`) whereas native website mode relativizes to the output page, so the "equals native" test excludes projects with `output-dir != dir` or normalizes them. **Books:** for formats that consolidate all chapters into one file before rendering (Typst and EPUB in the book-projects epic), downloading any chapter should produce the *whole book* instead of rendering just the active page, with a "this chapter only" alternative; the preview (the PDF pane) shows the active chapter alone. The staged path is R7 (active page, landed) and R9 (whole-book request for typst, pdf and epub; docx and pptx stay chapter-only).
- **D11 — code cells.** Unexecuted by default, but integrated with the cached-execution system that lets other peers contribute execution over the CRDT. `render_pandoc_request` takes the same capture inputs as the preview render (the capture splice is `insert_capture_splice_stage`, `pipeline.rs:~700`), splices results where cached, and counts the cells without results for the "N code cells not executed" status.
- **D12 — pandoc.wasm is pinned to the native `PANDOC_PIN` (3.11).** No version skew between hub and native, no separate golden version. Bumping the pin means new SHAs in the constants file (the runbook in R0). `PANDOC_PIN` is a floor enforced by `version::gate`; the wasm is an exact pin beside it.

## PDF (host epic phases H7-H9)

Goal: PDF output from hub-client without a server. pandoc.wasm turns the AST into typst source (`-t typst`, the same Pandoc-tail path as docx/pptx/epub, with the typst-specific Lua/params/template), a **typst wasm compiler** turns that `.typ` into PDF, and a **pdf.js viewer** displays it (plus "Download as PDF"). Everything is lazy: neither wasm is fetched until the first PDF request. For books, the PDF is the whole book with the active chapter located in it (D10).

**What native does today (so we match it).**
- Native pandoc writes `.typ`, then `TypstCompileStage` shells out to an external `typst` binary (`typst_compile.rs:236`; `--root <project>`, `--font-path ...`; floor 0.8, **not pinned**; local 0.14.2). No typst compiler is linked into q2.
- Vendored typst packages (showybox, fontawesome, theorion, octique, marginalia; 2.5 MB, of which 1.7 MB Font Awesome OTFs) are extracted into a package cache; other `@preview` packages are fetched by `typst-gather`. **Font search order matters:** vendored fonts, document `font-paths`, brand file fonts, Google font cache. `typst-available-fonts` is derived from `typst fonts`.

**Approach.**
- **Compiler:** `typst.ts` `@myriaddreamin/typst-ts-web-compiler@0.7.0` (targets typst **0.14.2**, matching native here; active) in a dedicated Worker, lazy-loaded. Wasm is 28.3 MB raw / 10.7 MB gzip -9 / 7.1 MB Brotli -q11 (measured; the repo serves gzip only, D6). Fallbacks: `typst-wasm` (younger, less used) or embedding the `typst` crate with our own `World` (more control, we own bumps and PDF export plumbing).
- **Virtual FS:** `map_shadow(path, bytes)` for the `.typ`, project files (images, brand assets) and the vendored packages (via the package-registry callback).
- **Fonts:** typst.ts ships none. Supply default fonts (Libertinus Serif, New Computer Modern, DejaVu Sans Mono from `typst-assets`, est. 4-8 MB) plus our vendored Font Awesome fonts, plus brand/project fonts from the VFS. Compute `typst-available-fonts` from the fonts the host loads instead of running `typst fonts`, taking family names from `createTypstFontBuilder().getFontInfo(bytes)` (returns `{info: [{family, variant, …}]}`; verified in Node on the default and Font Awesome fonts). `get_loaded_fonts()` is no source: it lists only fonts a compile has already used (none before the first compile) as debug-formatted strings. Init must pass `loadFonts(bytes, {assets: false})`: otherwise typst.ts fetches 17 fonts (typst-assets 0.13.1) from jsdelivr, and with no fonts a compile succeeds silently with a text-less PDF and no diagnostic.
- **Viewer:** `pdfjs-dist@6.x` (main 459 KB / worker 1.27 MB), Vite `?url` worker import, dynamic `import()` when the PDF view opens.
- **Pipeline wiring:** the `PandocRequest` for `pdf` is the typst-writer request with `output_path = *.typ` and a `post: compile_typst` step; the TS orchestrator chains pandoc worker -> typst worker -> pdf.js, with one progress/diagnostic channel. The PDF chain is font-list → request → pandoc → typst compile (the font list is a pandoc *input* whose source is the typst worker), so the typst compiler is loaded before pandoc runs; `render_pandoc_request` reserves an optional `typst_available_fonts` for it (`None` for the `.typ` download). typst.ts has no date option, so the PDF's `/CreationDate` and `/ID` come from the clock; the PDF request pins the document date from `source_date_epoch` (mechanism in R4).

**Decisions.**
- **T1 — self-hosted and lazy, same policy as pandoc.wasm (D6).** A ~28 MB (~9-11 MB compressed) second wasm plus fonts (~5-10 MB) is an opt-in download on first PDF use, served from our origin and runtime-cached.
- **T2 — target typst 0.14.2 (matching native here), with a version assertion in tests.** The assertion also covers writer-versus-compiler skew: the pandoc 3.11 typst writer's output against typst 0.14.2. Native uses whatever `typst` is installed (0.14.2 here, floor 0.8); whether native should also pin is decided separately. typst.ts 0.7.0 matches 0.14.2; its 0.8 line targets typst 0.15 (typst.ts `main` is on 0.15.1; 0.8.0-rc3 published).
- **T3 — packages.** The five vendored packages are bundled (works offline), and other `@preview` packages are fetched from `packages.typst.org` at compile time via the package-registry callback (fetched tarballs cached in the Cache API). CORS verified 2026-10-01: `index.json` (2.3 MB, which counts toward the first-use budget) and package tarballs both return `access-control-allow-origin: *` and `cross-origin-resource-policy: cross-origin`. A fetch failure (offline, unknown package) yields a clear diagnostic naming the package.
- **T4 — fonts.** Default fonts are lazy-fetched with the compiler; brand `source: file` fonts come from the VFS; Google fonts are deferred. Layout will differ from native whenever the font set differs.
- **T5 — trust typst.ts**, lazy-loaded; revisit when we integrate more tightly with typst or if version lag hurts.
- **T6 — a first attempt at incremental recompile (`incr_compile`, which yields typst.ts vector deltas for its own renderer, not PDF)**, to validate the architecture; it need not be polished. It is a separate PDF-preview mode, off by default, on the router mode enum (D8.7), because downloads are click-only. Compile-on-demand ("Download as PDF") remains the baseline. It is a scope risk, hence the time box; the H9 spike answered no. D2(b) was built for the preview separately (H10a, H10b).
- **T7 — viewer: model on Q1's preview.** Q1 (`src/core/pdfjs.ts`, `command/preview/preview.ts`) bundles the *stock pdf.js web viewer* (`viewer.html`, ~14 MB with cmaps/locales) and serves it, patching on the fly: default file name -> the rendered pdf, sidebar forced off when embedded in an iframe, toolbar z-index and no sidebar transition in css, and `pdf.worker.js` patched so `fingerprint` is constant per file (so zoom/scroll prefs survive reloads). Reload after a render is a navigation to `web/viewer.html`. For hub the same pattern is available (stock viewer in an iframe/blob URL with a stable fingerprint), versus the lighter `pdfjs-dist` `PDFViewer` component; the viewer phase starts from the stock viewer. Either way a recompile must keep a stable fingerprint and scroll position, and the viewer shows the active chapter only.

## Execution conventions

**Gates.** Rust tasks: `cargo clippy -p <crate> --all-targets -- -D warnings` + `cargo nextest run -p <crate>`; for any task that touches a `target_arch = "wasm32"` gate or ungates code, also a wasm compile check (clippy for the host target compiles none of the wasm branches): `cargo check --target wasm32-unknown-unknown` in `crates/wasm-quarto-hub-client` (its own workspace, own `Cargo.lock`) with `CC_wasm32_unknown_unknown=clang` and `CFLAGS_wasm32_unknown_unknown="-isystem $PWD/wasm-sysroot -fno-builtin"` (see `dev-docs/wasm.md`; `build-wasm.js` sets the same; run from that crate, where `wasm-sysroot` lives, and on macOS point `CC_wasm32_unknown_unknown` at Homebrew's `/opt/homebrew/opt/llvm/bin/clang`, since Apple's clang has no wasm backend), and `npm run build:wasm` at the end of R2 (nightly, `-Zbuild-std`). TS tasks: the hub-client vitest/wasm tests (`test:ci` is `hub-client/package.json:36`). One workspace nextest per phase boundary and before any push. The real CI check for the wasm build is `ts-test-suite.yml` (`.github/workflows/build-wasm.yml` is `workflow_dispatch`-only and builds `wasm-qmd-parser`). New Rust integration tests go in `crates/<crate>/tests/integration/<name>.rs`, registered alphabetically in `main.rs` (`.claude/rules/integration-tests.md`). New native tests must pass on Windows although CI does not run it: the pure path-normalizer tests are the guard, and recordings, schemas, goldens, new fixtures and `resources/pandoc-filters` get `eol=lf` in `.gitattributes`.

**Task preamble** (every task-level plan starts with it; every phase file points here): work on a topic branch `pandoc-wasm/<phase>-<slug>` cut from `feature/pandoc-wasm` in the phase's lane worktree (Parallel development below; `git switch -c`; `switch-task` needs a braid strand, which in-plan work does not get) and rebase it onto the integration branch for linear history; line numbers in the phase files are as of the plan's commit, so re-locate by symbol after R0's rebase; run the gates above (the wasm env is whatever `hub-client/scripts/build-wasm.js` sets); integration tests under `tests/integration/`; no `cfg(any(wasm32, test))`; `#[async_trait(?Send)]`; request paths `/`-normalized; a task ticks only its own checkbox, in the same commit as its work and only after its gate passes, and opens no braid strands for in-plan work.

**Human review checkpoints** (each is a STOP in the phase text; an agent hands back and waits): after the H0 gates and the R0 hashable-request recommendation, before R1/H1 start; after R1's schema publication and again after the prepare/execute split (the riskiest refactor); the H5 demo, before H6 and before R3-R8 are wired into the menu (the request phases themselves can proceed); and the H10a measurements (Task 0) and its warm-versus-fresh parity result (Task 7), before the pool is built; and the Word-open, WebKit and Firefox checks, which are manual. Each STOP is also a handoff point: the agent updates the phase's Handoff log, lands its work and stops.

**One agent per phase.** Each phase plan is executed start to finish by a single agent that works the checklist in order itself. It does not spawn sub-agents, forks or per-task workers, review agents included (a STOP is a hand-back to the human), whatever a general instruction about per-task subagents says. If a phase outgrows one session, hand it off (below) instead of dividing it among concurrent agents. Parallelism comes from running different phases in different lanes (below), one agent each.

**Handoff.** Any agent can be replaced at any point (context exhaustion, a STOP, a human decision), so a phase keeps its state in the repo, not in the agent's head:
- The checklist is the source of truth. Tasks are sized to fit one session; a large one is broken into sub-checkboxes that are each a commit, so nothing is half-ticked.
- Every phase file ends with a **Handoff log**: branch and worktree, last commit, tasks ticked, state and gotchas (surprises, rejected approaches, commands that worked: whatever the code does not say) and the next step. Update it in the commit that ends each task and before any stop. A stop mid-task commits a `WIP:` commit first, so the working tree is clean at a handoff.
- A discovery that affects another phase is written into that phase's file (or the evidence file) as plain plan text in the same commit, not left in the log.
- A new agent reads CLAUDE.local.md, this section, the phase file (checklist, then log) and `git log` for the branch, then re-runs the last ticked task's gate before continuing.
- Handoff points: the end of any task, each STOP, each phase boundary, and each landing in the lane table below.

**Parallel development.** Three worktrees are used. **workspace-3** holds the integration branch `feature/pandoc-wasm` and does only integration work: plan edits, fast-forward landings, human-checkpoint reviews and the workspace nextest before a push. It never carries a topic branch. **Lane R (workspace-6)** runs the request epic (Rust) and **lane H (workspace-7)** the host epic (TS); each has its own `target/` and `node_modules`, which stay warm across phases, so reuse a lane and do not `cargo clean` (the first build is cold; run `npm install` in lane H before TS work). A lane runs one phase at a time. Per phase, from the repo root:

```bash
git -C .worktrees/workspace-6 switch -c pandoc-wasm/r1-request-seam feature/pandoc-wasm   # start (lane R; workspace-7 for lane H)
# work and commit on the topic branch; to land (at a landing point below, or at the phase end):
git -C .worktrees/workspace-6 rebase feature/pandoc-wasm       # re-run the crate gates if the rebase brought in changes to the same crates
git -C .worktrees/workspace-3 merge --ff-only pandoc-wasm/r1-request-seam
# the lane continues on the same branch (rebase again) or retires it after the phase:
git -C .worktrees/workspace-6 switch parking/workspace-6 && git -C .worktrees/workspace-6 branch -d pandoc-wasm/r1-request-seam
```

History stays linear (rebase, then `--ff-only`; no merge commits). A landing needs a clean workspace-3 tree; if `--ff-only` fails because the other lane landed first, rebase again. A rebase conflict in `package-lock.json` is resolved by re-running `npm install`, never by hand. The phase-boundary workspace nextest runs in the lane before the phase's last landing.

| Step | Lane R (workspace-6) | Lane H (workspace-7) | Hand-off between lanes |
|---|---|---|---|
| 1 | R0 up to the extractor CLI; **land** | waits: H0's start gate is R0's extractor landing (H7 is not started early: PDF effort before the H0 gate is at risk) | the landed R0 capture wrapper, recordings, constants file and extractor start H0 |
| 2 | R0's hashable-request exploration | H0 | **STOP:** human review of H0 and R0 |
| 3 | R1: publish the contract; **land**; STOP for schema review; then the split (STOP after) | H1 once the contract has landed (H0 passed); then H2, then H4 | R1's landed schema and golden start H1 |
| 4 | R2 | H4, or H7 | R2's landing unblocks H3 |
| 5 | R3, then R4 | H3, then H5 for docx | **STOP:** H5 demo before H6 and before R3-R8 are wired into the menu |
| 6 | R5, R6, R8, R7 stages 0-1, then R9 (whole book) (R4-R6 share `pandoc_write.rs`; R3, R6, R7, R8 share `lib.rs`, the `.d.ts`, `wasmRenderer.ts` and the prefix builder) | wire R3-R7 entries into the menu as they land; H6; H7; H8 (needs H5, H7, R4); H9; H10a, H10b (warm pandoc for the PDF preview; H10a adds one `quarto-core` Rust test) | each request phase's landing unblocks its menu entry |

Landing points a lane must not skip (another lane or phase consumes them): R0's extractor task, R1's contract task, R2 as a whole, R4 as a whole. Land at other task boundaries whenever the tree is green, since small landings keep rebases small. A lane that runs out of work may take a phase from the other lane's column when it shares no file group with the other lane's current phase (the groups are named in the epics' Order paragraphs and in the table above); H1, H2, H3 and H7 all edit `ts-test-suite.yml`, the vitest aliases and `package-lock.json`, so only one of them is in flight at a time even across lanes.

**Running the lanes.** There is no coordinating agent: you start one agent per lane, each in its own worktree and its own Claude session (`cd .worktrees/workspace-6 && claude`, `cd .worktrees/workspace-7 && claude`), and relay between them. Lane R's order is R0, R1, R2, R3, R4, R5, R6, R8, R7, R9; lane H's is H0, H1, H2, H4, H3, H5, H6, H7, H8, H9, H10a, H10b. Every phase file has a **Lane**, a **Start gate** and a **Next in lane** line. The same prompt starts and resumes a lane (X is R or H, N is 6 or 7):

> You are the lane X agent (worktree .worktrees/workspace-N). Read CLAUDE.local.md, then the Execution conventions in claude-notes/designs/pandoc-wasm-architecture.md (one agent per phase, handoff, parallel development). Your current phase is the first in your lane's order whose Close-out is not fully ticked on feature/pandoc-wasm (a phase whose only open boxes are items marked "as each request phase lands" does not count; return to those when the named phase has landed); if a branch pandoc-wasm/<phase>-* exists, resume from the Handoff log in its phase file. Verify the phase's Start gate by reading the producer phases' ticked boxes with `git show feature/pandoc-wasm:<phase file>`. If the gate is not met, change nothing, say which gate is open and stop. Otherwise execute the phase yourself, without sub-agents.

- A box is ticked on `feature/pandoc-wasm` only when its work has landed there, so the ticks are the gate state. A STOP box is ticked by the agent only after you have said in its session that the review passed; the agent then lands and continues or stops per its Next in lane.
- An agent cannot wait or poll. When it is blocked (an unmet start gate, a STOP, a task that needs the other lane) it commits, updates the Handoff log, reports exactly what it is waiting for and stops. You restart it with the same prompt once the other lane reports the landing.
- A landing that unblocks the other lane is reported in a message at once (what landed and which phases it unblocks, from the phase's Unblocks line), not only in the final message, so you can relay it.
- Branches are shared by all worktrees of the repo, so no fetch is needed; nothing is pushed.

## Risks

- **Firefox is manual-only for this work:** run `spike/ff/` by hand. CI Firefox is tracked separately in braid `bd-phu943t7`.
- **Stale or corrupted wasm:** the loader verifies the decompressed wasm's SHA against `expected_pandoc_wasm_sha256` from the request on every load; the Cache API key includes the SHA and old entries are evicted.
- **Vendored Q1 Lua under wasm pandoc:** the mechanism and a fixture across all four formats are proven in Node; the full document range is not. The H0 gate covers pandoc-profile fixtures in a browser.
- **exnref browser floor and upstream churn (D4):** minimum Chrome/Edge 137, Firefox 131, Safari 18.4 per MDN; Chromium, WebKit 26.4 and Firefox 157 verified here. Upstream is still changing the exception-handling encoding (pandoc 3.10.2 "restore legacy exception handling for wasmtime compatibility", jgm/pandoc#11787), so a version bump needs the browser probe re-run.
- **Browser numbers are preliminary:** Node command-mode numbers are ~0.3-0.5 s per render, ~50 MB linear memory; a pre-plan Mac run gave a first docx of ~0.3 s in Chromium and ~0.6-0.8 s in WebKit (wasm compile ~0.3 s and ~1.2 s), ~53 MB linear memory (evidence §10); H0 and H3 measure on the real recordings.
- **Memory on weak devices:** the H10 warm preview keeps two pandoc workers (about 45 MB each and never shrinking until dropped at 512 MB or idle) resident beside the typst worker; ~+340 MB page RSS once pandoc loads (reactor-mode measurement); Rust wasm, Automerge and Monaco are also resident; mobile Safari may kill the tab. The idle-drop policy and the size hint are the mitigations.
- **Scope concentration:** the seam (R1-R2) is the largest Rust change; it is cut to the docx single-document slice, with the other formats, remote images, projects and typst as later phases.
- **Version drift:** the wasm is pinned to `PANDOC_PIN`, so bumping the pin means new SHAs (the runbook in R0); the vendored Lua (Q1 `v1.11.3`) is the compatibility reference.
- **PDF:** layout drift from different fonts/typst version; package availability offline; combined first-use download (pandoc ~16 MB + typst ~11 MB + fonts, all gzip) and memory (two Haskell/Rust-heavy wasm modules resident); typst.ts is a third-party wrapper whose release line may lag typst or change API (0.7 stable vs 0.8 rc).

## Noted, not scheduled

Ideas that matter if the feature grows but are not committed to here:
- A single `check-pandoc-wasm` job (nightly and on every bump) that also checks the module's WASI imports against an allowlist, records size/latency budgets, and greps the vendored Lua for sandbox-hostile calls after a Q1 bump; mirroring the pinned asset to a project-controlled location; a runtime kill-switch (`features.json` fetched network-first), since a redeploy reaches PWA users slowly.
- Capability routing: a local native q2 reached over the hub-provider channel, or a server, as alternative executors behind the same `execute(request)` interface (D7 already uses native pandoc in the embed). Sharing job *inputs* between peers is plausible; sharing *outputs* over the CRDT is not (unbounded history, unverifiable results).
- A confirmation listing external hosts before remote images are fetched.
- Housekeeping for later: remove the Node `--experimental-wasm-exnref` flag when Node ships exnref by default.
