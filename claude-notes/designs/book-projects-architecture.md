# Design: Book projects (`ProjectKind::Book`)

**Status:** Frozen decisions from design conversation 2026-09-21; corrected after a critical review pass the same day (see the epic doc's "Revision history" for the full list of what changed and why).
**Epic plan (authoritative for sequencing):** [`../plans/2026-09-21-book-projects-epic.md`](../plans/2026-09-21-book-projects-epic.md)
**Builds on:** `feature/pandoc-writer-hybrid` (single-document docx/pptx/typst/epub via Pandoc + vendored Q1 Lua — substantially complete on that branch) and the website-projects epic (`ProjectType` trait, two-pass orchestrator, sidebar/navbar generation, cross-document link rewriting).
**Q1 references investigated:** `src/project/types/book/*.ts`, `src/format/{typst,epub,pdf}/format-*.ts`, `resources/filters/crossref/sections.lua`, and the `tests/docs/smoke-all/typst/orange-book*` fixtures (the most rigorous numbering-correctness corpus in Q1's own test suite).

## 1. The problem

Q1 renders books by having `bookProjectType` inherit `websiteProjectType` and add: a chapter/part/appendix list with per-chapter numbering, two render modes (multi-file HTML vs. single-file merge for PDF/EPUB/Typst), and — for multi-file HTML only — a **DOM-postprocessing** fixup pass that resolves cross-chapter crossrefs and merges bibliographies by re-parsing rendered HTML.

Q2 has `ProjectKind::Book` as an enum tag already, dispatching to a no-op `DefaultProjectType` (`orchestrator.rs:627`, `bd-m1fzvpov`). This epic gives it a real implementation. Two constraints shape everything below:

- **No DOM postprocessors** (`CLAUDE.md`'s architecture policy). Q1's cross-chapter crossref/bibliography fixup must be re-expressed as an AST-level mechanism.
- **Fidelity to Q1's actual behavior is the goal**, verified empirically wherever practical (against `orange-book`, and against real `quarto render` invocations built for this design — see §6's and §7's appendices in the P2/P4 plans), not against a from-scratch redesign of the numbering scheme.

## 2. Two render modes, asymmetric difficulty

Q1's `BookExtension.multiFile` flag splits every book render into:

- **Single-file merge** (PDF/LaTeX, EPUB, Typst — Q1's actual "premium" book formats; `multiFile` defaults `false`): all chapters become one Pandoc document. Chapter-scoped numbering ("Figure 2.1", "Theorem A.1") comes from the *compiler's own* native, deferred-resolution counters — confirmed for Typst (`counter(heading)`-driven template) and empirically for LaTeX (`\chapter`/`\appendix`/`\ref{}`, see P2's appendix) — or from Q1's crossref Lua walking one continuous document's real headers (EPUB). **Neither needs external chapter-offset help**, and neither needs cross-document machinery. **A unified bibliography needs one real, new fix — found by a later review pass, corrected from an earlier, wrong assumption that it was automatic.** Q2's own citeproc filter runs per-chapter, *before* Normalization (well before P2's merge point) — unlike Q1's markdown-merge-then-single-`pandoc`-process architecture, which genuinely gets this for free. §6 has the full finding and the fix (defer each chapter's citeproc run to one pass over the assembled whole); once applied, single-file merge does get a correctly-numbered, deduplicated, book-wide bibliography — matching Q1's real single-file behavior, not just its output shape.
- **Multi-file HTML**: each chapter is rendered independently (today's Q2 Pass 2, unchanged). Numbering *within* a chapter needs to know "which chapter am I" (an externally-injected fact, since the chapter can't see the rest of the book). Resolving a reference *to another chapter's* entity needs project-wide knowledge no single chapter's render has.

This asymmetry is why the epic phases single-file merge (P2/P3) before multi-file HTML's harder pieces (P4/P5/P6): the genuinely novel piece (project-wide crossref resolution) is deferred until the simpler, better-precedented piece is validated end-to-end.

## 3. Book's Pass-2 dispatch — resolved as a concrete special case, not a new `ProjectType` trait method

**Revised by a seventeenth-pass research round: the original "`ProjectType` gains one new general hook" sketch is dropped. It was never `dyn`-safe, and — once actually researched rather than patched — its genericity turned out to be unneeded in the first place.**

The original sketch:

```rust
async fn render_documents(&self, docs: &[DocumentInfo], /* ...pass-2 plumbing... */)
    -> Result<Vec<Output>>
```

doesn't work as a `ProjectType` trait method: `ProjectType` is used throughout the orchestrator as `Box<dyn ProjectType>`, but `Pass2Renderer::render_batch` is generic over the implementing renderer with an associated `Output` type — a method reachable through a trait object can't be generic over that renderer or return its associated type.

**Research resolved this in favor of neither of the two originally-proposed fixes (parameterize `ProjectType<R>`; split onto a second `R`-parameterized trait) — both were solving a genericity problem that doesn't actually exist for this hook.** Traced precisely: `BookProjectType`'s Pass-2 override is only ever reachable through `ProjectPipeline<'a, RenderToFileRenderer<'a>>` — never through either of the other two `Pass2Renderer` implementors. `ProjectPipeline::new()` (`orchestrator.rs:959`) is defined in the *concrete* impl block (`impl<'a> ProjectPipeline<'a, RenderToFileRenderer<'a>>`), not the generic one; every real native call site (`quarto/src/commands/render.rs:826,1009`, `quarto/src/commands/publish.rs:286` — three, not "5+") constructs it that way. The only call sites using the generic constructor are in the WASM preview path — which, per this epic's own already-accepted Known Limitation, never invokes `BookProjectType`'s Pass-2 override at all. `project_type_for`'s other call sites (`render_to_file.rs:341`, the WASM one) never touch `Pass2Renderer` — they only call `.lib_dir()`/`.kind()`-shaped methods. So the hook's genericity was aspirational uniformity, not load-bearing — matching what P2/P4/P5 already independently decided for their own new mechanisms (`chapter_seeds`, the finishing-pipeline functions, `write_rendered_output`: all deliberately concrete to `RenderToFileRenderer`, not generic `Pass2Renderer` trait additions, for the identical reason).

**Resolved shape: don't touch `ProjectType` or `project_type_for` at all.** Add a new method to the *existing* concrete impl block:

```rust
impl<'a> ProjectPipeline<'a, RenderToFileRenderer<'a>> {
    pub async fn run_with_book_support(&mut self) -> Result<ProjectRenderSummary<RenderToFileResult>> {
        let result = if self.project_type.kind() == ProjectKind::Book {
            // concrete, RenderToFileRenderer-only book orchestration —
            // P2/P4/P5's mechanisms, no generics needed anywhere
        } else {
            self.run_inner().await // existing path's own body, unchanged
        };
        if let Err(e) = self.project.registry.shutdown_all() {
            tracing::warn!("engine registry shutdown_all failed at end of project render: {e}");
        }
        result
    }
}
```

**Corrected by an eighteenth-pass review that read `run()`'s body directly rather than trusting this doc's own prior restatement.** `run()` (`orchestrator.rs:1059-1072`) is not pure delegation to `run_inner()` (`orchestrator.rs:1097`): it calls `run_inner()`, then **unconditionally** calls `self.project.registry.shutdown_all()` (best-effort — logs and continues on error) to reap TS-engine Deno subprocesses, then returns `run_inner`'s original result untouched. This is real, load-bearing teardown, not incidental — `run_inner` is private and never called from anywhere else. The prior version of the code sketch above gave the non-book branch this teardown for free (`self.run().await` includes it) but never gave the book branch an equivalent — and nothing in this design doc or any phase plan (P1/P2/P4/P5, all grepped) previously paired `shutdown_all` with the book branch at all. An implementer following the old sketch literally would build book-mode orchestration that never reaps the engine registry — a silent, book-only regression (leaked Deno subprocesses) against every other project type. **Fixed above**: both branches now share one `shutdown_all()` call after the `if`/`else`, so parity holds regardless of which branch executes; the book branch's own orchestration body needs no teardown logic of its own. The three native CLI call sites still change one line each (`.run()` → `.run_with_book_support()`); `DefaultProjectType`/`WebsiteProjectType`, `ProjectType` itself, and every non-`RenderToFileRenderer` call site are untouched — a smaller blast radius than either originally-proposed fix, not a compromise between them.

**Honest cost, not hidden**: this permanently ties Book's special dispatch to `RenderToFileRenderer`. If Manuscript ever needs the same shape via a different renderer, this doesn't generalize for free — but that's consistent with, not a regression against, this epic's own stated philosophy below (a mechanism built for one real consumer, not speculatively generalized for a hypothetical second one).

**Why not a general, typed "Pass 3" facility** (a `Checkpoint` associated type on `Pass2Renderer`, a `needs_pass_three()` flag on `ProjectType`): the pause point book rendering needs is always the same fixed transform-phase boundary (see §8), and the only current consumer is Book. Manuscript's actual Q1 shape (one article + independently-rendered notebooks + MECA packaging, no merging, no cross-document numbering at all) doesn't need this mechanism — generalizing it now would bake a guess about Manuscript's future needs into shared, typed machinery. `run_with_book_support`'s concrete `ProjectKind::Book` branch is, if anything, *more* narrowly scoped than the original hook idea — it opens no door for other project types at all, on purpose. If Manuscript later needs something, it gets its own seam in its own shape (a different special case, or a real trait method if and when a second consumer's needs are actually known); only if two real consumers converge on the same shape does extracting shared machinery become justified.

## 4. Chapter model (shared by both render modes)

Ported from `book-config.ts`/`book-types.ts`, as idiomatic Rust (same ideas, not verbatim code):

```rust
enum BookRenderItemKind { Index, Chapter, Appendix, Part, References }
struct BookRenderItem {
    kind: BookRenderItemKind,
    depth: u32,
    text: Option<String>,   // part/appendix divider title
    file: Option<PathBuf>,  // chapter source
    number: Option<u32>,    // None for unnumbered / non-file items
}
```

`book.chapters` / `book.appendices` / `book.references` in `_quarto.yml` translate into a flat `Vec<BookRenderItem>` (numbering assigned in book order, appendices numbered separately as a fresh 1-based sequence that presents as letters) — **this list feeds the *existing, unmodified* `WebsiteProjectType` sidebar builder** (book sidebar = website sidebar generated from a translated `contents:` list, exactly as Q1's `bookProjectConfig` copies `book.*` into `website.*` before delegating). No new sidebar code. An `.unnumbered` chapter's file still gets a `BookRenderItem` (it renders and appears in the sidebar) but `number: None` — it consumes no slot in the numbering sequence, mirroring `book-config.ts`'s `inputIsNumbered` gate on `nextNumber++`.

`book.references` (`kBookReferences`) is its own designated-references-page config key, distinct from `chapters`/`appendices`, positioned after the main chapters and before appendices. Give it its own `BookRenderItemKind::References` and track which item it is explicitly. This deliberately improves on Q1's own mechanism, which locates the references *output file* later (in `book-bibliography.ts`'s `bookBibliographyPostRender`, §9/P6) by scanning `context.config.project.render` for the first file whose `inputTargetIndex(...).markdown.containsRefs` is `true` — a structural flag, not a filename match (corrected by a review pass: an earlier draft of this doc claimed Q1 matches against the literal substring `"references.html"`, which appears nowhere in Q1's source). Q2's `BookRenderItemKind::References` is still a genuine improvement — it names the references item explicitly at config-translation time rather than inferring it structurally after the fact — the fix here is only to the *reason given*, not the decision.

**Sidebar nav-item chapter-number decoration is a config-translation-time concern, not a render-time hook.** Q1 has a genuine, pre-existing per-project-type extension point for this — `ProjectType.navItemText` (`types.ts:64`), called generically by `website-navigation.ts` at render time, not something `book.ts` bolted on ad hoc. Q2 doesn't need an equivalent hook: chapter numbers are static and fully known once P1's `BookRenderItem` list exists, well before any chapter renders, so P1 bakes the decorated text (port of `numberChapterHtmlNav`) directly into each sidebar item during the `contents:` translation this section already describes — including computing the appendix *letter* itself for the sidebar text, since that's exactly the kind of static, config-time fact P1 exists to compute. **Confirmed free, not assumed**: `NavigationItem.text`/`SidebarEntry` are already typed as `ConfigValue` (`crates/quarto-navigation/src/item.rs:47`), which can hold real Pandoc inlines (`ConfigValueKind::PandocInlines`) rather than a plain string, and `ConfigMarkdownTransform`'s blessed-paths registry already markdown-parses `sidebar.contents.*.text` by default. `sidebar_to_html_with_options`'s renderer (`crates/quarto-navigation/src/render_html.rs:1057-1072`) is a genuine Pandoc-inline-to-HTML walker — a `[A]{.chapter-number}`-style span round-trips through it verbatim (attr-preserving `<span>`, line 1203-1217). No new field or mechanism needed for the decorated sidebar text this section describes.

**Cross-artifact risk this creates — weaker than a prior pass claimed, corrected by a ground-truth-verification pass: this is "provably equal by construction" only for the *order*-preservation half, not the ".unnumbered" half.** P1 computes the appendix letter directly from `BookRenderItem`'s book-order appendix sequence. §6/P2's single-file Typst path never computes a letter in Rust at all — Typst's own compiler assigns A, B, C… to appendix-mode level-1 headings strictly in the *document order they appear in the merged output* (confirmed: `orange-book.lua`'s appendix show-rule doesn't pick or compute a letter itself, it just tells Typst's native heading-numbering to switch to letters at that point).

**Correction: Q1's model *does* support marking an individual appendix chapter `.unnumbered`, independently of its siblings — a prior pass's claim to the contrary was wrong, found by reading `book-config.ts` directly rather than trusting the earlier restatement.** `findChapters` calls `findInputs(kBookItemChapter, ...)` **unconditionally for both** the `"chapters"` and `"appendices"` config keys (`book-config.ts:409`) — every individual appendix item gets `type: kBookItemChapter`, the exact same type an ordinary chapter gets (`kBookItemAppendix` is reserved for the synthetic "Appendices" divider heading only, line 427). Inside `findInputs`, the numbering gate — `if (type === kBookItemChapter && await inputIsNumbered(project, item.href))` (lines 371-376) — routes through `isNumberedChapter` (`book-shared.ts:117-127`), which checks the *individual chapter's own* front-matter title or first-heading `.unnumbered` class. This is the identical per-chapter mechanism ordinary chapters use; nothing about it excludes appendix items.

**Consequence: the order-preservation invariant is real but not sufficient on its own — there is a second way these two letters can legitimately desync, and research now points to it being real, not hypothetical.** If a user marks one individual appendix chapter `.unnumbered`, P1's sidebar-letter sequence must skip it (consuming no letter slot) the same way it already skips an `.unnumbered` ordinary chapter. **A research pass into `orange-book.lua`/its Typst package (`orange-book` `lib.typ:116-135`) found the Typst side likely does not skip it — probably a real, inherited Q1 bug, not a Q2 gap.** `orange-book.lua`'s `Header` handler doesn't assign letters at all; it fires one `#show: appendices.with(...)` rule once, at the first appendix heading, and gets out of the way. Letter assignment happens entirely inside Typst's own native `counter(heading)`, keyed by `numbering: (..nums) => numbering("A.1", ..vals)` — and Typst's documented counter semantics keep incrementing on every heading node regardless of whether `numbering: none` (what Pandoc's writer emits for `.unnumbered`) suppresses that heading's own *display*. So an individually-`.unnumbered` appendix chapter would still consume a native counter slot in the compiled PDF even though P1's Rust-side sequence correctly skips it — desyncing the two. `orange-book.lua` even has an adjacent maintainer comment about a related unnumbered-heading bug (`hide-parent: true`, worked around for TOC duplication, not counter-skipping), suggesting this corner was already known to be rough upstream.

**Decision: don't make Q2's side "smarter" than Q1's real behavior here — that would create Q2-only divergence, against the same principle P6 already applies to the numeric-citation-per-chapter-renumbering bug (port Q1's real behavior, including its real undocumented bugs, rather than exceed its fidelity).** The research above is reasoned from Typst's documented counter semantics and static code reading, not an observed compile (`orange-book` isn't vendored into this repo yet) — so treat it as a strong prior, not a confirmed fact. P1 needs a test for an individually-`.unnumbered` appendix chapter (sidebar: no letter shown, no slot consumed) regardless. P2/P3's already-planned fixture (a book with an `.unnumbered` appendix chapter through single-file Typst mode) is where this actually gets confirmed — if the real compile shows the letters desync as predicted, pin that with a documenting test (matching P6's pattern), not a code fix; if the real compile surprises and shows correct skipping after all, this whole paragraph's premise was wrong and the "provably equal" framing can be restored.

**Book projects render only to formats with book support**, mirroring `projectFormatsOnly: true` / `isSupportedFormat` (`book.ts:149-153`). Implement as the general rule `BookProjectType::is_supported_format`, not a docx/pptx-specific special case — P3's diagnostic for those two formats is one instance of this general mechanism, not separate logic.

`outputDir: "_book"` (`book.ts:115`) is `BookProjectType`'s own output directory — distinct from `WebsiteProjectType`'s `_site`. `lib_dir` delegates to website's `"site_libs"`; the output directory does not delegate, in Q1 or here.

This model has no per-render numbering-*injection* logic in it — that's deferred entirely to whichever render mode needs it (§7). It only answers "what are the chapters, in what order, with what part/appendix structure, and which ones are numbered at all."

**Config-level book features that are not render-mode-specific**, all Q1 computes once during `bookPreRender`/`bookProjectConfig` rather than per-chapter-render, and all real, previously-undocumented scope for P1:

- **Special-date resolution**: `book.date: today` / `last-modified` resolves once against the project, mirroring `book.ts`'s `bookPreRender` (`isSpecialDate`/`parseSpecialDate`).
- **Project-render-list additions**: a book's render list is normally *restricted* to exactly the files `BookRenderItem` names — unlike a website project, which defaults to rendering everything it finds. Two consequences Q1 explicitly patches for and Q2 must too, or these files simply never render in a book project: any file referenced from `page-footer` regions, and a `404.*` page sitting in the project directory if one exists.
- **Download/sharing sidebar tools**: PDF/EPUB/DOCX download buttons (for whichever single-file formats are configured) and a social-share menu (LinkedIn/Facebook/Twitter) — sourced from `book.downloads`/`book.sharing` config, not free from `WebsiteProjectType`.
- **Book-wide format defaults**: `number-sections: true` and `crossref.chapters: true`, applied uniformly regardless of render mode (see §6 for the citation and why this belongs here, not only in the single-file-merge phase).

Render-mode-*specific* book features (book stylesheet, cover image) are covered in §7 and §9 where they actually apply.

## 5. Reusing (and, where it genuinely helps, patching) the already-vendored `book-*.lua`

The pandoc-hybrid epic vendored Q1's Lua wholesale, including four book-specific files nobody had read for *this* epic until a design-question audit turned them up: `filters/quarto-pre/book-numbering.lua`, `filters/quarto-pre/book-links.lua`, `filters/quarto-finalize/book-cleanup.lua`, `filters/quarto-post/book.lua`. They do real, working, already-tested-by-Q1 things this design should reuse rather than reimplement in Rust — with one exception where a small, tracked patch to the vendored Lua is the cleaner choice (patching vendored Lua is not a hard rule against here — small, tracked patches already have a precedent in this epic, e.g. the `crossref-numbering` patch — and there's a draft upstream `quarto-cli` PR this could feed into).

- **`book-cleanup.lua`**: `cleanupBookPart` handles the `.quarto-book-part`-classed `Div` (Q1's own part/appendix divider wrapper, `::: {.quarto-book-part}\n# Title\n:::`) — keeps it for LaTeX, unwraps it for Typst (its own comment claims "the content is already transformed to `#part[...]` by book-numbering.lua" — **that comment is wrong, confirmed by reading `book-numbering.lua` directly**, see below), and **replaces it with an empty `Div` for every other format including EPUB** (functionally a deletion — no visible content survives — but implemented as `return pandoc.Div({})`, not a true node removal; a minor wording correction from a ground-truth-verification pass). Parts are print-only content: for EPUB/HTML they exist purely as sidebar navigation grouping (§4's sidebar translation), never as in-page content. This resolves P2's "part divider shape" question completely — emit exactly this `Div`, no new mechanism needed. Gated on `param("single-file-book", false)`, so this — and everything below — requires that filter param to be set true for *every* single-file-merge target (Typst, EPUB; LaTeX if ever implemented), not just Typst.
- **`book-numbering.lua`**: generates the Typst chapter-counter-reset show-rule *dynamically* from `crossref.categories.all` (not a static template rule — this is why it correctly covers custom `crossref.custom` kinds, which a Typst book extension's own bundled template alone does not). **Confirmed empirically that this is the only thing that resets Quarto's own figure/table/callout/equation counters**: a real 2-chapter Typst render with `top-level-division: chapter` set but *without* `single-file-book` produced continuous `Figure 1`/`Figure 2`, no reset at all. `top-level-division: chapter` is necessary (chapter boundaries) but not sufficient (numbering) — both must be set. Its `Header` handler also emits LaTeX's `\part{}`/`\cleardoublepage...\appendix` sequences and EPUB's `epub:type="appendix"` marking, all keyed off per-chapter metadata (`bookItemType`/`-Number`/`-Depth`/`appendix`) that Q1 threads through via `currentFileMetadataState()`, itself populated by parsing `<!-- quarto-file-metadata: base64(...) -->` HTML comments Q1 inserts at each chapter boundary in the merged markdown.

  **Correction (found while verifying the vendored Lua directly, not just citing it): Typst part/appendix handling is not in `book-numbering.lua` at all.** Its `Header` handler has an explicit comment — *"Typst part/appendix handling is delegated to book extensions (each Typst book package has different syntax for parts and appendices)"* — and does no Typst-specific work beyond the generic counter-reset show-rule above. The actual `#part[...]` emission, and — load-bearing — the **appendix-lettering mechanism** (a `#show: appendices.with("Appendices", ...)` rule that puts Typst's own numbering context into appendix mode) live entirely in the *Typst book extension's own filter* (e.g. `orange-book.lua`'s `Header` handler). This is real, upstream Q1 behavior, not a vendoring drift in this repo — confirmed byte-identical against `external-sources/quarto-cli`. It is the concrete mechanism behind this design's central premise: Typst book chapters/parts/appendices genuinely depend on the book extension, not just on Quarto's generic vendored Lua, for anything beyond simple counter resets.

  **This has a sharp, previously-missed consequence for the decision below.** `orange-book.lua` learns `bookItemType`/`bookItemNumber`/`appendix` via `quarto.doc.file_metadata()`/`quarto.utils.file_metadata_filter()` — which is *entirely* Q1's comment-marker mechanism (confirmed in `filters/common/filemetadata.lua`: this call chain does nothing but parse the `<!-- quarto-file-metadata: ... -->` comments). It has no Pandoc-attribute fallback. So:

  **Decision (revised after the above): emit *both* the comment markers and Pandoc attributes, don't patch-and-drop.** The original plan was to patch `book-numbering.lua`'s `Header` handler to read Pandoc attributes instead of porting Q1's markdown-round-trip comment-marker mechanism, on the reasoning that Q2 has a persistent AST and doesn't need it. That patch is still worth making (Quarto owns `book-numbering.lua` and can maintain it), but **dropping the comment markers entirely would silently break every unpatched Typst book extension** — including `orange-book`, the one this epic uses as its own test fixture (see below) — because their part/appendix/numbering logic has no other way to learn chapter identity. The fix costs nothing extra: P2's merge step already has every field (`resourceDir`/`bookItemType`/`bookItemNumber`/`bookItemFile`/`bookItemDepth`) from `BookRenderItem`, so it stamps **both** the `quarto-book-item-*` Pandoc attributes (for the tracked `book-numbering.lua` patch) **and** the original `<!-- quarto-file-metadata: base64(json) -->` markers in Q1's exact shape (confirmed against `book-render.ts`'s `bookItemMetadata`) — the latter purely for the benefit of extensions Q2 doesn't own and won't patch. Document this as the actual shape of the patch (not "delete the dependency on the shared file-metadata-state module," which is no longer accurate).
- **`book-links.lua`**: resolves an explicit cross-chapter markdown link (`[text](chapter1.qmd#sec-foo)`) into an in-document anchor, since after merging there's no separate `chapter1.html` to point at. **Decision: don't patch this file at all — resolve these links in Rust instead, before this Lua ever sees them.** P2 already has the complete picture at merge time (which chapter file maps to which real heading id in the merged document) — a small Rust transform, modeled on the same idea as `link_rewrite.rs` but resolving to an in-document anchor instead of a separate output path, runs immediately after merge assembly and before the Crossref phase. Once every such link is already `#<id>`-shaped, `book-links.lua`'s own `isRelativeRef` guard sees nothing left to do and no-ops harmlessly — matching how it already behaves for a document with no such links.
- **A related, pre-existing risk this surfaces**: Q2's own `LinkRewriteTransform` (Finalization phase, website epic) is *not* in `PANDOC_TRANSFORM_EXCLUDED` — it runs for Pandoc-hybrid targets today, and would try to rewrite the same links into website-style `.html` hrefs if given a `ProjectIndex`. Its own contract says it no-ops without one. **Decision: don't attach a `ProjectIndex` to the merged book document's `RenderContext`** — a defensive belt-and-suspenders alongside the Rust-side resolution above (by the time `LinkRewriteTransform` runs, in Finalization, the links are already resolved anyway, but this removes any chance of it acting on something unexpected). **Note for future maintainers**: this means *any* future Finalization-phase transform that assumes "a project render always has a `ProjectIndex`" will silently no-op on merged book documents specifically — a deliberate invariant of this design, not an oversight, but one worth grepping for before adding the next such transform.
- **`quarto-post/book.lua`**: a `quarto-title-block` code-cell mechanism, plus a PDF-only `\markboth`/`\markright` running-header workaround. The title-block mechanism is **broader than "per-chapter title/author overrides"** — `resources/projects/book/pandoc/title-block.md` (the template it renders) covers subtitle, author affiliations, date, and abstract, driven by *any* chapter front matter containing those keys, not an override-specific case. **Decision: scope out of v1 anyway** — the mechanism's guard (`el.attr.classes:includes('quarto-title-block')`) means it's already inert if Q2's merge simply never emits that construct, so no Lua patch is needed either way. But this is **missing functionality, not an intentional design divergence**: nothing architectural blocks porting it, and §7/P4's chapter-title-decoration AST-insertion point (`withChapterMetadata`/`formatChapterTitle`) is the natural, ready seam for it later. Tracked as `bd-ock6cyiy`, not this epic's job to build — P4 should structure its title-decoration insertion so that seam stays open (see §7). The PDF-only workaround is moot since LaTeX isn't implemented.
- **No *general* bundled-extension mechanism exists in Q2 yet — but this epic ships a narrow, Typst-book-specific default, resolved with the user rather than left as a v1 gap.** Q1 auto-loads `orange-book` with zero config for any Typst book with no explicit `format` extension named (`render-contexts.ts`'s `readExtensionFormat`, line 688-693: `project?.config?.project?.type === "book" && formatDesc.baseFormat === "typst"` → `effectiveExtension = "orange-book"`) — one of several Typst book extensions that work the same way (`orange-book` is the one bundled with Q1 itself, under `src/resources/extension-subtrees/orange-book/`; several more exist as ordinary third-party `@preview` Typst packages/Quarto extensions). Q2 has no equivalent *general* auto-load infrastructure, and building one is still out of scope (§11) — the closest existing plan, `claude-notes/plans/2026-09-03-julia-engine-static-declarations-epic.md`, is a provisional, **not-yet-started, not-yet-agreed** draft about bundling the Julia *engine* extension specifically, not a general Typst-template mechanism, and this epic doesn't wait on it.

  **Decision (resolved with the user, fifteenth pass): Q2 mirrors Q1's specific zero-config default — a Typst book target with no explicit format extension named auto-resolves to the locally-vendored `orange-book` — without building the general mechanism.** This is deliberately narrower than Q1's general `readExtensionFormat` seam (which dispatches on *any* project-type/format-pair, and would generalize to other Typst book extensions and other project types); Q2 hard-codes the single `book` + `typst` + `orange-book` case P2 already vendors, mirroring Q1's *outcome* for the one pairing this epic cares about, not Q1's *mechanism*. `_extensions/orange-book/` is vendored locally per this repo's External Sources Policy — never referenced from `external-sources/` at runtime — alongside `resources/typst-packages/`, **with its own README** (source tag/commit, re-vendor procedure) matching the convention every other vendored-resource directory in this repo already follows (`resources/scss/README.md`, `resources/typst-packages/README.md`, `resources/pandoc-filters/README.md`, etc.) — the one asymmetry a whole-system-composition review found and closed. A book project's `_quarto.yml`/`q2 create` scaffold needs **no** explicit extension reference to get chapter-scoped Typst numbering/appendix-lettering; P2 adds a test rendering a book fixture with no `format.typst` extension configured at all and confirming it resolves to `orange-book` and compiles successfully (§6/P2's checklist). The eventual general bundled-extension mechanism, if and when it's built, would let a user *override* this default with a different Typst book extension — that override path is not built in this epic; today the default is unconditional for a Typst book target with no explicit extension.

**A sharper version of the old open question, found by a taxonomy review of this epic's own deferred items, and now resolved by the decision above for the case that actually matters: what happens if a Typst book target has no book extension configured at all?** `book-numbering.lua`'s generic counter-reset (figures/tables/callouts/equations) fires regardless — it only checks `isTypstOutput()`/`single-file-book`, not any extension. Part wrapping and, critically, appendix-lettering are *entirely* extension-owned (§5) — with no extension loaded, an appendix chapter would silently render as an ordinary continuing chapter (no "Appendices" break, no letter form, e.g. "4.1" instead of "A.1"), not an error. **This no longer happens by default**, because of the decision above: a Typst book target with no explicit extension now resolves to `orange-book` automatically, matching Q1's own zero-config behavior, so the silent-degradation path this bullet used to describe is closed for the common case. It remains a live risk only if a future general bundled-extension mechanism adds a way to explicitly configure "no extension at all" for a Typst book — a case this epic doesn't build and therefore doesn't need to diagnose.

## 6. Single-file merge mechanism (P2/P3)

**Resolved, then substantially redesigned by a sixteenth-pass "step back and consider alternatives" conversation with the user.** The original framing (still true at the primitive level, wrong about how much is reused) treated this as "stop `AstTransformsStage` mid-phase via `execute_range`, resume it later." The redesign below keeps `execute_range` but reframes everything built *around* it: instead of one stage learning to pause and resume, there are now two independently-nameable, independently-buildable stage lists sharing one parameterized primitive. This closes gaps a later implementability review found in the original framing (`AstTransformsStage` never actually had a phase-bounded execution mode to reuse; there was no story at all for how a resumed chapter's output reaches disk) rather than patching them onto the old shape.

*Part 1 — does anything stop the pipeline mid-render?* `render_document_to_file` never calls `TransformPipeline::execute` itself: it delegates to `render_qmd_to_html` (`pipeline.rs:951`) / `render_qmd_to_pandoc` (`pipeline.rs:400`), each of which builds a full stage list (≈19 stages pre-`AstTransformsStage`, ≈25 total for HTML; the Pandoc list is the same minus `PANDOC_STAGE_EXCLUDED` plus `PandocWriteStage`/`TypstCompileStage`) and runs it via `Pipeline::run` (`stage/pipeline.rs:140`) — a flat loop with no stopping point, terminating in output-writing stages (`ApplyTemplateStage`, `PandocWriteStage`, …) neither P2 nor P5 wants for a paused chapter. `AstTransformsStage::run` (`ast_transforms.rs:104-256`) is where `TransformPipeline::execute` actually gets called (`ast_transforms.rs:230`) — **unconditionally, for both the JIT-built and `with_pipeline`-supplied cases; there is no phase-bounded execution mode today.** `build_analysis_pipeline`/`build_analysis_transform_pipeline` (`pipeline.rs:687-743`) is real precedent, but only for customizing pipeline *content* (a hand-curated, narrower transform list) — never for phase-bounded *execution* of the real one. **Corrected by an implementability review**: the fix is to make the range a first-class parameter of the stage itself, not a special-case mode bolted onto existing code — `AstTransformsStage::for_range(range: impl RangeBounds<TransformPhase>)`, whose `run()` always calls `execute_range(range)`; today's unconditional-`execute` behavior becomes the special case where `range == ..` (P2 builds this; it is the one change every other piece below depends on).

That one primitive gives two genuinely separate, independently-nameable stage lists — not one stage taught to pause and resume:

- **`build_html_pipeline_pause_stages(upper_bound)`** — the prefix of the real stage list through a range-bounded `AstTransformsStage`, and *nothing after it*. This is what P2's own per-chapter partial render needs (`..=Normalization`) and what P5's initial per-chapter render needs (`..=Navigation`).
- **`build_html_pipeline_finishing_stages(lower_bound)`** — new, and previously missing entirely: starts *directly* with a range-bounded `AstTransformsStage`, then the real, *unchanged* tail — `UserFiltersStage::post() → ResourceReportStage → CodeHighlightStage → MathJsStage → RenderHtmlBodyStage → ApplyTemplateStage`. **P2 needs an instance of this too, not just P5** — P2's own merge step feeds the merged `Pandoc` into "the unmodified single-document pipeline" starting from *Crossref*; that is this same primitive with `lower_bound = Crossref`. P5's resume is the same primitive with `lower_bound = Finalization`. Since P2 needs it first (chronologically, in the epic's own dependency order), **P2 builds this constructor generically; P5 reuses it with a different lower bound**, exactly mirroring how `execute_range` itself is already assigned.

Feeding either constructor requires one more new piece: a `run_pipeline_from_ast` sibling to `run_pipeline`, taking an already-built `PipelineData::DocumentAst` instead of raw bytes. This is mechanically clean at the `Pipeline` level — `Pipeline::new` derives its `expected_input`/`expected_output` from the first/last stage's own declared kind (not from any assumption about what ran before), and `AstTransformsStage`'s `input_kind()` is already `DocumentAst` — so a stage list starting with it validates with zero changes to `Pipeline` itself. **`run_pipeline_from_ast` needs its own complete `RenderContext↔StageContext` bridge**, the same shape as `run_pipeline`'s existing one (see the owned-field enumeration below for exactly which fields it must carry, and why that set differs between P2's and P5's use of it) — building this bridge correctly *is* the fix for the "bridge doesn't round-trip most owned fields" gap an implementability review found, scoped to what's actually needed rather than a blanket carry-everything rule.

*Part 2 — can `RenderContext<'a>` survive being held across the pause?* Resolved more simply than either plan previously assumed, precisely *because* of Part 1's shape: the new entry point takes `ctx: &mut RenderContext<'_>`, exactly like `render_qmd_to_html`/`render_qmd_to_pandoc` do — so **the caller, not this function, owns and constructs `RenderContext` per chapter**, and nothing ever needs to hold a *constructed* `RenderContext<'a>` across the pause at all. The book orchestrator instead holds one plain owned struct per chapter (`doc_info: DocumentInfo`, `binaries: BinaryDependencies` — or a book-shared `Arc`, since binary discovery has nothing chapter-specific about it — plus copies of `RenderContext`'s owned fields) and reconstructs a fresh, short-lived `RenderContext<'_>` borrowing from that struct's own fields immediately before each call into the new entry point, copying the mutated owned fields back out afterward. No self-referential struct, no unsafe, no `'a` that has to outlive the whole book — this is the same shape `render_document_to_file` already uses locally (owns `doc_info`/`binaries`, borrows into `RenderContext` locally); the only change is moving the owning scope from one function call up to a book-level `Vec`.

**The owned-field enumeration is not one shared list — a sixteenth-pass check found P2's and P5's actual needs differ by target format, not just by mechanism, and a naive "carry everything either might need" list would have P2 implementers writing dead code.** Both start from the same audited superset (`artifacts`, `diagnostics`, `crossref_index`, `ref_type_registry`, `project_index`, `resource_resolver`, `options`, `includes`, `pipeline_profile`, `observer`, `user_grammar_provider`, `resource_report`, `resource_copies`, `code_block_decorations`, `attribution_provider`, `attribution_data` — cross-referencing every `RenderContext` field against every transform's declared `phase()` and every non-transform writer's pipeline position), but the two phases genuinely need different subsets:

**Always needed, both phases**: `artifacts`, `diagnostics`, `project_index`, `resource_resolver`. **Needed as static passthrough, both phases, but for a subtler reason than "might be mutated"**: `ref_type_registry`, `options`, `includes`, `pipeline_profile`, `observer`, `user_grammar_provider`, `resource_report`. None of these is ever written by any `AstTransform` — `ref_type_registry`, for instance, is set once by `PreEngineSugaringStage`, a top-level `PipelineStage` that runs long before `AstTransformsStage` even starts, and only ever read afterward. They need to be *present* in a resumed/finishing-pipeline's reconstructed context only because the stage that originally set them doesn't run again in a from-AST finishing pipeline — not because anything mutates them mid-flight. Carrying them forward (or recomputing them identically) is risk-free either way.

**Needed by P5, not by P2 — checked per field, not assumed uniform:**

- **`crossref_index`**: P5's pause is *after* Crossref phase has run (Navigation comes after Crossref); Pass 3's aggregation step is defined as reading each chapter's `crossref_index.entries` directly. **P2's pause is *before* Crossref runs at all** (`..=Normalization`) — the field is still at its default, empty state when P2's cut happens. Nothing to carry.
- **`code_block_decorations`**: for P5's target (HTML), both `CodeBlockGenerateTransform` (writer, Normalization) and `CodeBlockRenderTransform` (reader, Finalization) run — a real producer-before/consumer-after-the-cut pair. For P2's targets (Typst, EPUB — Pandoc-hybrid), `"code-block-render"` is in `PANDOC_TRANSFORM_EXCLUDED` (`pipeline.rs:1831`), so the *consumer* never runs at all; the data would be computed and carried for nothing.
- **`attribution_provider`/`attribution_data`**: `AttributionGenerateStage` checks `format_supports_attribution(&ctx.format)` — `matches!(format.identifier, FormatIdentifier::Html)` — **first, before anything else**, and bails if false. For P2's targets, `attribution_data` is never populated in the first place, at any point in the render, pause or no pause. Carrying `None` forward is identical to a freshly-constructed context's own default.
- **`resource_copies`**: its two Normalization-phase writers, `FormatCssTransform`/`TitleBannerTransform`, are both gated identically (`ctx.format.is_html()` / `matches!(..., FormatIdentifier::Html)`) — dead for P2's targets by the same mechanism as attribution. Its third writer, `ResourceCollectorTransform` (image-reference collection — the one writer that *would* matter for Typst/EPUB, since compiled output needs the referenced image files present), is Finalization phase and runs fresh, once, on P2's *merged* document — never per-chapter, so it has nothing to do with the per-chapter pause point either.

So **P2's actual carry-list is short**: `artifacts`, `diagnostics`, `project_index`, `resource_resolver`, plus the seven static-passthrough fields. **P5's is the full sixteen-field superset.** Fields confirmed safe to omit from *either* list entirely: `format_options` (written only by Finalization-phase transforms, i.e. fresh, after both cuts, never before); `resolved_listings` (`ListingGenerateTransform`/`ListingRenderTransform` are both Navigation phase, fully resolved before P5's pause and never exercised by P2's Normalization-only call at all); `engine_registry_override`/`document_profile` (static test-seam input / post-hoc bridge-back, untouched by any in-flight transform).

**P2's own use of this is simpler than P5's in two ways now, not one.** P2 merges every chapter's `Vec<Block>` body into *one new* `Pandoc`/`RenderContext` built fresh for the merged whole, so it processes chapters one at a time — construct, call the pause-side entry point with `..=Normalization`, take the body plus its short field list, drop the struct, next chapter — and its finishing pipeline (`Crossref..`) ends in `PandocWriteStage`/`TypstCompileStage`, which already write the compiled output to disk *as part of the stage list itself*. **P5 is where the harder case lives, on both axes**: it produces N *separate* output files, so each chapter's owned struct — carrying the full field list — is held *simultaneously* in a book-scoped `Vec`, resumed independently via the finishing pipeline at `Finalization..`; and because P5's target is HTML, where writing is *not* a stage (it's the external `OutputSink` glue in `render_document_to_file`, entirely outside `run_pipeline`), P5 additionally needs that write logic split out into its own reusable function — see §8.

**A gap in P2's own contract, found by an eighteenth-pass review: the field-list audit above answers what a *resumed* context needs carried across a pause — it never specifies how P2's *freshly-constructed* merged-document `RenderContext` gets populated in the first place, since that context was never paused-and-resumed from any single chapter's own.** Two concrete risks this leaves open, neither previously called out anywhere in this doc or P2's plan: (1) **`diagnostics`/`artifacts` loss.** If chapter 3's Normalization pass emits an engine-execution diagnostic or registers an artifact, and the merge step's own checklist item only merges `Vec<(BookRenderItem, Pandoc)>` bodies (not each extracted chapter struct's `diagnostics`/`artifacts`), that data has no stated path into the merged document's fresh context — silently lost by the time the `Crossref..` finishing pipeline runs and writes output. The merge function must explicitly concatenate `diagnostics` and merge/union `artifacts` across all N extracted chapter structs, not just their `Pandoc` bodies. (2) **`project_index`/`resource_resolver` and the seven static-passthrough fields' source is implicit, not stated.** These are plausibly identical across every chapter (project-level, never chapter-mutated) — safe to source from any one chapter's copy, or better, compute once at book level before the per-chapter extraction loop starts — but no document says so explicitly, unlike P5's field-by-field rationale. State this as an explicit decision, not something left for an implementer to infer.

Run each chapter through its own pipeline through the **Normalization** phase (parse, engine execution, AST sugar — unchanged, per-document; stopped using the phase-bounded transform runner built for this purpose, see §8). Concatenate the resulting `Vec<Block>` bodies in book order, inserting `.quarto-book-part`-classed `Div` dividers for parts/appendices (§5), stamping each chapter's own top-level heading with `quarto-book-item-*` attributes (§5), and building book-level title metadata (`book.title`/`author`/`date`/`abstract`/`doi` → merged document `meta`, port of `withBookTitleMetadata`). A new Rust transform resolves any explicit cross-chapter file link (`[text](chapter1.qmd#sec-foo)`) to an in-document anchor immediately after assembly, before Crossref (§5) — and the merged document's `RenderContext` gets no `ProjectIndex` attached, so `LinkRewriteTransform` (Finalization) stays inert on it. Set `top-level-division: chapter` and the `single-file-book` filter param — **`top-level-division` is specifically the lever Typst and LaTeX share** (confirmed by reading both `format-typst.ts` and `format-pdf.ts`'s `BookExtension`s, and empirically for LaTeX below) so the target's own compiler/writer treats each chapter's H1 as a true chapter boundary; **`single-file-book` is the separate, and equally required, flag that activates the vendored book-specific Lua at all** (§5) — set both for every single-file-merge target. **EPUB's chapter boundary is a third, separate mechanism** (`--split-level`, P3) — do not conflate any of these three as one "general merge flag"; they're consequences of the same merge, but distinct settings with distinct, non-overlapping jobs.

Then run **one** Crossref-through-Finalization pass over the assembled whole, through the *unmodified* single-document Pandoc-hybrid pipeline (`feature/pandoc-writer-hybrid`'s `PandocWriteStage`/`TypstCompileStage`). **Chapter-number injection is not needed for either the numbering value itself (§2) or the counter-reset trigger (a merged document's own real H1 order is sufficient for `book-numbering.lua`'s dynamically-generated reset rule) — but the `single-file-book` param and the per-heading attributes above are still required inputs**, confirmed empirically: a real 2-chapter Typst render with `top-level-division: chapter` set but *without* `single-file-book` produced continuous, unreset numbering (`Figure 1`, `Figure 2`) — `top-level-division` alone is necessary but not sufficient.

**Empirical confirmation, LaTeX** (real `quarto render . --to pdf`, inspecting the intermediate `.tex` via `keep-tex: true` — not just reading `format-pdf.ts`): chapters compile to plain `\chapter{...}`/`\section{...}`, the appendix chapter is preceded by a bare `\appendix` command (LaTeX's own native letter-switch, no Quarto-side letter computation), and cross-references are emitted as deferred, compiler-resolved `\ref{}` (`See Chapter~\ref{sec-ch1} and Figure~\ref{fig-a}...`) — not baked static numbers. This is structurally the same pattern as Typst's `#ref()`: compiler-native, deferred, chapter-scoped automatically, once chapters are merged into one document with real top-level headings. LaTeX book output is not implemented this epic, but the abstraction this section is built around is now validated against two independent compilers, not one.

EPUB gets chapter splitting for free via `--split-level` on top of the same merge, plus a book-specific derivation: `epub-cover-image` from `book.cover-image` when not explicitly set (mirroring `epubBookExtension.onSingleFilePreRender`; see P3). DOCX/PPTX book output is explicitly out of scope (Q1's own book formats there produce N disconnected per-chapter files by default — not a real book feature even upstream).

**Book-wide format defaults**, confirmed by reading `book.ts`'s `formatExtras` directly: `number-sections: true` and `crossref.chapters: true` for every book format, `toc: false` for Typst specifically (Quarto's own TOC would duplicate the template's own), and `toc` already effectively `false` for EPUB (Q1's own default is `!isEpubOutput`). `crossref.chapters: true` matters concretely for EPUB, whose chapter-scoped numbering runs through the vendored `sections.lua` and reads this flag directly; it's inert for Typst's native-counter path but set uniformly, matching Q1's own structure. **These aren't single-file-merge-specific** — confirmed against `book.ts:213-224`, the base `number-sections`/`crossref.chapters`/`toc` object is set unconditionally at the top of `formatExtras`, *before* the `isHtmlOutput`/`isLatexOutput`/`isTypstOutput` branches that follow it — so multi-file HTML gets exactly the same `number-sections: true`/`crossref.chapters: true` defaults too. This belongs in P1 (§4), as a format-agnostic default applied once regardless of render mode; §6 (single-file merge) and §7 (multi-file HTML) both just inherit it rather than each setting it independently.

**Bibliography is not automatically unified either — a real, previously-wrong premise found by a review pass, not inherited from Q1 (Q1 doesn't have this problem at all, for a reason specific to Q2's own architecture).** §2's "one citeproc pass over the whole document" framing assumed Q2's citeproc filter runs where Q1's does — once, over the fully-merged document. It doesn't: `apply_citeproc_filter` runs inside `UserFiltersStage::pre()`, which executes *before* `AstTransformsStage` (hence before Normalization) for every format, Pandoc-hybrid included (`PANDOC_STAGE_EXCLUDED` doesn't exclude `UserFiltersStage`; `apply_citeproc_filter`'s `target_format` parameter is unused, confirming no format branch skips it). P2's own per-chapter entry point — "the prefix of `build_html_pipeline_stages_with_options` through `AstTransformsStage`... stopping before `UserFiltersStage::post`" — necessarily includes `UserFiltersStage::pre`, since it comes earlier in the stage list. So each chapter's citations get independently resolved, and its own separate bibliography built, *before* P2's merge step ever sees it. **Confirmed empirically, not just by reading the stage list**: a real single-document Typst render (`keep-typ: true`, citeproc configured) shows the citation already resolved to literal text ("(Smith 2020)") and a per-document bibliography block already baked into the `.typ` source, well before the Pandoc write stage runs.

This is why crossref numbering and bibliography aren't actually the parallel cases §2 (before this correction) treated them as: `CrossrefIndexTransform` runs *inside* the Crossref phase, downstream of where P2 stops (Normalization) — so it only ever runs once, after merge, naturally unified. Citeproc sits on the opposite side of that cut line — before Normalization, hence before merge.

**The fix, format-agnostic and simpler than it first looks: don't run citeproc per-chapter for book-merge chapters at all — defer it to one pass over the assembled whole, mirroring Q1's real architecture (not just its output shape).** Exclude the `Citeproc` entry from each book-merge chapter's own resolved filter list (checking both `.pre` and `.post` — a user can order citeproc into either, the same edge case P6's plan already notes) before that chapter runs through this phase's per-chapter entry point; run every other filter normally. After merge assembly, call `apply_citeproc_filter` (`crates/pampa/src/citeproc_filter.rs` — already a standalone function taking only `Pandoc`+`ASTContext`, no stage or `RenderContext` machinery required) once, directly, on the merged document, before the single Crossref-Finalization pass. Placement into the designated references chapter needs no new mechanism: citeproc's own existing convention (fill an `{#refs}`-id'd `Div` if the document has one) already lands the merged bibliography exactly where P1's `References`-kind chapter's own `{#refs}` div sits in the merged body — the same convention Q1's own book scaffold already relies on (P7's ported scaffold's References chapter is literally just a bare `{#refs}` div, no engine content).

**This achieves genuine Q1 parity for single-file merge, not just P6's necessarily-looser multi-file approximation.** A real, single, book-wide citeproc pass produces correct in-text citation numbers too — unlike P6's mechanism for multi-file HTML, which only merges the bibliography *list* and deliberately leaves per-chapter in-text numbering broken, matching Q1's own multi-file bug (§9). Single-file merge doesn't inherit that bug at all with this fix — it matches Q1's actual (bug-free, for this specific case) single-file behavior, because a real book-wide citeproc pass, run once, produces correct book-wide numbering as an ordinary consequence, not something that needs separate dedup/disambiguation-seeding logic the way P6's harder multi-file case does. §9 explains why multi-file HTML can't use the same trick (there's no single merged document for it to run one pass over — each chapter is a genuinely separate output file).

**Considered and rejected**: relying on Typst's own native citation engine instead of Q2's citeproc, mirroring how Typst already handles heading numbering natively. Tested empirically and doesn't work as a low-effort option — Typst's native `#bibliography()`/`#cite()` expect a Hayagriva-YAML or BibLaTeX bibliography, not the CSL-JSON file Q2's own citeproc (and Quarto users) actually use: skipping citeproc entirely and letting `Cite` nodes flow through to a native Typst `#cite()` call failed to compile against the same CSL-JSON fixture (`key 'smith2020' does not exist in the bibliography`). Pursuing this would need a bibliography-format-conversion step, and wouldn't help EPUB at all (no native citation engine there) — not worth the format-specific complexity when the uniform, Q2-side fix above works identically for both.

**Tangential, pre-existing, unrelated to books — filed separately, not this epic's job**: the same probe surfaced that Q2's Typst writer emits a native `#bibliography(("refs.bib"))` call *even when* Q2's own citeproc has already fully resolved every citation and built its own bibliography block — a possibly-redundant second bibliography-loading directive. Didn't visibly break this render, but worth a look outside this epic (`bd-wjn7jdzw`).

**Output filename**: port `bookOutputStem` — `book.output-file`, falling back to `book.title`, falling back to the project directory name, sanitized to a filesystem-safe name. Confirmed empirically: a real `quarto render . --to pdf` on a book titled "Numbering Probe" with no explicit `output-file` produced `Numbering-Probe.pdf`, not `index.pdf`.

**Two watch-tests grounded in `orange-book`'s own "Critical" assertions, not invented for this design**: (1) a reference to an *earlier* chapter's labeled theorem must show that theorem's original number after merge+compile — `orange-book` guards exactly this to catch a resolution-timing bug class in the Typst theorem package it uses; Q2 inherits this risk by construction (deferring to native resolution) so needs the fixture, not a code fix. (2) a custom `crossref.custom` kind (`orange-book`'s "Dinosaur") must get the same chapter-scoped, compile-time-resolved numbering as a built-in figure, with no special-casing anywhere in the merge mechanism.

## 7. Multi-file HTML: local numbering (P4)

Each chapter renders independently, exactly as today's Pass 2. The chapter needs one externally-injected fact before its own Crossref-phase transform runs: **its book chapter number** (and appendix-letter flag) — `None` for an unnumbered chapter, in which case no seed is applied at all. Q2 already has the exact counter this needs to seed — `CrossrefIndex.sections: Vec<u32>` (`crates/quarto-core/src/crossref/index.rs`), built by the existing `CrossrefIndexTransform`/`advance_sections`, already snapshotting into every crossref entry's `Order.section`. This mirrors Q1's mechanism exactly: `sections.lua`'s `crossref.index.section` is seeded from a `number-offset`-shaped param for precisely the same reason (an isolated per-chapter Pandoc process has no other way to know its chapter number).

Empirically confirmed (`scratchpad/minibook` experiment, real `quarto render`): seeding `sections = vec![chapter_number - 1]` before the chapter's walk begins reproduces Q1's observed numbering exactly (chapter 1 needs no seed; chapter *N* seeds `vec![N - 1]`, and its own H1 increments to `N`) — no changes needed to `advance_sections` itself.

**Gap found by an implementability review, resolved by a follow-up research round: the header's own number seeds correctly, but figures/tables/equations don't inherit it — turns out to be a pure display-layer bug, not a data-layer one.** `index_custom_target` (`crossref_index.rs:250-311` — the registration path for every non-`Header` crossref target: figures, tables, listings, theorems, equations) already sets `order.section = self.index.sections.clone()`, the *same* seeded section stack a header uses — combined with each book chapter rendering through its own independent `CrossrefIndex` (so `order.order`, the flat per-ref-type counter, already restarts at 1 per chapter for free), the data is already fully chapter-aware once the seed above is applied. `CrossrefIndex`/`Order`/`crossref_index.rs` need no changes.

The bug is confined to `crossref_render.rs`'s four display functions — `render_float_ref_target`, `render_theorem`, `render_equation`, `render_resolved_ref` — which each independently extract the bare `order.order` and format it flat, ignoring `order.section` (and ignoring `ctx.chapter_seed`, which is already in scope inside `CrossrefRenderTransform::transform`, the caller of all four). **Fix: read `ctx.chapter_seed.chapter_number` directly, not `order.section`** — safer, since `chapter_seed` is `None` for every non-book render and for an unnumbered chapter (no seed applied), so gating on `chapter_seed.is_some()` can't regress an ordinary document's existing flat numbering; reconstructing from `order.section[0]` instead would risk exactly that regression, since an ordinary multi-heading document already has a non-empty `order.section` today. Extract one shared helper, `format_crossref_number(order: u32, chapter_seed: Option<&ChapterSeed>) -> String` (`None` → `"{order}"`, byte-identical to today; `Some(n, is_appendix: false)` → `"{n}.{order}"`; `Some(n, is_appendix: true)` → `"{letter(n)}.{order}"`), called from all four sites in place of their current bare-`u32` extraction — `prefix_caption`'s `number: Option<u32>` parameter becomes `Option<String>` (pre-formatted). Pull the letter-vs-numeral conversion into its own tiny helper shared with P0's `@sec-` presentation code (the identical `is_appendix` branch), rather than duplicating it. Confirmed scope-safe: `"crossref-render"` is in `PANDOC_TRANSFORM_EXCLUDED` (same list as `code-block-render`), so this fix never runs for Typst/EPUB — 100% confined to Q2's native HTML writer, zero risk to P2/single-file merge. **This is also the previously-invisible prerequisite for P5's registry**: P5's plan already specifies its `ProjectCrossrefIndex` entries as storing `resolved_number` (a formatted string, e.g. `"2.3"`) — this fix is what actually produces that string; P5 was implicitly depending on a mechanism that didn't exist yet.

**A follow-up experiment with an unnumbered middle chapter** confirmed the interaction with §4's "no slot consumed" rule precisely: the unnumbered chapter's own figure numbered as plain, unscoped `Figure 1` (not `Figure 0.1` or any chapter-scoped form), and the *following* numbered chapter still correctly continued as chapter 2 (its figure: `Figure 2.1`) — the unnumbered chapter is invisible to the chapter sequence in both directions. This matches `sections.lua`'s own early-return on `.unnumbered` (P0 must port this exact behavior, not just the seeding).

**Representation decision:** keep an explicit `chapter_number: u32` / `is_appendix: bool` fact (computed once in `pre_render` from the `BookRenderItem` list, threaded into that chapter's `RenderContext`) as the single source of truth for "which chapter is this" — used by title decoration, sidebar, and (later) the project-wide registry key.

**How it actually reaches `RenderContext` (traced against real code — "threaded into" had no implementation path until this was checked), split across two phases in dependency order: a new `ChapterSeed{chapter_number, is_appendix}` type, a `RenderContext.chapter_seed` field, and a `RenderContext::with_chapter_seed(...)` builder matching the existing `with_project_index`/`with_resource_resolver`/`with_options` pattern — built by P0 (it needs this self-contained for its own tests and runs first) — plus a new field on `RenderToFileOptions` — built by P4, which computes and wires in the *real* per-chapter values.** **Revised (tenth pass): the per-chapter map lives on `RenderToFileRenderer` itself (a new `chapter_seeds: HashMap<PathBuf, ChapterSeed>` field plus a `with_chapter_seeds(...)` builder), not as a new parameter on the shared `Pass2Renderer` trait's `render_batch` method — the trait is also implemented by the WASM/preview renderers (`RenderToHtmlRenderer`/`RenderToPreviewAstRenderer`), which never render a book and would otherwise have to accept and ignore a parameter meaningless to them. See P4's plan for the full mechanism, including the wrinkle this surfaces: `RenderToFileRenderer.options` is one shared `&'a RenderToFileOptions` reference reused for every document in a batch, so applying a per-chapter seed means cloning-and-overriding that options value for just the seeded document, not mutating the shared reference. Deliberately keeps chapters going through `Pass2Renderer`'s existing (real, non-trivial: rayon thread pool, panic-safe, fail-fast, ordered artifact merge) batch machinery rather than a bespoke per-chapter loop that would forfeit it. **`is_appendix` has two numbering-related consumers, not one**: the `CrossrefIndex.sections` seed (a one-line integer seed, unaffected by appendix-ness itself — the counter doesn't know or care whether it's numbering a chapter or an appendix), and — corrected on review, previously understated — P0's `@sec-` presentation code, which needs `is_appendix` to decide letter-vs-numeral formatting and "Appendix"-vs-"Chapter" prefixing (`sections.lua` reads the equivalent fact for exactly this, see P0's plan). The counter algorithm itself is still not duplicated or parallel-tracked — only the presentation layer branches on appendix-ness, not the counting.

Chapter title decoration (chapter number prepended to the page's own H1/title metadata, appendix "Appendix A — Title" formatting, `.unnumbered` handling) ports `book-chapters.ts`'s `withChapterMetadata`/`formatChapterTitle` as idiomatic Rust — same algorithm, not a transliteration. **This is a different mechanism from sidebar nav-item text decoration** (`numberChapterHtmlNav`'s equivalent, §4) — the page's own title and its sidebar entry are decorated independently in Q1, and stay that way here: title decoration happens per-chapter at render time (this section); sidebar decoration happens once at config-translation time (§4/P1).

**Leave the seam open for `bd-ock6cyiy` (per-chapter subtitle/author-affiliations/date/abstract, tracked separately, not this epic's job — see §5's `quarto-post/book.lua` bullet).** When implementing this AST-insertion point, insert the title-decoration content as one block in what could later be a short, ordered sequence of decoration blocks near the H1 (title, then — later — subtitle/affiliations/date/abstract), rather than hard-coding "exactly one decoration block and nothing else can ever follow." No new code needed now; just don't paint the insertion point into a corner a future, separate strand would have to un-paint.

**HTML-render-time book features, also P4's scope** (both gated on `isHtmlOutput`/multi-file in Q1, so they belong with the phase that actually renders HTML, not with P1's format-agnostic config work):

- **`book.scss`**: a bundled stylesheet Q1 injects for HTML output (`bookScssBundle` in `book.ts`) — port directly.
- **Cover image**: Q1 prepends a markdown image to the index/Preface page's content (`book-render.ts`'s `onRender`), then uses a DOM postprocessor (`bookHtmlPostprocessor`) to move that image from before the first `<section>` wrapper to inside it. **Do not port the DOM postprocessor.** Read *why* Q1 needs it first — Pandoc's HTML writer wraps heading+content in `<section>`, and the image, prepended to raw markdown before any heading, lands outside that wrapper. The better fix, consistent with this repo's no-DOM-postprocessor policy, is to insert the cover-image `Block` in the correct position in the AST to begin with (inside the section, not before it) rather than porting a repositioning step at all. **Confirmed possible, with one real ordering constraint pinned down by tracing the actual mechanism.** Q2's HTML writer does zero section-wrapping logic itself (`crates/pampa/src/writers/html.rs:1715-1722` just checks `div.attr.1.contains("section")`) — the wrapping is a separate pre-write AST pass, `SectionizeTransform` (`crates/quarto-core/src/transforms/sectionize.rs`, wrapping `pampa::transforms::sectionize_blocks`), registered in the Normalization phase (`pipeline.rs:1392`) — a review pass found it's actually the 24th of 32 Normalization-phase transform pushes in `build_transform_pipeline`, not "early"; this only gives the cover-image insertion *more* room before it, not less, so it doesn't change the decision below. It turns the flat `Vec<Block>` into nested `Div{class="section level<N>"}` wrappers driven by heading level. **So inserting the cover-image `Block` right after the index chapter's `Header` in the flat `Vec<Block>` does land inside the resulting `<section>` — but only if that insertion happens before `SectionizeTransform` runs.** If the insertion instead happened later (a Finalization-phase or project-level pass, which is where a book-specific feature might naturally be tempted to live), the flat list no longer has a top-level `Header` to anchor on — it's already buried inside the section `Div`'s `content`, so the insertion would instead need to find that `Div` (by id or first-heading) and splice into its content at index 1. **Decision: do this insertion early**, in the same per-chapter Normalization-phase pass that already knows "this is the index/Preface chapter" (P1's chapter-model computation happens before render, so the fact is available), not as a later pass — avoids the section-splicing complexity entirely.

This phase ships **before** project-wide resolution exists (§8): a cross-chapter `@ref` uses the crossref system's *already-existing* unresolved-reference mechanism (`CrossrefResolveTransform` already emits an unresolved `CrossrefResolvedRef` custom node rather than erroring, specifically so a back-end renderer can show a visible placeholder) — no new placeholder shape needs inventing.

## 8. Pass 3: project-wide crossref registry (P5)

**Prior art found in-repo**: `crates/quarto-core/src/crossref/index.rs`'s own module doc anticipates exactly this — *"These types are serializable so per-file indices can be persisted under `.quarto/xref/<file-id>.json` and merged into a project-wide index... see Phase 4 of the design plan"* (`claude-notes/plans/2026-04-15-crossref-design.md`, whose own O8 explicitly defers appendix numbering "to the book-projects session" — this epic).

**Shape, relative to today's Pass 1 / Pass 2:**

- Pass 1 (unchanged, every project type): cheap, no-execution profile sweep.
- Pass 2, for book chapters only: run through engine execution, Normalization, local Crossref-phase numbering (§7), and **Navigation** (sidebar/navbar/TOC/page-nav/footer generation — all page-local, driven by config already fixed at `pre_render` or by the chapter's own already-final heading structure; none of it needs cross-chapter data) — then **pause**, immediately before `Finalization`. Hold the in-progress `(Pandoc, RenderContext)` plus the chapter's harvested crossref inventory (ids it defines, their local order/caption) in book-local orchestrator state — a plain `Vec`, not a new pipeline abstraction.

  **Corrected pause point.** An earlier draft of this design said the pause sits "between `Crossref` and `Finalization`" — imprecise, since `TransformPhase::Navigation` sits between those two in the real ordering (`Normalization, Crossref, Navigation, Finalization`), and grepping every `Navigation`-phase transform (`sidebar_generate/render`, `navbar_generate/render`, `toc_generate/render`, `footer_generate/render`, `page_nav_generate/render`, `breadcrumbs_render`, `listing_generate/render`, and others) confirms all of it must run *before* the pause, not be deferred. **Correction (review pass): "all of it is page-local" overstates this** — `ListingGenerateTransform` and `CategoriesSidebarTransform` both read `ctx.project_index`, which is genuinely cross-document data, not page-local. This doesn't break the pause-safety argument: `ProjectIndex` is Pass-1 data, already fully built before Pass 2 (and the pause) even begins, so reading it in a pre-pause transform is safe regardless — but the justification is "already-available project data, not local-only data," not "page-local." The actual precedent this design is modeled on, `link_rewrite.rs` (cross-document *link* rewriting from the website epic), has `phase() -> TransformPhase::Finalization` — confirming Finalization, after Navigation, is where cross-document resolution has always belonged in this pipeline.

- Pass 3 (new, book-only, lives entirely inside `run_with_book_support`'s multi-file-HTML branch, §3): aggregate every chapter's inventory into one project-wide registry (id → owning chapter href, **a resolved number the aggregation step itself must compute** — see the correction below, caption), then resume each chapter's held checkpoint and run `Finalization` (a new `CrossChapterCrossrefResolveTransform`, placed before `CrossrefRenderTransform` — both `Finalization` phase — finds the existing unresolved `CrossrefResolvedRef` nodes §7 already produces, resolves them against the registry, then `CrossrefRenderTransform` → `link_rewrite` → HTML write proceed unchanged).

**Mechanism, verified against real code end to end — both the transform loop and the per-chapter setup around it (see §6, now resolved rather than open).** `TransformPipeline::execute` (`crates/quarto-core/src/transform.rs:198`) is an 8-line loop over `Vec<Box<dyn AstTransform>>`; every `transform()` call takes `&self` (transform instances are stateless across calls) plus `&mut Pandoc`/`&mut RenderContext` — all state lives in those two parameters, not in the transform objects. `RenderContext<'a>`'s borrowed fields (`project`, `document`, `format`, `binaries`, `source_context`) are all shared/immutable — *once constructed* — so nothing about the loop itself prevents holding N chapters' state simultaneously; the owned fields Pass 3 needs to hold across the pause are the **full sixteen-field list** in §6 (§6's own list is shorter because P2's target formats make several of them inert — P5's target, HTML, makes every one of them real; see §6 for the field-by-field rationale, including why `resource_copies`, `code_block_decorations`, and `attribution_provider`/`attribution_data` — each found missing from an earlier version of this enumeration by successive review passes — are all genuinely load-bearing here even though they're dead weight for P2). Combined with the `?Send` single-task async convention this subsystem already uses, there's no thread-boundary concern either.

**A related question this pause mechanism raises but doesn't answer by itself: does anything *outside* the `TransformPipeline` loop — i.e., not subject to `execute_range`'s phase filtering at all — need special handling across the pause?** Checked directly (this was a live open question raised during this epic's fifteenth review pass, resolved before P2 implementation starts rather than discovered by regression): `AttributionGenerateStage` is the one thing in the pipeline that looks like it might be phase-sensitive but isn't — it's registered as an ordinary `PipelineStage` *before* `AstTransformsStage` in the full stage list (`pipeline.rs:354`, ahead of `UserFiltersStage::pre`/`AstTransformsStage` at lines 355-356), not as a member of the `Vec<Box<dyn AstTransform>>` `execute_range` iterates over (`pipeline.rs:5202`'s `t6_3_attribution_generate_is_stage_only_not_a_transform_pipeline_member` test pins this structurally). It therefore runs exactly once, in P2/P5's new stage-list-prefix constructor's initial (pre-pause) call, and is never re-invoked by either of P5's two `execute_range` calls — no double-fire risk. The actual risk this surfaced was a data one, not a control-flow one: see §6's `attribution_provider`/`attribution_data` carry-list finding above.

**§6's resolution closes the remaining question directly**: Pass 3 never actually needs to hold a constructed `Vec<RenderContext<'a>>` at all. Each chapter's own owned struct (`doc_info`, `binaries`, plus copies of `RenderContext`'s owned fields — §6) lives in the book-scoped `Vec`; `RenderContext<'_>` is reconstructed fresh, borrowing from that struct, immediately before each of the two `execute_range` calls (the initial one stopping after `Navigation`, the resume one starting from `Finalization`) and discarded right after. This is why "N chapters' state held simultaneously" is an ordinary data-ownership fact, not a lifetime hazard — `'a` never has to outlive the whole book, because no `RenderContext<'a>` is ever the thing being held.

**Concretely, redesigned by a sixteenth-pass "step back and consider alternatives" conversation: P5 reuses two mechanisms from §6, not one, and adds two genuinely new pieces of its own.**

*Reused from §6, built by P2:* `AstTransformsStage::for_range` (the parameterized primitive — P5 calls it with `..=Navigation` for the pause, exactly as before) and `build_html_pipeline_finishing_stages(lower_bound)`/`run_pipeline_from_ast` (the general finishing-pipeline mechanism — P5 calls it with `Finalization..` for the resume, where P2 calls it with `Crossref..` for its own merge-then-run step). Both are genuinely the same code, not parallel re-derivations — this is why P2 builds them and P5 reuses them, mirroring the existing convention for `execute_range` itself. **Composition risk carried over from the original design**: P2's own use only ever needs a lower-bounded range in the finishing-pipeline direction (`Crossref..`, no upper bound) and an upper-bounded range in the pause direction (`..=Normalization`, no lower bound) — P5 is the first caller needing *both* directions exercised together within one book render. P2's checklist should include a test exercising each bound form independently, not leave either half of the shared mechanism's contract proven for the first time by P5.

*New, and specific to P5 — the resume story's other two pieces, previously missing entirely from any plan:*

1. **`write_rendered_output`, a new function, split out of `render_document_to_file`'s existing tail.** `render_document_to_file` is really two halves today with no stage in between: a "render" half (resolve paths, build `RenderContext`, call `render_qmd_to_html`, get back a `RenderOutput { html, .. }`) and a "write" half (build an `OutputSink`, drain `ctx.artifacts`/`resource_copies`/`resource_report` into it, `sink.write(output_path, html)`, `sink.flush(...)`) — entirely ordinary, stage-free glue code (`render_to_file.rs:453-472`). **P2 doesn't need this split** — its targets (Typst, EPUB) write to disk *inside* the finishing pipeline's own tail stages (`PandocWriteStage`/`TypstCompileStage`), so P2's finishing-pipeline call already ends with the file written. **P5's target is HTML, where writing is external glue, not a stage** — so P5 needs the split made real: existing single-shot callers call both halves back-to-back (byte-identical behavior, a refactor not a redesign); P5's resume step calls `run_pipeline_from_ast(..., Finalization..)` to get a `RenderOutput`, then calls the *same* `write_rendered_output` — reused code, once per resumed chapter.
2. **Output-plumbing (`resolver`, `output_path`, `resource_paths`, `project_type`) is recomputed at resume time, not carried across the pause.** These are all computed once, deterministically, from `input_path`/`format`/`project`, before the pipeline runs in today's code — cheap enough to recompute identically at resume time rather than adding four more fields to the pause/resume carry-list.

**Correction found by an eighteenth-pass review: the aggregation step's `resolved_number` is not "already computed by the existing `CrossrefIndexTransform`" as an earlier draft of this section claimed — it must be produced by the aggregation step itself.** `CrossrefIndexTransform` (Crossref phase, pre-pause) only ever populates each entry's *raw* `Order` (the `order.order`/`order.section` counters) — the *formatted* display string ("2.3", "A.1") is produced exclusively by §7's `format_crossref_number(order, chapter_seed)` helper, called from `CrossrefRenderTransform`'s four display functions, a **Finalization**-phase transform. P5's pause point is *before* Finalization (immediately after Navigation) — `CrossrefRenderTransform` hasn't run for any chapter yet when aggregation happens, so no chapter has a formatted number to hand the registry. **The aggregation step must call `format_crossref_number` itself**, once per harvested crossref entry, using that chapter's raw `CrossrefIndex` order data plus its own `ChapterSeed` (both already available in the paused checkpoint) — this is a real, previously unstated step, not "just aggregation of what P4 already produces per chapter." The same correction applies to §12/P8's `StaticProjectAnalyzer`, below.

**Accepted v1 limitation, found by an eighteenth-pass review, resolved with the user rather than fixed in code: the resume/write loop is not atomic across chapters.** Aggregation builds the whole-book registry from *every* chapter's inventory before *any* chapter resumes — so chapter A's `write_rendered_output` can succeed, embedding a resolved number/link into chapter B, before chapter B's own resume-and-write has happened. If B's write subsequently fails (disk full, permission error — the same class `render_document_to_file` already surfaces as `Q-5-7`), the overall render still reports failure (the error propagates), but A's already-written file is left on disk referencing a chapter B that was never produced, until the next full re-render. This is a sharper version of a risk the codebase already accepts for ordinary multi-file project renders (some pages can already be written before a later one fails) — the book-specific wrinkle is that a written sibling can *embed* a reference to the failed one. **Decision (with the user): document as an accepted v1 Known Limitation** (epic doc), matching the treatment already given to memory scaling, non-parallelized resume, and numeric-citation renumbering — not a blocking gap, and not silent once documented. Revisit only if a real complaint surfaces; a cheap future mitigation, if needed, is buffering all N chapters' resolved `RenderOutput`s in memory and deferring every `write_rendered_output` call until all N resumes succeed (shrinks, not eliminates, the inconsistent-disk-state window).

**One dependency this phase should confirm, not assume, has landed**: P5's aggregation step reads whatever chapter-scoped numbers P4 actually produces — §7's `order.section`-vs-`order.order` gap (P4's own item, now resolved with a concrete fix — see §7) must actually be implemented before P5 relies on its output, or the registry aggregates flat, unscoped numbers with no error. (The `render_documents`/`Box<dyn ProjectType>` object-safety dependency this bullet used to name is resolved — see §3; P5's resume logic lives in `run_with_book_support`'s multi-file-HTML branch, a concrete method, not a trait override, so there's no signature to wait on.)

**In-memory now, not disk-persisted (yet):** the crossref-design plan's own Phase 4 sketch proposed disk persistence (`.quarto/xref/<file-id>.json`) for this merge. That's the right shape *once a freeze-style engine-result cache exists* — otherwise re-reading a persisted index and re-deriving the AST for Finalization means re-executing engines a second time, reintroducing the double-execution cost this design explicitly avoids (Q2 has no freeze mechanism yet; it's out of scope for the website epic too). Keep the `ChapterCrossrefInventory`/`ProjectCrossrefIndex` types serializable (matching `CrossrefIndex` already being `Serialize`/`Deserialize`) so swapping to disk-backed persistence — and gaining incremental-rebuild skip-ability for unchanged chapters — is a drop-in upgrade later, not a redesign. This also keeps the door open for the crossref design's own `StaticProjectAnalyzer` (a cheap, pre-engine, preview-time consumer that degrades unresolvable cross-file refs to placeholders) to eventually share the same `ProjectCrossrefIndex` merge type — not implemented this epic, but the type should not foreclose it.

**The cross-chapter resolve transform is the AST-level replacement for Q1's DOM postprocessor**: it runs before any HTML is written, consulting an in-memory registry, exactly mirroring the pattern `link_rewrite.rs` already established for cross-document *link* rewriting in the website epic — this is that same pattern, extended from explicit hrefs to crossref ids.

**`CrossChapterCrossrefResolveTransform` is registered unconditionally in the shared `build_transform_pipeline`, not spliced into a book-only pipeline** — it reads a new `RenderContext` field, `cross_chapter_crossref_registry: Option<Arc<ProjectCrossrefIndex>>` (P5's plan), and no-ops whenever that field is absent, which it is for every non-book render. This is deliberate, not incidental: it's what makes the transform a safe, always-present member of the one shared pipeline (matching every other transform's registration pattern in this codebase), and it's the reason §12/P8 can reuse this exact transform for book-aware preview — a second producer populates the same field from a cheaper source, with no pipeline-construction changes needed on either side.

## 9. Unified bibliography (P6)

**Why this section's mechanism can't be as simple as §6's single-file-merge fix.** §6 found (and fixed) the same underlying problem for single-file merge by deferring citeproc to one pass over the assembled whole document — free, correct in-text numbers, no dedup/disambiguation-seeding logic needed. That trick is unavailable here: multi-file HTML's whole point is N *separate* output files, so there is no single merged document to run one citeproc pass over. Each chapter's own citeproc pass must still run per-chapter (as it already does today), which is exactly why this section needs the harder machinery below — a registry-based bibliography-*list* merge, not a full re-run.

**Revised after reading Q1's actual `book-bibliography.ts` directly (previously this section's premise — "reuse whatever Q2's existing citeproc machinery already tracks per document" — was never verified and turned out to be false).** No per-document citation tracking survives past a single chapter's own render today: `quarto_citeproc::Processor` (the only thing holding resolved references/citation order) is constructed, used, and dropped entirely inside `apply_citeproc_filter`, called from `UserFiltersStage` — well before `AstTransformsStage`, i.e. before P5's pause point even exists for that chapter. `quarto-core` never sees it, only the already-mutated AST (`Cite` inlines already replaced with resolved text, a per-chapter bibliography `Div#refs` already written).

**Q1's own mechanism, confirmed by reading `book-bibliography.ts` in full, turns out to be narrower than assumed — which is what makes this tractable without inventing crossref-style deferred resolution.** `bookBibliographyPostRender` *is* a DOM postprocessor (same forbidden family as `bookCrossrefsPostRender`), but unlike the crossref one it never rewrites in-text citation marker text — only hyperlink targets. Concretely: it structurally collects cited reference ids from each chapter's already-rendered `data-cites` HTML attributes, rewrites each citation's `href` to point at the designated refs chapter, hides (not removes) each chapter's own local `#refs` div, and regenerates *one* merged bibliography fragment by shelling out to a fresh `pandoc --citeproc` subprocess with a synthetic `nocite:`-driven document — splicing that into the refs chapter. Because it never touches in-text numbers, **Q1 itself has the exact same "numeric styles show the wrong per-chapter-local number in text" bug this section documents below — silently, with no comment or issue reference anywhere in its own source acknowledging it.** This isn't a case of Q1 solving a hard problem Q2 is failing to match; Q1 never solved it either.

That reframes what Q2 actually needs, and shrinks it: since in-text numbers are never rewritten (matching Q1's real behavior, not a compromise), **no deferred-resolution AST node is needed for citations** — unlike crossrefs, which needed `CrossrefResolvedRef` specifically so a later pass could fix up an unresolved marker. What's needed instead: (1) a new serializable per-chapter `ChapterCitationManifest` (cited reference ids or the already-`Serialize`-able `Reference`s) threaded onto `RenderContext` from `apply_citeproc_filter`/`UserFiltersStage`, alongside that chapter's existing, unchanged citeproc pass; (2) P5's existing pause/aggregate/resume machinery carries it forward exactly like `ChapterCrossrefInventory` — no new pause point; (3) the aggregation step dedupes cited ids across chapters (tracking each id's first-cited-across-chapters order alongside the dedup) and builds *one* merged bibliography by invoking `quarto-citeproc`'s own in-process `Processor` directly over the union — genuinely simpler than Q1's approach (no subprocess, no synthetic document), but **not just `add_references` + `generate_bibliography_to_outputs()` alone**: traced against `Processor`'s real API and confirmed it also needs `get_initial_citation_number(id)` called once per id in book-wide first-citation order (numeric styles) and `process_citations_with_disambiguation` over one synthetic `Citation` per id in that same order (year-suffix/et-al disambiguation) — both already-public, document-free calls `generate_bibliography` itself doesn't trigger, and skipping them would silently mis-render the first real book using a numeric CSL style or two colliding author+year references; (4) AST-splice that merged bibliography into the designated references chapter during its Finalization resume, *replacing* (not just hiding) whatever local bibliography div citeproc's unchanged per-chapter pass already generated there.

**A real gap found by a nineteenth-pass review, now fixed, not left for P6 to discover on its own: every citing chapter would otherwise gain its own duplicate, unmerged local bibliography.** `apply_citeproc_filter`'s own `insert_bibliography` (`crates/pampa/src/citeproc_filter.rs:591-623`) auto-appends a fresh `#refs` div, with that chapter's own local bibliography, to any chapter that has citations but no explicit `{#refs}` div of its own — the common case for an ordinary book chapter. Since this section's whole mechanism deliberately leaves each chapter's own citeproc pass unchanged, this would otherwise fire for every citing chapter, not just the designated references one. **Fix: set `suppress-bibliography: true` in metadata for every book chapter except the designated references chapter, before that chapter's citeproc pass runs** — `CiteprocConfig.suppress_bibliography` (`citeproc_filter.rs:44,711`) is a real, pre-existing, standard Pandoc-compatible option that skips bibliography generation/insertion while leaving in-text citation rendering unconditional (`citeproc_filter.rs:110-126`), so this needs no new plumbing — the same metadata-mutation layer §6/P2 already uses for its own citeproc-deferral fix. Single-file merge is unaffected by this gap at all (it defers citeproc entirely to one pass post-merge, so no per-chapter auto-append ever happens there).

**A real gap this doesn't fix, now confirmed identical to Q1's own real (if undocumented) behavior, not merely an assumed-inherited Q1 bug**: for a *numeric* citation style (IEEE-like), each chapter's own local citeproc pass numbers its own in-text citation markers independently — chapter 2's `[3]` was assigned with no knowledge of chapter 1's citations. Merging the reference *list* doesn't fix an already-wrong in-text number. Verified against real `quarto` with a shared citation and an IEEE CSL: the same paper is cited as `[2]` in chapter 1 and `[1]` in chapter 2 — and confirmed, by reading Q1's source directly, that Q1 has this exact bug too (its `forEachCite` loop only ever rewrites `href`, never citation text). This is structurally the same class of problem §8 solves for crossrefs, and could in principle be fixed the same way (extend the project-wide registry to citations, resolved during the same Pass 3 resume) — **but that would make Q2 do more than Q1 does, which is scope creep against this epic's "port Q1 faithfully" goal, not a bug fix**. Recommendation: document as an inherited limitation (author-date styles are unaffected, since "Smith 2020" doesn't renumber) rather than building the fix in this epic — explicitly, unlike Q1's silence. This is a real design fork, not a unilateral call — revisit if a numeric-citation-style book is a real near-term use case.

## 10. Prerequisite: number-sections / `@sec-` (P0)

Q2 has no `number-sections`/`@sec-` implementation for any format (`bd-5aklrxgi`) — but the gap is narrower than "build from scratch." `CrossrefIndexTransform` already tracks the section-counter stack (§7) and already collects every `Header` into `CrossrefIndex.headings` (comment: *"kept for cross-file heading link fixup in book mode"*) — it just doesn't register headers as `sec`-typed crossref targets, and `CrossrefResolveTransform`/`CrossrefRenderTransform` have no `sec`-ref handling at all. This blocks only:

- Multi-file HTML's `@sec-` presentation ("Section 1.2", "Chapter 1") for Q2's native HTML writer.
- It does **not** block Typst (native `section-numbering` metadata key, already wired independently in `feature/pandoc-writer-hybrid`'s Phase 1) or LaTeX/EPUB (both use deferred, compiler/Lua-native resolution — see §6).

Scoped narrowly to what book mode needs — not a general number-sections feature. Also owns porting `sections.lua`'s "skip `.unnumbered`" early-return (§4/§7 both depend on this), since that's the same numbering machinery, not a book-specific addition on top of it. See plan P0.

## 11. Explicitly out of scope

- DOCX/PPTX book output (matches Q1: not a real book format there either).
- LaTeX/PDF book output (validated the abstraction generalizes — `top-level-division: chapter`, confirmed empirically in §6 — but not implementing it). **Not actually a book-specific scope decision**: Q2 has no LaTeX/PDF Pandoc-hybrid output at all yet, for *any* project type (no `LatexCompileStage` or equivalent exists in `quarto-core`) — so there's no book-specific format-support gap to diagnose or test here; `--to pdf`/`--to latex` already fails for a reason unrelated to books.
- Manuscript (`ProjectKind::Manuscript`): untouched. Its actual Q1 shape doesn't fit this mechanism (see §3).
- **Cross-chapter bibliography preview.** §12/P8 brings book-aware chapter numbering, title decoration, and cross-chapter *crossref* resolution to `q2 preview`/hub-client, but not a merged bibliography preview — there is no pre-engine analog to P6's per-chapter-citeproc-manifest mechanism (citation resolution isn't syntactically visible before engines run, unlike most crossref targets), and building one is a separate, harder problem §12 explicitly declines to take on.
- **Single-file-merge preview.** Preview always previews one chapter as ordinary HTML, regardless of the book's real single-file-merge target format — P2/P3's merge mechanism (Typst/EPUB compilation) has no preview analog to build; this was never a gap to close.
- **General bundled-extension auto-load** — the mechanism that would let *any* project type/format pairing resolve to a bundled default extension, and let a user override a book's default Typst extension to something other than `orange-book`. Q2 mirrors Q1's *specific* zero-config outcome for the one pairing this epic needs (Typst book → `orange-book`, hard-coded, no general dispatch — see §5's Decision) rather than building the general mechanism; the general mechanism remains unbuilt infrastructure, not this epic's job (see §5 for the current state of the closest related plan).
- `quarto install typst`-style auto-installation, freeze/incremental rebuilds for books, and anything else already out of scope for the website/pandoc-hybrid epics this one builds on.

## 12. Book-aware preview (P8)

**Added after the epic's original design was frozen** (a thirteenth-pass addition, prompted by a direct question about the preview gap this epic originally scoped out entirely — see §11's pre-edit history in the epic doc's revision log). This section gives `q2 preview`/hub-client the parts of book-awareness that are actually tractable without a full render, and is explicit about the two parts that remain out of scope (§11).

**Why this wasn't part of the original design at all**: preview renders one active document through `RenderToHtmlRenderer`/`RenderToPreviewAstRenderer`, a code path `run_with_book_support`'s book orchestration never touches. Nothing about Pass 3 (§8) — the pause/aggregate/resume machinery, the per-chapter checkpoint — applies here; preview needs a cheaper, single-document-at-a-time answer to the same two questions ("what chapter number/title am I" and "does this cross-chapter ref resolve, and to what") without ever holding N chapters' state simultaneously.

**Three components, of unequal size and unequal novelty:**

1. **Chapter-number seed + title decoration — reuses P0/P4's existing mechanism, adds no new numbering logic.** P4 already computes a `HashMap<PathBuf, ChapterSeed>` once per book render, before any chapter renders (§7), from P1's `BookRenderItem` list. Preview's WASM entry point (`RenderToPreviewAstRenderer::render`) doesn't currently receive this map at all. **Build the whole map, not a single lookup** (corrected by a later review pass — an earlier draft of this section scoped this down to "a lookup for the one document being previewed," which undersells what item 2 below actually needs: the static sweep must also seed *every swept sibling's own* local section counter with that sibling's own chapter number, or its approximate ordering comes out flat/unscoped instead of chapter-scoped). So: build the full `HashMap<PathBuf, ChapterSeed>` — reusing **P4's** existing chapter-number/appendix-flag computation (a ripple-check pass found this misattributed to "P1's existing... logic" in an earlier draft; P1 only builds the `BookRenderItem` list itself, P4 is the phase that turns it into the `HashMap<PathBuf, ChapterSeed>` — see P4's Decisions) — once per preview call that touches a book project, and apply the matching entry both to the previewed document and to every sibling the static sweep in item 2 touches.

2. **Cross-chapter crossref resolution — the genuinely new piece: `StaticProjectAnalyzer`, feeding P5's existing `CrossChapterCrossrefResolveTransform`, not a new resolution mechanism.** `StaticProjectAnalyzer` itself was named but never designed by the standalone crossref-design plan (`claude-notes/plans/2026-04-15-crossref-design.md`, Phase 4, explicitly "design only," three unchecked sketch items). Concretely: a new pre-engine (no knitr/Jupyter execution) sweep of every *other* chapter's parsed-but-not-executed AST — **scoped to exactly the files in `BookRenderItem`'s list, not every file `ProjectContext::discover` happens to enumerate** (a project can contain non-chapter `.qmd` files — include-shortcode partials, drafts — that must not be swept as if they were chapters with their own seed/counter) — extracting exactly the crossref targets that are already syntactically visible pre-engine in the single-file case (native `Figure`/`Table` captions, `#<reftype>-`-classed Divs, the code-block `#|label:` shorthand) plus each id's approximate order, computed by running the real section-counter logic (seeded per item 1) over that pre-engine AST. **That counter logic produces only the raw `Order` (section stack + flat counter) — not a formatted display string, corrected by an eighteenth-pass review that traced the same gap in P5's own aggregation step (§8).** `StaticProjectAnalyzer` must call §7's `format_crossref_number(order, chapter_seed)` itself on each swept sibling's raw order to produce the `"N.M"`/`"A.M"` string `ProjectCrossrefIndex`'s `resolved_number` field requires — it does not fall out of "the real section-counter logic" for free, and reimplementing the letter-vs-numeral composition inline here instead of calling the shared helper would risk drift from P0/P4's actual formatting. Reuse `build_analysis_pipeline`/`build_analysis_transform_pipeline` (already Normalization+Crossref-bounded, precedented elsewhere in this epic — §6/§8) for this per-sibling pass if it fits, rather than writing new per-file pipeline construction from scratch — check this at implementation time before assuming new plumbing is needed.
   - **This inherits, rather than invents, the existing degradation story for engine-generated ids.** An id that only exists via an engine-generated `output: asis` block and isn't listed in that chapter's `crossref.ids` manifest (D6 in the crossref-design plan) is already unresolvable pre-engine in the *single-file* case — cross-chapter preview just means the same gap now also applies to *other* chapters' asis-generated ids, not a new failure mode to design for.
   - **Duplicate ids across chapters need an explicit merge rule, not a silent last-wins overwrite** (found by a review pass — P5's own real Pass 3 explicitly plans a duplicate-id-across-chapters diagnostic; the static sweep inherits the identical risk and needs the identical care, since a naive merge could resolve a ref against the *wrong chapter's* content, a correctness bug, not just an approximate number). Rule: first-in-book-order wins, with a non-fatal diagnostic — preview must degrade, never crash, on ambiguous project state, unlike a real render, which can legitimately fail on it.
   - **The mechanism reuses P5's `CrossChapterCrossrefResolveTransform` verbatim — this does *not* modify `CrossrefResolveTransform`.** An earlier draft of this section proposed giving `CrossrefResolveTransform` itself a `project_index: Option<&ProjectCrossrefIndex>` handle, reviving the crossref-design plan's original D4 sketch — written before this epic designed P5's real mechanism. That would have given the codebase two different mental models for "how does cross-chapter crossref resolution work." P5's actual, already-decided mechanism (§8, above) is a *second*, later Finalization-phase transform that fixes up already-placeholder'd `CrossrefResolvedRef` nodes against a registry, reading a new `RenderContext` field, `cross_chapter_crossref_registry: Option<Arc<ProjectCrossrefIndex>>`, and no-opping when it's absent. That transform is registered unconditionally in the shared `build_transform_pipeline`, which resolves the one real open question this section used to have: does preview's own pipeline even reach a place to run such a fixup? Checked directly (`build_q2_preview_transform_pipeline` builds the *full* `build_transform_pipeline`, then applies a small named deny-list, `Q2_PREVIEW_TRANSFORM_EXCLUDED`, whose own doc comment states new transforms are *included by default*) — yes, automatically, with zero preview-specific pipeline changes. `CrossrefRenderTransform` (the later transform that would flatten a resolved `CrossrefResolvedRef` into final markup) is itself excluded from preview, so the CustomNode survives to React either way, resolved-by-`StaticProjectAnalyzer` or resolved-by-real-Pass-3, indistinguishably. **P8's only actual new work here is populating `cross_chapter_crossref_registry` from `StaticProjectAnalyzer`'s cheaper sweep instead of P5's real aggregation** — no new transform, no React change beyond item 3 below. Because the transform only ever touches nodes already left unresolved by the ordinary local `CrossrefResolveTransform` pass, a previewed chapter's own correct local resolution can never be shadowed by an approximate sibling entry, even under an id collision (resolution precedence is safe by construction, not a rule the transform has to check).
   - **Numbers from this sweep are approximate, and that's accepted, not hidden or flagged.** A number that shifts slightly once fully rendered (e.g. because an engine cell in an earlier chapter emitted more auto-numbered figures than the static sweep could see) is a known imprecision, not a bug to chase. No "approximate" confidence-indicator UI is planned for v1 — Q1 has no live cross-file preview at all to take a cue from here, and adding one is speculative complexity this epic has no signal it needs. The approximation never affects link *correctness*, only displayed numbers — see item 3.
   - **Invalidation and staleness.** Recompute the sweep on every preview call for a book project — no incremental/cached project-wide index in v1; that's real future work if profiling on a large book says otherwise, not designed for preemptively. **Content staleness across open editor tabs is not a real concern**: hub-client's Automerge-backed documents are already the live, synced source of truth regardless of which tab is open, so the sweep never reads a separate "unsaved buffer" that could be stale relative to what's actually being edited. **The honest cost-model caveat, corrected from an earlier draft**: this is *not* simply "as cheap as Pass 1's existing profile sweep," which was the justification an earlier draft used to wave off caching. Pass 1 is itself cached in IndexedDB across renders, and it stops at `DocumentProfileStage` — before `PreEngineSugaringStage` even runs, well short of the crossref machinery this sweep needs per sibling. So a book-preview call now does *three* distinct levels of per-file work (Pass 1's existing shallow sweep; this new, deeper per-sibling crossref sweep; the one previewed document's real full render) — real, additional, uncached per-call cost, not a free extension of something already cheap. This connects directly to the epic's existing Known Limitation that P2/P5 are "unverified at 50+ chapters" for memory — the same scale risk now also applies to preview *latency*, on every edit rather than once per render. Accepted for v1 anyway, on the same terms as that existing limitation: fine at small scale, unverified at large scale, revisit if it's a real complaint rather than a hypothetical one.

3. **Cross-document navigation — a small, well-located wire-contract addition.** Today, `CrossrefResolvedRef`'s `plain_data` (Rust: `crossref_resolve.rs`; TS: `ts-packages/preview-renderer/src/q2-preview/custom/CrossrefResolvedRef.tsx`) has no notion of "this ref's target lives on a different page" — the React component always renders a same-page anchor (`href="#{identifier}"`). Add one new optional `plain_data` field carrying the owning chapter's document path when (and only when) the resolved ref is cross-chapter (absent for same-page refs — additive, not a breaking change to the existing schema-conformance contract asserted by `schemaConformance.test.ts`). `CrossrefResolvedRef.tsx` gains a branch: when that field is present, call the already-threaded-but-currently-unused `onNavigateToDocument` prop (it's passed into the component today and forwarded to child inline nodes, but the crossref link itself never calls it) instead of emitting a bare same-page `href`. No other React component needs to change — `FloatRefTarget.tsx` and the rest of the numbering/caption rendering are already source-agnostic about where the number came from. **Note for a future reader**: `href` is built from `identifier` alone, never from `order` — so item 2's numbering approximation never taints the *link target*, only the displayed number.

**Explicitly still out of scope after this phase** (§11): cross-chapter bibliography preview (no pre-engine analog to P6's per-chapter citation manifest exists — citation resolution, unlike most crossref targets, isn't syntactically visible before engines run) and single-file-merge preview (moot — preview always renders as HTML regardless of the book's real target format).
