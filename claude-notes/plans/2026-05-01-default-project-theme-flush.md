# Default-project theme artifacts not flushed in hub-client

## Status

Draft — pending user review. Do not start implementation until
the user gives the go-ahead.

## Problem

After bd-h736 fixed default-project discovery, both native and
hub-client render `_quarto.yml`-rooted default projects. But in
hub-client, themes don't appear for default projects unless the
specific theme bytes happen to already be cached in the synthetic
VFS from a previous render under `project: { type: website }`.

User-reported symptoms (project at hub URL
`http://localhost:5173/#/p/309b0f5c-…/file/index.qmd`,
`_quarto.yml: project.type: default`, `format.html.theme: flatly`):

1. **Cold theme on default project** — no theme renders.
2. **Switch to website type, render, switch back to default** —
   theme renders correctly (the website render flushed bytes into
   VFS; default render now finds them on the URL path).
3. **Add a *new* theme** (e.g. change `flatly` → some unused theme)
   while the project remains `type: default` — no theme. (The new
   theme has a new fingerprint and a new URL; nothing pre-flushed
   them, so VFS-miss → no theme.)

Native renders of default projects are unaffected — the user
reported them as working, and I confirmed locally
(`/tmp/default-theme-test/index.qmd` with `theme: flatly` produces
`./index_files/quarto/quarto-theme-3a8b4a76bcc824ec.css` and a
matching `<link>` in `index.html`).

## Root cause

There are two Pass-2 renderers behind the orchestrator:

1. **`RenderToFileRenderer`** (native, `pass2_renderer.rs:173`).
   Calls `render_document_to_file`, which inside its body
   (`render_to_file.rs:264-297`) does:
   - Writes Page-scope artifacts in-place via the per-page resolver.
   - Drains Project-scope artifacts.
   - Branches on `has_shared_lib = !project_type.lib_dir().is_empty()`:
     - `true` (websites): merges drained Project-scope into the
       orchestrator's `project_artifacts` accumulator.
     - `false` (default projects): writes Project-scope in-place
       via the per-page resolver, which (with `lib_dir == ""`)
       routes them under `{stem}_files/...`. This is what produces
       `index_files/quarto/quarto-theme-<fp>.css` natively.

2. **`RenderToHtmlRenderer`** (WASM, `pass2_renderer.rs:276`). The
   hub-client live-preview renderer. *Always* drains Project-scope
   artifacts into the orchestrator's accumulator
   (`pass2_renderer.rs:330-337`), regardless of `lib_dir`. There is
   no in-place fallback.

3. **Orchestrator** (`orchestrator.rs:529-588`) calls
   `project_type.post_render(...)` after Pass-2.
   `WebsiteProjectType.post_render` calls `flush_site_libs` to
   write the accumulator's Project-scope artifacts at the
   resolver's chosen on-disk path. **`DefaultProjectType.post_render`
   is the trait default — a no-op** (`orchestrator.rs:163-174`).

So in WASM with a default project: artifacts get drained into the
accumulator but are never flushed. The HTML the renderer returns
contains URLs like `/.quarto/project-artifacts/quarto/quarto-theme-<fp>.css`
(generated by the per-page vfs_root resolver), but the iframe
post-processor finds nothing at that VFS path and the browser
silently ignores the link.

The trait doc (`orchestrator.rs:142-145`) explains the original
intent:

> Default projects ignore [project_artifacts] (single-doc renders
> flush per-doc inside `render_document_to_file` when no
> orchestrator is involved).

That assumption made sense pre-websites, when default projects
went through a single-doc path that bypassed the orchestrator
entirely. Today every render — native and WASM — goes through
`ProjectPipeline`, but only the *native* pipeline preserved the
per-doc fallback. WASM dropped it.

### Why the cross-render persistence makes the bug intermittent

Per `crates/wasm-quarto-hub-client/AGENTS.md`, the synthetic VFS
at `/.quarto/project-artifacts/...` is "load-bearing across renders"
— `flush_site_libs` writes there, the iframe post-processor reads
from there, and `vfs_clear` is explicitly **not** called between
renders.

Theme URLs are fingerprint-keyed, so `theme: flatly` always
resolves to the same VFS path regardless of project type. When the
user previously rendered the project as a website, the bytes
landed in VFS at the path the default-render's HTML embeds — so
the theme appears. The first render of a *new* fingerprint never
flushes anything for default projects; VFS-miss → no theme.

## Goals

1. **Fix the WASM Pass-2 path** so default projects flush their
   Project-scope artifacts to VFS, where the iframe post-processor
   can find them.
2. **Don't regress native default projects** — they currently
   write theme CSS to `{stem}_files/quarto/...` via the per-doc
   in-place flush, and the embedded `<link>` URL points at that
   same path. Whatever fix lands must keep native byte-identical.
3. **Don't regress websites** — `flush_site_libs` and the
   `lib_dir == "site_libs"` routing must continue to work
   end-to-end on both targets.

## Non-goals

- Restructuring how `ArtifactScope::Project` artifacts are
  represented or stored. The accumulator + scope abstraction is
  fine.
- Changing the trait default for `post_render`. Other project
  types that come along later may legitimately want the default
  no-op.
- Touching the iframe post-processor or the URL-generation side
  of the resolver. The HTML side already gets the right URL; the
  bug is purely on the on-disk-write side.

## Options considered

### Option A — `DefaultProjectType.post_render` calls `flush_site_libs`

Symmetric with `WebsiteProjectType`. Minimal code change.

**Native problem**: the project-level resolver for default projects
(built by `RenderToFileRenderer.build_project_resolver` →
`ResourceResolverContext::project_root(project.output_dir, "")`)
routes Project-scope to `{site_root}/{artifact_path}` (the
"default-project shortcut" in `resource_resolver.rs:262-272` falls
back to a bare `site_root` when the project-level resolver has no
real per-page context). This is **not** where the per-doc inline
flush wrote the bytes (`{stem}_files/quarto/...`). Adding the
post_render flush would create stray files at `{project_dir}/quarto/...`
that nothing references — at best dead bytes, at worst test
breakage and user-visible clutter in their project root.

We could gate the post_render flush on a "WASM only" property —
e.g. inspect whether the resolver is in vfs_root mode. Pragmatic,
but a leaky abstraction (the project type peeking at resolver
internals).

### Option B (preferred) — mirror the native `lib_dir` branch in `RenderToHtmlRenderer.render`

Make WASM behave like native: when `project_type.lib_dir()` is
empty (default project), flush Project-scope artifacts in-place
via the per-page resolver instead of draining to the orchestrator
accumulator. When non-empty (website), drain (current behavior).

In WASM, the per-page resolver is in vfs_root mode, so
`on_disk_path_for(Project, p)` returns `{vfs_root}/{p}` —
identical to what `flush_site_libs` would have done at post_render
time. The HTML's embedded URL is generated by the same resolver,
so URL and on-disk path round-trip perfectly.

This keeps the native and WASM Pass-2 renderers symmetric in their
treatment of the `lib_dir` branch, removes a real bug from WASM,
and doesn't touch native at all. It requires the renderer to call
`project_type_for(project).lib_dir()` (already done in the native
`render_document_to_file` body).

### Option C — promote the per-doc flush logic into a shared helper

Extract the lib-dir-branch logic from `render_document_to_file`
(`render_to_file.rs:264-297`) into a helper like
`flush_or_drain_project_artifacts(...)` and call it from both
`RenderToFileRenderer.render` and `RenderToHtmlRenderer.render`.

Cleanest factoring; eliminates the duplicated branch in two
call sites. But the native call site is currently inside the body
of `render_document_to_file` (which has access to a per-doc
resolver and an artifact store local to that call), so refactoring
without churn requires passing those handles into the helper.
Higher diff, marginal correctness gain over Option B.

### Recommendation

Option B. It's a small, targeted fix that brings WASM in line with
the native invariant the codebase already encodes. Option C is a
clean follow-up if we want to dedupe later.
