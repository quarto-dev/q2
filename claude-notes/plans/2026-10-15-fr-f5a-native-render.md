## Goal

The CLI chooses its format after it knows the project. A typst (or epub) book renders as a book with no `--to`; a named chapter, or several named files, each render on their own in the format their own front matter, or the project, gives them (the way Quarto 1 renders each named file as its own `render()` call); a named page that is not a chapter renders on its own too, in html books as well, with a quiet notice that it has no book numbering and cannot link to the book's chapters; naming every chapter of an *html* book keeps rendering the whole book, as today; the orchestrator's decisions each use the format FR11 says they should; html chapter renders stay on today's path. The three preview pseudo-formats stay accepted as `--to` values exactly as today (what they should mean is a separate question: `bd-pseudo-format-to-meaning-vxhyni3t`).

## Decisions

All from the epic; the plan-level ones. (There is no F5a-D5: the shared `--to` validation that sat there was dropped in round 5, see `bd-pseudo-format-to-meaning-vxhyni3t`; the numbers below are kept so other plans\' references to F5a-D6 stay valid.)

- **F5a-D1 `render_once` order:** build the overlay from `-M` (F1) and wrap the runtime **where `render_single_doc` and `render_project` create theirs** (F1 1.7), discover the project (honouring `--profile` and `QUARTO_PROFILE`), then resolve **where the project is final**: inside `render_single_doc` / `render_project` after the pre-render-script re-discovery. The refusal gate (`render.rs:950-959`) and the Q-20-8 warning move there; their output now follows any pre-render script output (note it in the Handoff log). The resolver gets the target (`RenderTarget` → `RenderMode`, F3a-D5; a standalone document is asked as `ActivePage(input)`), the request (`resolve_render_scope`), `resolve_project_format` for the render's dispatch format and, for named files, `resolve_document_format` (one call per named file); the Q-20-8 warning is fed by the resolver's key list. `--to` is `cli_to`; a runtime scalar `format` is the next requested format (FR2). **The refusal gate judges the resolved format of every file that will be rendered, all of them before any render starts** (a refused format never leaves partial output; the first refusal is the error). **`render_once` and the render path stop calling `detect_single_input_format`, `format_key_from_frontmatter` and `format_keys_from_frontmatter`, but the functions stay**: `preview_static.rs` still uses them until F5b deletes them (keeping the `quarto` crate compiling at this landing). `resolve_format` stays while `preview_static.rs` imports it; F5b removes it if nothing else does. The private `multi_format_warning_diagnostics` has no caller left and is deleted here (5a.7).
- **F5a-D2 Orchestrator formats (FR11):** `self.format` is the *dispatch* format: the project's for a render whose requested scope is Book, the document's resolved format for a Chapter render of one document. A separate field (`project_format`) holds the project's format; **Pass 1, its cache key and the book-wide index always use it**, and the nested chapter-alone pipeline receives it through a builder, `ProjectPipeline::with_project_format(Format)`, defaulting to `format` (`ProjectPipeline::new` has dozens of test and wasm callers, so its signature does not change); `render_chapter_alone_summary` takes the project format as a parameter and sets it with the builder. The public `render_chapter_alone` keeps its signature and passes the project's format itself, so Pass 1 never runs under the chapter's format. `post_render` and the css diagnostics follow the dispatch format (what was actually produced). For the several-files case (F5a-D3b) there is no single dispatch format: `self.format` is the project format, used only for Pass 1, its cache key and the Q-5-33 skip, and `post_render`, `render_batch` and the css diagnostics are decided per partition, not from `self.format`. Q-5-33 applies only when the requested scope is Book; a chapter render to a format with no book support is allowed (FR11, a wanted behaviour change). The gate's current conditions are known (research A9: it judges `--to` or the single input's front matter, not the project's format). **Consequence, decided by FR11 and recorded for the changelog:** once the gate judges the resolved project format, `q2 render` of a book whose project format is docx, pptx or revealjs is refused (`Q-5-33`) where it used to produce per-chapter outputs; `q2 render ch1.qmd` (chapter scope) is allowed. The `Q-5-33` text is made accurate in the same change: it names where the format came from (`--to` or the project's `format:`), not always "This book project targets".
- **F5a-D3 Chapter-alone uses the document's format (FR8):** the fix is at the orchestrator's call site, which passes the document's resolved format (including a non-member page's when it is the single active document); `render_chapter_alone_summary` passes **the resolved key (`format.target_format`) as the override, not `format.identifier.to_string()`**, so an extension format such as `acm-typst` stays itself (5a.5 tests it, or records it as a known limit if the fixture proves too heavy); the function's contract (use the format the caller gives) does not otherwise change. **Html chapter scope does not go through it:** the scope rule chooses chapter-alone only when the format consolidates; an html chapter falls through to today's `Subset`/`ActivePage` → `run_inner` path, unchanged, with its known cross-reference limitation (FR19, `bd-html-chapter-xref-szfxmvyg`).
- **F5a-D3b Several named files each render on their own (FR3, FR6).** A `Subset` of more than one file with a Chapter request is not a whole-book merge. `-M book-scope:book`, with one or several files, still merges the whole book. The loop is its own branch **at the top of `run_with_book_support`, before the Q-5-33 gate and before the `format_consolidates_book(&self.format)` test** (today a Subset of several files is judged by one `self.format` that means nothing for files whose formats differ); it applies to a Book project only. The steps:
  1. For each named file, `resolve_document_format` (F3a) and `book_membership` (`scope.rs:35`, pass-free). The refusal gate (F5a-D1) has already judged every one of them.
  2. **The collapse, re-applied where formats are known.** `classify_inputs` no longer collapses a Book project (it can say "Book" but knows no formats and has no overlay; it stays pure). The orchestrator makes the whole-book render only when it is equivalent to the per-file renders: the named files include **every chapter**, and **every named file's resolved format is the project's format and that format does not consolidate** (html, revealjs, ...). Then it sets the mode to `Full`, `self.format` to the project format, the named non-members as extras (F5a-D3c), and falls through to the existing dispatch (an html `Full` goes to `run_book_multi_file_html`, `:1055`), so cross-chapter references resolve as they do today. If any named file consolidates (typst, epub), or resolves to a different format than the project (an html book with one chapter saying `format: typst`, or a typst project whose chapters say `format: html`), there is no collapse and each file renders on its own: html chapters then keep the known unresolved-cross-chapter-reference limitation. For a **non-book** project the CLI collapse stays in `classify_inputs` (Gordon's decision: a subset of everything and a whole-project render are equivalent there, and the shortcut is not ours to override); the two rules do not disagree (a runtime `chapter` on a collapsed `Full` website is the FR6 info, on a `Subset` the FR5 "not a book" info).
  3. Otherwise **partition** the files by resolved format: each file whose resolved format consolidates (a member or a non-member alike) renders through `render_chapter_alone_summary` with the project's format passed in (F5a-D2, D3); all the others (html, revealjs, ...) render together as **one** `run_inner` `Subset` with no format override, so each uses its own format, exactly as one named html file does, with the named non-members among them added as extras (F5a-D3c).
  4. The partitions\' summaries are **aggregated once** (F5a-D3d). `q2 render sub/` is the same loop over the render-list files under `sub/`. F3b's interim "exactly one file" check (`render.rs`, marked `F5a: delete`) and the test that pins it are deleted here.

  Quarto 1 does the equivalent: each named file is an independent render. **Verify first (5a.3i)** what a `Subset` of every chapter does for an html book and for a consolidating book compared with a `Full` render; the expectation is: html `Full` goes to `run_book_multi_file_html` (cross-references resolved), an html `Subset` of every chapter goes to `run_inner` (chapter seeds are still installed, `orchestrator.rs:~1646`, so numbering is preserved, cross-chapter references are not resolved), a consolidating `Subset` of every chapter is one chapter-alone render per chapter.
- **F5a-D3c Named non-member pages (FR22).** A named page in the project that is not a chapter renders on its own, as a standalone page in its own format, in every format. In a consolidating format that is the chapter-alone path (today's behaviour). In an **html** book the smallest fix is: before dispatch, for a Book project in `Subset` or `ActivePage` mode (and for the F5a-D3b collapse), the orchestrator **appends** the named non-members\' relative paths to `project.extra_render_files`. `BookProjectType::pre_render` already merges them into the additions in every mode (`project_type.rs:134-137`), `restrict_render_list` keeps them, `pass_two` and `compute_augmented_render_set` find them in `project.files`, Pass 1 has seen them, and the `Full` html path renders them like footer pages (see "What exists"). It is an append: `prepare_page_in_book` overwrites (`chapter.rs:24`), so it is not reused for several files (its nested single-file use stays). Membership is decided with `book_membership`, so every format uses one rule. The page numbers from 1 (no chapter seed) and its references to chapters are unresolved, like Quarto 1's, and **the notice says so**. The notices are F3b's `scope_notices` (a pure function; `resolve_book_scope` emits them for the routes and wasm, so the orchestrator emits them **only for dispatches that did not go through `resolve_book_scope`**: non-consolidating formats and the loop's html partition; one Q-5-42 per named file; never twice): a quiet info for a named non-member in **any** chapter-scope situation (the default request, or an explicit `chapter` at the runtime, project, directory or document layer), and a **warning** for an explicit runtime `book-scope: book`. **Decided:** the output stays under `_book/` (what q2 does for footer pages today); the Q1 difference is recorded in the Handoff log and the docs, not matched. The page's navigation is whatever a footer page gets today (book sidebar with no active item, no prev/next, empty breadcrumb, the book's `<title>`; research A1): no stage changes, and the notice wording already says it has its own numbering and cannot link to the chapters. 5a.3g still verifies, at implementation time, that appending to `extra_render_files` makes the `Subset`/`ActivePage` path produce the same page.
