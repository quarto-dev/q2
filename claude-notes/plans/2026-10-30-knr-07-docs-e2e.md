## Goal

Someone using or maintaining q2 can learn, without reading the plans, what a knitr record
holds, when it is used, how it relates to Positron's cache, what falls back, and how to run
the harness. The end-to-end tests prove the whole path with R.

## What the docs must say

**User docs** (follow EXR-18's structure and placement; check what the repo registers):
- What is recorded for R chunks and inline expressions, where the record lives, and that
  plain `q2 render` writes none unless the merged metadata has `execute: {record: true}`
  (parent decisions 24 and 33).
- What an edit does: prose edits keep a record fresh; code and execution-relevant options
  make a unit stale; presentation-only chunk options (the structured profile\'s list in
  KNR-3) do not, except on a fallback chunk, whose hash counts every option; every
  `execute:` key makes the record stale (KNR-3, decisions 3 and 9).
- Positron: a knitr record is valid nbformat that Positron can present when placed by hand
  in its cache directory (KNR-5 K-S1); q2 does not deliver it there. q2 can import a Positron
  cache for R cells as display-only output, without setup-chunk options or htmlwidget
  dependencies; the outputs may look different from a knitr run (print width, data frame
  rendering, plot size). Replace EXR-18\'s "not presentable" caveat.
- What falls back and why: `child=`, level-3 cache hits, overridden `knit_hooks`, LaTeX
  (`latex`, `beamer`, `pdf`) and any target not yet covered (KNR-3\'s table), and engines
  that return only text; those chunks are opaque to Positron and rendered as before.
- Jupyter cells that set `panel`, `layout-ncol`, `code-fold` or the other cell options now
  render them (KNR-2, decision 1); say so in the release notes.
- Records written before the epic read as stale once and are re-recorded.
- When to run `{r}` through a Jupyter kernel instead (owned-languages epic), and what that
  changes.

**Developer docs** (`claude-notes/instructions/` or `dev-docs/`, as the repo does):
- The capture point and mechanism, the supported knitr range and what happens outside it
  (KNR-1, S1; the range is whatever S1 measures, not 1.44 to latest by assumption).
- How to run the differential corpus, read the report, classify a new difference, and add a
  fixture; the normalizer rules and why each exists.
- The skeleton or assembly mechanism of the flip (KNR-6) and the fallback unit marker.
- Update the replay-engine note for knitr (`claude-notes/instructions/replay-engine.md`).

**Diagnostics.** New codes (fallback chunk, overridden hook, count mismatch, unsupported
knitr version, unrecognized capture shape) are registered like parent decision 29 does for
`Q-18-4`: a catalog entry, a docs page under `docs/errors/engine/`, and the same corpus and
tests as the existing codes.

## End-to-end tests (R present; skip with the repo's pattern when absent)

- [ ] Render: a document with a figure, a table, an htmlwidget, an error chunk with
  `error: true`, and inline expressions renders as before (corpus shadow gate already
  proves the markdown; this proves the full pipeline output).
- [ ] Preview: edit prose (record stays fresh, no re-execution), edit code (unit stale),
  edit a presentation-only header option (stays fresh and presents with the new option), and
  edit `opts_chunk$set` in a setup chunk (only that unit is stale; downstream chunks keep the
  recorded options until the next run, KNR-3 decision 10).
- [ ] Hub: `provide-hub` writes a knitr record; a guest without R shows the host's output.
- [ ] Replay: record a trace with R present, then replay it with R hidden from the replay
  engine\'s environment (the record step skips when R is absent; the replay step must not
  need it), and compare. "Hidden" means a `PATH` without R, built with
  `std::env::join_paths` (no `:` literal, so it also works on Windows).
- [ ] Positron import: a Positron-shaped cache fixture for an R cell fills a knitr unit and
  presents; a fallback unit is skipped.
- [ ] Mixed document: structured and fallback chunks together.

## Exit criteria

- The docs build with `q2 render --strict` and are linked from the places EXR-18 links
  to; the diagnostics are registered; the end-to-end tests pass with R and skip cleanly
  without it; clippy and nextest green with counts against the live baseline.

## Risks

- Docs written from plans drift from what landed; write each section in the plan that
  lands it and use this plan to assemble and check.
- No R in CI: the end-to-end tests do not run there unless R is enabled in CI (epic
  decision 17: the tests are CI-ready and skip without R); say so in the PR.
