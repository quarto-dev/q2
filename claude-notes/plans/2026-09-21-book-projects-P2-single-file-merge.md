# Plan: Single-file chapter merge mechanism (book-projects P2)

**Date:** 2026-09-21 (revised twice after review passes; this revision folds in the already-vendored `book-*.lua` files)
**Epic:** [`2026-09-21-book-projects-epic.md`](2026-09-21-book-projects-epic.md)
**Design (authoritative):** [`../designs/book-projects-architecture.md`](../designs/book-projects-architecture.md) §5, §6, §8
**Q1 reference:** `book-render.ts`'s `mergeExecutedFiles`/`renderSingleFileBook` (concept only — Q1 concatenates markdown text with base64-encoded HTML-comment metadata; Q2 merges Pandoc AST directly). **Also**: the already-vendored `resources/pandoc-filters/filters/quarto-pre/book-numbering.lua`, `quarto-pre/book-links.lua`, `quarto-finalize/book-cleanup.lua`, `quarto-post/book.lua` — read these before writing any code in this plan, they do real work this plan depends on.

## Overview

The one genuinely new capability this epic needs for Typst/EPUB (and, validated but not implemented, LaTeX) book output: assemble several chapters into a single Pandoc document before the Crossref phase runs. Most of the hard part — chapter-scoped numbering, part/appendix structure, LaTeX's `\part{}`/`\appendix` sequence — turns out to already exist in vendored Lua from the pandoc-hybrid epic. This plan's actual job is: drive that Lua correctly (filter params, document attributes it expects) and add the small pieces of Rust it doesn't cover (the merge itself, cross-chapter link resolution, output-filename resolution).

This plan also builds the phase-bounded transform runner P5 (project-wide crossref registry) reuses — it's needed here first, at a different phase boundary (Normalization/Crossref) than P5's (Navigation/Finalization), but it's the same mechanism.

## Decisions

**Read `../designs/book-projects-architecture.md` §5 in full before implementing any of this section — it has the complete rationale for each vendored-Lua decision below.**

- Merge point is **after Normalization, before Crossref** — each chapter runs its own engine execution and AST-sugar transforms independently (unchanged), then bodies are concatenated as `Vec<Block>` (not markdown text).
- **New shared mechanism, redesigned by a sixteenth-pass "step back and consider alternatives" conversation — `execute_range` alone isn't the whole mechanism.** `TransformPipeline` gains a phase-range-bounded execute variant (`execute_range(&self, ast, ast_context, ctx, range: impl RangeBounds<TransformPhase>)`, using `TransformPhase`'s existing `Ord` derive) — an 8-line loop with all state living in `ast`/`ctx`, additive, not a redesign. But *invoking* it isn't free: `AstTransformsStage::run()` always calls `pipeline.execute(...)` today (`ast_transforms.rs:231`), for both the JIT-built and `with_pipeline`-supplied cases — there is no phase-bounded execution mode to reuse (an earlier draft overstated this as "an injection seam that already has a working consumer"; `build_analysis_pipeline` only ever customized pipeline *content*, never bounded *execution* of the real one). **Fix: make the range a first-class parameter of the stage itself** — `AstTransformsStage::for_range(range)`, whose `run()` always calls `execute_range(range)`; today's behavior becomes the default case where `range == ..`. Build this here.
- **Two stage-list shapes, not one, both built by this phase.** `build_html_pipeline_pause_stages(upper_bound)` — the prefix through a range-bounded `AstTransformsStage`, nothing after it — is what this phase's own per-chapter partial render uses (`..=Normalization`) and what P5's initial per-chapter render uses (`..=Navigation`). **`build_html_pipeline_finishing_stages(lower_bound)` is new, and this phase needs an instance of it too, not just P5**: the merged document's own run through "the unmodified single-document pipeline" starting from Crossref *is* this same primitive with `lower_bound = Crossref` — starts directly with a range-bounded `AstTransformsStage`, then the real, unchanged tail (`UserFiltersStage::post → ResourceReportStage → CodeHighlightStage → MathJsStage → RenderHtmlBodyStage → ApplyTemplateStage`, or the Pandoc-hybrid equivalent ending in `PandocWriteStage`/`TypstCompileStage`). Build it generically (parameterized on the lower bound); P5 reuses it with `Finalization..` instead of `Crossref..`, mirroring how `execute_range` itself is already assigned.
- **Part/appendix dividers are resolved, not TBD**: a `.quarto-book-part`-classed `Div` wrapping a `# Title` heading — exactly `book-render.ts`'s own `::: {.quarto-book-part}\n# Title\n:::`. The already-vendored `book-cleanup.lua` handles it from there: keeps it for LaTeX, unwraps it for Typst (its own comment claims book-numbering.lua already transformed the content to `#part[...]` — **that comment is wrong**, see below), deletes it entirely for every other format including EPUB (parts are print-only content; for EPUB/HTML they're sidebar-navigation-only, per §4/P1's sidebar translation).
- **Correction, found by reading `book-numbering.lua` directly rather than trusting `book-cleanup.lua`'s comment about it: `#part[...]` for Typst is not emitted by any vendored Quarto Lua at all.** `book-numbering.lua`'s `Header` handler has an explicit comment — "Typst part/appendix handling is delegated to book extensions (each Typst book package has different syntax for parts and appendices)" — and does no Typst-specific part/appendix work. The real `#part[...]` emission, and the **appendix-lettering mechanism** (a `#show: appendices.with(...)` rule that puts Typst's own numbering context into appendix mode), live in the Typst book extension's own filter (e.g. `orange-book.lua`). See design doc §5 for the full mechanism and why this matters for the decision below.
- **Two filter-param/attribute mechanisms activate the vendored Quarto Lua** — both required, neither optional, confirmed empirically that neither alone is sufficient:
  1. **`single-file-book: true`** filter param, set for every single-file-merge target (not just Typst) — gates `book-cleanup.lua`'s part handling, `book-numbering.lua`'s counter-reset generation, and (moot here, see below) `book-links.lua`.
  2. **`quarto-book-item-type`/`-number`/`-depth`/`-file`/`-appendix` Pandoc attributes**, stamped on each chapter's own top-level heading during merge (P2 already has this information from `BookRenderItem` — no separate tracking pass needed), consumed by a small, tracked patch to `book-numbering.lua`'s `Header` handler: read `el.attr.attributes["quarto-book-item-type"]` etc. directly instead of `currentFileMetadataState().file.bookItemType`. Document this patch the same way the existing `crossref-numbering` patch is tracked (a named, minimal diff against the pinned vendor tag) — patching vendored Lua is not a hard rule against here, and there's a draft upstream `quarto-cli` PR this could feed into.
- **Revised: emit the comment markers too, don't replace them.** The original plan here was "this replaces Q1's `<!-- quarto-file-metadata: ... -->` comment-marker mechanism" — patch-and-drop. That's wrong: the Typst book extension's own filter (`orange-book.lua`, used **unpatched** as this epic's test fixture — see below) learns `bookItemType`/`bookItemNumber`/`appendix` *exclusively* via `quarto.doc.file_metadata()`, which parses those exact comment markers and nothing else. Dropping them would silently break the extension's part/appendix/numbering logic with no error — a real, previously-missed failure mode (resolved with the user: emit both). **The merge step now stamps both forms** from the same already-known `BookRenderItem` fields: the Pandoc attributes above (for the tracked `book-numbering.lua` patch) *and* the original `<!-- quarto-file-metadata: base64(json) -->` markers in Q1's exact shape (`resourceDir`/`bookItemType`/`bookItemNumber`/`bookItemFile`/`bookItemDepth`, confirmed against `book-render.ts`'s `bookItemMetadata`) — no separate tracking pass, just two serializations of the same data.
- **`orange-book` is vendored locally, and auto-resolves as the default Typst book extension — resolved with the user (fifteenth pass), not left as "reference it explicitly from fixture config."** Q2 has no *general* bundled-extension infrastructure (see design doc §5/§11), but this epic mirrors Q1's one specific zero-config outcome it needs: a Typst book target with no explicit `format.typst` extension named resolves to the locally-vendored `orange-book`, mirroring Q1's own `render-contexts.ts` default (`readExtensionFormat`) for the `book` + `typst` pairing — hard-coded to this one pairing, not a general dispatch mechanism. Copy `_extensions/orange-book/` into a local resource directory per this repo's External Sources Policy (never referenced from `external-sources/` at runtime), alongside `resources/typst-packages/`. This is deliberately the *unpatched* extension — the point of the "emit both" decision above is that it should work without touching the extension's own code at all. A user who *does* explicitly name a different `format.typst` extension gets that one instead, unchanged; the default only fires when no extension is named at all. **Vendoring mechanism revised 2026-09-24 with Gordon: `orange-book` is vendored as an extension subtree under `resources/extension-subtrees/` (the PR #717 infrastructure now on `main`), not hand-copied — see items 80-81.**
- **`orange-book`'s vendored directory gets its own README** — a whole-system-composition review found this was the one vendored-resource directory in this epic with no source-tag/re-vendor documentation, unlike every sibling (`resources/scss/README.md`, `resources/typst-packages/README.md`, `resources/pandoc-filters/README.md`, `resources/revealjs/README.md`, `resources/js/README.md`). Write one in the same shape: which upstream tag/commit it's pinned to, and the procedure for re-vendoring when that pin moves.
- **Cross-chapter link resolution is Rust, not a Lua patch**: a new transform, modeled on `link_rewrite.rs`'s pattern but resolving to an in-document anchor instead of a separate output path, runs immediately after merge assembly (before Crossref). It has the complete picture at merge time (which chapter file maps to which real heading id). Once links are already `#<id>`-shaped, the already-vendored `book-links.lua` (gated on the same `single-file-book` param) sees nothing left to do and no-ops — no patch needed there. **Also**: don't attach a `ProjectIndex` to the merged document's `RenderContext`, so the pre-existing `LinkRewriteTransform` (Finalization, not in `PANDOC_TRANSFORM_EXCLUDED` — it runs for Pandoc-hybrid targets today) stays inert as a defensive backstop.
- **Scoped out, not silently dropped, but broader than "override": `quarto-post/book.lua`'s per-chapter `quarto-title-block` mechanism.** `resources/projects/book/pandoc/title-block.md` (the template it renders) covers subtitle, author affiliations, date, and abstract — driven by any chapter front matter setting those keys, not an author/title-override-specific case. Its guard means it's already inert if Q2 simply never emits that code-cell construct — no patch, no Rust work, just don't build the feature. This is missing functionality, not an intentional divergence; tracked as `bd-ock6cyiy`, not this phase's (or this epic's) job — document the real scope (subtitle/date/abstract, not just title/author) in the epic's Known Limitations, and see design doc §7 for the note asking P4 to leave its title-decoration insertion point extensible for that future work.
- Book-level title metadata (`book.title`/`author`/`date`/`abstract`/`doi` → merged document `meta`) is a direct port of `withBookTitleMetadata` — small, mechanical.
- `top-level-division: chapter` is the lever Typst and LaTeX share (confirmed by reading both `format-typst.ts` and `format-pdf.ts`'s `BookExtension`s, and empirically for LaTeX — see the appendix below). **It is not a general "this is a merged book" flag** — EPUB's chapter boundary is the separate `--split-level` mechanism (P3), and `single-file-book` (above) is a third, separate flag. Three distinct settings, three distinct jobs.
- **Format defaults specific to single-file-merge targets**, ported from `book.ts`'s `formatExtras`: `toc: false` for Typst specifically ("orange-book generates its own"), and `toc` already effectively `false` for EPUB (Q1's own default is `!isEpubOutput`). (`number-sections: true`/`crossref.chapters: true` are now P1's job, format-agnostically — this phase just inherits them; `crossref.chapters: true` matters concretely for EPUB's `sections.lua`-based numbering and is inert for Typst's native-counter path, but P2 doesn't need to set it itself.)
- **Output filename resolution**: port `bookOutputStem` — `book.output-file`, falling back to `book.title`, falling back to the project directory name, sanitized to a filesystem-safe name. Confirmed empirically: a real `quarto render . --to pdf` on a book titled "Numbering Probe" with no explicit `output-file` produced `Numbering-Probe.pdf`, not `index.pdf`.
- **Bibliography needs a real fix too — found by a review pass, not inherited for free from "citeproc just runs once over the merged whole."** That premise (design doc §2, before correction) was wrong: Q2's own citeproc filter (`apply_citeproc_filter`, inside `UserFiltersStage::pre()`) runs *before* `AstTransformsStage`/Normalization, for every format — meaning it would run independently per chapter, before this phase's merge step ever sees the chapters, producing N separate, non-deduplicated bibliographies rather than one unified one. **Fix, mechanism corrected by an implementability review**: `resolve_filters(...)` (`filter_resolve.rs:73`) is recomputed fresh from `doc.ast.meta["filters"]` *inside* `UserFiltersStage::run()` at stage-execution time — there is no seam for a caller to hand in an already-resolved, pre-edited filter list, so "exclude the `Citeproc` entry from each chapter's own resolved filter list" describes mutating an object that doesn't exist at any point this phase can reach. The actual mechanism: strip `"citeproc"` from each book-merge chapter's `meta["filters"]` array (metadata, not a resolved list) before that chapter's metadata reaches `UserFiltersStage` — i.e. a pre-render metadata mutation, checking both possible orderings (`.pre`/`.post`, since a user can order it into either) at the point that array is read, not a post-resolution filter-list edit. Run every other filter normally. After merge assembly, call `apply_citeproc_filter` (`crates/pampa/src/citeproc_filter.rs`, a standalone `Pandoc`+`ASTContext` function, no stage/`RenderContext` machinery needed) once, directly, on the merged document, before the single Crossref-Finalization pass. No new type, no dedup/aggregation logic, and — unlike an earlier draft of this fix — no dependency on P6's mechanism: placement into the references chapter is free via citeproc's own existing `{#refs}`-div-filling convention, which already lands wherever P1's `References`-kind chapter's own `{#refs}` div sits in the merged body. This achieves genuine Q1 parity (correct in-text citation numbers too, not just a merged list — see design doc §6 for why this is *better* than P6's necessarily-looser multi-file mechanism, not just different). Confirm at implementation time that no Normalization-phase transform assumes citeproc has already run on a chapter by the time it executes. **Mechanism as landed (revised 2026-09-24, see item 89's note): the strip is performed by `UserFiltersStage::pre()` itself, gated on the render context's `defer_citeproc` flag — exactly "at the point that array is read," one frame earlier than this paragraph's original wording.**
- The merged document then runs through the **unmodified** `feature/pandoc-writer-hybrid` single-document pipeline (Crossref phase, Finalization, `PandocWriteStage`) — no changes to that pipeline itself in this phase, except the one-time deferred citeproc call immediately after merge assembly, above. **This needs one new entry point that isn't itemized anywhere — found by an implementability review.** `render_qmd_to_pandoc`/`run_pipeline` both hardcode their *initial* `PipelineData` as `LoadedSource` built from raw QMD bytes (`pipeline.rs:800-803`) — there is no existing entry point that starts a stage list from an already-built `PipelineData::DocumentAst`, which is what the merged `Pandoc` already is. This is mechanically supported by the underlying machinery (`Pipeline::run` only checks `input.kind() == self.expected_input`; `AstTransformsStage`'s own `input_kind()`/`output_kind()` are already `DocumentAst`) but requires a genuinely new function — a `run_pipeline_from_ast` sibling, or a `run_pipeline` variant parameterized on the initial `PipelineData` — exactly as load-bearing as the per-chapter partial-render entry point above, and equally a checklist item, not a detail folded into "runs through the unmodified pipeline."
- **`run_with_book_support()`'s single-file-merge branch** (not a `ProjectType::render_documents` trait override — resolved by a seventeenth-pass research round, design doc §3): for a single-file-merge target format, this is where the merge logic lives — collect all chapters' post-Normalization ASTs, merge, hand off. (Multi-file HTML's branch, added in P4, is a different code path within the same concrete method, dispatched on target format.)

## Appendix: LaTeX empirical confirmation (upgrading a design-doc claim from "read the source" to "verified")

Built a 3-chapter + 1-appendix book fixture and rendered it with the real `quarto` binary, `--to pdf` with `keep-tex: true`, and inspected the intermediate `.tex` directly.

Observed:
```
\chapter*{Preface}\label{preface}
\chapter{Chapter One}\label{sec-ch1}
\section{A subsection}\label{sec-sub1}
\chapter{Chapter Two}\label{sec-ch2}
\cleardoublepage
\phantomsection
\addcontentsline{toc}{part}{Appendices}
\appendix
\chapter{Appendix Stuff}\label{sec-apx1}
```
and, for cross-references: `See Chapter~\ref{sec-ch1} and Figure~\ref{fig-a} from chapter one.` — a genuine `\ref{}`, resolved by LaTeX at compile time. The full `\cleardoublepage`/`\phantomsection`/`\addcontentsline`/`\appendix` sequence before the appendix chapter matches `book-numbering.lua`'s `Header` handler exactly (confirmed after re-checking with fuller context — an initial narrower grep had only shown the trailing `\appendix` line and looked like a discrepancy; it wasn't). This is structurally identical to Typst's `#ref()`/native-counter behavior, just via a different compiler's own native mechanism and different vendored-Lua code path. LaTeX book output remains unimplemented this epic, but the abstraction P2 is built around is now validated against two independent compilers. (For completeness, if LaTeX book output is ever picked up: `book.ts`'s `formatExtras` also sets `documentclass: scrreprt` and `papersize: letter` alongside `top-level-division: chapter` for LaTeX specifically.)

## Appendix: multi-chapter Typst validation (the empirical finding that corrected this plan)

Built a minimal 2-H1 Typst document (not a full book merge — just enough to isolate the mechanism) and rendered it with the real, already-built `q2` binary on this branch:

- With neither `top-level-division: chapter` nor `single-file-book` set: figures numbered continuously (`Figure 1`, `Figure 2`) — the baseline.
- With `top-level-division: chapter` set alone: **identical result** — still `Figure 1`, `Figure 2`, no chapter-scoping at all. This is the finding that overturned an earlier draft of this design, which assumed the counter reset was baked into the static vendored template and needed nothing from Q2 beyond real chapter boundaries.
- Chapter-scoped reset requires `book-numbering.lua`'s dynamically-generated show-rule, which only fires under `single-file-book: true` — not yet re-tested end-to-end with that param set (doing so meaningfully requires this plan's own merge/attribute machinery to exist first), but the mechanism is now fully understood from reading the Lua directly, not inferred.
