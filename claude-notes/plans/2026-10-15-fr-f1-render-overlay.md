## Goal

## Decisions

- **F1-D1 The overlay type.** `RenderOverlay { files: HashMap<PathBuf, Vec<u8>>, metadata: Option<serde_json::Value> }` deriving `Debug` (`RenderToFileOptions` derives `Debug, Clone, Default`, `render_to_file.rs:99`), plus `RenderOverlay::apply(self: &Arc<Self>, inner: Arc<dyn SystemRuntime>) -> Arc<dyn SystemRuntime>` returning the wrapper (an empty overlay returns `inner` unchanged). The `&Arc<Self>` receiver compiles on the pinned nightly (`nightly-2026-04-28`) with no `#![feature]` (checked with a throwaway program in round 4). `OverlayRuntime` keeps its name and file behaviour and gains the metadata field; `OverlayRuntime::new(inner, files)` keeps its signature (the book download keeps using it until it moves to `apply` in 1.5). Constructors for tests and callers: `RenderOverlay::with_metadata(value)`, `with_files(map)`.
- **F1-D2 Wasm-compilable.** The module is ungated and its impl uses the same `cfg_attr(not(wasm32), async_trait)` / `cfg_attr(wasm32, async_trait(?Send))` pair as `SystemRuntime`. F1's gate includes `cargo check --lib --target wasm32-unknown-unknown` for `quarto-core` (and the wasm crate), with the C-toolchain env from `dev-docs/wasm.md` (Homebrew LLVM's `clang` on macOS), so the wasm check is here and not three plans later; the spike showed it passes. The wasm crate is excluded from the workspace (`Cargo.toml:11-12`) and has its own `.cargo/config.toml` (build-std), so its check runs from its directory: `cd crates/wasm-quarto-hub-client && CC_wasm32_unknown_unknown=clang CFLAGS_wasm32_unknown_unknown="-isystem $PWD/wasm-sysroot" cargo check --target wasm32-unknown-unknown` (derived from `hub-client/scripts/build-wasm.js:150-170`; run in round 5 with `CC_wasm32_unknown_unknown=/opt/homebrew/opt/llvm/bin/clang` on the scratch copy with the ungate: exit 0). (Round-4 reading found no blocker: no `Rc` in the module and the trait is already `Send + Sync`.)
- **F1-D3 Metadata merge semantics.** The wrapper's `runtime_metadata()` is the inner runtime's value with the overlay's merged on top: both objects, recursively, overlay keys win; any non-object overlay value replaces (so an overlay scalar `format` replaces an inner map-valued `format`, which matters only if both are set on one render). Arrays are replaced, not concatenated. Either side `None` returns the other. (The inner value is the wasm preview settings; the overlay sits on top so a per-request value beats them.) Because the merge is overlay-wins and recursive, `merge(merge(b, o), o) == merge(b, o)`.
- **F1-D4 One rule: whoever creates the runtime for a render wraps it, once.** The overlay travels as `Option<Arc<RenderOverlay>>` on `RenderToFileOptions` (a new field, default `None`) for the CLI paths, and as a `metadata: Option<serde_json::Value>` on the preview route's `RenderJob`, `BookDownloadParams` / `BookDownloadRequest` (F4 fills these from the wire; here they default to `None`/empty), from which the creator builds the overlay. The **creators** (the list under "What exists") call `overlay.apply(runtime)` at the point they obtain the runtime, before the project is discovered, so everything downstream (the resolver F5a adds, Pass 1, Pass 2, the nested chapter-alone pipeline, the seam) sees one wrapped runtime: `render_single_doc` and `render_project` (`render_once`\'s own runtime only classifies the arguments and stays un-overlaid, which is fine); `render_blocking`, **once at the top of the function and keyed by the canonical `active` path**, so `resolve_book_scope`, `render_chapter` and `render_document` all see it and a fake `RenderSeam` in the route tests sees it too (not inside `RealRender.render_document`, which runs after the resolver and is bypassed by fakes); `render_book_download` (the `OverlayRuntime::new` at `:177` becomes `apply`, F1-D4's single wrap for that path); and each wasm entry, which obtains its runtime itself (`get_runtime_arc()`) or discovers on the raw one and must wrap it **before** its first `ProjectContext::discover` and pass the wrapped runtime down (F4 supplies the overlay). **`ProjectPipeline::new`, `render_to_file` and `render_document_to_file` never wrap**; `options.overlay` is data the creator reads, not something the pipeline applies, and the nested pipeline in `render_chapter_alone_summary` (`chapter.rs:95`) receives the runtime already wrapped. There is no identity check (`Arc<dyn SystemRuntime>` has no downcast hook: no `Any` supertrait, `traits.rs:313-315`, and adding one would touch a core trait, `SandboxedRuntime` at `sandbox.rs:302` and every forwarding mock), and none is needed: if a future path wraps twice, behaviour is observationally identical (file reads answer from the outer overlay first with the same bytes, `path_metadata` is `PathMetadata { size, ..meta }` through an inner overlay, and F1-D3's merge is idempotent), which a unit test of the wrapper pins. Nothing is added to `StageContext`.
- **F1-D5 `-M` syntax (Quarto 1's).** `KEY<sep>VALUE`, split at the first `=` or `:`; the value is parsed as a YAML scalar or flow value (`-M toc:true` is a boolean, `-M 'format:{html:{toc:true}}'` a nested map); a value that does not parse is kept as a string; a missing separator is an error with a clear message (Q1 ignores it; an error is friendlier). Repeated keys: the later wins (so `-M format:typst -M 'format:{typst:{toc:true}}'` does not both select and configure; use `--to` plus the map, FR2). Dotted keys are not expanded (`-M a.b:1` sets the key `a.b`). Path-valued keys (`-M css:foo.css`) are not rebased relative to the document, and YAML tags are lost, because the runtime layer is built from JSON (`json_to_config_value`, `SourceInfo::generated`, no `mark_format_path_values`); say so in the help text and docs. Unlike Quarto 1, `-M` lands in the runtime layer for every document including Pass 1 profiles. `-M format:x` and `-M book-scope:...` are meaningful (FR2, FR5) only once F3a lands: F1 carries the values and the merge stage sees them, but nothing selects a format or a scope from them yet, so F1's help text must not claim selection (F3a revises it). The parsing function lives in `quarto-core` (reachable from `quarto`, `quarto-preview` and `quarto-test`, all of which depend on it) so F5b and F8 call the same function.
- **F1-D6 The Pass 1 key hashes the runtime metadata.** A new `Pass1KeyInputs` field holds the canonical JSON (keys sorted) of `runtime.runtime_metadata()`, written length-prefixed into the hash; `PROFILE_KEY_VERSION` becomes 4. When the runtime has none the field is empty, so a plain render's key changes only through the version bump. The preview's `book-scope` alternating between `chapter` and `book` therefore produces cache misses for a profile it does not affect; accepted (simple, correct; measure only if it is ever noticeable).

- Interim state after F1 lands: `-M` is accepted and merged into every document's runtime layer, but `-M format:x` and `-M book-scope:...` do nothing until F3a; the help text must not promise otherwise.
