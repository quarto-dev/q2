## Why, and what the spike measured

The PDF preview refresh is dominated by the pandoc leg. With the Module resident and a fresh instance per render, callouts.qmd to typst takes 160 / 285 / 152 ms (Chromium / WebKit / Firefox). One warm instance, driven through the module's exported `hs_init_with_rtsopts` and `convert` (not `_start`, which traps on re-entry), takes **105 / 99 / 111 ms**, saving 55 / 186 / 41 ms. Task 0(e) reconciled the WebKit column against the raw JSON (`d2b/results/webkit-all.json`: fresh 285, warm 99, where the note had said 291 and 104) and carried the corrected figures into this paragraph and the note's verdict, section 6 and Firefox summary; the figures above are the corrected ones. The floor is about 58 ms even for an empty document (Lua state, `init.lua` and `main.lua`, template), so the target is "about 105 ms", not "under 20 ms". Output was byte-equal to a fresh instance in every run, and memory is flat (44 MB over 100 renders of one document). Cost is superlinear in document size (callouts x10 0.56 s, x100 10.9 s), so callouts alone says little about large documents.

**Goal of H10a and H10b together:** the PDF preview renders through a small pool of warm pandoc instances that behaves like a realtime system: a new edit starts rendering at once, an older pandoc render is never killed because a newer one exists, and the pane shows the newest result that has finished. **H10a builds the executor** (everything that runs inside one warm instance and everything that makes its output equal to a fresh run); **H10b builds the pool, the preview controller and the browser matrix**. H10a changes nothing a user can see: no code path of the shipped UI calls the warm executor until H10b.

**Scope decisions, fixed for both phases:**
- **Preview only, on its own runner.** Preview and Download share `DownloadController.runWasm` and, today, the one app-wide `PandocRunner` (`pandocService.ts:15-21`), whose single `current` slot makes either supersede the other (`pandocRunner.ts:172,201-202`). The preview gets a **second runner sharing the one `PandocLoader`** (H10b). Download, parity and the book menu keep the existing runner and the fresh path. Download stays fresh for scope and risk, and because docx/pptx/epub parity needs a pinned `SOURCE_DATE_EPOCH` that pandoc's Haskell side reads once from the WASI environ. Typst has no pandoc-side timestamp; its date pin is the JS-side prelude at `downloadController.ts:317`.
- **The argv-to-defaults translator lives in the TS host and is guarded from the Rust side** (Task 2). One Rust test, a matrix of fixture documents and one allowlist file are added; the request schema, golden and builder do not change.
- **No RTS options** on the production path (the spike's `-H64m` made the first `convert` cost about 1 s). Fault injection is the only user of RTS options (Task 5). The Rust request carries none (`crates/quarto-core/src/pandoc_request/types.rs:61`).
- **No kill on supersede** (H10b).
- **The pool is a subsystem with a generation key** (H10b): the pandoc.wasm sha (`request.expected_pandoc_wasm_sha256`), the limits given at `init`, `share_tree_version` and the allowlist `version`. A change reboots the pool (the key cannot change within one page session; it is a defensive invariant). Fault injection is per run and lives in `WarmSession` (Task 5b), not in the key.

**Terms.** *Warm instance*: one instantiation of `pandoc.wasm` that has run `hs_init_with_rtsopts` once and serves many `convert` calls. *Fresh path*: today's `execute()`, one `_start` per worker. *Fallback*: a warm-eligible request that the translator rejects with `UnsupportedArgv` and that therefore runs through the fresh path. *Poisoned*: a warm instance that can no longer be trusted (Task 5). *Canary convert*: `convert` on the one-line document `x` with `{"from":"markdown","to":"plain"}` and no filters; it succeeds on a healthy instance. *Warm-up*: one throwaway `convert` that replays a retained copy of the latest completed real request (one whose render took under `WARMUP_MAX_MS = 500`) on a new instance with its output discarded (H10b); Task 0(a) decides whether it makes the instance hot.

  - [x] **5a: poison and memory policy.** Heap exhaustion kills a warm instance for good (every later `convert` throws exit 1; fresh gives 251). `os.exit(n)` throws but leaves the instance usable, so it does **not** poison. An instance is poisoned by a wasm trap, an fd-2 out-of-memory message, or a thrown exit after which the canary convert fails; a poisoned instance is dropped and replaced before the next request. After each render, **in the same handler, before accepting the next request**, read `memory.buffer.byteLength`; over 512 MB (measured: about 113 MB at a 1.5 MB AST, 317 MB at 6 MB, 1.2 GB at 24 MB, so 512 MB is a backstop for filter blowups and for ASTs far past the wall timeout) the instance is reported as `retire: true`. Linear memory never shrinks, so on this path worker memory is not recycled per render.
