## Overview

Spawn and manage the shared Deno subprocess that hosts all TS engine
extensions. Defines the `EngineTransport` trait, `StdioTransport`
implementation, the `TsEngineHost` **demux** + lifecycle, error handling,
per-request timeouts, **cooperative** cancellation, stderr forwarding, and the
bundle-embedding story. The protocol is **multiplexed** (per-request `id`
envelope + `Cancel`) over the child's **stdin/stdout** in the original v1
design — see the canonical model in
`claude-notes/designs/engine-host-concurrency.md`. (Moving the protocol off
stdout onto loopback TCP was **Phase 1.6**; it has since landed as
[Plan 1a.6](2026-07-08-plan1a6-off-stdout-loopback-tcp.md) — `StdioTransport`
is gone and the protocol now rides a loopback-TCP socket, with stdout/stderr
diagnostic-only. The v1/stdio framing below is preserved as the historical
design rationale.) This is the q2-side counterpart to Plan 1b's harness — they
communicate via the protocol defined in plan1a-protocol.

- [x] Define the **split** transport seam in `crates/quarto-core/src/engine/ts_process.rs`.
  Per the canonical design (`engine-host-concurrency.md:166`: *"`EngineTransport`
  splits into a write half (shared, internally mutexed) and a read half (owned by
  the reader thread)"*), this is **two** pieces, not one `Arc<dyn EngineTransport>`
  carrying both `send` and `recv`. **The split is load-bearing for teardown** (see
  Design Note "Teardown & reaping"): the reader thread owns its read half *directly*,
  so its blocking point is the OS pipe read — not an `Arc` clone that would pin the
  child alive and deadlock `Drop`. ALL multiplexing (`id` correlation, pending map,
  timeout, cancel) still lives in `TsEngineHost`. Swappable: `StdioTransport`
  (original v1 impl; deleted since Phase 1.6 landed), `TcpTransport` (Phase
  1.6, now the sole impl), `WebSocketTransport` (WASM, future) are the same
  seam.
  ```rust
  /// SHARED WRITE HALF — held by the host as `Arc<dyn EngineTransport>`, called
  /// by concurrent workers. Sync/blocking; concurrency lives on the Deno event
  /// loop, surfaced via the demux (Design Note "Why sync").
  pub trait EngineTransport: Send + Sync {
      /// Write one framed `Request`. Internally serialized by a short-held write
      /// lock (microseconds — one framed write); NEVER held across a wait.
      fn send(&self, frame: &Request) -> Result<()>;
      /// Send `Shutdown` and flush. Does NOT reap the child — the host owns
      /// reaping (see "Teardown & reaping").
      fn shutdown(&self) -> Result<()>;
  }

  /// OWNED READ HALF — moved into the demux reader thread at `ensure_started`.
  /// Owns the child's stdout (v1) directly.
  pub trait EngineReadHalf: Send {
      /// Block for the next frame. `Err(RecvError::Eof)` = channel closed
      /// (process exit/crash); `Err(RecvError::Malformed(String))` = a
      /// non-`Response` line on the protocol channel (the v1 stdout footgun).
      fn recv(&mut self) -> Result<Response, RecvError>;
  }
  pub enum RecvError { Eof, Malformed(String), Io(std::io::Error) }
  ```

  ```rust
  /// SHARED write half (held by the host as `Arc<StdioWriteHalf>`). The inner
  /// `Option` is **required** (spike): `shutdown(&self)` must *close* stdin to
  /// give the child stdin-EOF, and you can only drop the `BufWriter` out through
  /// `&self` by `take()`-ing it — `Mutex<BufWriter<…>>` (no Option) cannot.
  pub struct StdioWriteHalf { write: Mutex<Option<BufWriter<ChildStdin>>> }
  impl EngineTransport for StdioWriteHalf { /* send: newline-framed JSON to stdin; shutdown: write Shutdown then write.lock().take() to close */ }

  /// OWNED read half (moved into the demux reader thread). Owns stdout
  /// directly — taken via `child.stdout.take()` (the `lsp/integration_test.rs:94`
  /// idiom) — plus a clone of the shared child handle to reap on EOF.
  pub struct StdioReadHalf {
      read: BufReader<ChildStdout>,
      child: Arc<Mutex<Option<std::process::Child>>>,  // shared w/ host; see Teardown
  }
  impl EngineReadHalf for StdioReadHalf { /* recv: read line → Response | Eof | Malformed */ }

  /// `StdioTransport::spawn` launches `deno run … <bundle>` (piped stdio) and
  /// hands the host the three wired pieces. The `Child` lives in
  /// `Arc<Mutex<Option<Child>>>` so BOTH the host (`shutdown`/`Drop`: kill+wait)
  /// and the read half (unexpected-EOF: reap the exit code) can reach it, with
  /// `Option::take()` enforcing single-shot reaping (see "Teardown & reaping").
  /// stderr is `take()`n into the stderr thread.
  /// fn spawn(ctx) -> Result<(Arc<StdioWriteHalf>, StdioReadHalf, Arc<Mutex<Option<Child>>>)>
  ```
  There is **no `Drop` on the transport halves** — guaranteed reaping moved to
  `TsEngineHost::Drop`, which owns the shared `Arc<Mutex<Option<Child>>>` (the
  old `StdioTransport::Drop { child.kill() }` couldn't fire while the reader
  thread held the transport alive — that was finding #2). `std::process::Child`
  still has **no** `kill_on_drop` (that is a `tokio::process::Command` method —
  why `daemon.rs:146` can use it: that path is tokio); the host's explicit `Drop`
  supplies the same SIGKILL-on-Unix / TerminateProcess-on-Windows guarantee.
  **Sync model (decided — see Design Notes "Why sync").** The native render
  driver is `pollster::block_on` on a dedicated thread; project renders fan out
  over rayon, each worker calling `pollster::block_on`
  (`render_to_file.rs:337`, `orchestrator.rs:1301/1445`). There is **no ambient
  tokio reactor** (`crates/quarto/src/main.rs` is a plain `fn main`), and
  `ExecutionEngine::execute` is a **sync** trait method. A blocking worker that
  parks on its own response slot starves nothing — the thread is already
  dedicated to that one document. So the transport is blocking `std` I/O.
  **Do not** introduce a tokio runtime for the transport and **do not** wrap
  the `execute()` call in `block_in_place` — there is no multi-thread runtime to
  host it, so `block_in_place` would panic. The Deno-side concurrency reaches
  Rust through the demux reader thread, not through async Rust.

  **The demux (in `TsEngineHost`, not the transport).** `ensure_started` spawns
  **one reader thread** that **owns the `StdioReadHalf`** and loops `read.recv()`,
  routing each `Response` by `id` to a `pending: Arc<Mutex<HashMap<u64, PendingSlot>>>`
  entry (the reader holds a *clone of that field*, never `Arc<Self>`).
  Each `PendingSlot { engine: String, tx: SyncSender<Result<FromEngine,
  ExecutionError>> }` carries its request's **engine name** so a crash broadcast
  can name the right engine (finding #3). A response whose `id` is no longer
  pending (late reply after a cancel) is dropped. A worker's
  `host.request(msg, window, &cancellation)` allocates an `id`, registers a
  `PendingSlot` over a **`sync_channel(1)`**, `write.send(Request { id, msg })`,
  then blocks on the slot's `Receiver` in a `recv_timeout`/cancel-poll loop.
  **Slot-delivery invariant (finding #5):** the reader does `pending.remove(id)`
  (releasing the pending lock) **before** `tx.send(...)`, and the channel is
  capacity-**1**, so the single reader thread's one send always succeeds without
  blocking — even if the worker already timed out and abandoned its `Receiver`.
  Never `sync_channel(0)` (rendezvous would stall the whole demux). **No lock is
  held across the wait** — the write mutex and pending mutex are each held for
  microseconds — so a worker on a 5-minute `Execute` never blocks another
  worker's discovery call. (In v1 the reader thread reads the child's **stdout** —
  the protocol channel; **stderr** is drained by a separate reader thread — see
  "Stderr forwarding".)

  **Teardown — two paths.** The primary path is the explicit `shutdown()`
  method, called by Plan 1c's `EngineRegistry::shutdown_all` from the
  **orchestrator's explicit end-of-render call** (not `ProjectContext::Drop` —
  ProjectContext has no `Drop`; q2's convention is explicit shutdown methods.
  `shutdown_all` does not exist yet — see "Lifecycle caller is Plan 1c"). The
  `TsEngineHost::Drop` SIGKILL+join is a belt-and-suspenders backup for
  a panic or a forgotten shutdown. The exact graceful-vs-forced sequence, the
  single-shot reap, and the crash-vs-expected-exit distinction are in Design
  Note "Teardown & reaping" (this is where findings #1/#2/#4 land).

  **Observable difference between the two paths.** Clean
  `host.shutdown()` sends a `Shutdown` protocol message and waits for
  the child to exit normally — final stderr lines flush, the child
  writes whatever final state it wants to disk (e.g., daemon
  transport-file updates), exit code is 0. The `Drop`/timeout/cancel
  fallback is SIGKILL: any in-flight stderr is truncated, late
  flushes are lost. For daemon-backed engines (Jupyter, Julia) this
  is fine because daemons write transport files eagerly; the daemon
  process itself is detached and survives the harness either way.
  For trivial engines, late stderr loss is the only observable cost,
  and we accept it as the price of guaranteed reaping. If a future
  engine needs reliable post-execution output, it should write
  during `execute()`, not during shutdown.

      write: OnceLock<Arc<dyn EngineTransport>>,
      /// Shared child handle for kill/wait. `Option` so reaping is single-shot
      /// (`take()`); shared with the reader thread (which reaps on unexpected
      /// EOF) and the host's `shutdown`/`Drop` (which kill+reap).
      child: Arc<Mutex<Option<std::process::Child>>>,

      /// tell an **expected** exit (quiet) from a **crash** (broadcast

      /// field* (not `Arc<Self>`) or it pins the host alive and `Drop` never runs

      /// **`Mutex<Option<JoinHandle>>`, NOT `OnceLock<JoinHandle>`** — `join`
      /// consumes the handle by value, and you cannot move it out of an
      /// `OnceLock` through `&self`; `shutdown(&self)` does `.lock().take()` then
      /// `join()`, single-shot (spike-confirmed; pass-3 finding A).

      stderr_reader: Mutex<Option<std::thread::JoinHandle<()>>>,

      /// filled by the stderr reader thread (see "Stderr forwarding"). Drained
      /// to populate `ProcessCrashed.stderr` on EOF. No prior ring-buffer
      /// precedent in-tree — green-field, but a few lines; a plain
      /// `Arc<Mutex<VecDeque<String>>>` shared sink (standard idiom; the tree
      /// has no existing threaded-line-reader sink to mirror).
      recent_stderr: Arc<Mutex<std::collections::VecDeque<String>>>,

      /// Sent verbatim with every `LaunchEngine` message. The protocol
      /// permits per-engine overrides (see plan1a-protocol appendix), but the common
      /// path uses this single stashed value — "in practice all engines
      /// in a project share the same context."
      host_context: EngineHostContext,

      /// Construct with the project's static context (pandoc_path,
      /// runtime_dir, project_dir, is_single_file, etc.). Cheap — no
      /// subprocess spawn yet.
      ///

      /// constructor *taking* an already-built `EngineHostContext` plus the
      /// `quarto_util::quarto_runtime_dir()` helper that sources its

      /// `is_interactive_session`, `running_in_ci` — happens at
      /// `ProjectContext::new` time and is **Plan 1c Phase 2**'s work. Plan 1a
      /// tests pass a hand-built context.
      pub fn new(host_context: EngineHostContext) -> Self;
      /// Lazily spawn the subprocess (piped stdin/stdout/stderr), `take()` its
      /// stdout/stderr into the reader + stderr threads, store the `Child` in
      /// `self.child`, and store the thread handles. **Idempotent, race-safe,
      /// fallible** — Pass-1 discovery calls it concurrently from rayon workers.
      /// **Init shape (spike-validated; pass-3 finding C):** double-checked —
      /// fast-path `self.write.get().is_some()`, else take ONE coarse init lock
      /// (reuse the `reader` mutex), re-check, spawn, and **commit by `write.set()`
      /// LAST**. A spawn failure leaves `write` unset → the next call retries
      /// (never a cached half-init). **No `Mutex<HostState>` enum** — it would be
      /// more ceremony, since the shared fields are already individually
      /// `Arc`/`Mutex` for the reader to clone. **The reader thread captures
      /// field-clones** (`self.pending.clone()`, `self.child.clone()`,
      /// `self.recent_stderr.clone()`, `self.shutting_down.clone()`) + the owned
      /// `StdioReadHalf` — **never `Arc<Self>`** (spike-confirmed: `Arc<Self>`
      /// leaks the child and `Drop` never runs).
      pub fn ensure_started(&self) -> Result<()>;

      /// **The demux entry point.** Allocate a fresh `id`, register a
      /// `PendingSlot { engine, tx }` over a `sync_channel(1)`,
      /// `write.send(Request { id, msg })`, then block on the slot's `Receiver`,
      /// polling `cancellation.is_cancelled()` on a sub-window tick
      /// (`min(window.unwrap_or(MAX), 250ms)`). Returns the correlated
      /// `Response`'s `FromEngine`. On timeout/cancel: send `Cancel { target:
      /// id }`, poison + lazily relaunch the affected engine instance (NOT a
      /// whole-subprocess SIGKILL — see "Timeout/cancel: cooperative &
      /// instance-scoped"), and return a timeout/cancelled error. On EOF (child
      /// stdout closed → reader thread ends): the slot resolves to
      /// `Err(ProcessCrashed{..})`.
      ///
      /// `window` is **`Option<Duration>`**: `Some(10s)` for discovery,
      /// `Some(resolved execute.timeout)` (default 300s) for Execute, and
      /// **`None`** for a user-disabled timeout (`execute.timeout: false`) — a
      /// `None` window blocks indefinitely on the slot but still polls
      /// `is_cancelled()` each tick, so Ctrl-C still works. See "Per-request
      /// timeouts" and the `execute.timeout` Design Note.
      pub fn request(&self, msg: ToEngine, window: Option<Duration>, cancellation: &Cancellation)
          -> Result<FromEngine>;

      // Thin wrappers over `request` with the 10s discovery window. Both go
      // through the demux like any other request (cheap: LoadEngine ~10–50ms;
      // LaunchEngine ~0 — it only constructs the `ExecutionEngineInstance`,
      // starting no daemon; the expensive engine startup happens lazily inside
      // `execute()` on the Deno side).
      pub fn load_engine(&self, engine_path: &Path, cancellation: &Cancellation)
          -> Result<LoadEngineResult>;
      pub fn launch_engine(&self, engine: &str, cancellation: &Cancellation)
          -> Result<LaunchEngineResult>;

      /// Shut down the entire subprocess (all engines). Idempotent. The
      /// real caller — `EngineRegistry::shutdown_all`, invoked by the
      /// orchestrator's explicit end-of-render call (NOT `ProjectContext::Drop`)
      /// — is **Plan 1c** (see "Lifecycle caller is Plan 1c"); in Plan 1a this
      /// is exercised only via `MockTransport`.
      pub fn shutdown(&self) -> Result<()>;

      /// Test-only: build a host around a caller-supplied **pair of halves**,
      /// **bypassing the subprocess spawn but STILL starting the real reader
      /// thread** — so unit tests exercise the production demux path (pending
      /// map, `id` routing, slot blocking), not a synchronous shortcut. The
      /// `write` half goes into the same `OnceLock<Arc<dyn EngineTransport>>` the
      /// live path uses; the `read` half is moved into the spawned reader thread.
      /// `MockTransport::pair()` produces both halves sharing internal state (a
      /// plan1a-host deliverable — see Design Note "MockTransport & the test
      /// demux"); the read half **blocks `recv()` until the write half's matching
      /// (id-echoed) response is scripted-ready**, so the reader never sees a
      /// spurious EOF. No tokio, no `block_on`; the only background threads are
      /// the std reader threads the production path also uses. (There is no
      /// real `Child`, so the test host's `child` slot is `None` — `ProcessCrashed`
      /// in tests is driven by the mock signalling EOF, code/stderr seeded.)
      #[cfg(test)]
      pub fn with_transport(
          write: Arc<dyn EngineTransport>,
          read: Box<dyn EngineReadHalf>,
          host_context: EngineHostContext,
      ) -> Self;
  }

- [x] **Timeout/cancel: cooperative & instance-scoped (NOT whole-subprocess
    SIGKILL).** Under parallel Pass-2 the subprocess is shared, so a timeout or
    cancel on one document **must not** kill it out from under siblings still
    mid-`Execute`. The mechanism:
    1. On `recv_timeout` elapse — or observed `is_cancelled()` — send
       `Cancel { target: id }`. The Deno harness aborts *that task's*
       `AbortSignal`; the request resolves as `Cancelled` (or its natural
       result if it finished first).
    2. **Poison policy — scoped by request type, not by guessing daemon state.**
       Rust *cannot* tell "ambiguous" from "clean": the daemon (Julia control
       server / Jupyter kernel) is a separate process the JS only talked to over
       a socket, so aborting the JS-side `AbortSignal` never proves the daemon
       went idle — even a clean-looking `Cancelled` doesn't. So don't classify;
       scope by **which request was interrupted**:
       - **`Execute` is the only request that engages a daemon** (it starts/uses
         it lazily). Cancel/timeout of an `Execute` → **always poison that engine
         instance.**
       - Every other request (`LoadEngine`, `LaunchEngine`, `ClaimsLanguage`,
         `ClaimsFile`, `MarkdownForFile`, `IntermediateFiles`) engages **no**
         daemon → just fail the request; **no poison, no relaunch.**
       **Poison = invalidate the instance on both sides** so the next
       instance-tier request re-runs `LaunchEngine` (~0) and gets a fresh
       `ExecutionEngineInstance` that re-discovers/restarts the detached daemon:
       (a) the harness drops its `instance` entry; (b) `TsEngine` clears its
       cached launched-state — which is why that cache must be **clearable
       (`Mutex<Option<…>>`), not a `OnceLock`** (plan1a-engine; the `discovery`
       cache can stay `OnceLock` — `LoadEngine` is permanently idempotent).
       Blast radius = **one engine instance**, not the subprocess.
       *(Future opt-in, not v1: an engine that performs a real interrupt — e.g.
       Jupyter `interrupt_request` + ack — may carry `clean: true` on its
       `Cancelled` response to let the harness skip the poison.)*
    3. **A *concurrent* same-instance request transparently re-launches — it is
       NOT failed.** Parallel Pass-2 means the poisoned instance can have a
       concurrent user, not just a future one: worker A's `Execute` poisons the
       julia instance while worker B has an `Execute` queued behind it on the
       harness's per-engine queue. When the harness dequeues B and finds the
       instance dropped, it **re-runs `engine.launch(stashedContext)` to
       reconstruct it, then runs B** — B never sees a half-torn-down instance and
       never fails for A's timeout. (Self-healing: if the detached daemon is
       genuinely wedged, B's re-run hits *its own* `window` and poisons again on
       its own merits.) This is plan1b's harness contract; q2 is unaware. See
       the design note's poison section.
    4. **Whole-subprocess SIGKILL (`child.kill()`) is reserved** for genuine
       everyone-affecting failures: subprocess crash, a compromised/unparseable
       protocol stream, and final teardown.
    **Return a *distinguishable* forcible-abort error**, NOT a generic
    `ExecutionError::ExecutionFailed`: a user-cancel → `ExecutionError::Cancelled`
    (the variant already exists); a timeout → a distinct variant naming the
    engine + operation (add `ExecutionError::Timeout { engine, operation }`).
    This is the boundary contract plan1a-engine's poison policy depends on:
    `TsEngine::execute` poisons **only** on these forcible-abort errors
    (`Cancelled | Timeout`), never on a plain `ExecutionFailed` from a normal
    engine error — a user-code error leaves the daemon alive (kernels survive
    cell errors), so poisoning then would relaunch needlessly.

## Design Notes

### `execute.timeout` (q2) vs `execute.daemon` (Q1) — different axes

Q1 has **no `execute.timeout`**. It overloads **`execute.daemon`**
(`document-execute.yml:116`, `anyOf: [number, boolean]`, default 300, jupyter-only):
`true`/absent ⇒ persistent kernel daemon with a **300s idle keep-alive**;
`false` ⇒ one-shot kernel; number `N` ⇒ daemon with an **N-second idle
keep-alive**. That number is the **daemon's between-render lifetime**, passed to
`execJupyter("start", { timeout })` — it does **not** cap a single execution
(`jupyter-kernel.ts:422`). Q1 jupyter has no per-execution abort at all.

q2's `execute.timeout` is a **different axis**: the Rust host's **per-`Execute`
abort budget** (`recv_timeout` → `Cancel` → poison). It interrupts a running
cell; `execute.daemon` governs process reuse across renders. They are
**complementary, not substitutes** — do not replace one with the other.

**Architectural consequence:** in the q2 engine-host model, daemon lifecycle
belongs to the **engine extension + harness** (q2 is deliberately unaware of
daemon state — that's the basis for the request-type-scoped poison policy).
q2 forwards the full merged metadata as `TsFormatInfo.metadata`, so an engine
that wants `execute.daemon` semantics **reads it off the wire itself** (exactly
as Q1's julia-engine and jupyter do). **q2 does not interpret `execute.daemon`.**
We only borrow its `number|boolean` **tri-state shape** for `execute.timeout`
(`false` ⇒ `None` window). `timeout` is free in Q1's namespace, so no collision.

### MockTransport & the test demux

The transport is **split** (shared write half + owned read half); **all**
correlation lives in the `TsEngineHost` demux (pending map + one reader thread).
For tests to cover that demux, `with_transport` starts the **real reader
thread**, which loops `read.recv()`. So the mock must supply **both** halves
over shared state: `MockTransport::pair() -> (Arc<dyn EngineTransport> /*write*/,
Box<dyn EngineReadHalf> /*read*/)`. The read half's `recv()` **must block until a
paired response is available** — a passive `VecDeque` that returns "empty" reads
as **EOF and false-triggers the crash path**. So the shared state carries an
internal condvar/`sync_channel`: the write half's `send()` records the `ToEngine`
and (echoing its `id`) makes the scripted response available (optionally after a
delay); the read half's `recv()` blocks until one is, returns it, blocks again
when drained; a test-only `signal_eof()` (or the write half's `shutdown()`)
returns `RecvError::Eof` to drive the crash test. Responses are **keyed by `id`
with optional delay**, not a flat FIFO — the timeout / cancel / sibling-unaffected
/ crash tests each need to withhold one response while another returns.

**Ownership:** `MockTransport` is a **plan1a-host** deliverable (it lives in
host's `ts_process.rs` and host's own timeout/cancel/crash tests need it);
plan1a-engine *consumes* it. This removes the earlier circular reference where
host tests depended on an engine-owned type. There is **no `std::sync::mpsc` /
`sync_channel` anywhere in the tree today** (verified) — the demux is green-field
and should follow the standard `std::sync::mpsc` idiom; the only reader-loop +
`id`-correlation precedent to mirror is the LSP harness
(`quarto-lsp/tests/integration_test.rs:38`). plan1a-engine's race tests
introduce `std::sync::Barrier` (also new to the tree, but the right tool).

### `quarto_version` source (invariant)

`EngineHostContext.quarto_version` is the **user-facing q2 release version** that
engine extensions gate compatibility on. Plan 1c sources it via
`env!("CARGO_PKG_VERSION")` evaluated in quarto-core — **correct only because the
workspace version is unified** (`[workspace.package] version`, and both
`quarto-core` and the `quarto`/`q2` bin use `version.workspace = true`, so the
constant is identical across crates). If any crate ever pins its own `version`,
Plan 1c must re-source this from the `quarto` binary crate. (Plan 1a only
*takes* a built context; this is a heads-up for Plan 1c's construction site.)

### Daemon non-reaping (explicit non-goal)

Plan 1a reaps the **subprocess** — via explicit `shutdown()` and the `Drop`
SIGKILL backstop. It does **not** reap **detached daemons** (Julia control
server / Jupyter kernel). Those are separate processes the engine talks to over
a socket; they outlive any single render by design and are discovered via
transport files. A daemon left mid-computation after a cancel is a *per-daemon*
recovery concern (the next user of that engine may find it busy) — the same
situation Q1 faces, and out of scope here. What Plan 1a guarantees is that the
**subprocess and its sibling requests** survive a per-document cancel/timeout.

### Teardown & reaping (findings #1, #2, #4)

The crash/teardown path is the part of this design the parallel-Pass-2 rework
stressed hardest. The model, grounded in the in-tree precedents
(`lsp/integration_test.rs`, `knitr/subprocess.rs:388`, `jupyter/session.rs:202`,
`pass2_renderer.rs:486`):

**Ownership.** The `Child` lives in `Arc<Mutex<Option<Child>>>`, shared by the
host (kill/wait) and the read half (reap-on-crash). Its `stdout`/`stderr` are
`take()`n out at spawn into the two reader threads (the `lsp:94` idiom); the
write half (`stdin`) is the shared `Arc<dyn EngineTransport>`. **The reader
thread owns its `StdioReadHalf` directly** — its blocking point is the OS pipe
`read()`, *not* an `Arc<dyn EngineTransport>` clone. This is what makes a forced
kill able to unblock it (finding #2): an `AtomicBool` cannot interrupt a blocking
`read()` — only closing the pipe (killing the child) does (research:
`pass2_renderer.rs` uses the flag only to *skip new work*, never to interrupt I/O).

**`shutting_down: AtomicBool`** distinguishes an **expected** exit from a
**crash** on EOF — it does *not* stop the reader. Set it *before* any kill.

**Graceful `shutdown()`** (the Plan 1c caller's path):
1. `shutting_down.store(true)`.
2. Send the `Shutdown` frame; flush; drop the write half (close stdin) → the
   harness sees stdin EOF and exits cleanly.
3. Reap once: `child.lock().take().map(|mut c| c.wait())` (exit 0).
4. `join()` the reader + stderr threads (they EOF when the pipes close).

**Forced `TsEngineHost::Drop`** (panic / forgotten shutdown backstop):
1. If `!shutting_down`: set it, then `child.lock().take().map(|mut c| { let _ =
   c.kill(); let _ = c.wait(); })`. `kill()` is idempotent / safe on an
   already-dead child; ignore the error. **Use the std precedents** —
   knitr's `subprocess.rs:388` single `wait()` and the LSP harness's
   `child.stdout.take()` + `kill()`-ignored (`lsp:258`) are `std::process::Child`.
   The `jupyter/session.rs:204` / `daemon.rs` kill-ignored idiom is the same
   *shape* but on `tokio::process` (`start_kill()`), so don't copy its method
   names onto `std::process::Child` (which has `kill()`, not `start_kill()`).
2. Killing closes stdout → the reader's `read()` EOFs → it sees `shutting_down`
   and exits quietly (no `ProcessCrashed` broadcast — nobody's waiting at Drop).
3. `join()` both threads. **No cycle:** the kill is independent of the reader's
   `Arc<Mutex<Option<Child>>>` clone; the reader was blocked on the *pipe*, which
   the kill closes.

**Single-shot reap.** Only one party calls `wait()` — whoever `take()`s the
`Option<Child>` first; the other finds `None`. (`wait()`-twice is the bug
`knitr/subprocess.rs:388`'s single-call pattern avoids.) On an *unexpected*
crash the reader is that party (it needs the code *now*, for the broadcast);
on shutdown/Drop the host is.

> **Why the `Child` is shared, not host-owned.** A host-owned `Child` (reaped
> only by `&mut self` in Drop) cannot give the reader thread the exit code at
> crash-broadcast time — but error category 6 requires `code` + `stderr` in the
> error delivered to the blocked workers. Sharing via `Arc<Mutex<Option<Child>>>`
> lets the reader reap at the instant it broadcasts, without re-introducing the
> teardown cycle (the reader never blocks *on* the mutex — only on the pipe).

**Spike-validated (2026-06-24).** A ~250-line std-only spike (since removed;
`/bin/cat`/`/bin/sleep` as the child) proved this model end-to-end, 5/5 tests
green under watchdogs:
- `drop_without_shutdown` returns **instantly** and reaps the child — the
  field-clones reader does not pin the host.
- The **`Arc<Self>` reader variant actually deadlocks** (an `#[ignore]`d test
  confirms the leaked child survives `drop` — `Drop` never runs). This is the
  failure the field-clones design avoids.
- `shutdown(&self)` `take()`+`join()`s the handle via `Mutex<Option<JoinHandle>>`;
  `OnceLock<JoinHandle>` provably cannot (can't move out through `&self`).
- Forced struct deltas folded above: `StdioWriteHalf.write` needs the inner
  `Option` (to close stdin through `&self`); `pending` must be `Arc<Mutex<…>>`;
  handles must be `Mutex<Option<…>>`; crash `code` is `None` on signal death.
- `ensure_started` is cleanest as double-checked "commit `write.set()` last under
  one coarse lock" — **no `HostState` enum** needed.

### Why sync (not async tokio)

The Rust transport is **blocking `std` I/O**, by design, not by trait inertia.
The native render driver is `pollster::block_on` running a stage future to
completion on one thread; project renders fan that out over a **rayon** pool,
one `pollster::block_on` per worker (`render_to_file.rs:337`,
`orchestrator.rs:1301/1445`). The CLI entrypoint (`crates/quarto/src/main.rs`)
is a plain `fn main` — **there is no ambient tokio reactor**. `ExecutionEngine::
execute` is a sync trait method, and the existing engines (e.g. Jupyter) already
do blocking work under it.

**Sync does NOT mean serial.** Concurrency is real — it lives on the **Deno
event loop** (cross-engine requests interleave) and is surfaced to blocking Rust
workers by the **`TsEngineHost` demux**: each worker blocks on its *own* pending
slot, so N workers proceed concurrently with no head-of-line blocking. The
earlier "sync ⇒ lockstep ⇒ no concurrency" framing is retired (it predated
parallel Pass-2); the correct statement is "sync Rust transport + a demux that
bridges to the concurrent async harness." See
`claude-notes/designs/engine-host-concurrency.md`.

Consequences that shaped this plan:

- A worker blocking on its slot is *already dedicated* to one document. It
  starves no reactor; this is the existing execution model.
- **Do not** reach for `tokio::process` / `tokio::time::timeout` /
  `select!` on the Rust side. They would require standing up a runtime the
  native path deliberately avoids, only to bridge it back to the sync trait.
  The std-thread demux + `mpsc::recv_timeout` design gives the per-request
  timeout / cancel / poison semantics with no runtime.
- **Do not** wrap the `execute` call in `tokio::task::block_in_place` (as the
  Jupyter path does): that requires a multi-thread tokio runtime and would
  **panic** under `pollster`.
- `std::process::Child` has no `kill_on_drop`; the explicit `Drop` impl on
  `StdioTransport` supplies the same guarantee (the `kill_on_drop` precedent at
  `daemon.rs:146` is a `tokio::process::Command` — a different runtime).

The async lives where it belongs — the **Deno harness** (Plan 1b): a
non-blocking read loop dispatches each request as a task, serialized per engine
instance. The one future pull toward an *async Rust* trait is a
`WebSocketTransport` for a WASM-resident engine host (WebSockets are inherently
async); it is a `#[cfg(not(wasm32))]`-isolated *sibling* introduced later and
does not force async onto today's native transport (originally
`StdioTransport`, now `TcpTransport` since Phase 1.6 landed).

### Shared subprocess

All TS engine extensions share **one Deno subprocess per project render**.
The subprocess is spawned lazily on first need (any TS engine's discovery
query or execute call). Each engine is loaded into the subprocess via a
`LoadEngine` message (cheap), then optionally launched via `LaunchEngine`
(also cheap — `engine.launch(context)` only constructs the
`ExecutionEngineInstance` object and starts no daemon; only sent when an
instance method is needed). The expensive engine startup (Julia control
server / Jupyter kernel: 5+s) happens lazily inside the engine's
`execute()` on the Deno side, never at `LaunchEngine`. The subprocess is
shut down at the end of the project render.

This avoids spawning N Deno processes — important because Julia is bundled,
so anyone with an additional TS engine extension has at least two. Each
Deno process costs ~100-200ms startup and ~30-50MB memory.

All protocol messages carry an `engine: String` field for routing to the
correct engine within the subprocess. The harness maintains a
`Map<string, { discovery, instance? }>` internally — `instance` is undefined
until `LaunchEngine` runs for that engine.

The lifecycle is managed by `TsEngineHost`. See Phase 2 for the
authoritative ownership model: `Arc<EngineRegistry>` is constructed
at `ProjectContext` construction time (Plan 1c Phase 2 owns the
construction sequence), threaded onto per-document `StageContext` as
`registry: Arc<EngineRegistry>`, and shared across Pass 1
(`EngineClaimsFileStage` — Plan 1c) and Pass 2 (`EngineExecutionStage`).
Individual `TsEngine` structs hold `Arc<TsEngineHost>` clones plus
their engine name. Test overrides migrate from
`HtmlRenderConfig::engine_registry` (`pipeline.rs:118`) /
`RenderToFileConfig::engine_registry_override` (`render_to_file.rs:112`)
to building a `ProjectContext` with a custom registry; see Plan 1c Phase 2.

Future-WASM compatibility: the `EngineTransport` trait abstracts the
wire (originally `StdioTransport`, now `TcpTransport` since Phase 1.6
landed); a future `WebSocketTransport` for a
browser-resident engine host slots in without restructuring the
ownership model (it carries the same multiplexed `id` envelope). WASM
hub-client adoption of TS engine extensions is out of scope for these plans;
when it lands it will adopt the same `Arc<EngineRegistry>` model with a
different transport.

### Blast radius: one engine instance, not the subprocess

Under parallel Pass-2 the subprocess is **shared by many in-flight documents**,
so a per-document timeout/cancel must be *contained*. The mechanism (Phase 2
"Timeout/cancel: cooperative & instance-scoped"):

- A timeout/cancel of an **`Execute`** (the only daemon-engaging request — see
  the Phase 2 poison policy) sends `Cancel { target: id }` and **always poisons
  that engine instance**, lazily relaunching it on next use. Cancel/timeout of
  any non-`Execute` request engages no daemon and is just failed. Blast radius =
  **one `ExecutionEngineInstance`**, not the subprocess — siblings mid-`Execute`
  are untouched.
- A **whole-subprocess SIGKILL** is reserved for genuine everyone-affecting
  failures (crash, compromised control channel, teardown), and *those* do lose
  all instances' harness-side state — acceptable because they are already fatal
  to the render.

The poison/relaunch cost is small. `LaunchEngine` is ~0 (it only constructs the
`ExecutionEngineInstance`; the daemon is **never** started there — Julia control
server / Jupyter kernel start lazily inside `execute()`). Quarto's daemon-backed
engines spawn those daemons as **detached** processes that outlive any single
render, discovered via transport files in the runtime dir: Julia uses a single
fixed name (`julia_transport.txt` in `juliaRuntimeDir()`); Jupyter uses
md5-hashed-per-target filenames in a `jt/` subdir
(`external-sources/quarto-cli/src/execute/jupyter/jupyter-kernel.ts:308-324`).
So a poisoned instance costs roughly a module-state reset + a `LaunchEngine`
(mostly a transport-file read + socket reconnect), not a full daemon relaunch.

> A detached daemon left mid-computation after a cancel is a *per-daemon*
> recovery concern (the next user of that engine may find it busy) — the same
> situation Q1 faces, and out of scope here. What matters for parallelism is
> that the **subprocess and its sibling requests** survive, which this design
> guarantees.

### Transport abstraction

The transport abstracts the communication channel between q2 and the
engine-host subprocess. Per `engine-host-concurrency.md:166` it is a **split**
seam: a shared `EngineTransport` **write half** + an owned `EngineReadHalf`
moved into the reader thread. The original v1 impl was `StdioTransport`
(newline-framed `Request`/`Response` JSON over the child's stdin/stdout).
Phase 1.6 has since landed, replacing it with `TcpTransport` (loopback TCP) as
the sole impl — `StdioTransport` is deleted. A future `WebSocketTransport`
(WASM) shares the same seam.

**The Rust transport is synchronous; the *system* is concurrent.** `send`
(write half) and `recv` (read half) are blocking `std` I/O — the deliberate fit
for the consumer (`ExecutionEngine` is a sync trait; `TsEngine` calls through
with no `async`/`await`/`block_on`, and the pipeline's executor is `pollster`,
not tokio, so there is no reactor to drive async stdio). But the halves are a
*dumb framed duplex*; **multiplexing lives in `TsEngineHost`** (id-correlated
pending map + one reader thread), and the **concurrency is real** — it runs on
the Deno event loop and is surfaced to blocking Rust workers by the demux. The
earlier "strict request/response lockstep, so async buys no concurrency"
framing is **retired** — it predated parallel Pass-2; see
`claude-notes/designs/engine-host-concurrency.md`.

**Future direction — engine server:** the protocol is transport-agnostic
(self-contained framed messages). A future `WebSocketTransport` would run the
engine-host as a standalone server (e.g. a browser WASM hub-client that cannot
spawn processes connects to a locally-running engine server with OS access). It
carries the **same multiplexed `id` envelope** over a different wire — being
inherently async, it is a `#[cfg(not(wasm32))]` sibling that may run async
internally behind the (sync) host-facing seam. No protocol changes — only a new
transport and a way to start/discover the server.

### Phase 1.6 — the protocol moved off stdout (loopback TCP) — LANDED

> **Landed:** [Plan 1a.6](2026-07-08-plan1a6-off-stdout-loopback-tcp.md)
> (plan dated 2026-07-08, implemented since). This note is the canonical
> *transport-owner* rationale; the plan carries the checklist, TDD test plan,
> cross-platform analysis, the engine-impact worked example (Julia), and the
> fd-3/UDS rejection.

Multiplexing (the demux + `id` + `Cancel`) did **not** require leaving stdout —
it was orthogonal. The *reason* to leave stdout was to delete the `console.log`
footgun (an engine writing to stdout corrupted the protocol). That cleanup was
**Phase 1.6**; the original v1 design kept the protocol on stdin/stdout with
the stdout contract described above, but Phase 1.6 has since landed and that
contract is gone.

The channel is now **loopback TCP** (`TcpTransport`), **not** a Unix-domain
socket + Windows named pipe:

- `std::net::TcpListener`/`TcpStream` is **blocking std, uniformly
  cross-platform, no new dependency, no `#[cfg]` fork** — it actually satisfies
  the "blocking std primitives" property that UDS + named-pipe *cannot* (std has
  `UnixListener` but **no** Windows named-pipe support; that needs the
  `interprocess` crate or raw winapi). An earlier draft's "Unix socket / named
  pipe" framing was wrong on that point.
- It **matches the existing local-IPC precedent** — Jupyter kernels already talk
  over localhost TCP via `runtimelib` (`daemon.rs`).
- q2 binds `127.0.0.1:0` (ephemeral) and passes the non-secret address via argv
  (`--control 127.0.0.1:<port>`); the one-time token is written as the first
  line on the child's stdin (not arg/env — see Plan 1a.6's "Token delivery"
  section for why those were rejected), and the child's stdin is closed after
  that line. The harness dials back and presents the token as a pre-line on
  the socket before any framed message. The token (not filesystem perms)
  closes the "any local process can connect" gap — and the Deno subprocess is
  already fully-trusted/local.

Phase 1.6 also flipped stdout/stderr to diagnostic-only and deleted the
"console.log corrupts the protocol" contract. That contract no longer holds:
a stray `console.log` is harmless.

### Cross-cutting consequences (WASM gating, timeout semantics)

**WASM gating — a hard compile constraint.** `ts_protocol.rs` (pure serde) stays
ungated and compiles for `wasm32`. But the entire **`ts_process.rs`** —
`TsEngineHost`, the demux, the transport (originally `StdioTransport`, now
`TcpTransport`) — uses `std::thread`, `std::process`, and `std::net`, none of
which exist on `wasm32-unknown-unknown`. It must be
gated **`#[cfg(not(target_arch = "wasm32"))]` in its entirety** (like
`engine/jupyter`, `engine/knitr`, `engine/fixture` already are), and `TsEngine`
must be registered native-only. Otherwise the `wasm-quarto-hub-client` build
breaks even though `cargo build --workspace` passes — the exact
`cargo xtask verify` trap. **Caveat for the future `WebSocketTransport`:** the
thread-based demux is *native-specific*; a WASM-resident engine host would
multiplex on the JS event loop, not a `std::thread` reader. The
`EngineTransport` *trait* is the shared seam; the *demux implementation* is not
portable as-is.

**No new socket dependency.** The original v1 stdio transport had no dep;
Phase 1.6's loopback TCP (now landed) uses `std::net` (already available; no
`interprocess`, no winapi, no `#[cfg]` fork).

**Timeout includes same-engine queue wait.** Because same-engine requests
serialize on the harness's per-instance queue, a document's `recv_timeout(window)`
ticks *while it waits in that queue behind another document's `Execute`*. So
under same-engine contention the Execute timeout effectively measures
"queue-wait + execution," not execution alone. Accepted for v1 (the window is
generous and same-engine work is serial on the daemon regardless); flagged so a
later "spurious timeout under contention" report isn't mis-diagnosed. If it ever
bites, the fix is a harness `started`-ack that resets the Rust-side timer when
the request actually begins executing — out of scope now.

### Diagnostic stream handling (Rust side)

In the original v1 design the protocol ran on stdout, so **stderr was the
diagnostic stream** (forwarded to q2's logging). Phase 1.6 has since landed
and frees *both* stdout and stderr for diagnostics; stderr remains the
diagnostic stream in practice. The harness (Plan 1b) writes level-prefixed
lines (`[INFO]`, `[WARN]`, `[ERROR]`) to stderr; the Rust side parses those
prefixes and routes to the matching level. Unprefixed stderr lines are logged
at INFO. **In the original v1 design, an engine's `console.log` went to
*stdout* in Deno — which was the protocol at the time — so it corrupted the
stream and was caught as malformed protocol (see the stdout contract above).
Phase 1.6 has removed that hazard: stdout is diagnostic-only, and a stray
`console.log` is harmless.**

### Error categories and handling

Following Quarto 1's approach: **errors propagate up, render fails, user sees the
message.** No silent recovery, no engine removal from the registry on failure.

1. **Deno not found** — `is_available()` returns false before any subprocess call.
   Clear error: "Deno is required for the {name} engine extension but was not found
   in PATH." Render fails.
2. **Engine module load failure** — Subprocess starts but `LoadEngine` gets back
   an `Error` response. Fatal for this engine. Forward the TS-side error message
   (import failure, missing exports) to the user. Render fails. Other engines
   already loaded in the subprocess are unaffected.
3. **Engine launch failure** — `LaunchEngine` returns an `Error` response. Fatal
   for this engine but not for the subprocess. Other engines (loaded or
   launched) in the subprocess are unaffected.
4. **Discovery errors** — `claimsLanguage`/`claimsFile` throw inside the engine.
   Subprocess sends `Error` response. Propagate as `ExecutionError`. Render
   fails. **Scoped to engines q2 actually consulted:** the static-hint
   pre-filter (plan1a-engine) skips engines whose declared `language_hints` /
   `file_extension_hints` exclude the input, so no `LoadEngine` /
   `ClaimsLanguage` / `ClaimsFile` is ever sent for those engines. Crashes
   that would have happened during such a never-issued query don't
   manifest — the engine module is never loaded, so its module-level
   side effects never run. This is the intended behavior: an extension
   that's irrelevant to the document under render shouldn't be able to
   break the render via its own module-load errors. A failure surfaces
   only when q2 has reason to consult the engine.
5. **Execution failure** — `Error` response during execution. Forward the message
   and optional stack trace. Matches Quarto 1 behavior.
6. **Process crash** — the protocol channel closes (demux reader thread hit
   EOF — the child's **stdout** in the original v1 design, the accepted
   loopback-TCP socket since Phase 1.6), child process exited unexpectedly.
   No Quarto 1 equivalent (in-process
   engines can't crash independently). The reader thread reaps the child for its
   exit `code`, snapshots `recent_stderr`, and resolves **every** in-flight slot
   with `Err(ExecutionError::ProcessCrashed { engine, code, stderr })`. Mark
   subprocess dead and **abort the render** — Plan 1a does **not** promise
   respawn-and-continue. This is one of the few **whole-subprocess** failures
   (see "Blast radius: one engine instance, not the subprocess").
7. **Timeout** — a request exceeds its `window`. **Cooperative, instance-scoped**
   (NOT whole-subprocess SIGKILL): send `Cancel { target: id }`, poison + lazily
   relaunch the affected engine instance, report a timeout error naming the
   engine and operation. Siblings on the shared subprocess are untouched. See
   Phase 2 "Timeout/cancel: cooperative & instance-scoped."
8. **Cancellation (Ctrl+C)** — `StageContext.cancellation` reaches `request` via
   the new `ExecutionContext.cancellation` field (plan1a-engine); `request`
   polls `is_cancelled()` on each `recv_timeout` tick. **Same cooperative
   `Cancel`+poison path as a timeout**, not a SIGKILL. See Phase 2 "Cancellation
   wiring."
9. **Malformed protocol (original v1 design; retired by Phase 1.6)** — in the
   original v1 design, a line on **stdout** (then the protocol channel) that
   failed to parse as a `Response` meant the channel was compromised: SIGKILL
   the subprocess (a whole-subprocess failure) and report via a clearly-worded
   `ExecutionError::Other` (NOT `ProcessCrashed`), naming a stray
   `console.log`/`console.info` as the most likely cause. Phase 1.6 has since
   landed and retired this category — stdout is no longer the protocol, so a
   stray `console.log` no longer triggers it.

### Stdio contract (Rust side) — original v1 design, retired by Phase 1.6

In the original v1 design, the protocol ran on **both** of the child's
standard streams — `Request`s in on stdin, `Response`s out on stdout — so the
engine had to leave **both** alone:

- **Must not write stdout.** `console.log`/`console.info` and
  `Deno.stdout.writeSync` were forbidden; a non-`Response` line on stdout was
  detected as malformed (category 9) and killed the subprocess. Engines used
  `console.error`/`console.warn` or `quarto.console.*` (stderr) for diagnostics.
- **Must not read stdin.** An engine that read `Deno.stdin` (e.g. an
  interactive prompt) stole protocol bytes the harness's read loop needed —
  the *symmetric* footgun. The harness owned stdin; engines could not touch it.

The harness did not override `console.*` or reassign the streams — protection
was by contract, not mechanism. **Phase 1.6 has since landed and deleted both
halves** by moving the protocol to loopback TCP
([Plan 1a.6](2026-07-08-plan1a6-off-stdout-loopback-tcp.md)); stdin/stdout are
now free for the engine, and this contract no longer applies. See Plan 1b's
"Stdout/stderr contract" for the current engine-author rules.

**Large-payload deadlock-freedom (load-bearing regardless of transport).**
Because the protocol shares a bounded OS channel, a big `Execute` `input`
could deadlock a naive implementation — but does not, because **both sides
drain continuously**: q2's dedicated demux reader thread always reads the
protocol channel while a worker writes to it, and the harness's non-blocking
loop always reads while it writes. This was a *required* property of the
original v1 stdio channel, not an optimization, and remains required for the
Phase 1.6 TCP channel — do **not** collapse the demux reader thread into the
worker, and do **not** make the harness await a handler before reading the
next frame (T5).

### Bundle embedding

The harness bundle is embedded in the q2 binary via
`include_str!(concat!(env!("CARGO_MANIFEST_DIR"), "/../../ts-packages/quarto-engine-host-deno/dist/engine-host-deno.js"))`
in `ts_process.rs`, gated behind `#[cfg(not(target_arch = "wasm32"))]`.
**Anchor the path at `CARGO_MANIFEST_DIR` (the crate root, an absolute path),
not at the source file.** From `crates/quarto-core` only two `..` reach the repo
root, and — unlike a source-file-relative `include_str!("../../../../…")` — the
hop count does **not** change if `ts_process.rs` later moves within the crate
(the `../`-counting trap the integration-tests rule warns about). The `q2 mcp` /
`q2-preview-spa` bundles use the heavier `include_dir!("$ENV_DIR")` + `build.rs`
form; for a single JS file the `CARGO_MANIFEST_DIR` `concat!` is the same
robustness with less ceremony.

**Plan 1a ships a placeholder bundle file** — the path
`ts-packages/quarto-engine-host-deno/dist/engine-host-deno.js` must exist
for `include_str!` to compile. Plan 1a creates this file with a single
line of placeholder content:

```javascript
console.error("@quarto/engine-host-deno bundle is a placeholder. Run 'npm run build' in ts-packages/quarto-engine-host-deno to produce the real bundle (Plan 1b).");
Deno.exit(1);
```

The file goes in git so checkouts compile cleanly. Plan 1b replaces the
content with the real esbuild output. The file path is permanent across
both plans; only the bytes change.

**Why the bundle is committed — the `q2 mcp` / `q2-preview-spa` pattern.**
The harness is a **generated build artifact**, embedded into the binary,
exactly like the two existing TS bundles in this tree:

- `q2 mcp` embeds `ts-packages/quarto-hub-mcp/dist-bundle/` via `include_dir!`;
  `cargo xtask build-hub-mcp-bundle` builds it; a placeholder is embedded on
  fresh clones; `q2 mcp --launcher-info` prints the embedded bundle's git
  commit / dirty flag / build time so staleness is diagnosable.
- `q2 preview` embeds `q2-preview-spa/dist/` via `include_dir!`, built by
  `cargo xtask build-q2-preview-spa`.

The earlier draft cited `crates/quarto-system-runtime/js/dist/ejs-bundle.js`
as "the established repo convention." **That file does not exist** — that
crate embeds no JS, and the only `include_str!`/`include_bytes!` JS in the
tree is *source* under `resources/…` (reveal.js, clipboard, bootstrap), which
is a different thing from a generated bundle. The harness is **not** source;
it is the MCP/SPA case. So this plan adopts that pattern's obligations, not a
"bundle-is-source" framing:

- **xtask build step** (Plan 1b): a `cargo xtask build-engine-host-bundle`
  (esbuild) that regenerates `dist/engine-host-deno.js`, wired into
  `cargo xtask build-all` like the MCP/SPA bundle steps.
- **placeholder on fresh clones** (this item) so plain `cargo build` compiles
  with no npm/esbuild having run — `include_str!` just needs the path to exist.
- **staleness diagnostic** (Plan 1b): surface the embedded bundle's git
  commit / dirty flag / build time (mirroring `q2 mcp --launcher-info`) so a
  stale embed is detectable, since a plain `cargo build --bin q2` re-embeds
  whatever bytes are on disk.

`@quarto/engine-host-deno` is **not** published to a registry (decided): the
harness ships *only* embedded in the binary, so its version is locked to the
binary and the frozen wire protocol it speaks. (Only `@quarto/api` /
`@quarto/types` and engine extensions distribute via jsr/npm — see the grand
plan's "Distribution of the engine-author SDK.") A future move to
fetch-on-first-use (reusing the Deno/hub-MCP cache machinery) is possible if
the harness cadence ever decouples from the binary, but it is explicitly out
of scope here.

This separation lets Plan 1a land standalone — the Rust code compiles
and Plan 1a's tests run against `MockTransport` (a plan1a-host deliverable —
see Design Note "MockTransport & the test demux"), not the embedded
placeholder. Production use of TS engine
extensions requires Plan 1b's bundle to have replaced the placeholder;
until then, any attempt to actually launch a TS engine fails immediately
with the placeholder's error message — clear, actionable.

At runtime (with the real bundle), the embedded string is extracted **once** to
a **content-hash-keyed** path under `quarto_util::quarto_runtime_dir()` (already
a Plan 1a deliverable) — `<runtime_dir>/bundles/engine-host-deno-<sha8>.js`,
where `<sha8>` is a short hash of the embedded bytes computed once at first
extraction and cached in a `OnceLock` (a 200–500 KB sha256 is sub-millisecond)
— written **atomically** (write to a sibling temp file, then rename) and
**write-if-absent**.

**Key on the content hash, NOT `CARGO_PKG_VERSION`** (decision; corrects an
earlier draft). The workspace version is constant across dev rebuilds, so a
version-stamped + write-if-absent file would **silently serve a stale bundle**
when a dev rebuilds the harness without bumping the version — the exact
stale-artifact trap the `q2 mcp` / `q2-preview-spa` `--launcher-info` machinery
exists to guard against (and the 2026-05-20 stale-WASM incident). The content
hash makes stale-serve impossible: **new bytes → new hash → new filename → fresh
extraction**, while **identical bytes → same filename → reuse**, keeping Deno's
module cache warm and concurrent renders race-free (same hash ⇒ identical bytes
written via temp+rename; a hash-named file is never *replaced* while a Deno child
has it open — new bytes get a new name — which also dodges the Windows
"can't overwrite an in-use file" hazard a fixed-name overwrite would hit).
The hash in the path is itself an extraction-layer staleness tell, **orthogonal
to** Plan 1b's embedded-layer diagnostic: Plan 1b's `--launcher-info` catches
"cargo embedded a stale `dist/`"; the content hash catches "extraction served a
stale file." Both layers stay needed. (Old-hash siblings accumulate a few hundred
KB each; optional best-effort unlink of other `engine-host-deno-*.js` on a
successful fresh extraction, or just ignore.) The `bundles/` subdir keeps this
q2-internal artifact separate from engine transport files (Julia
`julia_transport.txt`, Jupyter `jt/`) that also live under `runtime_dir`.

It is then
executed with `deno run --allow-all <extracted-path>`, the protocol originally
flowing over the child's stdin/stdout (v1); Phase 1.6 has since landed and
adds `--control <addr>` (argv) plus a one-time token on stdin for the
loopback-TCP channel — see
[Plan 1a.6](2026-07-08-plan1a6-off-stdout-loopback-tcp.md). **Do not** mint a
fresh per-spawn tempfile — that litters temp and defeats Deno's cache. The
real bundle is expected to be 200–500 KB
depending on `@quarto/api/jupyter` complexity (see Plan 1b's "Bundle size note"
for details and possible future mitigations such as a cargo feature gate).

### Lifecycle caller is Plan 1c (clarification 6)

Plan 1a delivers `TsEngineHost` and its `shutdown()`, but the *caller* that
invokes it — `EngineRegistry::shutdown_all`, called **explicitly by the
orchestrator at end-of-render** — does **not exist yet**. (`ProjectContext`
itself *does* exist today, `project/mod.rs`, but Plan 1c's `shutdown_all` and
the `Arc<EngineRegistry>`-on-`ProjectContext` ownership move do not.) **Teardown
is an explicit method call, NOT `ProjectContext::Drop`:** ProjectContext is
`Clone`-by-value and has no `Drop`; a destructor that killed a shared subprocess
would fire on every clone. Per plan1c, the orchestrator (the same code path that
drops `ProjectContext` at end-of-render) calls `registry.shutdown_all()`
explicitly before letting the context drop, with `TsEngineHost::Drop`'s SIGKILL
as the backstop for panic/early-return paths. **Caveat — the `Drop` backstop is
best-effort under `Arc` fan-out:** with the host reached as `Arc<TsEngineHost>`
cloned into every `TsEngine` (and via `Clone` `ProjectContext`), `Drop` fires
only when the *last* clone drops — which is render-end **iff** no clone escapes
the render scope. So the explicit `shutdown_all()` is the real timeliness
guarantee; `Drop` guarantees the subprocess is eventually reaped (never leaks
past process exit), not that it is reaped *promptly* if a clone is cached beyond
the render. This is a reason to keep the explicit call load-bearing, not to lean
on `Drop`. Today the registry is an owned
`EngineRegistry` (cheaply `Clone`) carried as `Option<EngineRegistry>` on
`HtmlRenderConfig`. Therefore in Plan 1a the
spawn → load → launch → request → shutdown lifecycle is exercised **only via
`MockTransport`** (and the optional `deno`-gated `StdioTransport` smoke test);
the real end-to-end shutdown-on-render-end path lands and is verified in Plan
1c. This is the honest scope — Plan 1a is unit-complete, not end-to-end
complete, for teardown.
