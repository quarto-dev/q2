## Why

H10a makes one warm instance produce the same bytes and diagnostics as a fresh run. H10b makes the PDF preview use warm instances without ever wasting an in-flight render. The pane renders 250 ms after an edit when the warm path is on and H10a Task 0(f) showed the whole warm refresh at 200 ms or less (500 ms otherwise, also the value when the warm path is off, `PdfPreviewPane.tsx:23`), and a warm pandoc leg takes 99-111 ms (about 105). Two renders overlap when the whole refresh (pandoc leg, typst, viewer) exceeds the debounce, which Task 0(f) measures; for large documents (callouts x10 is 0.56 s, x100 is 10.9 s) and slow machines it always does. The pool exists so that those cases never block, kill or waste a pandoc render, and the latency win applies to the common case. The measured benefit is on the pandoc leg only; typst and pdf.js are outside it.

**Design in one paragraph.** A *warm runner* (a second `PandocRunner`-family runner sharing the one `PandocLoader`) owns a pool of at most two persistent workers (the second is created at the first overlap). A new request goes to an idle worker, otherwise it replaces the single pending request (latest wins; replaced requests resolve `superseded`) and starts when a worker frees. An older render that a newer request has superseded keeps running; only a wall timeout, the grace rule and a reboot terminate a worker. The preview controller tags every request with a sequence number, lets runs overlap, and applies a result only by the rules in Task 3. The preview has its own typst runner (Task 2), serialized and never killing a running job, because the app-wide `TypstRunner` has one slot and aborts the previous job (`typstRunner.ts:159,201-204`), which would let an older run displace the newest.

  - [x] **1b: pool, dispatch and generation.** The warm runner is constructed in `pandocService.ts` next to the app-wide singleton (`getPreviewPandocRunner()`), sharing its `PandocLoader`. Each worker is spawned and `init`-ed once (one `ready`). The **generation key** is the string `sha | JSON-stable limits | share_tree_version | allowlist version`; each worker records the key it was built with, and the runner compares it with the request's key on every dispatch. The key cannot change within one page session (`share_tree_version()` is a `OnceLock` over embedded resources, `crates/quarto-core/src/pandoc_request/share.rs:54-65`, and the sha and limits are fixed per build), so it is a defensive invariant exercised by tests, not user-visible behaviour. A mismatch is a **reboot**: every worker of the old generation is terminated at once (idle, busy or warming, its `loader.hold()` released), and a worker of the new generation is spawned. **Load.** The module load is owned by the pool with its own `AbortController`: no run's signal, replacement or detach cancels it (the loader aborts a download when its waiters reach zero, `pandocLoader.ts:274`), and `onLoadProgress` events are forwarded to the newest pending or running request. Requests that arrive while no worker is ready (module load, first `init`) replace the single pending request, so a load completes into one dispatch of the newest request, never a burst of stale starts. **Dispatch:** an idle worker, otherwise the single pending slot (latest wins; a replaced request resolves `superseded`). A pending request has no wall timer and no grace clock until it is dispatched. The share tree is cloned each run by `postMessage` (not transferred; about 1 ms measured); request buffers go through `prepareForPost`, which transfers them (`transfer.ts:10-26`), so a transferred request cannot be replayed. **The second worker** is created at the first request that arrives while the only worker is busy, or when the first render completes, whichever comes first (a heavy first render must not be starved of its spare). It carries the generation key of the most recent request. **Warm-up:** the pool keeps a pre-transfer copy of each dispatched request's `files` and `resource_refs` until that render completes; if the render took under `WARMUP_MAX_MS = 500` (by the runner clock) the copy becomes the replay request and is kept until replaced, otherwise it is dropped. A new worker with a replay request available is warmed by running it once with its output discarded; with none available it starts cold. A warming worker is busy but is never counted as superseded and its warm-up is excluded from the median and from *k*; a failed warm-up is ignored. If Task 0(a) failed, the spare is never warmed and is treated as cold. `retire: true` from a worker means the pool terminates it when idle (releasing its `hold()`) and replaces it with a worker of the current generation key (a retired worker is never a generation orphan, since there are none); a poisoned instance is replaced inside `WarmSession` and is no pool event. A replacement for a grace-terminated worker takes the current generation key and is cold unless a replay request is available. `RunOptions.docKey` (the controller passes the path joined with the `projectKey`, absent for Download) is what the grace rule keys on. An `AbortSignal` on a warm run means *detach*: a dispatched run's result is dropped and the worker keeps running under the grace rule; a pending, undispatched request is removed from the pending slot and resolves `aborted`. A signal never terminates a worker by itself. Tests (fake `Worker`, same commit): reuse across runs; two overlapping runs on two workers; spare created at the first overlap; latest-wins coalescing with `superseded` for replaced requests; many requests during module load producing one dispatch, and an abort or detach during load that does not cancel it; both workers busy with the newest waiting; generation change terminating every old worker and spawning a new one; warm-up replay below and above `WARMUP_MAX_MS`, a failed replay ignored, and a replay built from a retained copy (the transferred request is empty); `retire: true` replacement; detach of a dispatched run and removal of a pending one.
  - [x] **1c: grace and wall timeout.** **Grace rule:** when a newer request arrives while a run is in flight on a worker, that run is *superseded* and its grace clock starts at the later of the supersede and its dispatch (a request waiting for a worker has no clock). It gets `graceMs = min(wallTimeoutMs, GRACE_CAP_MS, max(1000 * 2^k, 3 * median))`, with `GRACE_CAP_MS = 16000`, *k* the count of consecutive grace terminations since the last completed render (reset to 0 by any completion, capped at 4 so that 1000 * 2^k stops at the cap), and *median* the median of the last five completed warm render times (dispatch to result on the runner clock, not `stats.runMs`; warm-ups excluded) **of the current `docKey`** (none on a cold start, so only the doubling term applies). `graceMs` is evaluated once, when the run is superseded. *k* and the median reset on a `docKey` change and on a reboot. A superseded run that is still running when its grace expires has its worker terminated, resolves `superseded` (the controller treats it as a silent end because a newer run exists; only the wall timeout resolves `timeout`), and a replacement is created in the background. The doubling guarantees that a document that legitimately takes 2 s or 10.9 s eventually completes under continuous typing, and a runaway filter holds a worker for at most 16 s, never for the 120 s wall timeout, once something newer exists. When both workers hold superseded renders, the newest request waits for the first to finish or be terminated, so its wait is bounded by `graceMs` (at most 16 s; state this in the docs). A run that is not superseded is limited only by the wall timeout, which starts at dispatch. Tests (fake timers and the injected clock, same commit): grace-terminate then re-create; *k* doubles after a termination, resets after a completion and stops growing at the cap; the median is per `docKey` and resets on a `docKey` change and a reboot; a simulated 2 s render with edits every 0.6 s eventually shows a result; a 10.9 s render under continuous edits completes, and the number of terminations before its first frame is recorded from this simulation (Task 6 copies it into the docs); a runaway whose wait for the newest request never exceeds 16 s; a 1.5 s render with edits every 400 ms is not killed (the spare takes the newest request); wall timeout resolving `timeout`.
  - [x] **1d: lifetime and idle.** The loader's idle drop only clears its main-thread reference (`pandocLoader.ts:313-317`) and frees nothing while workers hold Modules, and `hold()` keeps `busy > 0`, so the loader's own timer never arms while a worker lives. The warm runner therefore owns one runner-wide idle timer (`DEFAULT_IDLE_MS`, reset at every run start and every settle, never firing while a render is in flight), each live worker holds a `loader.hold()` released exactly once on **every** termination path (grace, wall timeout, poison, memory retire, reboot, idle, release), and `PandocLoader` gains an `onDrop` listener (called from `dropResident()`, `pandocLoader.ts:237-240`, today used only by tests and typst fonts) that terminates the pool. The pool has `acquire()` and `release()`, a refcount the pane calls at mount and unmount (it covers React StrictMode's mount, cleanup, mount); when the count reaches zero the workers linger 30 s, `acquire()` cancels the linger, and after it they are terminated whether busy or idle (a detached run has no consumer). A mounted pane relies on the 5-minute idle. Tests (same commit): per-worker `hold()` release on each termination path, idle termination, `acquire`/`release` linger including a remount inside and after 30 s, `dropResident()`.
