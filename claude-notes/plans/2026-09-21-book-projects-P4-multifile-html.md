# Plan: Multi-file HTML book mode, local numbering (book-projects P4)

**Date:** 2026-09-21 (revised after a critical review pass)
**Epic:** [`2026-09-21-book-projects-epic.md`](2026-09-21-book-projects-epic.md)
**Design (authoritative):** [`../designs/book-projects-architecture.md`](../designs/book-projects-architecture.md) §7
**Q1 reference:** `book-chapters.ts`'s `withChapterMetadata`/`formatChapterTitle`/`chapterInfoForInput`, `resources/filters/crossref/sections.lua`, `book.ts`'s `bookScssBundle`/`bookHtmlPostprocessor`, `book-render.ts`'s cover-image markdown prepend

## Overview

Each chapter renders independently — exactly today's Pass 2, unchanged — but needs one externally-injected fact before its own Crossref-phase transform runs: its book chapter number (and appendix-letter flag). This phase ships a fully usable multi-file HTML book *before* cross-chapter reference resolution exists (P5): a same-chapter `@ref` resolves correctly; a cross-chapter `@ref` shows a visible, honest "unresolved" placeholder rather than silently wrong output.

This phase also owns the two book-specific features that are genuinely tied to HTML rendering (not config-level, hence not P1): the book stylesheet and the cover image.

## Decisions (see design doc §7 and the appendix below for the experiments that ground these)

- Keep an explicit `chapter_number: u32` / `is_appendix: bool` fact (computed once in `pre_render` from P1's `BookRenderItem` list) as the single source of truth for "which chapter is this" — used by title decoration, sidebar, and P5's future registry key.
- This fact has **two** numbering-related consumers, not one (corrected on review — an earlier draft said "only consumer"): seeding `CrossrefIndex.sections = vec![chapter_number - 1]` (P0's seed capability) before that chapter's `CrossrefIndexTransform` walk begins, and P0's `@sec-`/section-number *presentation* code, which needs `is_appendix` on the `RenderContext` to letter-format (not numeral-format) the resulting number and prefix "Appendix" instead of "Chapter" (see design doc §7 and P0's plan — `sections.lua` does the equivalent). The counter itself stays appendix-agnostic; only presentation branches on `is_appendix`. No parallel counter, no changes to `advance_sections` itself. An unnumbered chapter (`chapter_number: None`) gets no seed at all — its own local numbering starts fresh and unscoped, exactly as observed (see appendix).
- **How the fact actually reaches `RenderContext` — traced against real code, not assumed (a critical-review pass caught that "threaded into each chapter's `RenderContext`" had no implementation path as originally written).** Neither `RenderToFileOptions` nor `Pass2Renderer::render_batch*` has any per-document seed channel today, and `RenderContext` is built entirely internally inside `render_document_to_file` with no caller hook. **P0 builds the `RenderContext`-level half of the fix already** — `ChapterSeed{chapter_number, is_appendix}`, the `RenderContext.chapter_seed` field, and the `RenderContext::with_chapter_seed(...)` builder (following the existing `with_project_index`/`with_resource_resolver`/`with_options` pattern) — since P0 needs that plumbing self-contained for its own tests and runs before this phase. **This phase's job is the other half: getting a *real* per-chapter value into that already-built field for an actual multi-chapter render.** `render_document_to_file`/`RenderContext::new` are low-risk to extend for this (only two production call sites for `RenderContext::new`, no stray struct-literal construction elsewhere in the crate): add a new `chapter_seed: Option<ChapterSeed>` field on `RenderToFileOptions` (already derives `Debug, Clone, Default`, so no other caller is affected), applied via `.with_chapter_seed(...)` right after `RenderContext::new(...)` in `render_document_to_file`, before the pipeline runs.

  **Revised after a review pass (tenth pass): don't touch the `Pass2Renderer` trait signature at all.** The original plan here added a `HashMap<PathBuf, ChapterSeed>` parameter directly to `Pass2Renderer::render_batch`/`render_batch_serial`/`render_batch_parallel` — but `render_batch` is a *trait* method (`crates/quarto-core/src/project/pass2_renderer.rs:126`), implemented by `RenderToHtmlRenderer` and `RenderToPreviewAstRenderer` (the WASM/preview renderers) as well as `RenderToFileRenderer` (the only one that ever renders a book chapter). Widening the trait signature would force every current and future `Pass2Renderer` implementor to accept and ignore a parameter meaningless to it. **Fix: confine the seed map to `RenderToFileRenderer` itself**, via a new field (`chapter_seeds: HashMap<PathBuf, ChapterSeed>`, default empty) and a matching `RenderToFileRenderer::with_chapter_seeds(mut self, seeds: HashMap<PathBuf, ChapterSeed>) -> Self` builder — the same idiom `RenderContext`'s own builders use, and consistent with how `format_override` already flows into this same struct from `ProjectPipeline::with_format_override` (`pass2_renderer.rs:239-245`). No trait method gains a new parameter; `Pass2Renderer::render_batch`'s signature is untouched, so `RenderToHtmlRenderer`/`RenderToPreviewAstRenderer` need no changes at all.

  **One real mechanical wrinkle this surfaces, not avoided by either approach: `RenderToFileRenderer.options: &'a RenderToFileOptions` is one shared borrowed reference used for every document in a batch call** (`pass2_renderer.rs:239`, `render_batch_serial`/`render_batch_parallel` both take `options: &RenderToFileOptions` and forward the same reference to every `render_document_to_file` call in the loop, `pass2_renderer.rs:374-414`, `432-483`). A per-document seed can't be expressed by mutating that shared reference. Since `RenderToFileOptions` is `Clone` (already derived), the fix is: **the lookup itself has to live inside `render_batch_serial`/`render_batch_parallel`, not `RenderToFileRenderer::render`/`render_batch`** (corrected by an implementability review — those two methods just dispatch to the free functions, which own the actual per-doc loop; `render`/`render_batch` never see individual documents). Since those free functions' public contract can grow one additional plain parameter (they're private to this module and not part of the `Pass2Renderer` trait), thread `self.chapter_seeds` into them; inside the per-doc loop, look up `chapter_seeds.get(&doc.input)`; if present, clone `options`, call `.with_chapter_seed(...)` on the clone, and pass that owned value to `render_document_to_file` for that one document; if absent, pass `options` through unchanged (no clone in the common non-book path). Keyed by each chapter's own input path, not position — `render_batch_parallel`'s `par_iter` doesn't preserve a stable index-to-doc mapping worth relying on.

  **This still deliberately keeps using `Pass2Renderer::render_batch*` rather than a bespoke per-chapter loop** — `render_batch_parallel` is real, already-tuned machinery (a dedicated rayon thread pool, `catch_unwind` panic safety, `fail_fast` short-circuiting, ordered artifact-store merging, perf instrumentation), not a thin wrapper worth reimplementing per project type. Book chapters get the same parallel rendering every other project type gets, for free — not a Known Limitation, a non-issue.
- Chapter title decoration ports `withChapterMetadata`/`formatChapterTitle` (chapter number prepended to the page's own H1/title metadata, "Appendix A — Title" formatting, `.unnumbered`/`.unlisted` handling) as idiomatic Rust. **This is distinct from, and does not cover, sidebar nav-item text decoration** (`numberChapterHtmlNav`'s equivalent) — that's P1's job, baked into the sidebar translation at config time rather than here at render time (see P1's plan for why). **Leave this insertion point extensible**: `bd-ock6cyiy` (per-chapter subtitle/author-affiliations/date/abstract, tracked separately, not this phase's job) has the same natural seam — insert the title-decoration content as one block in what could later be a short, ordered sequence of decoration blocks near the H1, not a single hardcoded block that a future change would have to restructure.
- **`number-sections: true`/`crossref.chapters: true` are P1's job now**, applied uniformly regardless of format — this phase inherits them rather than setting them itself (previously mis-scoped to P2 only; see P1's plan).
- **`book.scss`**: port `bookScssBundle` directly — an SCSS bundle Q1 injects for HTML output, gated the same way Q1 gates it (Bootstrap-based HTML themes).
- **Cover image**: Q1's mechanism is two parts — (1) prepend a markdown image to the index/Preface chapter's content (`book-render.ts`'s `onRender`), and (2) a DOM postprocessor (`bookHtmlPostprocessor`) that moves the resulting `<img>` from before the first `<section>` wrapper to inside it, because Pandoc's HTML writer wraps heading+content in `<section>` and the image — prepended to raw markdown before any heading — lands outside that wrapper. **Do not port part (2).** Per this repo's no-DOM-postprocessor policy, insert the cover-image `Block` in the *correct* position in the AST from the start (inside the section, immediately after the opening heading) rather than porting a repositioning step. **Confirmed against the real writer (design doc §7): the writer itself does no section logic — a separate pre-write pass, `SectionizeTransform` (Normalization phase, `pipeline.rs:1392`), wraps headings into `Div{class="section level<N>"}` by heading level before the HTML writer ever runs.** Inserting the cover-image `Block` right after the index chapter's `Header` works *only if done before `SectionizeTransform` runs* — do this insertion as an early Normalization-phase step (the same pass that already knows, from P1's chapter model, "this is the index/Preface chapter"), not a later pass; a later insertion point would have to splice into the already-built section `Div`'s content instead of the flat block list.
- A cross-chapter `@ref` uses the crossref system's *already-existing* unresolved-reference mechanism (`CrossrefResolveTransform` already emits an unresolved `CrossrefResolvedRef` node, specifically so a renderer can show a placeholder instead of erroring) — no new placeholder shape.
- **`run_with_book_support()`'s multi-file branch** (not a `ProjectType::render_documents` trait override — resolved by a seventeenth-pass research round, design doc §3) (dispatched on target format being HTML-based) drives chapters through the ordinary per-document `RenderToFileRenderer`/`Pass2Renderer` path — unmodified except for the `with_chapter_seeds(...)` call described above, which is how the chapter-number/appendix fact actually reaches each chapter's `RenderContext`.
- **Out of scope for this phase, and for the epic**: `q2 preview` never calls `run_with_book_support()`'s book orchestration at all — it renders a single active chapter through a different per-document code path (`RenderToHtmlRenderer`/`RenderToPreviewAstRenderer`). A previewed chapter therefore gets none of this phase's chapter-number seeding or title decoration; it renders exactly as if it were a lone, non-book document. Documented as a deliberate epic-level Known Limitation, not something this phase needs to address.

## Appendix: the experiments that ground this phase's numbering contract

Built a minimal 2-chapter + 1-appendix HTML book (`scratchpad/minibook`) and rendered it with the real `quarto` binary. Observed, directly:

- Chapter 1's own subsection: `header-section-number="1.1"`. Chapter 2's figure: `Figure 2.1`. Appendix figure: `Figure A.1` — appendix letters are a separate sequence from the numeric chapters (not continuing as "4").
- A cross-reference from the appendix back to chapter 1/2 figures showed their **original** numbers (`1.1`, `2.1`) with correctly fixed-up cross-file `href`s (`chapter1.html#fig-a`) — this is the *reading* side P5 must reproduce (P4 itself doesn't attempt cross-file resolution).
- `@sec-ch1` (an id on chapter 1's own H1) rendered as plain "Chapter 1" text, not "Section 1" — confirms the "Chapter N" presentation convention P0 needs to support.
- Title/nav decoration (`<span class="chapter-number">A</span> <span class="chapter-title">Appendix Stuff</span>`, "Appendix A — Appendix Stuff") matched `numberChapterHtmlNav`/`formatChapterTitle` exactly.

**Second experiment, added after a review pass questioned whether the unnumbered-chapter claim was actually observed**: inserted an `.unnumbered` chapter (`chapter1b.qmd`, with its own figure) between chapter 1 and chapter 2 and re-rendered. Observed:

- The sidebar/pagination still labels the surrounding chapters "1" and "2" — the interlude is invisible to the chapter sequence.
- Chapter 2's figure is still `Figure 2.1`, not `Figure 3.1` — confirms no slot was consumed.
- The interlude's own figure rendered as plain `Figure 1` — flat, unscoped, not chapter-relative in any form. This is a real, specific finding (not derivable from the first experiment, which only tested the Preface/index page — a different `BookRenderItem` kind that's excluded from chapter numbering for an unrelated reason) and is now what this phase's test actually asserts, rather than a generalization from a different case.
