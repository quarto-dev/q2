## Goal

Julia is the first engine that is engine-driven and raw: QNR runs the whole
document and returns one nbformat notebook with raw outputs. Make that notebook a
first-class engine execution record, including inline expression results, without
changing what Quarto 1 or today's q2 see, and flip Julia to the Rust presenter only
once a parity suite shows the two presenters agree.

Verified 2026-10-28; paths are under `external-sources/` (symlinks to the working
checkouts of the Julia engine on `q2/node-port` and of QNR). The QNR line numbers below
were taken at `9f9efa5` (an older base, upstream v0.18.1 era). On 2026-10-29 that commit
was rebased onto upstream `v0.18.6` as `bf09735` on the fork branch
`feat/quarto2-handled-languages`, and upstream refactored `parsing.jl`, `evaluation.jl`
and `socket_json.jl` in between (for example `_evaluate_markdown_cell!` moved from
`evaluation.jl:483` to `:487` and `_get_handled_languages` from `socket_json.jl:147` to
`:148`). Treat every QNR line number here as approximate and re-verify it when the task
that uses it starts.

**Engine side** (`external-sources/quarto-julia-engine/src/julia-engine.ts`):

- `execute` (199) runs the whole file: `executeJulia` (739) sends
  `{ type: "run", content: { file, options, sourceRanges } }` (763), where
  `options` is the entire `ExecuteOptions` object, so any key core adds reaches QNR.
  The response notebook is `response.notebook` (802).
- The engine sets `nb.metadata.kernelspec` (236), writes the notebook for
  `keep-ipynb` before presenting (249-255), then presents with
  `quarto.jupyter.toMarkdown(nb, ...)` (260). That call mutates `nb` in place (the
  comment at 257-259), so a record must be copied before it. The returned
  `ExecuteResult` carries markdown, supporting dir, filters, pandoc, includes or
  `engineDependencies`, `preserve` and `postProcess` (316-333).
- It declares `canFreeze: true` (126) and, statically, a primary claim on `julia`
  only (`_extensions/julia-engine/_extension.yml`). The engine is vendored into q2
  as an extension subtree from `q2/node-port` of Gordon\'s fork
  (`claude-notes/instructions/extension-subtrees.md`), and QNR is pinned
  `=0.18.2` in `_extensions/julia-engine/Project.toml`. The engine\'s
  `ensure_environment.jl` runs `Pkg.instantiate()` or `Pkg.update()` on that project;
  there is no `Manifest.toml` in the extension directory, so the pin resolves from the
  registry today (verified 2026-10-29).
- **The pinned QNR release has no ceding.** The `handledLanguages` cede commit
  (`bf09735`) is in no upstream release: `handled_languages` appears under `src/` in
  neither `v0.18.2` (the pin) nor `v0.18.6`, nor in upstream `main` (verified 2026-10-29).
  So with the registry release, a multi-engine document cannot make QNR cede another
  engine\'s cells. The fork is already required for that, independent of this plan\'s
  new options.

**QNR side** (`external-sources/QuartoNotebookRunner.jl/src/`):

- Chunks alternate markdown, code, markdown (`parsing.jl:163-266`): every code cell
  is preceded by a markdown chunk even when empty, and a trailing empty markdown
  chunk is added if the last chunk is code. Output cell ids are `string(nth)`
  over that list (`evaluation.jl:175-256`), expansion cells use `nth_mth`
  (`evaluation.jl:308-388`) and python or R cells add a markdown
  `*_code_prefix` cell with the fenced source (`evaluation.jl:266-286`). Every
  output cell has empty `metadata = (;)`. Chunks do carry `file` and `line`
  (`parsing.jl`), they are just not emitted.
- Inline spans: `_evaluate_markdown_cell!` (`evaluation.jl:487`, the marker at `:488`;
  verified 2026-10-31) walks CommonMark
  inline `Code` nodes only, so spans inside fenced blocks are never evaluated. It
  evaluates any `Code` node whose literal starts with the hard-coded marker `{julia} `,
  `{python} ` or `{r} ` (a literal single space; `evaluation.jl:488`; `INLINE_CODE_PATTERN`
  at `parsing.jl:3` only gates the chunk), sends each
  as `RenderRequest(inline = true)`, records errors with `record_error!(:inline,
  ...)`, takes `text/markdown` as is or escaped `text/plain`
  (`cell_processing.jl:105-118`), and **replaces the span inside the markdown cell
  source**. The returned notebook therefore carries no trace of the span code.
- **Front matter is never walked for spans.** QNR's parser enables CommonMark's
  `FrontMatterRule` (`parsing.jl:19`), so the front matter is not an inline `Code`
  node and a `{julia}` span in it is never evaluated. A review run of CommonMark with
  that rule, on a document with a span in a `title:` and another in the body, found only
  the body span. UNVERIFIED that the CommonMark version in the Julia depot used for that
  run is the one QNR pins (QNR's Manifest was not instantiated). The same run found no
  `Code` node in an HTML comment or a fence, and a tab after the language token is found
  as a node but QNR's marker needs a literal space.
- Ownership: `handledLanguages` is read at `socket_json.jl:148-150` and at
  `evaluation.jl:84` (in `evaluate!`, which passes it to `raw_text_chunks`), and used
  only in `parsing.jl:173,191` (cede cells, fold into the cache hash). It never
  reaches `_evaluate_markdown_cell!` (grep of
  `src` and `test`: no other use, and no QNR test mentions it). So in a
  multi-engine document Julia evaluates `{python}` and `{r}` spans that another
  engine owns.
- Which cells QNR recognizes at all: `toplevel_language` (`parsing.jl:48-57`) accepts
  exactly the info strings `{julia}`, `{python}` and `{r}`, and only for a code block
  whose parent is the Document (verified 2026-10-29). QNR never executes any other
  language, so for cells a positive ownership set would add nothing over
  `handledLanguages`: `ownedLanguages = {julia}` is the same as
  `handledLanguages = {python, r}`. Cells nested in blockquotes or lists are never seen
  by QNR although q2\'s resolver (an AST walk) sees them; that is upstream and Quarto 1
  behavior and this plan leaves it alone (decision below).
- **The plumbing path (verified 2026-10-31).** `evaluate!` reads
  `_get_handled_languages(options)` at `evaluation.jl:84`, but `_evaluate_markdown_cell!`
  is called from the cell loop in `evaluate_raw_cells!` (defined at `:184`, loop call at
  `:237`), a different function. That function receives `merged_options`
  (`evaluation.jl:136-142`), which `_extract_relevant_options` (`options.jl:101`) rebuilds
  from the front matter and the request options, so top-level keys such as
  `handledLanguages` and `emitUnits` do not survive into it. Both must therefore be added
  as keyword arguments to `evaluate_raw_cells!` and passed on to
  `_evaluate_markdown_cell!`. **Not verified:** how the 0.18.2 to 0.18.6 upstream
  refactors (#454, #455) touch that path.
- Cache: only with `execute.cache: true` (`evaluation.jl:89`); the hash covers the
  Julia version, `handled_languages`, the whole front matter, code cell sources (the
  literal of each code node, which includes its `#|` option lines), markdown
  chunks that contain inline code, and params (`parsing.jl:170-266`,
  `evaluation.jl:80-83`); prose-only edits reuse outputs and swap markdown in
  (`evaluation.jl:96-128`; the reused code cells keep their old annotation, so a `line`
  recorded in `metadata.quarto` goes stale after a prose edit above them: consumers must
  not use QNR\'s `line`, and core aligns by `unit` and re-locates lines itself);
  files are `.cache/<name>.<hash>.json` with
  `SCHEMA_VERSION` 1.0.0 (`cache.jl:3-15`), three per notebook. Any code change
  reruns the whole notebook (the comment at about `evaluation.jl:134`). QNR cannot
  execute a single cell.

**Presenters.** The TS presenter is `ts-packages/quarto-api/src/jupyter/to-markdown.ts`
(1069 lines, a rewrite of Q1's; documented simplifications in its header: ANSI
stripped only, no retina sizes, no slide delimiters, math-aware LaTeX) with
`display-data.ts` (`displayDataMimeType` precedence, ported). The Rust presenter is
`format_outputs` (`engine/jupyter/text_execute.rs:728`), which does not handle
`text/markdown` or widgets (comment at 725-727). How far they diverge on real
Julia output was not measured; that is Part B3.

Existing coverage: `crates/quarto-core/tests/integration/julia_engine_e2e.rs`
(julia and node gated), and the engine smoke docs
`external-sources/quarto-julia-engine/tests/docs/julia-engine/` (`keep-ipynb`,
`source-ranges`, `error`, `large-payload`).

## Design decisions (from the epic; do not re-litigate)

- Rust is the long-term single presenter. Julia stays presented by the TS
  `toMarkdown` until the parity suite shows the two agree; only then does it flip.
- Additive and default-off in QNR: with no new options, QNR output is byte-identical
  to today and Quarto 1 is unaffected.
- The record is additive annotation, not a different notebook. QNR keeps emitting
  the notebook the TS presenter expects (prefix cells, substituted spans) and adds
  metadata; q2 builds the record from the shared unit list (the stage\'s one scan) plus
  QNR outputs aligned by unit index over the units this engine owns.
- Core, not the engine, owns unit identity: the stage scans units once (EXR-2), fills
  the ids with EXR-4\'s id function and hands every engine the same list (epic decision
  38). QNR positional ids are an alignment key only. The engine uses the `line` it is
  given: core re-locates each unit\'s `line` in the text this engine receives, not the
  original text, in a multi-engine run (EXR-2 `locate_units`, carried by EXR-7). The
  engine validates counts for its owned units only.
- **The hash rule is declared as data (epic decision 35).** The Julia engine supplies
  its `recordInfo.hashDefinition` (EXR-7 wire, EXR-4 struct); core owns the algorithm.
  Whether a flat declaration is enough for QNR\'s own rule is task B1a; a rule that
  cannot be declared as data is reported as a finding, not added as code.
- QNR keeps its own `.cache`; q2 records are independent of it. No single-cell
  execution for Julia is promised.
- **No external release gate.** QNR changes land on Gordon\'s fork
  (`gordonwoodhull/QuartoNotebookRunner.jl`, branch `feat/quarto2-handled-languages`,
  upstream `v0.18.6` plus the cede commit) and the engine changes on the fork of the
  engine (`q2/node-port`). q2 consumes the QNR fork by commit hash, not by registry
  release. Upstreaming either fork is a follow-up that belongs to no plan.
- **QNR ownership stays a negative list (decided with Gordon, 2026-10-30; item 7
  amended 2026-10-31).** QNR gets
  no positive `ownedLanguages` option and `toplevel_language` is not generalized.
  Instead: (1) inline-span evaluation honors the existing `handledLanguages` list (the
  marker `{(?:julia|python|r)} ` is hard-coded in `_evaluate_markdown_cell!` at
  `evaluation.jl:488`, and the
  cede commit `bf09735` filters only cells, at `parsing.jl:186-192`); (2) the new
  `emitUnits` option stays; (3) the Julia engine keeps passing `handledLanguages`, the
  complement of ownership, as today; (4) `toplevel_language` keeps its three languages
  and its top-level rule, so QNR does not execute cells nested in blockquotes or lists
  (upstream and Quarto 1 behavior); (5) in record mode, units that the resolver or
  scanner sees and QNR does not run produce a count mismatch, and the safe outcome is
  no record plus a diagnostic, never a failed render; (6) the positive `ownedLanguages`
  set stays on the TS wire (JOL-4, EXR-7) for engines that need it, such as marimo
  (`sql`, `python.marimo`), and the Julia engine ignores it; (7) **a span whose
  language no engine owns stays literal (epic decision 42: the stage\'s one scan returns
  every span and each engine\'s view marks the ones it owns, so a span no view owns is
  never evaluated).** Core adds the languages of such spans to the `handledLanguages` it
  sends, so QNR cedes them (with item 1 in place) and live output and replay agree. This
  departs from Quarto 1, where QNR evaluates a `{python}` span in a Julia document that has
  no Python cells. A language another engine owns is ceded as before.
- **Front-matter spans are outside Julia\'s view (decided with Gordon, 2026-10-31,
  decision D4).** The shared scan claims a span in the document\'s own front matter
  (epic decision 41) but QNR never evaluates one (Background). EXR-7 therefore carries a
  wire flag on each span unit (`inFrontMatter`, name proposed here for EXR-7 to adopt)
  and Julia\'s view leaves such units out of alignment. A Julia document with a `{julia}` span in its front matter keeps a record for
  its other units, and Julia does not evaluate the front-matter span (it stays literal;
  a Jupyter engine in the same sequence that owns the span\'s language still evaluates it).
- **Cell expansions in record mode (decided with Gordon, 2026-10-30; attachment design
  accepted 2026-11-01).** An `expand` cell is emitted by QNR as one mock cell with id
  `nth` (`role: expansion_source`) followed by one cell per expansion with id `nth_mth`,
  each with its own options (`evaluation.jl:308-388`). Until Julia flips, such a notebook
  yields no record and a diagnostic (B2), and never fails the render. At the flip, an
  expansion attaches to the owning unit as **extra outputs tagged `expansion`**, with each
  expansion's own options (`echo`, figure captions, and the rest) stored in its tag. A
  unit still maps to exactly one record cell, so the record format and matching are
  unchanged. Expansions as units of their own was rejected: it would break the one-to-one
  mapping between units and record cells.
- **No `inFence` flag (revised with Gordon, 2026-10-31).** An earlier version of EXR-2
  claimed spans inside language-named unbraced fences and flagged them `inFence`. EXR-2
  decision 2 now never claims a span inside any fence, which is what QNR does (it parses
  CommonMark inline code and never sees a span in a fence), so the scanner and QNR agree on
  fences and no flag is needed. A conformance corpus of tricky spans (multi-backtick spans,
  indented code) still compares QNR with the scanner and classifies every difference (B2).

## Out of scope

- Single-cell execution in QNR; changing QNR caching semantics.
- Julia freeze behavior (`canFreeze` is recorded, not acted on).
- The percent-script (`.jl`) claim path.
- Changes to how Julia cells are presented to Quarto 1.

## Exit criteria

- With the new options absent, QNR and the engine are byte-identical to before.
- A Julia run in record mode yields a record whose units align with the core
  scanner, including inline spans, and a span in a language another engine owns is not
  evaluated by Julia, and neither is a span in a language no engine owns. A document
  whose units QNR does not all run (nested cells, the B2b span cases) still yields a
  record, with no cell for those units, which present as their source (B5b), and
  renders. A malformed notebook fails the render with a clear message.
- The parity report exists and every divergence is classified; the flip happened
  only if none is unaccepted. Otherwise Julia ships additive-only and the plan
  records why.

## Risks and open questions

- **Span discovery disagreement.** QNR sees only CommonMark inline code; the scanner
  claims spans in prose and the document\'s own front matter and never inside a fence, so
  fences do not differ (the `inFrontMatter` flag handles front matter). Measured by B2b: the
  two differ on a double-backtick span, a tab after the language token, a backslash-escaped
  opening backtick and a span in indented code. Handled in B5b by pairing on content in order;
  the one residual risk is the known limit there (identical code, an unrun unit first).
- **Cell expansion.** `expand` cells produce several output cells for one unit, each
  with its own options. An expansion attaches to the owning unit as extra outputs tagged
  `quarto_expansion` (decided 2026-11-01; B4a landed it: a marker output carrying the
  expansion's source and `#|` options, then its tagged outputs). Unverified against a real QNR
  run with `expand` cells until B5.
- **Python and R cells under QNR.** QNR also executes them (PythonCall, RCall) and
  adds prefix cells; under q2 resolution those languages normally belong to
  other engines, so `handledLanguages` (the complement of ownership) makes this path
  inert for a language another engine owns, and, with B1b, for the language of a span no
  engine owns. **Open for Gordon:** a *cell* in a language no engine owns (for example a
  `{python}` cell in a Julia document with `engine: julia` and no Python engine) is not
  ceded: `handled_languages_for` adds only languages owned by another engine, so QNR runs
  the cell, as in Quarto 1, but Julia's view does not own it and the record has no unit
  for it. The output shows live and not in a replay. This is a known limitation, documented
  rather than fixed, because ceding such cells would make them stay literal and differ from
  Quarto 1 (settled arbitrarily, Gordon 2026-10-31: revisit if wrong). Confirm in A0.
- **Nested cells.** QNR keeps its top-level, three-language rule, so it does not run
  `{julia}` cells inside blockquotes or lists, which the resolver sees. Measured (B5b): QNR
  leaves such a cell as plain text in a markdown cell with no annotation. The unit gets no
  record cell and core presents it as its source, so it renders and does not execute, as in
  Quarto 1\'s Julia engine.
- **Double presentation cost.** Until the flip, Julia presents in TS and core
  builds a record; a copy of a large notebook is held. Measure with `large-payload`.
- **Cache interplay.** A QNR cache hit must return annotated cells; the cache key
  and schema bump above cover it, and `cache_manifest_invalidation_test.jl` should
  gain a case.
- **Fork workflow churn.** A QNR fork commit, an engine fork commit with the new pin,
  and a subtree pull into q2 are three steps across three repositories; record the
  commit ids in this plan as each lands. The forks diverge from upstream (QNR is
  already 4 commits behind `upstream/main` as of 2026-10-29), so a rebase is a recurring
  cost until the changes are upstreamed (a follow-up outside every plan).
- **`[sources]` needs Julia 1.11 or later.** If q2 users run older Julia, use the
  `Pkg.add` route (A-pre).
- **Fixture drift 0.18.2 to 0.18.6.** Upstream changed output and stderr ordering; the
  parity goldens (B3) must be generated against the pinned fork commit, not 0.18.2.
