## Open decisions for Gordon

Settled on 2026-10-02 (Gordon answered the first round; recorded so the next agent does not re-ask):
- **Menu semantics (D-1):** on a book page, typst/pdf/epub "Download as" downloads the **whole book**, and a secondary **"This chapter only"** item downloads the active chapter alone (the R7 stage-1 path, unchanged). docx/pptx stay chapter-only and silent (Q-5-33, settled in R7).
- **EPUB (D-2):** in scope for this phase; EPUB gets no stage 3 (an EPUB download has no viewer).
- **Active page that is not a book chapter (D-3):** chapter-alone, if possible. The wasm path has no clear way to render a `.qmd` outside the book's render list as part of the book, so such a page is rendered alone as today, with no warning (it is a page of the project, not of the book). The plan tests what really happens for each kind of non-chapter page (see Tests first) and reports the result in the Handoff log.
- **Anchors (D-4):** a Rust-computed chapter map plus PDF-outline navigation, with no `typst.lua` edit. Detail in R10.
- **Size guard (D-5):** no new cap beyond R2's mount limits; per-chapter progress and cancel; no confirmation before a long render.
- **Captures for a whole book (D-6, Gordon, 2026-10-02): every chapter gets its own recorded results, keyed by path.** The point: a collaborator runs code in another chapter and publishes the results; rendering the book from a different chapter shows their new results in their chapter. The export takes `captures_by_path: { [projectRelativePath]: Uint8Array }` (the gzipped `EngineCapture[]` each path already has in the project's `captures` sidecar; the host fetches them at click time with `getBinaryDocById`, one per chapter that has a `captureDocId`), and each chapter's pause pipeline receives only its own entry. Facts the design rests on (read from the code when this was decided): the request path splices with `CaptureSpliceStage` (`stage/stages/capture_splice.rs`), which is fail-soft and keyed by `(structural_hash(cell), occurrence_index)`, **not** `ReplayEngine`'s hard-failing byte check; so a wrong capture does not fail a render, it silently gives an identical-looking cell in another chapter the wrong output, which is why captures must be per chapter and never shared. The stage also writes a capture's supporting files into the document's own directory and folds the capture's includes into that document's metadata. The pause builders take no captures today (`build_pandoc_pipeline_pause_stages`, `pipeline.rs:715`), so without a task here the book path would splice nothing, not even for the active chapter.

**D-6 re-checked against the code (2026-10-02 planning pass, no conflict).** Findings that shape the tasks, none of which changes the decision:
- The host collects the bytes the way `useActiveCaptureBytes` does for one file (`hub-client/src/hooks/useActiveCaptureBytes.ts`: `captures?.[path]?.captureDocId`, then `getBinaryDocById(docId)` from `@quarto/preview-runtime`, `content` is the gzipped `EngineCapture[]`), once per chapter, in parallel, **before** the export call. The export's own VFS snapshot is taken when the call starts (`render_pandoc_request`, `wasm-quarto-hub-client/src/lib.rs:~1629`), so captures and VFS can differ by the fetch latency; that is harmless because splicing is fail-soft (a stale capture splices what still matches). The `captures` sidecar keys are the paths the editor uses (`currentFile.path`), the same strings the export receives as `path`; the Rust side must key `captures_by_path` on the chapter's project-relative, `/`-normalized path and convert from the VFS absolute path (`/project/ch1.qmd` to `ch1.qmd`) in one tested helper.
- Parse each chapter's gzip when its turn comes and drop the parsed `Vec<EngineCapture>` before the next chapter; `parse_capture_from` (`lib.rs:~1467`) takes one blob, so the book path calls it inside the loop (a hook or a closure from the wasm crate), never for all chapters up front.
- The capture stage materializes a capture's supporting files with `runtime.file_write`-style calls at `doc_ast.path.parent()` (`capture_splice.rs:~182-200`). In the export the runtime is the click-time **snapshot**, so these writes never reach the live VFS; and the chapter loop's `doc_ast.path` is the chapter's own path, so each chapter's files land in its own directory (D-6(c)).
- **Those files are only mounted if the request's `resource_refs` walk knows the chapter's directory** (next section, "Chapter-relative resources"); this is a new task, not covered by the earlier text.
- The "open item" (engine includes of later chapters dropped by the merge): **does not matter for the request path.** `fold_capture_includes_into_meta` writes `meta.rendered.includes.*` (`capture_splice.rs:75`); the only reader of that key is the HTML template (`template.rs:1178`), and the pandoc profile excludes `apply-template`/`render-html-body`; `PandocPrepareStage` and `PandocWriteStage` never read `rendered.includes` or `ctx.includes`. Native has the same first-chapter-only seeding (`BookLevelState`, `single_file_render.rs:140-175`) and the same irrelevance for typst and EPUB. Record it, add one regression test (a capture with `includes` in chapter 2 does not change the request), and write no code for it.
- `unexecuted_cells` is a field of `RenderContext` that `ChapterPauseState` does not carry (`pipeline.rs:1374-1409`); `render_chapter_paused` must read `ctx.unexecuted_cells` before `extract_from` (or the struct gains the field, like `execution_skipped`) and the driver sums.

Still open (recommendation first; Gordon decides):
- **Q-9-1 — the book request's `job_id` ignores the active chapter.** Recommendation: yes. The whole-book request is the same bytes whichever chapter is active, so the active chapter must not enter the request; it travels only in the response envelope (`stats.book`). Two chapters of one book then share a job id and the host may reuse a cached output. Confirm that sharing is wanted before H8 caches PDFs by job id.
- **Q-9-2 — failing chapters.** Native fails the whole render if any chapter errors (`render_chapter_paused` returns `Err`). Recommendation: the same in the browser, reported as the failed chapter's diagnostics with its file name (a book with one broken chapter does not download). The alternative, skipping the broken chapter with a warning, would silently produce a book that native refuses to make.
- **Q-9-3 — native bug found while planning: images in a subdirectory chapter are mis-pathed in a native single-file typst/EPUB book** (reproduced with `target/debug/q2 render . --to typst` on a book with `sub/two.qmd`; details in "Chapter-relative resources"). `![](local.png)` in `sub/two.qmd` becomes `image("sub/local.png")` and `_book/` gets no `sub/` directory, so the file is not there for typst; `![](/img/a.png)` becomes `sub/img/a.png`, which exists nowhere; the typst compile stops on the first missing file with `Q-21-3` (file not found, searched at `_book/sub/img/a.png`). Chapters at the project root work. The browser request has the same `.typ` text for these images, but its page sits at the project root, so `sub/local.png` resolves there once the collector mounts it; the site-root image would still be wrong. **Recommendation:** R9 does not touch native output (its guard says native is unchanged), mounts subdirectory chapters' local images correctly, and keeps site-root images in subdirectory chapters out of its parity fixture; Gordon files one braid strand for the native bug (a bug outside every plan), whose fix then applies to both paths. Alternative: fix the double-prefix at its root (the Lua `resourceRef` prepends the chapter dir to a target the Rust link rewrite already made page-relative) inside R9, which changes native output and needs its own review.
- **Q-9-4 — "no size cap" is not literally true.** R2's mount limits still apply to a book (`resources/pandoc-wasm.json`: `limits.image_bytes` 25 MiB, `limits.total_bytes` 300 MiB for all `resource_refs` plus files). A book with many large images stops with an error naming the file that crossed the limit (`crates/quarto-core/src/pandoc_request/resources.rs`, "collection stops at the size limits"), before any pandoc run. **Recommendation:** keep it: the limit is the host's mount guard, the message is clear, and raising it is a host decision (H1). Confirm that "no new cap" means exactly this.

## Overview

Today a book chapter downloads as the active page alone (R7 stage 1). For the formats native consolidates into one file (`is_supported_format`: html, typst, epub, `project/book/project_type.rs:38`; of the downloadable formats that is typst, hence pdf, and epub) the target is the whole book. Native does this in `run_with_book_support` (`project/orchestrator.rs:1013`): Pass 1 and `pre_render`, then `render_book_single_file` (`project/book/single_file_render.rs:187`) renders each chapter through `Normalization` with a paused pipeline, merges them (`merge_book_chapters`, which stamps `quarto-book-item-*` on every heading), runs the Crossref phase alone, applies the deferred citeproc once, and runs the unchanged tail. This phase makes the same sequence available in the browser, ending in a `PandocRequest` instead of a pandoc process.

### Shape

- A new `ProjectPipeline` method (generic impl, ungated) runs `pass_one` and `pre_render` (as `run_book_single_file_merge` does, `orchestrator.rs:1088-1110`), then the shared core, and returns a `PandocRequestOutcome` plus the book info; `render_project_request` (`pandoc_request/render.rs:230`) calls it when the project is a book, the format consolidates and the scope is "book". The renderer type from R7 (`RenderToPandocRequestRenderer`, `project/pass2_renderer.rs:1397`) renders one page; a whole book is not a per-page Pass 2, so the book path does not go through `Pass2Renderer::render`. Instead the new method owns the chapter loop, as `run_book_single_file_merge` does natively.
- Chapters render **one after another** on the main thread (wasm is single-threaded). Per chapter the loop holds only its paused `Pandoc` and the small extracted `ChapterPauseState`; the per-chapter `RenderContext` is torn down before the next chapter (`render_chapter_paused` already does this). Every chapter's context sets `execution_policy = ExecutionPolicy::None` (the browser has no engines; `build_request_in_context` does this for single documents, `render.rs:167`) and receives only its own captures.
- The request is built from the merged document exactly like a single document: the same `ctx.prepare_options` (`collect_resources: true`, the share root as temp root), `PrefetchRemoteImagesStage`, `PandocPrepareStage`, and `resource_refs` collected from the merged AST (R2's limits apply to the sum over all chapters). The merged document's synthetic input path is the project root plus the book's output stem (`book_output_stem`, `project/book/config.rs`), so `doc_dir` is the project root, as natively. **Image targets are not yet page-relative when chapters merge** (the earlier draft said they were; `LinkRewriteTransform` is a Finalization transform and chapters pause after Normalization): the merged document's own Finalization pass rewrites them once, against the website-mode resolver the core installs for the synthetic page (rooted at `project.dir`, as R7's renderer does), and the chapter directory is applied afterwards by the vendored Lua, which is what "Chapter-relative resources" below mirrors for the mounted files.
- Cancellation/snapshot (R6, D8.5): the click-time VFS snapshot already backs every Rust read of one export call, and the call is one async call tagged with the click id by hub-client, so a superseded whole-book call is discarded by the existing check. A cancel that should also stop the work is delivered through the progress hook (see "Progress and cancel"), not through the runtime.

### Seam facts (verified by reading the code, 2026-10-02)

- **Where the shared core splits.** `render_book_single_file` (`single_file_render.rs:187`) runs: per-chapter paused render (`render_chapter_paused`, `..=Normalization`, `defer_citeproc = true`) and accumulation of artifacts/diagnostics; `merge_book_chapters`; `normalize_authors_meta`; `resolve_cross_chapter_links`; book metadata (`single-file-book`, `top-level-division`, `toc`, `epub-cover-image`, `:305-362`); output-path and resolver setup (`:364-392`, the first part of which is native-only); the merged `RenderContext` (`:394-407`); **a Crossref-only pass** (`for_range(Crossref..=Crossref)`, `:446-451`); **citeproc** on the merged AST, skipped when `citation-location: margin` (then the bibliography/csl paths are rebased root-relative instead, `:470-495`); then the **finishing pass from `Navigation`** (`build_pandoc_pipeline_finishing_stages(TransformPhase::Navigation, ..)`, `:527`), `finalize_rendered_output` (native only). The core is everything up to and including the finishing pass; it returns the finished `RenderedOutput`, the context's diagnostics, `execution_skipped`, the summed `unexecuted_cells`, and (wasm) `ctx.pandoc_request`.
- **What `ChapterPauseState` carries** (`pipeline.rs:1374-1409`): `artifacts`, `diagnostics`, `project_index`, `resource_resolver`, `ref_type_registry`, `options`, `includes`, `pipeline_profile`, `observer`, `user_grammar_provider`, `resource_report`, `execution_skipped`. It does not carry `unexecuted_cells` (add), `pandoc_request` (not needed: the chapters never reach the prepare stage), `crossref_index`, `document_profile`, or any `prepare_options`; the per-chapter context must **not** get `prepare_options`, only the merged one. The per-chapter `RenderContext` is built with no `project_index` and no `resource_resolver` (`ChapterPauseState::new` leaves them `None`), so **no link or image rewriting has run on a chapter when it is merged**: `LinkRewriteTransform` and `ResourceCollectorTransform` are `Finalization` phase (`link_rewrite.rs:108`, `resource_collector.rs:78`), after the pause. The merged document's own Finalization pass rewrites links and images once, relative to the page the merged document pretends to be.
- **`pass_one` and `pre_render` run on wasm for a book.** `run()` has done this since R7 (the book chapter vitest `renders the active chapter of a book alone` passes in the built wasm; `run_inner` calls `pass_one` (`orchestrator.rs:1507`) and the book `pre_render` in `book/project_type.rs:~80-150`, which touch only `ProjectContext`, the index and `runtime`). `pass_one` on wasm is the sequential `pass_one_dispatch_async` (`:2162`) over **every project file**, not only chapters; the Pass-1 profile cache is a transparent miss on wasm (`profile_cache.rs` header: `cache_get` defaults to `Ok(None)`), so every click re-parses every project file's head. That is today's cost for any project page and the book adds none to it.
- **`apply_citeproc_filter` does not run in the browser when a bibliography or CSL file is involved.** Evidence: in the built wasm (`hub-client/wasm-quarto-hub-client`, scratch vitest, not committed), `---\nbibliography: refs.bib\nciteproc: true\n---` with `refs.bib` in the VFS returns `success: false, error: "Bibliography file '/p/refs.bib' not found: operation not supported on this platform"`, the same for a book project's chapter; inline `references:` metadata resolves fine (the `Cite` node is gone and the reference text is present). Cause: `citeproc_filter.rs:221,238` call `std::fs::read_to_string`, the unsupported stub on `wasm32-unknown-unknown`. `cargo check --target wasm32-unknown-unknown` passes (it compiles) and would not have caught it, which is why the first test below is a runtime one. This also affects today's single-document and chapter-alone paths whenever `citeproc: true` or `filters: [citeproc]` meets a `.bib`/`.json` bibliography or a `csl:` file (documents with bibliography metadata but no citeproc switch leave `Cite` nodes for pandoc and are unaffected). `base_dir` is already threaded for relative resolution (bd-oqoozmtr); the missing piece is a runtime. `pampa` already depends on `quarto-system-runtime` (`unified_filter.rs:21`), so the fix is to give `apply_citeproc_filter`/`load_csl_style`/`load_bibliography` a `&dyn SystemRuntime` and read through it. Callers to update: `unified_filter::apply_filter` (`:234`, has `runtime`), `single_file_render.rs:499`, `book/bibliography.rs`/`book/citeproc.rs` (they call `load_csl_style`), and the pampa unit tests.
- **Memory held at once, by reading the code.** The wasm export holds: the click-time VFS snapshot (a full clone of every project file plus a few MB of bootstrap SCSS, `wasm.rs:294`; today's cost for any click); `chapters: Vec<(BookRenderItem, Pandoc)>` with all N paused ASTs until `merge_book_chapters` consumes them (it moves blocks; peak is about one AST copy, not two); the merged AST; then `pandoc-prepare` serializes the merged AST to `pandoc-input.json` bytes (a second, usually larger, copy) next to the `resource_refs` bytes (every image of every chapter, capped at 300 MiB by `limits.total_bytes`); the envelope then copies those bytes into `Uint8Array`s (`request_files_to_js`, a third copy, before the Rust request drops). Per-chapter `RenderContext`s and parsed captures are dropped each iteration (`render_chapter_paused` returns only the AST and the small state); each chapter's `SourceContext` is dropped too, which is why chapter diagnostics need the handling in the next bullet. Nothing in the loop is quadratic in N except `resolve_cross_chapter_links` (a map lookup per link) and the Pass-1 pass over all files. The measurement task records the real numbers; nothing here suggests a cap is needed before they exist.
- **Chapter diagnostics lose their source context.** `render_book_single_file` collects every chapter's `DiagnosticMessage`s into one `Vec` and the merged `DocumentAst` carries `SourceContext::new()` (`:422`, the "known scope gap" comment): a warning or error located in chapter 3 resolves its span against no file. The export's `diagnostics_to_json(&outcome.diagnostics, &outcome.source_context)` (`lib.rs:613`) takes one context. For Q-9-2 ("the failed chapter's diagnostics with its file name") and for ordinary warnings, each chapter's diagnostics must be converted with that chapter's `SourceContext` before it is dropped, or the outcome must carry per-diagnostic contexts; the plan's task below does the former via a per-chapter `ChapterDiagnostics { file, diagnostics, source_context }` list that the wasm wrapper converts.

### Chapter-relative resources

Native: `merge_book_chapters` prefixes each chapter with the `quarto-file-metadata` markers (`merge.rs:~100-135`, `{resourceDir}`), and the vendored `resourcerefs.lua` rewrites every relative `Image.src` to `resourceDir/src` inside pandoc (a leading `/` is stripped: `common/paths.lua:4-24`). So the `.typ` text carries `sub/local.png`. The browser request builds `resource_refs` in Rust from the merged AST **before** that Lua runs: `pandoc_write.rs:1177-1184` collects every `Image` target in the merged AST and calls `collector.add_image(&doc_dir_abs, target, ..)` with the single document directory (the project root for a merged book). A chapter-relative target `local.png` in `sub/two.qmd` is therefore looked up at `<root>/local.png`, not `<root>/sub/local.png`, and silently not mounted (pandoc then reports `Q-11-1`, or typst fails to compile). The same gap hides capture supporting files (D-6(c)) and chapter-relative `bibliography`/`csl` for margin citations.

Fix (task below): the walk tracks the current chapter directory from the same markers (or, equivalently, from the `quarto-book-item-file` attribute on each heading) and mirrors `resourceRef`: a target beginning `/` or a URL is unchanged, anything else is resolved against `<doc_dir>/<resourceDir>`. The tested cases: root chapter, subdirectory chapter, `../img` from a subdirectory (normalized), a site-root image in a root chapter, capture files in a subdirectory chapter. The Rust walk must agree with the Lua on every string, so the test compares the set of mounted paths with the images pandoc actually opens (replay through real `pandoc` natively, reading the `--verbose` log or checking `Q-11-1` warnings are absent).

### Progress and cancel

Chapters render on the main thread in one macro task: wasm futures that never await a JS promise run to completion without yielding, so neither a status update nor an `AbortSignal.abort()` can be delivered during the loop. The loop therefore awaits a host hook between chapters. Shape: an ungated trait in `quarto-core` (`BookRenderHooks`, `#[async_trait(?Send)]`) with `before_chapter(index, total, file) -> Result<(), Cancelled>`; the wasm crate implements it with the optional `onProgress(i, n, file)` JS callback (awaited if it returns a promise, so the host can `await new Promise(r => setTimeout(r))` to let the browser paint) and a check of the call's `AbortSignal.aborted` after the await. `SystemRuntime` stays unchanged. Native passes no hooks. A cancel returns an outcome with `error: "cancelled"` and no request; the host already discards a superseded call.

## Decisions

- The whole-book path is chosen inside Rust. The export gains an optional `options.scope: 'auto' | 'chapter'` (default `'auto'`); `'auto'` means whole book when the project is a book, the format consolidates (typst, pdf, epub), and the active file is a chapter in `project.book_render_items`; otherwise the active page alone. The response envelope's `stats.book` says what happened: `{ scope: 'book' | 'chapter', chapters: N, active: <index or null> }` and, for `scope: 'book'`, the R10 chapter map (R10 defines the full shape, including what `active` indexes; R9 ships `scope`, `chapters` and `active` only). The host never re-derives this.
- `scope: 'chapter'` is exactly the R7 stage-1 behavior and stays the path for docx/pptx and for the "This chapter only" menu item.
- Part and appendix dividers have no file; `merge_book_chapters` already handles them from `item.text`. `index.qmd` is an ordinary first chapter when listed in `book.chapters`, so it is located like any chapter.
- The merged document gets the same metadata the native core sets (`single-file-book`, `top-level-division: chapter` for typst/pdf, `toc: false` for typst, `epub-cover-image` from `book.cover-image` for EPUB: `single_file_render.rs:~300-345`). These move into the shared core unchanged so the two targets cannot drift.
- `PandocRequestInput` gains `scope: BookScope` (`Auto` default, `Chapter`) and `captures_by_path: BTreeMap<String, Vec<u8>>` (gzipped blobs keyed by project-relative `/`-path; the existing `captures` stays for the single-document path); the book method takes the same fields. Gzip parsing happens per chapter inside the loop (`parse_capture_from` moves from the wasm crate into `quarto-core` so native tests can drive it, or the wasm crate passes a closure; the task chooses, preferring the move).
- The shared core's inputs that `RenderToFileOptions` carried become a small ungated `BookRenderOptions { engine_registry_override, execution_policy }`; the native caller builds it from its `RenderToFileOptions`, the wasm caller sets `execution_policy = None`.
- Progress and cancel use an ungated `BookRenderHooks` trait (see "Progress and cancel"); no `SystemRuntime` change.
- Chapter diagnostics keep their own `SourceContext` (per-chapter list on the book outcome); the merged document keeps `SourceContext::new()`, the existing known gap, unchanged for native.
- Native must not change. The refactor is verified by the existing book tests plus a before/after byte comparison of the `.typ`/`.epub` content of the book fixtures (Tests first).
