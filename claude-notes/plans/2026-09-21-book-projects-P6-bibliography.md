# Plan: Unified bibliography for multi-file HTML (book-projects P6)

**Date:** 2026-09-21
**Epic:** [`2026-09-21-book-projects-epic.md`](2026-09-21-book-projects-epic.md)
**Design (authoritative):** [`../designs/book-projects-architecture.md`](../designs/book-projects-architecture.md) §9
**Q1 reference, mechanism now confirmed, not just "problem shape":** `book-bibliography.ts`'s `bookBibliographyPostRender` (read in full, 316 lines, alongside `book-crossrefs.ts` for comparison). It **is** a DOM postprocessor — same forbidden family as crossref resolution — but a narrower one than initially assumed (see Decisions below for exactly what it does and doesn't do).

## Overview

**Revised after tracing Q1's actual mechanism (previously this said "reuse whatever Q2's existing citeproc machinery already tracks per document," which turned out to be false — nothing is tracked today; see below).** Q1's own bibliography merge is meaningfully narrower than its crossref one: it merges the reference *list* project-wide but **never rewrites in-text citation marker numbers** — only their hyperlink targets. That means, unlike P5's crossref mechanism, this phase does **not** need a deferred/unresolved-placeholder AST node (`CrossrefResolvedRef`'s equivalent) — citeproc's normal per-chapter resolution can stay exactly where it runs today. What's actually needed is smaller: a new serializable per-chapter citation manifest threaded out to `RenderContext`, reused through P5's existing pause/aggregate/resume shape, and one merged bibliography built via `quarto-citeproc`'s own in-process `Processor` (an improvement on Q1's approach of shelling out to a fresh `pandoc --citeproc` subprocess with a synthetic `nocite:` document).

## Decisions

- **This phase's mechanism is multi-file-HTML-specific because there's no single merged document to run one citeproc pass over.** A review pass found the same underlying problem (Q2's citeproc runs per-chapter, before Normalization, not once over a merged whole) also affects single-file merge — but there, P2 fixes it completely by deferring citeproc to one pass over the assembled document (design doc §6), getting correct in-text numbers for free, no dedup/disambiguation-seeding logic needed. That trick isn't available here: multi-file HTML produces N separate output files, so each chapter's own citeproc pass must still run per-chapter, which is exactly why this phase needs the registry-based, list-only merge below.
- **Reuse P5's pause point exactly** (after Navigation, before Finalization, same held `Vec` of per-chapter checkpoints) — do not introduce a second, citation-specific pause.
- **No per-document citation tracking exists in `quarto-core` today — this is new plumbing, traced against real code, not assumed.** `quarto_citeproc::Processor` (`crates/quarto-citeproc/src/types.rs:249-272`, the only thing holding resolved references/citation order) is constructed, used, and dropped entirely inside `apply_citeproc_filter` (`crates/pampa/src/citeproc_filter.rs:69-129`), called from `UserFiltersStage` — well before `AstTransformsStage`/P5's pause point even runs. `quarto-core` never sees it; only the mutated AST comes back (`Cite` inlines already replaced with resolved text, a per-chapter bibliography `Div#refs` already written). Add a new field to `RenderContext` — a `ChapterCitationManifest` (cited reference ids, or the already-`Serialize`-able `Reference`s themselves) — populated by `apply_citeproc_filter`/`UserFiltersStage` during each chapter's own *unchanged* citeproc pass, the same shape as `crossref_index` today. P5's per-chapter owned struct (its `Vec` of held checkpoints) carries this forward exactly like `ChapterCrossrefInventory`.
- **The citeproc-reordered-into-`.post` edge case gets a real diagnostic — resolved with the user (fifteenth pass), previously left unowned.** `filter_resolve.rs`'s ordering logic can place citeproc into `UserFiltersStage::post` (after `AstTransformsStage`, i.e. after this chapter's `ChapterCitationManifest` would need to have been captured) if a user's `filters:` config lists citeproc after an explicit `quarto` sentinel. For an ordinary single document this is harmless (citeproc still runs, just later); for a book-merge or multi-file-HTML book chapter specifically, it means that chapter's citations silently never reach the manifest — the merged bibliography would be missing that chapter's references with no error. **Decision: detect this at the point this phase resolves each chapter's filter list and emit a diagnostic** naming the chapter and explaining that citeproc must resolve in `.pre` for its citations to be included in the book-wide merge — don't attempt to also support the `.post` ordering (no test coverage, no design work here to make the manifest-capture point conditional on where citeproc lands).
- **Q1's actual mechanism, confirmed by reading `book-bibliography.ts` directly**: per chapter, it structurally collects cited reference ids from each already-rendered chapter's `data-cites` HTML attributes (`book-bibliography.ts:158/309-315`), rewrites each in-chapter citation's hyperlink `href` to point at the shared refs chapter (`:161`), and *hides* (not removes) that chapter's own local `#refs` div. It then regenerates **one** merged bibliography fragment by shelling out to a **fresh `pandoc --citeproc` subprocess** with a synthetic markdown document whose front matter lists every deduped cited id via `nocite:` (`generateBibliography`, `:254-299`), and splices the result into the designated refs chapter. **Q2 does this natively instead**: dedupe cited ids across chapters' manifests during Pass 3's aggregation step, then build the merged bibliography by invoking `quarto-citeproc`'s own in-process `Processor` directly over the union — no subprocess, no synthetic document.
- **Traced `quarto-citeproc`'s actual public API to confirm this is buildable as described, not just plausible — and found one real refinement needed.** `Processor::new(style)` → `add_references(refs)` → `generate_bibliography_to_outputs()` genuinely needs no document/`Cite`-walking (`crates/quarto-citeproc/src/types.rs:294,442,615`) — confirmed a document-free path exists. But `generate_bibliography` reads two pieces of state it doesn't compute itself: `citation-number` values (from `get_initial_citation_number`, `types.rs:455`, normally populated by processing citations in document order — the rendered citation-number path falls back to blank/`Output::Null` for every id if never called, which is wrong for numeric CSL styles; a review pass found the previously-stated `i32::MAX` fallback is real but belongs to a different code path, bibliography *sort-key* comparison, not the render path — the conclusion that these calls are mandatory is unaffected) and disambiguation state (year-suffix/et-al, populated by `process_citations_with_disambiguation`, `types.rs:1015`, not computed by `generate_bibliography` itself). Both entry points are already `pub` and document-free — they take a bare id or a synthetic one-item `Citation`, not an AST. **The correct merge sequence**: aggregate each id's first-cited-across-chapters order (a free byproduct of walking chapter manifests in book order) alongside the dedup, then on one fresh `Processor`: `add_references(refs)`, call `get_initial_citation_number(id)` once per id in that order (numeric styles), call `process_citations_with_disambiguation(&[one synthetic Citation per id, same order])` once (year-suffix/et-al disambiguation), then `generate_bibliography_to_outputs()`. Skipping the middle two calls would silently produce wrong output the first time a real book uses a numeric CSL style or has two colliding author+year references — this is not optional polish, it's part of the mechanism.
- The merged bibliography is injected as real `Block`s into the `book.references`-designated chapter's AST (identified via `BookRenderItemKind::References`, added in P1) during that chapter's Finalization resume, **replacing** whatever bibliography div citeproc's own unchanged per-chapter pass already generated there (a real AST removal — an improvement on Q1's CSS-`display:none` hide, since Q2 has full AST control and Q1 only has a rendered DOM to hide things in).
- Each chapter keeps its own in-body inline citations rendering normally (author-date or numeric, per the document's citation style) — only the trailing reference-list block is unified; Q1 does the same (only ever rewrites hrefs and hides the local list, never touches inline citation text).
- **A real gap found by a nineteenth-pass review: every citing chapter would get its own duplicate, non-unified local bibliography, not just the designated references chapter — not previously caught by passes 7/8/12/15/16-18.** `apply_citeproc_filter`'s own `insert_bibliography` (`crates/pampa/src/citeproc_filter.rs:591-623`) auto-appends a fresh `#refs` div at the end of the document, with *that chapter's own, unmerged* bibliography, whenever a chapter has citations but no explicit `{#refs}` div already in its content — which is the common case for an ordinary book chapter (it cites sources but has no reason to declare its own references div; only the designated `BookRenderItemKind::References` chapter does). Since P6 deliberately leaves each chapter's own citeproc pass unchanged (this section's whole premise), every such chapter would silently gain a duplicate, partial, non-deduplicated local bibliography *in addition to* the correct merged one in the references chapter — directly contradicting this epic's "unified bibliography" goal and its own "never a silent, wrong... fallback" principle. **Fix, resolved with the user: use the existing `suppress-bibliography` metadata key, not new plumbing or post-hoc AST surgery.** `CiteprocConfig.suppress_bibliography` (`citeproc_filter.rs:44`, read from metadata at `citeproc_filter.rs:711`) is a real, pre-existing, standard Pandoc-compatible option — when `true`, `apply_citeproc_filter` skips `generate_bibliography`/`insert_bibliography` entirely (`citeproc_filter.rs:120-126`) while still rendering in-text `Cite` inlines normally (that step is unconditional, `citeproc_filter.rs:110-118`). This phase sets `suppress-bibliography: true` in metadata for every book chapter *except* the one `BookRenderItemKind::References` item, before that chapter's own citeproc pass runs — mirroring the exact metadata-mutation pattern P2 already uses for its own citeproc-deferral fix (stripping `"citeproc"` from `meta["filters"]` before `UserFiltersStage` reads it), not a new filter-level flag and not generate-then-strip AST manipulation during Finalization resume. Single-file merge (P2) was never exposed to this gap at all — it defers citeproc entirely to one pass over the assembled document, so no per-chapter auto-append ever happens there.
- **Known, deliberately-not-fixed gap: numeric citation styles renumber per chapter — confirmed to be Q1's actual behavior too, not just an assumed-inherited risk.** Verified against real `quarto` with a shared citation and an IEEE-style CSL: the same paper cites as `[2]` in chapter 1 and `[1]` in chapter 2. Reading `book-bibliography.ts` directly confirms **Q1 never rewrites in-text citation marker text at all** (`forEachCite`'s per-chapter loop only ever calls `link.setAttribute("href", ...)`) — no comment, TODO, or issue reference in Q1's own source acknowledges this; it is a silent, undocumented Q1 bug, not a solved problem Q2 is failing to match. Building the fix would mean inventing a deferred-resolution mechanism for citations that Q1 itself never built and that P5 only built for crossrefs because Q2's architecture policy required an AST-level replacement for something Q1 did via DOM surgery — doing it here would make Q2 exceed Q1's own behavior, which is scope creep against "port Q1 faithfully," not a bug fix. **Document explicitly** (unlike Q1's silence) as an inherited, confirmed-identical limitation.
