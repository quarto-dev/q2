## Goal

Let a TypeScript engine (Julia, marimo, user extensions) take part in execution
records without a breaking protocol change. Core tells the engine which units it
found and which languages it owns; the engine may hand back a notebook, in the
nbformat shape EXR-4 defines, together with a self-description of what that
notebook is and the declaration of its execution-input hash rule (epic decision 35). Old engines and old cores keep working unchanged.

## Design decisions (from the epic; do not re-litigate)

- All new wire fields are optional and versioned; no npm publish of the Quarto API
  until Jupyter, Julia and knitr have exercised the contract (bd-ixz93hjp).
- **Do not edit the vendored types.** q2-only fields follow the existing
  precedent (`signal`, `htmlDependencies`): added in the host by cast, typed in
  the host's own `types.ts`, and documented for q2-native engines. The vendored
  `ExecuteOptions` and `ExecuteResult` stay a parity copy of Q1.
- The granularity declaration travels with the result, not in static engine
  metadata. The static declarations (`_extension.yml`) are checked by Q1's closed
  external-engine schema, so a new key there would break Q1
  (`external-sources/quarto-julia-engine/_extensions/julia-engine/_extension.yml`
  comments).
- `ownedLanguages` and `units` are separate wire revisions. JOL-1 (Plan 4d-B) already
  adds the Rust field `owned_languages` to `TsExecuteOptions` (the plan\'s
  `ts_protocol.rs:361` and `:391` sites) and JOL-4 (Plan 4d-C) adds the host passthrough;
  this plan adds `units`, `notebook` and `recordInfo`, and shares only the doc-comment
  correction on `handled_languages` with JOL-4. `handled_languages`
  stays unchanged. Engines choose which they read: marimo uses the positive
  `ownedLanguages` set; the Julia engine keeps passing `handledLanguages` to QNR and
  ignores `ownedLanguages` (EXR-8, decided with Gordon, 2026-10-30).
- **One unit list, scanned once (epic decision 38).** The engine-execution stage scans
  units once, on the text entering the stage before any engine runs, fills each unit\'s
  id with EXR-4\'s id function (EXR-5 Phase 2 owns that call; this plan only verifies it),
  and passes the same list to every engine through `ExecutionContext.units`. In a
  multi-engine run the text an engine receives has had earlier engines\' fences
  reconciled away, so a per-engine scan would number cells differently from the document.
  Each engine\'s wire units therefore keep the original `id` and `index` and carry that
  engine\'s own `owned` flag (epic decision 42: the stage applies no ownership filter; the
  flag comes from EXR-2\'s `view_for_engine`, which `TsEngine::build_execute_options` calls
  with `ctx.owned_languages`, because only the engine side knows its own `owns` rule),
  while `line` is re-located into the text that engine receives by EXR-2\'s `locate_units`.
- **The hash rule is declared by the engine, as data (epic decision 35).** `recordInfo`
  may carry `hashDefinition`: the engine\'s `HashDefinition` in camelCase, the same
  shape as the Rust struct that EXR-4 defines (`id`, `version`, `granularity`,
  `presentationCellOptions`, `presentationExecuteKeys`, `documentKeys`, and an optional
  `profiles` map of named alternatives; a unit names its profile in its cell metadata
  as `quarto_hash_rule`). It is versioned and optional; an engine that omits it gets the conservative default (empty
  exclusion lists, so everything counts: over-invalidates, never shows stale output).
  EXR-4 defines `HashDefinition` and `Granularity` (camelCase field names, `unit` and
  `document` as values) and EXR-7 reuses both and only puts them on the wire, so there is no
  new dependency edge (EXR-7 already depends on EXR-4). Core computes the hash; the
  hash does not depend on `outputKind`.
- Alignment contract: a record from a per-unit engine must have a count of
  annotated units equal to the core scanner count for the units that engine owns
  (each engine validates its owned units only). On a mismatch the
  engine yields no record and a diagnostic naming both counts (epic risk 1), and the
  render itself is not failed while the record is additive (before that engine\'s
  flip). Whether a mismatch may fail the render after an engine flips to core
  presentation is decided in that engine\'s flip task (decided with Gordon, 2026-10-30;
  EXR-8 sets the Julia case, nested cells that QNR does not run, and EXR-9 applies the
  same rule to marimo).
- **No offsets in v1** (decided with Gordon, 2026-10-30). A wire unit carries `id`,
  `index` (cells only), `kind`, `language`, `line`, `owned` and
  `inFrontMatter`, and no `start` or `end`. Engines work by line (QuartoNotebookRunner
  chunks carry `file` and `line`), and an offset has no safe unit: the existing source map
  counts UTF-8 bytes while the TS side slices UTF-16 strings (see the risks). An explicit
  UTF-16 offset is added later only if an engine needs one. `inFrontMatter` is true for a
  span in the document\'s own front matter (epic decision 41), which a TS engine may not
  be able to evaluate: QuartoNotebookRunner never evaluates front matter, so the Julia
  engine excludes such units from its owned count (EXR-8 consumes the flag). An explicit UTF-16 offset is added later only if an
  engine needs one.
- **No extension page yet** (decided with Gordon, 2026-10-30). The q2-only fields are
  documented in code comments beside the `signal` precedent now; a documented
  extension page for q2-native engine authors waits until Jupyter, Julia and knitr
  have exercised the contract (bd-ixz93hjp).

## Wire shape

Options (core to engine), all optional:

```json
{
  "ownedLanguages": ["julia"],
  "units": [
    { "id": "3-1a2b3c4d-unlabeled", "index": 3, "kind": "cell", "language": "julia",
      "line": 12, "owned": true },
    { "id": "1-9f8e7d6c-inline", "kind": "inline", "language": "julia", "line": 20,
      "owned": true, "inFrontMatter": false }
  ]
}
```

`line` is the 1-based line of the unit in this engine\'s `input`, which in a
multi-engine run is not the original text, so engine 2\'s lines differ from the
document\'s; core re-locates it with EXR-2\'s `locate_units` before the wire. `id` is the id
from EXR-4\'s id function (`{index}-{hash8}-{label|unlabeled}` for a cell,
`{n}-{hash8}-inline` for a span; engines may echo it back), `index` is the document-wide
cell index and `owned` says whether this engine runs the unit; `id` and `index` come from
the stage\'s one scan and `owned` from this engine\'s view of it. Ceded units are in the
list with `owned: false`. `inFrontMatter` is true only for a front-matter span and is
omitted when false. There are no byte or UTF-16 offsets in v1 (design decisions above).

`handledLanguages` is the existing field and does not change shape. Under epic decision
42 and the 2026-10-31 review, core adds the languages of spans no engine owns to it, so
that QuartoNotebookRunner cedes those spans and they stay literal; EXR-8 owns that rule
and its test, and this plan only guarantees the field reaches the engine unchanged
(`stage_handled_languages_reach_the_wire_unchanged`).

Result (engine to core), all optional:

```json
{
  "notebook": { "nbformat": 4, "nbformat_minor": 5, "metadata": {}, "cells": [] },
  "recordInfo": { "version": 1, "granularity": "unit",
                  "outputKind": "raw", "alignment": "ids",
                  "hashDefinition": { "id": "julia", "version": 1,
                                      "granularity": "document",
                                      "presentationCellOptions": [],
                                      "presentationExecuteKeys": [],
                                      "documentKeys": [] } }
}
```

`granularity` is `unit` or `document`; `outputKind` is `raw` or `rendered`
(rendered outputs also carry the `quarto_format` metadata key from EXR-4);
`alignment` is `ids` (cells carry unit ids) or `positional`. `hashDefinition` is
optional and its `granularity` is EXR-4\'s `Granularity` (the same two values); the example
values are illustrative, EXR-8 and EXR-9 supply the real ones. `outputKind` describes the
outputs only: it plays no part in the hash rule, which the declaration carries.

### Notebook reading and diagnostics (decided while implementing Phase 1b)

- **The engine's notebook is not a core record.** It is a plain nbformat-4 notebook with
  no `quarto_record_version`, no hashes and no `quarto_` cell metadata beyond what the
  engine echoes, so `record::read_record_value` (which validates core's own record
  format) would reject every real engine notebook. Core reads it leniently in
  `engine/ts_record.rs`: `nbformat` 4, a `cells` array, and each cell well formed. A cell
  names its unit with `metadata.quarto_cell_id` (the wire `id`); its kernel is
  `metadata.quarto_kernel`, else the notebook's `metadata.kernelspec.name`.
  `RecordBuilder` supplies source, ids, hashes and location from the stage's unit.
- **Alignment counts.** `ids`: annotated cells (those with `quarto_cell_id`) against the
  engine's owned, stage-numbered units. `positional`: code cells against all the engine's
  owned units in order (a unit an earlier engine's output introduced has no id: it takes
  its place in the order but is never recorded).
- **Problems are warnings, not errors.** A mismatch, an unknown or duplicate id, or a
  malformed notebook drops the record and adds an uncoded warning
  (`diagnostics::engine_record_diagnostic`, beside `engine_error_diagnostic`) to
  `ExecuteResult::warnings`, which the stage drains. Routing it through
  `engine_error_diagnostic` itself would fail the render, which this plan rules out while
  the record is additive. `--strict` promotes the warning.
- **`can_freeze`** in the record entry is the engine's launch-time `can_freeze`.

## Risks and open questions

- **Offset units (why there are none).** Verified 2026-10-30: `build_source_map`
  (`crates/quarto-core/src/engine/ts_engine.rs:688-713`) accumulates `line.len()`, which
  is UTF-8 bytes, while the TS side treats `start` as an index into the engine\'s
  JavaScript string, which is UTF-16 (`ts-packages/quarto-engine-host-node/src/mapped-source.ts:72-100`).
  I found no conversion and no non-ASCII test in `quarto-engine-host-node`. Wire units
  therefore carry `line` and no offsets.
- **Open question: does the existing source map misalign on non-ASCII input?** Probed
  2026-11-01 (a throwaway vitest, not kept): a map built with UTF-8 byte lengths over
  `"é é\nabc\nxyz\n"` and a file whose offsets are UTF-16 indexes mis-maps the `xyz` line
  through `rehydrateMappedString`, so the misalignment is real when entry lengths are bytes.
  The probe mixed its own offset units, so it shows the mechanism, not the size of the
  effect in production. It was not run end to end, and it is an existing issue outside this
  epic. Check it with a non-ASCII fixture while the host tests are open (Phase 2), and
  record the result here; fixing it, if confirmed, is separate work.
- **Masking.** Units must be computed after nested-cell masking, once, on the text
  entering the stage (`engine_execution.rs:514-537`), or display blocks create
  phantom units. A test with a nested fence pins it. The text a later engine receives
  differs (earlier fences are reconciled away), which is why only the position (`line`,
  through `locate_units`) is re-located per engine and the other fields come from the single
  scan.
- **Wire size.** A notebook with base64 figures travels over the engine-host
  pipe. Julia already returns whole notebooks to the engine process, but the host
  to core hop is new; measure with a large-figure fixture
  (`external-sources/quarto-julia-engine/tests/docs/julia-engine/large-payload`).
- **Version negotiation.** None exists; additive fields rely on ignore-unknown on
  both sides. If a future breaking change is needed, add `recordInfo.version`
  checks first.
