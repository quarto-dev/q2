# Plan: editorial marks to Word and PowerPoint, in Rust (document import P6)

**Date:** 2026-10-03
**Epic:** [`2026-10-03-document-import-epic.md`](2026-10-03-document-import-epic.md) (I3, I4, I20, I23; Findings → "The export side")
**Depends on:** P3 landed (T1 shares P3 T4's vocabulary; T7 runs P3's `finish_import`), and P1's fixtures. Independent of P4 and P5; it can run alongside them. **Unblocks:** the epic Close-out's round-trip check.
**Branch:** `import/p6-editorial-marks-export` from `feature/hub-import`.

## Why

Import (P3) turns Word's tracked changes, highlights and comments into q2 editorial marks. Rendering those marks back to docx is the other half, and today it lives outside q2, in Gordon's extension `quarto-ooxml-editorial-marks` (`~/src/quarto-ooxml-editorial-marks`, MIT; two Lua filters, 366 lines). Nothing in quarto-core converts the marks: without the extension they reach pandoc as unknown `quarto-*` span classes. The extension also has three limits that a Rust port removes:
- its docx filter runs at `post-quarto`, which for docx is **inside the pandoc subprocess** (`UserFiltersStage::post` forwards into `main.lua`, `stage/stages/user_filters.rs:159-170`; the hybrid check is `is_pandoc_hybrid` at `:59-70`), interleaved with the vendored Q1 Lua filters (its README notes the ordering limits);
- attribution stamping needs a second filter at `pre-quarto`, because only q2's Lua engine has `quarto.attribution` and source ranges;
- it doesn't know the I4 commented-range shape, so docx → qmd → docx loses comment ranges and replies.

This plan ports both filters to one Rust AST transform, **always on** for docx and pptx (I23), and adds the I4 shape.

## Where it runs

A docx/pptx render (native `q2 render --to docx`, or the hub's "Download as") runs `build_pandoc_prefix_stages` (`pipeline.rs:554`): the HTML stage list minus `PANDOC_STAGE_EXCLUDED`, with `ast-transforms` running `build_transform_pipeline` minus `PANDOC_TRANSFORM_EXCLUDED`. Then `user-filters-post`, then `PandocWriteStage` (native subprocess) or `PandocPrepareStage` (the browser's pandoc.wasm request). A transform in `build_transform_pipeline` that survives the cut therefore reaches **both** the native and the browser path, before pandoc.

What it sees: the renderer transforms are on `PANDOC_TRANSFORM_EXCLUDED` (`pipeline.rs:2611-2669`: `code-block-render`, `crossref-render`, `callout-resolve`, `panel-tabset-resolve`, `attribution-render`, …), so for docx/pptx callouts, tabsets and crossrefs are still `Block::Custom` nodes when this transform runs; pandoc's subprocess (the vendored Q1 Lua) renders them later. The walk must therefore descend into Custom slots (`ast_walk.rs:86` shows how), and marks inside them reach pandoc already converted.

`EditorialMarksOoxmlTransform` (`crates/quarto-core/src/transforms/editorial_marks_ooxml.rs`, name `editorial-marks-ooxml`, `TransformPhase::Finalization`):
- registered immediately before `resource-collector` (also Finalization), after every content transform that survives the docx cut (`cross-chapter-crossref-resolve`, `example-embed-render`; the docx survivor list is the T2.3 test, `pipeline.rs:6446`);
- self-gating: it acts only when `ctx.format.identifier` is `FormatIdentifier::Docx` or `Pptx` (`format.rs:29,31`) and returns otherwise (the early-return shape of `PanelTabsetTransform`, `transforms/panel_tabset.rs:107-121`, though that one gates on the profile);
- not added to `PANDOC_TRANSFORM_EXCLUDED`, and a no-op for the q2-preview profiles, so it needs no `Q2_PREVIEW_TRANSFORM_EXCLUDED` entry either;
- **bucket B3** ("shared post-core service; crosses the cut and runs for Pandoc too", `pipeline.rs:2691-2693`). The transform is registered for every profile and excluded for none, so adding it breaks six tests by design, all updated in T2a's commit: `BUCKETS` (`pipeline.rs:2736`, whose doc comment requires the entry in the same commit; `resource-collector`'s entry is at `:2805`) checked by `bucket_classification_is_total_over_the_html_pipeline` (`:6510`) and `neutral_core_invariant_no_b2_b4_survives_the_pandoc_cut` (`:6573`); and four exact name lists, each gaining `editorial-marks-ooxml` immediately before `resource-collector`: HTML `t1_4_html_render_profile_produces_todays_exact_name_list` (`:6176`; there it lands after `code-block-render`, `pipeline.rs:2405-2406`), revealjs `t1_5_revealjs_render_profile_produces_todays_exact_name_list` (`:6264`), the docx survivor list `t2_3_pandoc_docx_profile_produces_exact_surviving_name_list` (`:6446`; after `example-embed-render`), and the preview list `t2_5_html_preview_profile_produces_todays_preview_exact_name_list` (`:6620`). Also add a row to the bucket table in `claude-notes/designs/pandoc-hybrid-architecture.md` §6 (heading `:174`; the `ResourceCollector` row is `:196`).

**Coexistence with the extension:** once this transform has renamed the classes, the extension's Lua filter finds no `quarto-*` marks and does nothing, so a project that still lists it renders the same (T6 tests this). With attribution on, its `stamp-attribution.lua` now also has data for docx (`b6b1817e1`) and runs at `pre-quarto`, before `ast-transforms`, so it may stamp `author=`/`date=` first; T5's rule that an explicit `author=` or `date=` wins then leaves those marks alone, with the same data and the same result.

## The rules (ported from `ooxml-editorial-marks.lua`)

A mark is a `Span` or `Div` whose **first** class is `quarto-insert`, `quarto-delete`, `quarto-highlight` or `quarto-edit-comment`.

**docx** (pandoc's docx writer handles these span classes natively):
- **Insert / delete, inline:** replace the first class with `insertion` / `deletion`; keep the id, other classes and attributes (`author`, `date` become `w:author`, `w:date`).
- **Insert / delete, block:** the writer ignores Div classes, so wrap the inlines of every leaf `Para`/`Plain`/`Header` inside, at any depth, in `Span ("", [insertion|deletion], [author?, date?])`. A nested mark Div is converted on its own and not wrapped again; a `CodeBlock` is left as is. Inline marks inside the wrapped paragraphs are still converted, as the extension does (verified 2026-10-03: its filter on a `::: ++` holding `[-- ]` and `[!! ]` writes `w:ins`, `w:del` and `w:highlight`; pandoc writes and re-reads nested `insertion` > `deletion` and `insertion` > `mark`).
- **Highlight:** a **bare** `Span ("", ["mark"], [])`. Drop the id, classes and attributes, because the writer applies the highlight only to a bare span (verified: with an id or an attribute the text comes out plain). Block form: wrap the leaf blocks the same way.
- **Comment, inline (`[>> msg]`):** `Span ("", ["comment-start"], [id, author, date?]) [msg]` followed by `Span ("", ["comment-end"], [id]) []`. Other attributes have no OOXML home and are dropped.
- **Comment author:** a comment with no `author` (after stamping) gets `author="unknown"`, pandoc's own default for insertions and deletions. Without it pandoc writes a `w:comment` with no `w:author`, and pandoc's docx reader then drops the comment's start and text (verified 2026-10-03); the hub's "Download as" never stamps, so every unattributed `[>> ]` would hit this. Decided with Gordon 2026-10-03.
- **Comment, block (`::: >>`):** the message is the Div's blocks flattened to inlines by a new `blocks_to_inlines` with `pandoc.utils.blocks_to_inlines` semantics, which the Lua uses: `LineBreak` between blocks, a `CodeBlock` becomes `Code`, lists, quotes and Divs are flattened recursively (verified: Para, Para, CodeBlock, BulletList → `one LineBreak two LineBreak Code "x=1" LineBreak li`). Neither quarto-core copy has these semantics (`pandoc_filters/meta_coerce.rs:56` joins with `SoftBreak` and drops other blocks; `transforms/title_block.rs:160` joins with nothing), so T1 adds a third, tested, and leaves those two alone. The body keeps the blocks, with `comment-start` spliced at the start of the first block and `comment-end` at the end of the last. Either goes into its own `Para` when that block has no inlines (a `CodeBlock`). An empty Div gives one `Para` holding both markers. Insert, delete and highlight marks in the body are converted like marks anywhere else (the extension leaves them as `quarto-*` spans; decided with Gordon 2026-10-03). A **comment** mark in the body is not converted: it folds into the message as text and stays in the body as a plain span, its mark classes stripped (decided 2026-10-04, see the Handoff log: otherwise the extension's filter converts it a second time), so it doesn't become a second Word comment that repeats its text inside the outer range (decided with Gordon 2026-10-03, review; keeps example 05 at three comments).
- **A plain Div holding blocks and a trailing comment** (the extension's `05-comment-on-code.qmd`, a `.quarto-edit-comment-container` Div) is not a mark: its comments convert where they stand.
- **Comment ids:** always numeric, `0`, `1`, `2`, … in the order the `comment-start` spans are emitted in document order; the mark's own id is ignored for `w:id`. OOXML's `w:id` is `ST_DecimalNumber`, and pandoc writes the id verbatim (verified: `quarto-comment-1` lands in `w:comment w:id`). Deterministic (I20). This diverges from the extension, whose test 02 asserts the id `comment-id`; T6 ports that assertion as a count only. Decided with Gordon 2026-10-03.
- **Nesting:** a mark inside an insert, delete or highlight is converted independently. A mark inside a **comment's message** folds into the comment's text: the message is built from the unconverted content, with the mark classes stripped from every span in it, as `document_profile.rs` treats a comment as a leaf. For a block comment, the comment marks in its body fold too (above).
- **New, the I4 commented range:** a `Span ("", [], [])` whose content **ends in** a run of one or more `quarto-edit-comment` spans is a commented range (I4). `Space`/`SoftBreak` between the comment spans of the run is allowed and dropped (hand-written `[range [>> a] [>> b]]`; P3 never emits it). It becomes, in place of the span: one `comment-start` per comment in the run, in order, then the range inlines (the span's content minus the run), then the matching `comment-end`s in the same order. The first comment is the range's comment; the rest are its replies, sharing the range: the equal-range shape P3 T4 reads back (epic Findings, "Replies"; verified that flat `end, end` writes and re-reads as the nested shape P3 expects). Nested ranges are converted innermost first; ids still follow emission order of the `comment-start` spans in the final inline list. pandoc writes no `commentsExtended.xml`, so Word shows the replies as separate comments on the same text, not as a thread. A span with attributes, or whose comment isn't trailing, isn't a commented range: its comments are converted as inline comments where they stand. **Known ambiguity:** when a Word range ends in a point comment, P3 imports `[text [>> pt] [>> c]]`, the same qmd as "`pt` with reply `c`". Export reads it that way, so in Word `pt` gains the range and `c` becomes its reply; the qmd round-trips equal (accepted with Gordon 2026-10-03, review; P3 unchanged).
- pandoc's `paragraph-insertion` / `paragraph-deletion` classes are import-only (P3 drops them); export never emits them.

**pptx** (the pptx writer has none of these classes, verified: it writes their text plain, and PowerPoint comments are anchored to slide positions): each mark becomes one `RawInline (Format "openxml")` run (`<a:r><a:rPr …/><a:t xml:space="preserve">…</a:t></a:r>`, as the Lua writes it, since a comment's text starts with a space; verified kept verbatim between pandoc's own runs in `ppt/slides/slide1.xml`), or for a Div a `Para` holding one, with the content flattened to text, XML-escaped. Inlines use `transforms::metadata_normalize::inlines_to_plain_text` (`pub(crate)`, `metadata_normalize.rs:128`); a Div's blocks are flattened block by block and **joined with a space** (Lua's `stringify` joins with nothing, giving `onetwo`; decided with Gordon 2026-10-03). Insert: `<a:rPr u="sng"/>`. Delete: `<a:rPr strike="sngStrike"/>`. Highlight: `<a:rPr><a:highlight><a:srgbClr val="FFFF00"/></a:highlight></a:rPr>`. Comment: italic dark red (`C00000`) text ` [<author or "comment">: <message>]`. The I4 rule is docx-only: for pptx the wrapper stays a plain Span and its comments become bracketed runs where they stand. Rich formatting inside a pptx mark is lost, as in the extension.

**Attribution stamping (ported from `stamp-attribution.lua`):** before the rewrite, for every insert, delete and comment mark (not highlights, which have no author in OOXML), when `ctx.attribution_data` is set. It is set for docx and pptx: `AttributionGenerateStage` (`pipeline.rs:370`, before `ast-transforms`, not stage-excluded) returns early unless `format_supports_attribution` (`attribution/types.rs:218`; also checked at `transforms/attribution_generate.rs:71`), which `main`'s `b6b1817e1` widened to `Html || identifier.is_pandoc_hybrid()` (docx, pptx, epub, typst and the other pandoc-writer formats), doc comment included, with the stage test `pandoc_hybrid_formats_populate_sidecar` (`stage/stages/attribution_generate.rs:242`, docx, pptx and typst). P6 does not touch the gate. The skip tests use `pdf` (`tests/integration/attribution_generate.rs:240`) and `Revealjs` (`stage/stages/attribution_generate.rs:265`), neither of them Pandoc-hybrid, and still hold; `attribution-render` and the viewer stay on `PANDOC_TRANSFORM_EXCLUDED`, so nothing else consumes the data for docx. Then call `query_attribution` (`transforms/attribution_render.rs:182`, private today; make it `pub(crate)` or move it beside `resolve_byte_range` in `attribution/resolve.rs`, don't copy it). It already resolves the `SourceInfo` with `resolve_byte_range` (`attribution/resolve.rs:27`, public) and rejects a range in another file than the blamed one and an empty range, the same checks the Lua's `lookup_range(r[1], r[2], r.file_id)` makes; The returned `AttributionRecord` is only `{actor, time}` (`attribution/types.rs:192-195`); the name is `data.identities.get(&rec.actor).map(|i| &i.display_name)` over the public `AttributionData.identities` field (`types.rs:126`), the join `AttributionLookupHandle::identities` (`handle.rs:54-60`) and `quarto.attribution.lookup` (`crates/pampa/src/lua/quarto_api.rs:509-548`) make. `AttributionLookupHandle` isn't needed. On a hit, as `stamp-attribution.lua:33-43` does: set `author` to the name when there is one, and `date` to `time` as UTC ISO 8601 (`YYYY-MM-DDTHH:MM:SSZ`, formatted with the `time` crate, already a quarto-core dependency; a `time` above 1e11 is milliseconds) even when there is no name, each only if the source didn't set it. No hit: leave the mark alone. The browser path passes no attribution data (`render_pandoc_request`), so stamping happens only in native renders with `--attribution=git`.
