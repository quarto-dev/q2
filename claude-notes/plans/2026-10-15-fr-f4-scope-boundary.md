## Goal

The last special scope paths go. A request that wants an explicit book or chapter scope, or any other per-request metadata, sends a generic `metadata` JSON object; the native route or the wasm entry builds a `RenderOverlay` from it (F1). No route, wasm option, TypeScript client or Rust signature carries a `scope` any more. The F3b adapters are deleted.

## Decisions

- **F4-D1 The wire shape.** Native route bodies and the wasm request options gain `metadata?: Record<string, unknown>` (a JSON object, the overlay's metadata); `scope` is removed from all of them. The server or wasm entry builds `RenderOverlay::with_metadata(metadata)`: native passes it as `RenderToFileOptions.overlay`, `render_book_download` takes it in its params, the wasm entries call `overlay.apply(runtime)` at the point where they create their runtime (F1's creator rule: the code that creates a runtime wraps it once, nothing downstream wraps again). Unknown keys are not validated here (it is general metadata); a non-object `metadata` is a 400 on the routes and a diagnostic on wasm.
- **F4-D2 What each client sends (FR13).** The PDF preview, in the embed (`PdfPreviewPane`) and the SPA (`PdfPane`) **and the non-embed PDF preview controller (`createPdfPreviewController` → `wasmDeps('chapter', …)`)**: `{ "book-scope": "chapter" }` (explicit, so a document's own `book-scope: book` cannot turn a PDF preview into a book; F8 later merges the CLI's `-M` overlay *under* this value, so the pane's chapter always wins). The Download menu: `{ "book-scope": "book" }` for "Download book as X"; `{ "book-scope": "chapter" }` for "This chapter only" and for the plain entry of a consolidating format; no `metadata` for other formats. The menu's entries and behaviour are otherwise unchanged (the paired entries, the stale-click notice, the captures branch for `book`); this plan changes what is passed, not what the menu does.
- **F4-D3 The captures pre-gate reads the request's metadata.** `may_render_book(key, scope)` becomes `may_render_book(key, metadata)`: the async side builds the `Format` from the key through `render_format_and_target` (`may_render_book` takes a key string; `format_consolidates_book` takes a `Format`), asks `format_consolidates_book`, and reads the request's explicit `book-scope` through F3a's `requested_book_scope` (the JSON adapter over the metadata object; FR5), the same function the resolver uses. An explicit `chapter` skips `resolve_all_captures` (exactly today's PDF-pane behaviour); anything else on a consolidating format loads them, as the book download does; the resolved scope computed inside `render_blocking` from the overlay and the target then decides whether the book branch uses them. **A request with no `book-scope` on a consolidating format deliberately loads the captures**, although the target default for one document is `chapter`: a `book-scope: book` in the document, directory or project layer (which the async side cannot see without a read) would otherwise render a book with empty captures. The price is one full capture read for every no-scope request on a consolidating format; a code comment at the gate says why, and the test below pins it. This is the metadata-based reading of the epic, not a special case: the same value drives both sides. A test pins that the PDF pane's request does not call `resolve_all_captures`, and that a request with no `book-scope` on a consolidating format does; the PDF route's key is `TYPST_PDF_KEY`.
- **F4-D4 The editor text, and where the overlay is applied on the preview route.** The route puts the request's editor text (`job.content` / `source_override`) into the overlay's `files` under the document's path, so the resolver's document layer is read from the buffer, not the disk copy (a `book-scope` edited in the buffer is honoured). No separate content parameter is added to `resolve_render_scope`. **The overlay wraps the runtime once, at the top of `render_blocking`** (`render_helper.rs:412`), as soon as the canonical `active` path is known and **before** `resolve_book_scope` (`:429`): the resolver, `render_chapter_alone` and `render_document` then all see the request's metadata and buffer. The overlay's file key must be the canonical `active` path (the overlay normalises lexically only: `overlay_runtime.rs:46-57`), the same convention `book_download` uses. This replaces F1's earlier "apply in `RealRender.render_document`" (`render_helper.rs:196`), which is too late for the resolver and invisible to a fake `RenderSeam` in the route tests; with the wrap at the top, the fake seam sees the overlay too. (`PreviewOutDir::create` runs on the raw runtime: project discovery does not read the buffer. 4.2 confirms.)
- **F4-D5 Wasm's process-wide `vfs_set_runtime_metadata` stays** (editor preview settings). A per-call `metadata` option is overlaid on top of it by F1's merge; it does not replace it.

- Cross-language: the Rust route and the TypeScript client must change in the same plan, or the embed breaks. Keep both in this plan's commits and run the browser tier if at all possible.
- `downloadController.ts` is large and its book/chapter branches carry the captures logic: change what it passes, not what it does.
- `render_helper.rs`, wasm `lib.rs` and the download TS files are hot (F3b touched them with adapters, the parity epic's plans before that): rebase carefully.
- A stale embedded SPA or a stale wasm artifact makes any manual check meaningless: follow 4.5's rebuild chain first.
