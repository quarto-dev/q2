## Design decisions (from the epic, do not re-litigate)

1. Freeze is not documented as a feature. The docs may mention that records are laid out so freeze
   can use them later, in a developer-facing note, never in the user guide as a promise.
2. The fake kernel is scripted (a table of execute requests to replies), speaks the real Jupyter
   messaging protocol through the same client path q2 uses, and needs no external install.
3. Workspace test runs are recommended to Gordon, not run unprompted; when run, the delta is reported
   against the live baseline taken at the start of this plan.
4. **Staleness is documented as the epic decided it** (epic decision 8): for a record, a prose-only
   edit does not mark it stale and does not re-execute in preview or hub; a code edit, a `#|` line,
   an inline expression or an execution-relevant front matter key does. The preview cache keeps its
   whole-input key, so this is not a promise that nothing re-runs.
5. **Span-only documents are documented as needing an engine key** (epic decision 11, as in q1):
   a document with inline expressions and no executable cell renders them literally unless **its
   own front matter** selects an engine (`jupyter: python3`, `engine: jupyter`); the same key in
   `_quarto.yml` does not make a cell-less page run, because q1 ignores `engine:` in `_quarto.yml`
   when it picks an engine and q2 follows it for cell-less pages (checked against q1 on
   2026-10-31). Escape a span you want shown as code with doubled braces.
5a. **Where a span is evaluated is documented as decision 41 settled it** (epic decision 41: which
   places are claimed): prose, attribute values and the document's own front
   matter, are evaluated; a span inside any fence (braced or not, whatever its language), inside an HTML comment, or in project-level
   metadata (`_quarto.yml`, `_metadata.yml`, extension or format defaults) is left as written. A
   span in a language no engine owns also stays as written (epic decision 42: ownership is decided
   per engine from one shared scan).
6. **One cell-opener rule** (epic decision 13): the docs describe the language token and say that
   options go in `#|` lines, never inside the braces.
7. **Positron is documented as a separate file** with the reasons in EXR-4, and the importer as
   display-only (epic decision 14).

## Out of scope

- Documenting freeze, single-cell execution, or Positron internals for end users.
- Changing code behavior; this plan only adds tests and docs. A failure found by the new tests is
  fixed in the plan that owns the behavior.

## Exit criteria

- The new end-to-end and parity tests pass on a machine with no Python, R or Julia installed.
- User docs render strictly and match the behavior the tests pin.
- The design documents and the 05-27 plan carry the amendments; no document still says freeze reuses the trace.
- The epic's checklists are reconciled and committed.

## Risks and open questions

- **Docs ahead of code.** The inline-expressions page already promises behavior; update it in the same
  commit as each behavior lands so it never lies for long.
- **Fake kernel fidelity.** A scripted kernel can hide protocol bugs a real kernel exposes; keep at least
  one engine-gated test against real `ipykernel` where the parity suite already does.
- **Doc location for records** (`.quarto/` is gitignored in many projects) may confuse users who expect to
  commit them; word the docs carefully until freeze exists.
- **Empty values differ by engine** until strand bd-30k2j00f is answered; the docs state it, and a
  cross-engine parity test must not assert equality for that case.
