## Goal

Leave the epic documented, covered end to end without external installs, and with the
design record consistent with the code:

- user docs say what inline expressions do in each engine, which documents run them (a
  span-only document needs an engine-selecting key), where records are written, what they are
  for, and what editing prose versus code does to a record in preview and hub;
- an integration test runs the whole flow (unit scan, execution, record, presentation,
  replay) against a scripted fake kernel, so CI needs no Python, R or Julia;
- cross-engine parity tests cover the new shapes;
- the design documents and the 05-27 plan no longer say things the epic reversed;
- the workspace test counts are reported against a live baseline, with every delta accounted for.

## Design decisions (from the epic, do not re-litigate)

1. Freeze is not documented as a feature. The docs may mention that records are laid out so freeze
   can use them later, in a developer-facing note, never in the user guide as a promise.
2. The fake kernel is scripted (a table of execute requests to replies), speaks the real Jupyter
   messaging protocol through the same client path q2 uses, and needs no external install.
3. Workspace test runs are recommended to Gordon, not run unprompted; when run, the delta is reported
   against the live baseline taken at the start of this plan.
4. **Staleness is documented as the epic decided it** (epic decision 8): for a record, a prose-only
   edit does not mark it stale and does not re-execute in preview or hub; a code edit, a `#|` line,
   an inline expression or an execution-relevant front matter key does. The preview cache keeps its
   whole-input key, so this is not a promise that nothing re-runs.
5. **Span-only documents are documented as needing an engine key** (epic decision 11, as in q1):
   a document with inline expressions and no executable cell renders them literally unless **its
   own front matter** selects an engine (`jupyter: python3`, `engine: jupyter`); the same key in
   `_quarto.yml` does not make a cell-less page run, because q1 ignores `engine:` in `_quarto.yml`
   when it picks an engine and q2 follows it for cell-less pages (checked against q1 on
   2026-10-31). Escape a span you want shown as code with doubled braces.
5a. **Where a span is evaluated is documented as decision 41 settled it** (epic decision 41: which
   places are claimed): prose, attribute values and language-named unbraced fences, and the document's own front
   matter, are evaluated; a span inside a braced fence, inside an HTML comment, or in project-level
   metadata (`_quarto.yml`, `_metadata.yml`, extension or format defaults) is left as written. A
   span in a language no engine owns also stays as written (epic decision 42: ownership is decided
   per engine from one shared scan).
6. **One cell-opener rule** (epic decision 13): the docs describe the language token and say that
   options go in `#|` lines, never inside the braces.
7. **Positron is documented as a separate file** with the reasons in EXR-4, and the importer as
   display-only (epic decision 14).

## Out of scope

- Documenting freeze, single-cell execution, or Positron internals for end users.
- Changing code behavior; this plan only adds tests and docs. A failure found by the new tests is
  fixed in the plan that owns the behavior.

## Phase A: tests first

- [ ] Reuse the base fake kernel from EXR-3 and its JOL-5 extensions (it exists once); add whatever
  scripted replies these tests still need: stream, `execute_result`, `display_data` (including
  `image/png`), `error`, an `execute_reply` with `status: error`, and an execution with no
  `execute_result`.
- [ ] End-to-end test, Jupyter: a document with a cell, a prose paragraph with a `{python}` span,
  and a second cell, run against the fake kernel; assert the produced record's units and ids, the
  presented markdown, and that presenting the saved record again (no kernel) gives the same markdown.
- [ ] End-to-end test, IEE value and error policy (EXR-3, decided 2026-10-29 and 2026-10-30): a span
  that errors is fatal and names the source location `file:line:col`; a statement reports "inline
  expression produced no value" (fatal); a span whose value is `None` renders the text `None`; an
  empty-string value leaves the span source in place (parity with q1; strand bd-30k2j00f); a span
  with no usable result leaves the source in place and emits a warning with the file and line, and
  the render succeeds.
- [ ] End-to-end test, replay without the engine: with the Jupyter engine unavailable, presenting a
  record succeeds (the freeze-groundwork requirement from the epic).
- [ ] End-to-end test, trace replay (epic decision 9): record a trace of a Jupyter document against
  the fake kernel, replay it with `--replay` and no kernel, and assert the presented markdown equals
  the live run; a Jupyter trace recorded before EXR-5 (so it has no record) fails with the "re-record this trace" error.
- [ ] End-to-end test, staleness (epic decision 8): record a document, edit only prose, and assert
  the record is still fresh and nothing re-executes; edit a code cell, a `#|` line and a span in turn
  and assert each marks it stale. Legacy payloads keep the byte compare (a prose edit flips them).
- [ ] End-to-end tests, span-only documents (epic decisions 11 and 42), each against the fake
  kernel, named so a failure says which rule broke:
  - `e2e_span_only_document_without_engine_key_stays_literal`: no engine key, the spans stay
    literal and no kernel starts;
  - `e2e_span_only_document_with_jupyter_key_runs`: `jupyter: python3` in the document's own front
    matter, the spans run (the kernel's language owns them, epic decision 42);
  - `e2e_span_only_page_with_project_level_engine_key_stays_literal`: `engine: jupyter` only in
    `_quarto.yml`, a cell-less page's spans stay literal and no kernel starts (the engine-resolution
    rule that keeps a declared engine on an empty scan only for the document's own front matter;
    JOL-2a).
- [ ] End-to-end tests, where a span is evaluated (epic decision 41), each against the fake kernel,
  asserting the presented markdown and that the record holds a unit only for evaluated spans. Unit
  level counterparts live in EXR-3 (`jupyter_inline_in_front_matter_is_evaluated`,
  `jupyter_inline_in_html_comment_is_not_run`, `jupyter_inline_in_display_fence_is_not_run`,
  `jupyter_inline_unowned_language_untouched`); these are the whole-flow versions, so they name
  their own tests:
  - `e2e_span_in_front_matter_is_evaluated`: a `title:` span in the document's own front matter is
    evaluated and the presented document metadata holds the value;
  - `e2e_span_in_project_metadata_stays_literal`: the same span written in `_quarto.yml` is left
    as written, and takes no span number (the next span in the document keeps number 0);
  - `e2e_span_in_html_comment_is_literal`;
  - `e2e_span_in_braced_fence_is_literal` (a `{python}` span inside an executed `{r}` fence, and
    inside a display fence);
  - `e2e_span_no_engine_owns_stays_literal` (a `{zzz}` span in a document where no engine owns `zzz`
    stays as written, the document renders, and the record has no unit for it).
- [ ] Conformance test for the token rule (epic decision 13), using EXR-2's fixtures: `{python.marimo}`
  is one language token, `{python .marimo}` is `python` plus a class, `{Python}` matches
  case-insensitively, and `{python echo=false}` is rejected with Q-2-36.
- [ ] Cross-engine parity additions to `engine_output_parity.rs`: an inline-expression case
  (strand bd-u996g8g2 asks for exactly this), a record-present case (live output equals
  present-from-record output) for Jupyter, and shape parity for a Julia record against a Jupyter record
  once EXR-8 lands. Reuse `assert_blocks_parity`; the tests skip with a note when an engine is missing.
- [ ] Record determinism: recording the same document twice with the same scripted kernel gives
  byte-identical record files (the committable-file requirement).
- [ ] Docs examples are executable: every code sample added to the user docs is either
  rendered by the docs build or covered by a test with the same text.

## Risks and open questions

- **Docs ahead of code.** The inline-expressions page already promises behavior; update it in the same
  commit as each behavior lands so it never lies for long.
- **Fake kernel fidelity.** A scripted kernel can hide protocol bugs a real kernel exposes; keep at least
  one engine-gated test against real `ipykernel` where the parity suite already does.
- **Doc location for records** (`.quarto/` is gitignored in many projects) may confuse users who expect to
  commit them; word the docs carefully until freeze exists.
- **Empty values differ by engine** until strand bd-30k2j00f is answered; the docs state it, and a
  cross-engine parity test must not assert equality for that case.
