## 0. Goal

When a Quarto 2 HTML document contains `Math` elements (inline `$…$` or
display `$$…$$`, with or without `{#eq-…}` labels), the rendered HTML
must typeset the math automatically — matching the "batteries
included" experience users have in Quarto 1, but routed through q2's
own pipeline rather than delegating to Pandoc.

Concretely, after this work:

- `quarto render foo.qmd` on a doc containing `$x^2$` produces an HTML
  page that displays `x²` rendered as math when opened in a browser.
- The user has a single user-facing knob (`html-math-method:`) to pick
  the engine and override its URL, matching Quarto 1's surface.
- The HTML writer's existing `<span class="math …">\(…\)</span>` /
  `\[…\]` markup is preserved as a publicly-described AST → HTML
  contract, so a Quarto-2 Lua filter could in principle implement
  custom math handling by manipulating those publicly-visible nodes
  (the same property our navbar rendering has).
- Hub-client (WASM) preview also typesets math live.

### Non-goals (v1)

- All five Pandoc math methods. v1 supports `mathjax` and `katex`;
  `webtex`, `gladtex`, `mathml`, `plain` are deferred (they each have
  different markup contracts; ballooning the predicate matrix on day
  one is not warranted).
- A general `JsFeature` abstraction. Bootstrap (bd-4eyf) was
  consumer #1 of the "predicate → `js:*` artifact" pattern; math is
  consumer #2 with extra requirements (inline config, content-driven
  trigger, two engines). We extract a shared abstraction once a third
  consumer arrives — not now.
- Server-side prerendering of math (e.g., `mathjax-node` ahead-of-time
  conversion). Out of scope for the renderer pipeline; a future
  optimization that can be layered on if needed.

## 1. Open question for the user

**Before I start writing code, I need one decision from you:**

> **Q1.** Should v1 support **both MathJax and KaTeX** as user-selectable
> engines, or **MathJax only** with KaTeX deferred?

Both options are tractable; my mild recommendation is **both**, because:

- The two engines share ~95% of the stage scaffolding (predicate, AST
  walk, asset registration, template-slot population). The only real
  divergence is the inline-config block and a few output-marker
  details that the q2 HTML writer already emits compatibly for both.
- Having two engines from the start forces us to keep the stage
  parameterized rather than hardcoded for one engine — which is
  cheaper to do upfront than to retrofit.
- Quarto 1 supports both, and users with `html-math-method: katex`
  already in their YAML expect it to keep working.

If you'd rather start with MathJax-only and add KaTeX later, the
plan still works — every parameterized branch becomes an `unimplemented!()`
guard until KaTeX is enabled.

**The rest of this plan assumes "both", with explicit notes wherever
the design changes if you pick MathJax-only.**

## 2. Engine landscape (May 2026)

To inform the engine choice. I am not recommending a switch away from
MathJax/KaTeX as the *default* user-facing options — I am answering
"what are we matching" and "what should the default be".

| Engine | License | Bundle (loader) | Coverage | Notes |
|---|---|---|---|---|
| **MathJax 3** | Apache 2.0 | ~1.0 MB (`tex-chtml-full`); ~150 KB (`tex-chtml`) | Best LaTeX coverage, broadest extension ecosystem (`mhchem`, `physics`, `cancel`, `ams`, …) | Async; MathJax 3 has closed the historical perf gap with KaTeX. Default in Pandoc and Quarto 1. |
| **KaTeX** | MIT | ~270 KB JS + ~23 KB CSS + fonts | ~95% of common LaTeX; macro language is limited (no asterisks in names, no variadic args — limits `physics`/some `mhchem` code paths) | Synchronous render. Good error reporting. Wide adoption (Khan Academy, GitBook, Notion, etc.). |
| **Temml** | MIT | ~80 KB (no fonts; uses MathML) | KaTeX fork that emits MathML instead of styled HTML | All mainstream browsers (Chrome ≥109, Edge, Firefox, Safari) now have native MathML. Smallest footprint, best a11y story (screen readers natively understand MathML). Doesn't work in IE. |

**Sources for the landscape survey:**

- [BigGo: KaTeX vs MathJax (2026 update)](https://biggo.com/news/202511040733_KaTeX_MathJax_Web_Rendering_Comparison)
- [Temml Comparison of TeX Coverage](https://temml.org/docs/en/comparison)
- [MathJax 3 Hacker News thread](https://news.ycombinator.com/item?id=22582343)
- [mhchem extension status across both engines](https://mhchem.github.io/MathJax-mhchem/)
- [Material for MkDocs: Math reference](https://squidfunk.github.io/mkdocs-material/reference/math/)
- [Andrew Lock: Rendering Math in HTML — MathML, MathML Core, AsciiMath](https://andrewlock.net/rendering-math-in-html-mathml-mathml-core-and-asciimath/)

### Recommendation for v1 default

**Keep MathJax as the default.** Reasons:

1. Drop-in match for Quarto 1 — existing users see no behavior change.
2. Best extension coverage; "batteries included" requires features
   like `\mathchoice`, `\substack`, full `mhchem`, `physics`, `cancel`,
   `ams` that KaTeX either doesn't support or partially supports.
3. The `\tag{N}` mechanism we already inject in `CrossrefRenderTransform`
   (`crates/quarto-core/src/transforms/crossref_render.rs:589`) was
   designed against MathJax's behavior; KaTeX honors it but MathJax is
   the reference implementation.
4. Pandoc's default is MathJax, and our HTML writer already emits
   `\(…\)` / `\[…\]` delimiters — also matched to MathJax's defaults.

### Should we offer Temml as a third option?

**Not in v1** — defer to a separate beads issue. Reasons:

- Temml's output contract (raw MathML in the page) is fundamentally
  different from MathJax/KaTeX (which take TeX-source text and
  typeset client-side). It would require either (a) a new server-side
  TeX→MathML conversion stage or (b) shipping the Temml JS runtime to
  do the conversion in the browser. Either path is a separate feature,
  not a parameter of the same one.
- 2026's MathML browser support story is good enough that this is a
  worthwhile future bet, but the implementation work is roughly the
  size of MathJax+KaTeX combined, and lower priority for v1.
- Once `MathJsStage` exists, adding a `temml` arm is mechanically
  similar to the `katex` arm. Easier to do as a follow-up than to
  block this work on it.

I'll file a follow-up beads issue ("evaluate Temml as a third math
engine for HTML") so it doesn't get lost.

## 3. Existing pipeline state (verified)

These are the load-bearing facts — verified by reading the source —
that the design is built on. Cited so the next person can re-check.

### 3.1 AST shape — math is already a typed node

`crates/quarto-pandoc-types/src/inline.rs` —
`Inline::Math(Math)` with `Math { math_type: InlineMath | DisplayMath, text: String, source_info }`.
No `Block::DisplayMath` variant; display math is wrapped in a
paragraph.

### 3.2 Equation labels — already plumbed

- Parser (pampa) emits `Span(id="eq-…", classes=["quarto-math-with-attribute"], [Math(DisplayMath, …)])` from `$$…$$ {#eq-foo}` syntax.
- `EquationLabelTransform` (`crates/quarto-core/src/transforms/equation_label.rs:41-225`) converts that to `CustomNode("Equation")` with the math inline preserved in `slots["content"]`. Runs in the **normalization phase** of the transform pipeline.
- `CrossrefRenderTransform` (`crates/quarto-core/src/transforms/crossref_render.rs:589-633`) appends `\tag{N}` to the math text during the **finalization phase** so MathJax/KaTeX render the equation number.

**Implication for math detection:** any "does this doc contain math?"
walk must descend into `CustomNode.slots`, otherwise it will miss
labelled equations. (See §4.3.)

### 3.3 HTML writer — already MathJax/KaTeX-compatible

`crates/pampa/src/writers/html.rs:754-767`:

```rust
Inline::Math(m) => {
    let class = match m.math_type {
        MathType::InlineMath => "math inline",
        MathType::DisplayMath => "math display",
    };
    let (open, close) = match m.math_type {
        MathType::InlineMath => ("\\(", "\\)"),
        MathType::DisplayMath => ("\\[", "\\]"),
    };
    write!(ctx, "<span class=\"{}\"", class)?;
    write_inline_source_attrs(inline, ctx)?;
    write!(ctx, ">{}{}{}</span>", open, escape_html(&m.text), close)?;
}
```

This emits exactly what MathJax expects (`\(…\)` / `\[…\]`) and what
KaTeX's auto-render extension expects when configured for those
delimiters. **No writer changes are needed for v1.**

### 3.4 Pipeline composition

`crates/quarto-core/src/pipeline.rs::build_html_pipeline_stages_with_options()`,
in execution order:

```
ParseDocumentStage
MetadataMergeStage
IncludeExpansionStage
IncludeResolveStage          ← writes meta.rendered.includes.{header, before-body, after-body}
DocumentProfileStage         ← profile checkpoint (BEFORE engines/sugar/transforms)
LinkResolutionStage
UnwrapProfileStage
PreEngineSugaringStage
EngineExecutionStage
CompileThemeCssStage
BootstrapJsStage             ← #[cfg(not(target_arch = "wasm32"))]
UserFiltersStage::pre()
AstTransformsStage           ← runs EquationLabelTransform + CrossrefRenderTransform
UserFiltersStage::post()
ResourceReportStage
CodeHighlightStage
RenderHtmlBodyStage          ← serializes AST → HTML body string
ApplyTemplateStage           ← collects js:/css: artifacts; populates header-includes
```

`build_wasm_html_pipeline()` is the same minus `EngineExecutionStage`
and `BootstrapJsStage`.

**Implication for math placement:** the math stage must run **after
`AstTransformsStage`** (so it sees `\tag{N}`-decorated equations) and
**before `ApplyTemplateStage`** (so registered artifacts are emitted).
Two natural candidates: between `CodeHighlightStage` and
`RenderHtmlBodyStage`, or between `RenderHtmlBodyStage` and
`ApplyTemplateStage`. We pick the latter (§4.3).

### 3.5 Templates and the slot contract

`crates/quarto-core/src/template.rs` defines two templates:

- `MINIMAL_HTML_TEMPLATE` (lines 74-102) — for `theme: none / pandoc / minimal: true`.
- `FULL_HTML_TEMPLATE` (lines 131-236) — for everything else.

Both currently have, in `<head>`, in this order:

```
$for(css)$ <link rel="stylesheet" href="$css$"> $endfor$
$for(scripts)$ <script src="$scripts$"></script> $endfor$
$for(header-includes)$ $header-includes$ $endfor$
```

`scripts` is populated from `js:*` artifacts (apply_template.rs:166-180,313).
`header-includes` is wired from `meta.rendered.includes.header` by
`set_includes_list()` (template.rs:419-445).

**There is no `$math$` slot today.** We will add one (§4.4).

### 3.6 Project scope and resource resolution

bd-4eyf established that Project-scoped `js:` artifacts land in the
project lib dir (e.g., `_site/site_libs/quarto/<file>`) for multi-doc
projects, and per-doc (`<doc>_files/<file>`) for single-doc renders.
`ResourceResolverContext` produces correct relative URLs from nested
pages (`docs/api.html` gets `../site_libs/quarto/<file>`). Math will
use the same scope+layout convention.

## 4. Design

### 4.1 New stage: `MathJsStage`

Lives at `crates/quarto-core/src/stage/stages/math_js.rs`. One stage
parameterized by engine; selects MathJax or KaTeX from
`html-math-method`. Both engines share:

- A trigger predicate (does the rendered body contain math?).
- The artifact-registration shape (Project-scoped `js:mathjax-*` or
  `js:katex-*` keys).
- The template-slot population (`meta.math` — see §4.4).

### 4.2 Configuration knobs

User-facing surface mirrors Quarto 1:

```yaml
# Bare string form (shorthand)
html-math-method: mathjax | katex
# or
html-math-method:
  method: mathjax | katex      # required
  url: "https://cdn..."        # optional override of default
  # MathJax-specific (passed verbatim into window.MathJax = {...}):
  mathjax-config: { ... }      # advanced; defer to v1.1 if too much surface
```

**Default when key absent:** `mathjax`, vendored locally (see §4.5).
**Default URLs (CDN, matching Pandoc):**

- `mathjax` → `https://cdn.jsdelivr.net/npm/mathjax@3/es5/tex-chtml-full.js`
- `katex` → `https://cdn.jsdelivr.net/npm/katex@latest/dist/` (loader + CSS derived from this base)

**Override path:** when `url:` is set, that URL is emitted as the
loader `<script src="…">`. Used for CDN pinning, custom mirrors, or
self-hosted setups (e.g., user has copied MathJax into the project
and wants relative URLs).

**No artifact registration in v1.** The default case emits two
`<script>` blocks into the `$math$` slot (config + loader); the
`url:`-override case does the same with the user URL. We do not ship
bytes locally. See §4.5 for the rationale and how this matches Q1.

### 4.3 Trigger: AST walk, not body string-scan

The handoff plan offered three trigger options; here is the chosen
design:

**Choice: dedicated stage that walks the AST after `UserFiltersStage::post()` and before `RenderHtmlBodyStage`**, rather than scanning the rendered HTML string or piggybacking on the writer.

Rationale:

- **Correctness:** the AST is the source of truth. `EquationLabelTransform`
  has already moved math into `CustomNode("Equation")` slots by this
  point; the walker descends into those. `CrossrefRenderTransform`'s
  `\tag{N}` injection is irrelevant to the walker (it just looks for
  `Inline::Math`, regardless of text content).
- **Cost:** O(N) on the AST, but `N` is the document size and the walk
  short-circuits on the first `Math` node encountered. For the common
  case (no math), it visits everything but does nothing else; for the
  math case, it returns true immediately.
- **Why not piggyback on `RenderHtmlBodyStage`:** that stage already
  walks the AST, but adding a side-channel signal couples the renderer
  to a separate pipeline concern. The writer is single-purpose; the
  math stage is single-purpose; keeping them decoupled has worked
  for `CompileThemeCssStage` / `BootstrapJsStage` and should keep
  working here.
- **Why not the document profile (`DocumentProfile.has_math`):** the
  profile checkpoint runs *before* engines, sugaring, and transforms.
  A Jupyter cell that emits LaTeX, or a sugar transform that injects
  display math, would not be reflected. Putting math detection in the
  profile would be wrong by construction.

**Walker implementation:** a small visitor function in `math_js.rs` that
returns `bool`, descending blocks → inlines → `CustomNode.slots`. About
30-40 lines including the recursive cases. Unit-testable in isolation.

### 4.4 Inline config + loader injection: a new `$math$` slot

The pinch point identified in the handoff plan: **MathJax wants an
inline config script BEFORE the loader script**, but q2's templates
emit `$for(scripts)$` before `$for(header-includes)$` — so config in
`header-includes` would land *after* the loader, which is the wrong
order.

**Decision:** add a **`$math$` template slot** to both `MINIMAL_HTML_TEMPLATE`
and `FULL_HTML_TEMPLATE`, positioned **immediately before**
`$for(scripts)$`:

```
$for(css)$ <link rel="stylesheet" href="$css$"> $endfor$
$math$                              ← NEW
$for(scripts)$ <script src="$scripts$"></script> $endfor$
$for(header-includes)$ $header-includes$ $endfor$
```

This matches Pandoc's convention (Pandoc's HTML template also has a
`$math$` slot — see `external-sources/pandoc/src/Text/Pandoc/Writers/HTML.hs:317-385`),
which keeps q2's behavior portable for users who supply custom Pandoc
templates.

`MathJsStage` populates `meta.math` with the inline configuration:

```html
<script>
window.MathJax = { tex: { inlineMath: [['\\(', '\\)']], displayMath: [['\\[', '\\]']], tags: 'ams' }, options: { skipHtmlTags: ['script','noscript','style','textarea','pre'] } };
</script>
```

(Exact content TBD during implementation — `tags: 'ams'` is the key
flag for `\eqref` / `\tag` to work; everything else is defensible
defaults.)

The **loader script** is then emitted by one of two paths:

| Mode | `$math$` slot contents | `$for(scripts)$` |
|---|---|---|
| Default (CDN) | inline config + `<script defer src="${default_cdn_url}">` | unchanged |
| User-provided `url:` | inline config + `<script defer src="${user_url}">` | unchanged |

Both cases put config + loader together in `$math$`. The artifact
pipeline is not involved (no bytes to ship). Order inside `$math$` is
fixed: config block first, loader second — what MathJax expects.

The artifact-registration path (`js:mathjax` Project-scoped) was
considered and rejected for v1; see §4.5. If a future feature adds
local-vendoring opt-in, the artifact path becomes the *vendor* branch
and the table above grows a third row.

**Why a new template slot rather than reordering existing slots:**

- Reordering `$for(header-includes)$` ahead of `$for(scripts)$` would
  silently change the meaning of `header-includes:` for users who
  rely on it landing late in `<head>`. That's a user-facing surface
  break.
- Reordering would also stop matching Pandoc's slot order — bad for
  custom-template portability.
- Adding `$math$` is additive; existing custom templates that don't
  reference `$math$` are unaffected, and our built-in templates get
  the right ordering by construction.

### 4.5 Vendor vs CDN — corrected against actual Pandoc / Q1 behavior

**Important correction to the predecessor handoff plan.** The handoff
plan claimed "Quarto 1 vendors the components-only build" — that is
**wrong**. Verified by reading both Pandoc and Quarto 1 sources:

- **Pandoc** never bundles MathJax. Its `MathJax url` constructor
  emits `<script defer src="${url}">`, where the default URL is
  `https://cdn.jsdelivr.net/npm/mathjax@3/es5/tex-chtml-full.js`
  (`external-sources/pandoc/src/Text/Pandoc/Options.hs:206`,
  `external-sources/pandoc/src/Text/Pandoc/Writers/HTML.hs:318-328`).
- **Quarto 1** also does not vendor MathJax. It wraps Pandoc's URL in
  a small dynamic-load shim (`mathjaxScript()` in
  `external-sources/quarto-cli/src/command/render/template.ts:183-205`)
  but the URL is still the CDN default.
  `pandoc-dependencies-html.ts` copies Bootstrap, fonts, and other
  per-format resources into `_site/site_libs/`, but **never MathJax**.

So the actual user behavior for Q1 today: a default `quarto render`
emits `<script src="https://cdn.jsdelivr.net/...">` and the browser
fetches MathJax from jsDelivr at page load. Offline rendering already
*does not work* in Q1 by default; the workaround is `html-math-method.url:`
pointed at a local mirror.

This re-frames the question.

**Revised v1 default: CDN-default (parity with Q1)**, with a
`html-math-method.url:` escape hatch for self-hosting / mirrors. No
vendored MathJax bytes shipped in the q2 binary.

Reasons:

- **Match the user's existing experience.** A Q1 user migrating to q2
  with the same `_quarto.yml` should see the same network behavior —
  no surprise local-vs-CDN switch.
- **Avoid binary bloat** (10-15 MB of MathJax components, or even
  ~1 MB for the loader, for a feature that Q1 itself doesn't bundle).
- **WASM bundle stays sane** — the hub-client preview doesn't grow by
  ~1 MB just to ship a math runtime.
- **CSP / jsDelivr availability** isn't a regression vs Q1 — anyone
  affected today already had to override the URL.

KaTeX is small enough (~440 KB total) that vendoring it is on the
table without binary-size concerns, but for **engine-default symmetry**
we ship CDN URLs for both. KaTeX's CDN default is jsDelivr too
(matches Pandoc's `defaultKaTeXURL`).

**This means:**

- The math stage **does not register a `js:mathjax` / `js:katex`
  artifact** in the default case. There are no bytes to ship.
- The math stage populates `meta.math` with **both** the inline config
  block AND a `<script defer src="${cdn_url}">` loader, in that order.
- The artifact-registration path becomes the *vendored / self-hosted*
  branch — used only when the user explicitly opts in (see "vendor
  opt-in" below).

**Vendor opt-in (deferred but worth designing for):** users who need
offline / airgapped builds can set `html-math-method.url:` to a
self-hosted URL. q2 will not host MathJax for them in v1. A future
feature could ship a small CLI helper (`quarto install mathjax`) that
downloads the bundle to a project directory and points the URL at it
— mirrors Q1's manual workaround but automates it. **Out of scope for
this issue.**

**Q2 (revised): confirm CDN-default is the right call.**

My strong recommendation is **CDN-default (parity with Q1)** for the
reasons above. Alternative paths and their tradeoffs:

- **(a) CDN-default (my recommendation):** matches Q1, no binary
  growth, no WASM bloat. Offline users do what they do today.
- **(b) Vendor the loader only (~1 MB) by default:** strictly more
  generous than Q1, but adds 1 MB to every q2 binary for users who
  may not even use math. Hard to justify when Q1 doesn't.
- **(c) CDN-default + ship a `quarto install mathjax` helper as a
  separate v1 feature:** the cleanest "we're better than Q1" answer,
  but doubles the v1 scope. File as follow-up, not v1.

Going with (a) unless you say otherwise.

### 4.6 Hub-client (WASM) — STAGE WIRED, RENDERING BLOCKED BY IFRAME SANDBOX

**Discovered after implementation (2026-05-04):** the hub-client
preview iframe is sandboxed *without* `allow-scripts`
(`hub-client/src/components/render/DoubleBufferedIframe.tsx:347,355`
and `MorphIframe.tsx:564` set
`sandbox="allow-same-origin allow-popups"`). A comment in
`hub-client/src/utils/iframePostProcessor.ts:149-167` documents that
script inlining is disabled for the same reason — no `<script>`
element inside the preview iframe executes today.

That means:

- The WASM pipeline does correctly include `MathJsStage` (verified by
  `test_build_wasm_html_pipeline` and `cargo xtask verify` green).
- `meta.math` is populated and the `$math$` template slot emits the
  config + loader markup into the rendered iframe HTML.
- But neither MathJax's CDN loader nor KaTeX's, nor our inline
  `window.MathJax = {…}` config block, ever runs — the iframe drops
  every `<script>` on the floor. The user sees raw `\(e=mc^2\)` text.

**Original §4.6 reasoning was wrong.** I claimed math is "safe under
iframe reinit because the engine typesets once on `DOMContentLoaded`."
True for an unsandboxed iframe; false for hub-client's deliberately
script-sandboxed preview. CDN-default + a JS engine + a script-less
sandboxed iframe is fundamentally incompatible.

**Decision (2026-05-04):** leave the hub-client gap as-is. The native
CLI rendering path was verified live in Chromium (see Browser smoke
log); that's the correctness story for v1. There is an independent
existing plan to isolate the preview iframe on a subdomain via
service workers and re-enable script execution there; once that
lands, math typesetting in hub-client should "just work" with no
changes to this stage. Until then, hub-client preview shows raw TeX
delimiters for math content. Filed: see follow-up issue below.

The structural choice "include `MathJsStage` on the WASM pipeline"
still stands — it's harmless (populates `meta.math`, no bytes
shipped) and means we don't have to revisit the pipeline wiring
when the sandbox unblocks scripts.

(For posterity, the original §4.6 reasoning is preserved below; treat
it as historical until the sandbox unblocks scripts.)

---

**Both engines should ship to hub-client**, but the reasoning needs to
be more precise than "math is stateless" — it isn't.

MathJax and KaTeX both mutate the DOM during typesetting: each
`<span class="math …">` is replaced (or wrapped) with engine-specific
markup (`<mjx-container>` for MathJax, `.katex` / `.katex-display`
for KaTeX). The state is in the DOM, not held in JS objects.

What matters for the hub-client iframe-reinit model:

- **Safe under reinit:** each iframe load starts with a fresh DOM,
  the engine walks it once on `DOMContentLoaded`, done. Nothing leaks
  across reinits — unlike Bootstrap, where component state (open
  modals, expanded collapses) lived in JS class instances that the
  reinit blew away mid-interaction.
- **Cost per reinit:** MathJax 3 typesets a small page in tens of
  milliseconds; KaTeX is faster (synchronous). Visible flicker on
  rapid reinits is possible but not math-specific — every render
  pays similar typeset cost.
- **Future caveat (not a v1 problem):** if the hub-client preview
  ever moves off the iframe-per-render model and re-renders into a
  shared DOM, we'd need to call `MathJax.typesetClear()` (or limit
  the typeset call to new nodes) to avoid accumulating stale
  `<mjx-container>` siblings. Worth a note so the next person
  knows; not in scope here.

**Pipeline change:** `MathJsStage` is *not* gated behind
`#[cfg(not(target_arch = "wasm32"))]`. It's added to both
`build_html_pipeline_stages_with_options()` and
`build_wasm_html_pipeline()`.

**Bundle-size constraint:** the WASM bundle is currently ~14 MB.
Adding 1 MB of MathJax loader is not great but acceptable. Adding 15
MB of MathJax components would double the bundle, which is not
acceptable. This is another reason recommendation §4.5(c) is the
right call for the binary in general, and we'll size-test the WASM
bundle as part of Phase 4 verification.

**Live verification:** after wiring up, smoke-test in the actual hub-
client preview that `$x^2$` renders as math (not as raw `\(x^2\)`
text). Bootstrap had the same browser-smoke gate via chrome-devtools-mcp;
we follow the same protocol for math.

### 4.7 Filter extensibility (the navbar property)

The user asked for math to share the navbar property: that q2's
built-in implementation manipulates publicly-described AST aspects in
a predictable way, so a Lua filter can in principle replace it.

For math, the public AST surface is:

1. **`Inline::Math(MathType, String)`** — the typed node a user filter
   can inspect / construct / replace. (Documented in
   `quarto-pandoc-types`.)
2. **`CustomNode("Equation")`** — the typed wrapper for labelled
   equations. (Documented in `equation_label.rs`.)
3. **`<span class="math inline">\(…\)</span>` / `<span class="math display">\[…\]</span>`** — the HTML markup our writer emits. A filter
   that wants to replace MathJax with, say, server-side prerendering
   can post-process this markup, since it's stable and matches
   Pandoc's convention.

**No new public AST is invented for math handling.** `MathJsStage`
inspects existing typed nodes (option 4.3) and writes to existing
public template variables (`meta.math`, plus a `js:mathjax` /
`js:katex` artifact key). All of this is documentable and would be
reproducible by an external filter.

I'll add a section to `crates/quarto-core/src/stage/stages/math_js.rs`
module docs describing this contract.

## 7. Open risks / things to watch

- **Snapshot baselines may shift.** `tests/fixtures/phase5-single-doc-baseline/expected_hashes.txt` was re-captured for bd-4eyf because Bootstrap added a `<script>` tag. Math should NOT change that baseline (its fixture is math-free). If hashes shift, the predicate is over-triggering.
- **`$math$` slot in custom templates.** Existing user-supplied custom templates won't have `$math$`. They'll silently miss math output. Document this in the template variables doc and add a `quarto check` warning. (File a follow-up beads issue if not done in this work.)
- **MathJax + Bootstrap `<head>` ordering.** Bootstrap JS is registered with key `js:bootstrap` (sorts before `js:mathjax`). The artifact pipeline emits in sorted-key order, so Bootstrap loads first. That's the right order for MathJax (it just typesets math; doesn't depend on Bootstrap).
- **`html-math-method: false` / `none`** — Quarto 1 doesn't support disabling math. We may want to allow `html-math-method: none` for users who do their own thing. Cheap to add: stage skips both artifact + slot.
- **Custom user MathJax config.** v1 ships our default config block. Users with `html-math-method: { mathjax-config: {...} }` (object) need their config merged in. v1.1 if not in v1; document the surface and decide during impl.
- **CDN availability.** With CDN-default, jsDelivr being down breaks math rendering for users. Same risk as Q1; not a regression. If we later want to be more robust, vendor opt-in (see §4.5 "Vendor opt-in") is the path.
- **CSP impact.** The inline `<script>window.MathJax = {…}</script>` block requires `'unsafe-inline'` in any restrictive CSP, or a nonce. Bootstrap had no inline script so this is the first time q2 introduces this constraint. Document it in user-facing docs.
- **`bd-telo` dependency.** Top-level `navbar:` vs nested `website.navbar:` (filed during bd-4eyf) is unrelated, but if math user-docs are colocated with website docs, prefer the form bd-telo doesn't break.
