# Plan: Book-aware preview for `q2 preview` / hub-client (book-projects P8)

**Date:** 2026-09-22 (revised after an implementor-standpoint technical review the same day — see the epic doc's revision history for what changed and why)
**Epic:** [`2026-09-21-book-projects-epic.md`](2026-09-21-book-projects-epic.md)
**Design (authoritative):** [`../designs/book-projects-architecture.md`](../designs/book-projects-architecture.md) §12
**Q1 reference:** none — Q1 has no live, cross-file-aware preview at all (its editor preview is the same single-document-at-a-time model Q2's currently has); this phase has no port target, only Q2's own crossref-design plan's unbuilt `StaticProjectAnalyzer` sketch (`claude-notes/plans/2026-04-15-crossref-design.md`, Phase 4).

## Overview

P0–P7 gave `run_with_book_support()` (design doc §3 — a concrete method on `ProjectPipeline<'a, RenderToFileRenderer<'a>>`, not a `ProjectType` trait override, resolved by a seventeenth-pass research round) real chapter numbering, single-file merge, and project-wide crossref/bibliography resolution — but none of it reaches `q2 preview`/hub-client, which renders one active document through an entirely different, per-document code path (`RenderToPreviewAstRenderer`) that never calls `run_with_book_support()`. Today a previewed chapter renders exactly as if it were a lone, non-book document: no chapter number, no title decoration, and any cross-chapter `@ref` shows as the existing generic unresolved-placeholder (`?fig-ch1-plot?`), not a working link.

This phase closes the numbering/title-decoration gap (cheap — reuses P0/P4's existing machinery) and builds the one genuinely new piece the original epic explicitly deferred: a pre-engine `StaticProjectAnalyzer` that gives preview an approximate, cross-chapter-aware crossref resolution, feeding **P5's own `CrossChapterCrossrefResolveTransform` unmodified** — not a new resolution mechanism — plus the small wire-contract addition needed for the resulting link to navigate to the right chapter in hub-client. It deliberately does **not** attempt cross-chapter bibliography preview or single-file-merge preview — see Decisions.

## Decisions

- **Chapter-number seed + title decoration reuse P0/P4's mechanism as-is, applied to every swept sibling, not just the previewed document.** Build the full `HashMap<PathBuf, ChapterSeed>` — reusing **P4's** existing chapter-number/appendix-flag computation (corrected by a ripple-check pass: this was previously misattributed here to "P1's existing... logic"; P1 only builds the `BookRenderItem` list itself, P4 is the phase that turns it into the `HashMap<PathBuf, ChapterSeed>`, per P4's own Decisions) — once per preview call that touches a book project. Apply the matching entry both to the previewed document's own render *and* to every sibling `StaticProjectAnalyzer` sweeps below — a sibling's local section counter can't produce a correctly chapter-scoped approximate number without its own chapter-number seed.
- **Recompute per preview call; no new caching layer, and the "cheap" framing needs an honest caveat.** Both the chapter-seed map and the static crossref sweep are pre-engine operations, but the sweep genuinely goes deeper per file than Pass 1's existing profile sweep does — Pass 1 stops at `DocumentProfileStage`, before `PreEngineSugaringStage` even runs, and Pass 1 itself is IndexedDB-cached across renders rather than naively recomputed. So this phase adds a real, additional, uncached third level of per-file work on a book-preview call (Pass 1's existing shallow sweep; this new, deeper per-sibling sweep; the previewed document's own real render). Accepted for v1 anyway, on the same terms as the epic's existing "unverified at 50+ chapters" memory limitation — fine at small scale, unverified at large scale, revisit with real caching (most likely extending Pass 1's existing IndexedDB cache rather than inventing a new one) only if it's a real complaint, not decided preemptively.
- **`StaticProjectAnalyzer` extracts only what's already syntactically visible pre-engine**, scoped to exactly the files in `BookRenderItem`'s list — not every file `ProjectContext::discover` happens to enumerate (a project can contain non-chapter `.qmd` files, e.g. include-shortcode partials, that must not be swept as if they were chapters). Extracted set matches the single-file crossref design's own D2/D6: native `Figure`/`Table` captions, `#<reftype>-`-classed `Div`s, the code-block `#|label:` shorthand. An id only produced by an engine (`output: asis`, not listed in that chapter's `crossref.ids` manifest) is unresolvable by this sweep — inherited, not new, degradation, matching the existing single-file behavior. **Found by an eighteenth-pass review: the section-counter logic run over each sibling produces only a raw `Order`, not the formatted display string `ProjectCrossrefIndex.resolved_number` requires.** That formatting is design doc §7's `format_crossref_number(order, chapter_seed)` helper — a call `StaticProjectAnalyzer` must make itself (same helper P4/P5 use, not an inline reimplementation of the letter-vs-numeral composition, which would risk drifting from theirs). Check whether `build_analysis_pipeline`/`build_analysis_transform_pipeline` (already Normalization+Crossref-bounded, precedented elsewhere in this epic) can be reused directly for the per-sibling pass before writing new per-file pipeline construction.
- **Duplicate ids across chapters need an explicit merge rule.** P5's own real Pass 3 explicitly plans a duplicate-id-across-chapters diagnostic; the static sweep inherits the identical risk (a naive last-wins merge could resolve a ref against the wrong chapter's content — a correctness bug, not just an approximate number). Rule: first-in-book-order wins, with a non-fatal diagnostic — preview must degrade, never crash, on ambiguous project state. **Note the resulting asymmetry, found by a composition review, not a design fork to resolve**: the identical authoring mistake looks harmless in preview (a soft, non-fatal note) but produces a hard `Error`-severity diagnostic the first time the author runs a real render (P5's mechanism, matching this codebase's existing duplicate-id-is-an-error policy for single documents). This is a deliberate, correct consequence of "preview degrades gracefully, real render doesn't" — but worth one sentence on P7's docs page so it isn't a support surprise: a duplicate id that previews cleanly may still fail a real render.
- **No new resolution mechanism — this reuses P5's `CrossChapterCrossrefResolveTransform` verbatim.** `CrossrefResolveTransform` is **not** modified (an earlier draft of this plan proposed giving it a `project_index` handle directly — reverted; see design doc §12 for why that would have duplicated P5's already-decided mechanism). The only new work is populating the `RenderContext` field P5's transform already reads — `cross_chapter_crossref_registry: Option<Arc<ProjectCrossrefIndex>>` — from `StaticProjectAnalyzer`'s cheaper, pre-engine sweep instead of P5's real post-engine aggregation. Because that transform is registered unconditionally in the shared `build_transform_pipeline` (P5's plan) and preview's own pipeline (`build_q2_preview_transform_pipeline`) builds the *full* shared pipeline before applying a small named deny-list that new transforms join by default, it runs in preview automatically — no preview-specific pipeline change needed. `CrossrefRenderTransform` (which would flatten the resolved node into final markup) is itself excluded from preview regardless, so the `CrossrefResolvedRef` CustomNode reaches React the same way whether it was resolved by real Pass 3 or by this phase's sweep.
- **Resolution precedence is safe by construction, not a rule to implement.** The transform only ever touches nodes `CrossrefResolveTransform` already left unresolved — a previewed chapter's own correct local resolution can never be shadowed by an approximate sibling entry, even under an id collision.
- **Numbers from this sweep are approximate; the link is not.** A number that shifts slightly once fully rendered is a known imprecision, not a bug to chase — no "approximate" confidence-indicator UI is planned for v1 (no Q1 precedent, no evidence of need). `CrossrefResolvedRef`'s `href` is built from `identifier` alone, never `order`, so the approximation never taints navigation correctness, only the displayed number.
- **Content staleness across open editor tabs is not a real concern.** hub-client's Automerge-backed documents are already the live, synced source of truth regardless of tab-open state — the sweep never reads a separate "unsaved buffer" that could be stale relative to what's actually being edited.
- **Cross-document navigation is a small, additive wire-contract change**: one new optional `plain_data` field on `CrossrefResolvedRef` naming the owning chapter's document path, present only for cross-chapter refs (absent/unchanged for same-page refs, so existing non-book preview is unaffected — regression-tested below). `CrossrefResolvedRef.tsx` calls the already-threaded, currently-unused `onNavigateToDocument` prop when that field is present, instead of the current unconditional same-page `href="#{identifier}"`.
- **Explicitly out of scope, not silently dropped**: cross-chapter bibliography preview (no pre-engine analog exists to P6's per-chapter citeproc manifest — citation resolution isn't syntactically visible before engines run for most CSL styles) and single-file-merge preview (preview always renders as plain HTML regardless of the book's real single-file target format; P2/P3's merge has nothing to preview here). Both stay listed in the design doc's §11/epic's Known Limitations, narrowed rather than removed.

## Checklist

### Tests first
- [ ] Regression test: previewing a chapter in a *non-book* project is byte-for-byte unaffected by this phase's changes — no chapter seed applied, `cross_chapter_crossref_registry` stays `None` (P5's own no-op guard covers this; confirm it holds through the preview path too), `CrossrefResolvedRef`'s `plain_data` gains no new field for a same-page ref.
- [ ] Test: previewing chapter 2 of a real multi-chapter book fixture shows chapter-scoped numbering ("Figure 2.1", not "Figure 1") and chapter-title decoration ("Chapter 2 — Title"), matching what a real `BookProjectType` render of that same chapter would produce.
- [ ] Test: an `.unnumbered` chapter previews with no chapter-number seed applied (matches P0/P4's existing unnumbered-chapter behavior, exercised here through the preview path specifically).
- [ ] Baseline test: before this phase's crossref-resolution mechanism is wired up, a cross-chapter `@ref` in preview degrades to the existing unresolved-placeholder rendering (`?id?`), not a crash — pins today's starting behavior so the improvement is measurable.
- [ ] Test: `StaticProjectAnalyzer` resolves a cross-chapter `@ref` to the target chapter's approximate kind/number when the target is a statically-visible crossref (native figure/table caption, `#<reftype>-`-classed Div, `#|label:` shorthand) in another chapter, with that chapter's own `ChapterSeed` correctly applied so the number is chapter-scoped.
- [ ] Test: an `@ref` to an engine-generated (`output: asis`, un-promised) id in another chapter still degrades to the unresolved-placeholder rendering, not a crash or an incorrect resolution.
- [ ] Test: two chapters independently defining the same crossref id produce a non-fatal diagnostic and a deterministic (first-in-book-order) resolution in the static sweep, not a silent last-wins overwrite and not a preview crash.
- [ ] Test: a non-chapter `.qmd` file present in the project directory but absent from `BookRenderItem`'s list is not swept by `StaticProjectAnalyzer` and cannot be resolved as a cross-chapter target.
- [ ] Regression test: `CrossChapterCrossrefResolveTransform` (P5) does not accidentally resolve a previewed chapter's own crossref id against a stale/approximate sibling entry — same-chapter local resolution always wins.
- [ ] Test: the new `plain_data` field is present (with the correct owning-chapter path) for a cross-chapter-resolved ref, and absent for a same-chapter-resolved ref.
- [ ] `schemaConformance.test.ts` extended (both directions) to cover the new field, per the existing convention for `CrossrefResolvedRef`'s key array. **This requires a matching entry in `crates/quarto-pandoc-types/resources/custom-node-schema.json`'s `CrossrefResolvedRef.plain_data` block, not just the `.tsx` key array** — found by an implementability review: T4.3 in `schemaConformance.test.ts` strictly checks the TS component's key array against this schema file's keys (`toEqual` on sorted arrays), so extending only `CROSSREF_RESOLVED_REF_PLAIN_DATA_KEYS` without a corresponding schema entry makes that exact test fail, not pass. Mirror `order`'s existing entry shape.
- [ ] React test: `CrossrefResolvedRef` calls `onNavigateToDocument` with the correct target when the new field is present, and renders the existing same-page `href` unchanged when it's absent.

### Implementation
- [ ] `RenderToPreviewAstRenderer` gains the full per-chapter seed map (built the same way P4 builds it), applied to the previewed document via the equivalent of P4's `with_chapter_seeds` builder.
- [ ] New `StaticProjectAnalyzer` module: pre-engine sweep of `BookRenderItem`-listed sibling files' parsed AST — check whether `build_analysis_pipeline`/`build_analysis_transform_pipeline` can be reused directly before writing new per-file pipeline construction — producing a `ProjectCrossrefIndex` (P5's merge type), with the seed map from above applied per sibling, `format_crossref_number(order, chapter_seed)` (design doc §7) called explicitly to produce each entry's `resolved_number` string, and the duplicate-id merge rule applied during aggregation.
- [ ] Populate `RenderContext.cross_chapter_crossref_registry` (P5's field) from the `StaticProjectAnalyzer` sweep in the preview render path only; confirm no other call site sets it, and confirm P5's transform requires no changes to consume it.
- [ ] New optional `plain_data` field on `CrossrefResolvedRef` — TS reader in `CrossrefResolvedRef.tsx`, plus a matching entry in `crates/quarto-pandoc-types/resources/custom-node-schema.json`. **Rust-side citation corrected by an implementability review**: `crossref_resolve.rs`'s `build_resolved_ref` only builds the *local, same-page* resolution — the cross-chapter mutation that actually sets this field belongs wherever P5's `CrossChapterCrossrefResolveTransform` is implemented (not yet written; that file doesn't exist until P5 lands), reusing the same `serde_json::Value::Object`-mutation idiom `crossref_resolve.rs` already uses for `order`.
- [ ] `CrossrefResolvedRef.tsx`: branch on the new field, calling `onNavigateToDocument` instead of the bare same-page `href` when present.
- [ ] `cargo clippy -p quarto-core --all-targets -- -D warnings`; `cargo nextest run -p quarto-core`; `npm run build --if-present -w ts-packages/preview-renderer`; phase-boundary `cargo nextest run --workspace` with delta reported.

## Details

**End-to-end verification (this repo's standing rule):** exercise this through a real hub-client preview session (or, at minimum, the WASM-level integration tests already used for the non-book preview path) against a real multi-chapter book fixture with a cross-chapter reference — inspect the previewed chapter's rendered number, the cross-chapter link's `href`/navigation behavior, and confirm a non-book project's preview is unchanged. Record the exact fixture and what was inspected in this checklist as each item completes.

**Dependency note**: this phase depends on P5's `CrossChapterCrossrefResolveTransform` and `RenderContext.cross_chapter_crossref_registry` field existing and being registered in the shared `build_transform_pipeline` exactly as P5's plan now specifies (see that plan's Decisions) — confirm P5 has landed in that shape before starting this phase's implementation, not just that P5 is "done" in name.
