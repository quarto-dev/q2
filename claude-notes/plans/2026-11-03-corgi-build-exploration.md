## What corgi is

[corgi](https://github.com/ConradIrwin/corgi) is a cargo-compatible
build driver. Cargo still resolves dependencies (`Cargo.lock`), but corgi
plans and runs the rustc/build-script actions itself:

- **One content-addressed store per machine** (`/Users/Shared/corgi`),
  shared by every checkout and worktree. Worktrees are what we use most
  (`.worktrees/*`, `create-worktree`), and each one now pays for a cold
  `target/` of 12+ GB.
- **workspace-hack-style feature unification.** Features are unified
  across the whole workspace by default, so `-p foo` does not rebuild
  dependencies with different features. `[roots.*]` defines separate
  feature universes.
- **Sandboxed rustc, build.rs and proc macros** (macOS `sandbox-exec`).
  They get no network, a whitelisted env, and read access only to the
  package's own `.rs` files plus declared `[extra-inputs]`. corgi rejects
  any artifact whose bytes contain the workspace path, which is what
  makes cross-checkout sharing safe.
- **Hermetic toolchain.** corgi downloads its own pinned Zig-based
  C toolchain, macOS SDK and rust toolchain (it read our
  `rust-toolchain.toml`) and declared `[tools.*]`.
- **Tests run one process per test and in parallel, like nextest, and
  passing runs are cached.**
- Optional remote cache (Cloudflare R2) populated from CI.

Platform support: macOS and NixOS. "Normal" Linux distros and Windows
are in progress upstream.

## What it took

### corgi-side gaps (patched locally on `q2-compat`)

| # | Gap | Our trigger | Patch |
|---|-----|-------------|-------|
| 1 | `.cargo/config.toml` `target.<t>.runner` is a hard error | `target.wasm32-unknown-unknown.runner = "wasm-bindgen-test-runner"` | Ignore `runner`. It only changes how a binary is launched. |
| 2 | `[lints]` `check-cfg` is a hard error ("not supported yet") | workspace `unexpected_cfgs` check-cfg `cfg(coverage_nightly)`, and the same in `wasm-bindgen-futures-patch` | Emit `--check-cfg <v>` for each entry, as cargo does |
| 3 | An `[extra-inputs]` pattern that matches nothing fails the build | Five build scripts embed an npm-built tree (`q2-preview-spa/dist`, `hub-client/dist-preview-embed`, `ts-packages/quarto-hub-mcp/dist-bundle`, `trace-viewer/dist`, `agents-docs-dist`) when it exists and a placeholder when it doesn't | A leading `?` marks a pattern optional: matching nothing is a valid, hashed state |

All three patches are small and generic. They are good upstream
issues/PRs; #3 most needs discussion, because it is a design question
for corgi.

The patches live in `external-sources/corgi` on branch `q2-compat`
(`external-sources/` is gitignored, so they are not in this repo).
Build the patched binary outside the q2 tree, because the q2 workspace
glob otherwise claims `external-sources/corgi`:

```bash
git -C external-sources/corgi worktree add /tmp/corgi-q2 q2-compat
cargo build --release --manifest-path /tmp/corgi-q2/Cargo.toml
```

### q2-side changes (on this branch)

1. **`corgi.toml`**, generated by `scripts/corgi/scan-extra-inputs.py`
   from the hand-written `scripts/corgi/corgi.base.toml`. The scanner
   finds literal paths in `include_str!` / `include_bytes!` /
   `include_dir!` / `concat!(env!("CARGO_MANIFEST_DIR"), …)`, rust-embed
   `#[folder]`, and our own `include_error_table!` proc macro. It turns
   each path into a package-relative glob. The base file holds what a
   scan can't see:
   - `[tools.cmake]` (pinned 3.31.6 macOS universal tarball) for
     `wasmtime-c-api-impl`. tree-sitter's `wasm` feature pulls it in,
     for quarto-highlight's native user-grammar loader.
   - Build-script reads: `resources/scss`, highlight styles, the CSL
     suite, and tree-sitter C sources.
   - The optional (`?`) npm-built trees.
   - `[env.QUARTO_GIT_HASH]` (release builds only).

   About 25 packages need declarations. Keeping the list current by hand
   would be a chore, which is why a generator exists. A real adoption
   would make it an xtask and add a verify check that fails when
   `corgi.toml` is stale.
2. **`crates/lua-src-wasm`** (our `[patch]` fork of `lua-src`) embeds
   its Lua 5.4 sources with `include_dir!` and extracts them to
   `OUT_DIR`. Before, it located them through
   `env!("CARGO_MANIFEST_DIR")`, which bakes an absolute workspace path
   into the rlib. corgi refuses such artifacts, and they could never be
   shared between checkouts anyway. The change is harmless under cargo.
3. **`quarto-citeproc`**: rust-embed gains `debug-embed` and
   `deterministic-timestamps`. Without `debug-embed`, debug builds bake
   the absolute `locales/` path into the binary and read the files at
   runtime. corgi's README calls out rust-embed for exactly this. Cost:
   debug builds embed about 60 small XML files, which is negligible.
4. **`quarto-trace/build.rs`** uses a precomputed `QUARTO_GIT_HASH` env
   var when one is set, because git can't run in the sandbox. corgi's
   `[env]` probe computes it outside the sandbox, for release builds only.
   Dev builds under corgi report `unknown`, so a new commit no longer
   rebuilds quarto-trace and everything above it (quarto-core, …). Cargo
   behaviour is unchanged.

### Things that just worked

- The pinned nightly from `rust-toolchain.toml` and the
  `[patch.crates-io]` entries.
- C builds via `cc` (tree-sitter grammars, Lua, mimalloc, jemalloc, …)
  through corgi's Zig toolchain.
- CMake-driven `wasmtime-c-api-impl`, once cmake was declared.
- Build scripts that `watch_dir` a missing tree. `quarto-build-support`
  tries to `create_dir` it, the sandbox denies the write, and the helper
  falls back to watching `build.rs`. corgi ignores `rerun-if-changed`
  anyway: inputs are hashed.

## Candidate upstream issues for corgi

1. Accept `target.<triple>.runner` in `.cargo/config.toml`. Ignoring it
   is enough for builds; ideally `corgi test --target wasm32-…` would
   use it.
2. Support `[lints.rust.unexpected_cfgs] check-cfg = [...]` (emit
   `--check-cfg`).
3. Optional extra-inputs (the `?` prefix here, or a
   `[optional-inputs]` table) for build scripts that embed a generated
   tree only when it exists.
4. Set `CARGO_MANIFEST_DIR` (and the other runtime `CARGO_*` vars cargo
   sets) when running test binaries, as `cargo test` and nextest do.
   That gives tests a portable migration target off compile-time
   `env!("CARGO_MANIFEST_DIR")`.
5. `default-members` is ignored: bare `corgi check` at a virtual
   workspace root fails with "no root package". `--workspace` is
   required.

## Out of scope / not attempted

- **WASM** (`crates/wasm-quarto-hub-client`, `wasm-qmd-parser`): these
  are separate workspaces built with wasm-pack and their own
  `.cargo/config.toml`. corgi has a `--target` flag and Zig-based
  cross-compilation, but wasm-pack and wasm-bindgen post-processing
  are outside its model. `cargo xtask` keeps owning these.
- **xtask / verify integration.** `cargo xtask verify` still drives
  cargo + nextest. Nothing here changes CI.
- **Linux CI / remote cache.** Linux support upstream is NixOS-only.
  Our CI runs on Ubuntu, so an R2-backed shared cache isn't available to
  us yet.
- **Windows.** Unsupported upstream. Per corgi's design, cargo stays
  the source of truth and corgi is an opt-in local accelerator.
