## Goal

Marimo produces an **engine execution record** like every other engine: one
unit per marimo-owned cell, in document order, each carrying the cell\'s
rendered output, plus the notebook-level header include the interactive mode
needs. A record must replay without launching marimo, `uv` or node.

## Design decisions (from the epic; do not re-litigate)

1. **Unit = marimo-owned cell.** The set is exactly what `cellOwnedByMarimo`
   selects, in document order. The stage scans units once
   ([EXR-2](2026-10-28-exr-02-unit-scanner.md)), fills the ids with EXR-4\'s id function
   and gives marimo the same list as every other engine (epic decision 38: one list,
   re-located per engine). **Marimo validates `kind: cell` units whose own
   `cellOwnedByMarimo` rule holds; it locates them by `line`, not by the `owned` flag**,
   because the view\'s language-level `owned` cannot express marimo\'s class rule (a bare
   `{python}` cell in a view that marks `python` owned is not marimo\'s). Core re-locates
   each unit\'s `line` into the text marimo receives (EXR-2 `locate_units`, carried by
   EXR-7); marimo matches its own chunks to units by that `line`. The join to the
   engine\'s per-cell outputs is by order over those units, guarded by a count
   check over them only. A span unit that marimo\'s view marks owned gets nothing: marimo
   runs no spans, so it stays literal with no output and no record unit. The existing count
   assertion on the live markdown path is unchanged. For the record, a count
   mismatch follows the epic\'s alignment contract (EXR-7, decided with Gordon,
   2026-10-30): no record plus a diagnostic naming both counts, and the render
   succeeds while the record is additive (marimo has no flip in this plan, so that is
   the rule throughout it).
2. **Rendered, like knitr.** One `display_data` output per unit with
   `text/x-quarto-markdown` holding the projected markdown string, tagged with
   the output format in its output metadata. Presenting a marimo unit is
   placing that string.
3. **Includes fold into the record.** The header content (not the temp file
   path) is stored at notebook level and re-materialized as a header include on
   replay. It is the same for every marimo document at a given engine version
   (about 52 KB), so store it once per record.
4. **Per-engine metadata.** The engines list carries `quarto_can_freeze: false`
   for marimo, as provenance only; nothing reads it in this epic.
5. **Additive.** The engine returns per-cell outputs alongside the unchanged
   `markdown`; the core records them and a shadow test asserts
   `place(record) == result.markdown`. No flip in this plan; marimo leaves the
   legacy path at [EXR-17](2026-10-28-exr-17-legacy-removal.md).
6. **Engine changes land on the fork; no release is needed for q2.** Changes go on
   `q2/node-port` of Gordon\'s fork, then `dist` is rebuilt and the q2 fixture is
   re-synced with `scripts/sync-marimo-fixture.sh`, so `marimo_fixture_fresh.rs` stays
   green. q2\'s tests pin the fixture, not a published engine release. Upstreaming to
   `marimo-team/quarto-marimo` is a follow-up outside every plan.
7. **Hash definition, declared by the engine (epic decision 35).** Marimo cells are
   reactive across the document, so the declaration uses `granularity: document`: the
   execution-input hash is over all owned cells\' sources plus `eval`, `external-env`,
   `pyproject`, the bare-sql flag and the mode. This declaration is the single source
   of the marimo rule and is authoritative: EXR-4\'s marimo bullet points here and
   must not state a different rule (it once said per-cell source). The engine returns it
   as `recordInfo.hashDefinition` (EXR-7 wire, EXR-4 struct), core stores the full
   declaration in `quarto_engines[].hash_definition` and computes the hash. The
   Positron-style per-unit `quarto_content_hash` is still emitted for display matching.

11. **Core's join for marimo: `recordInfo.coverage` (Gordon, 2026-11-01, option A).** Core's
    count check compares the notebook with the units owned by language, which is wrong for
    marimo's class rule. `recordInfo` gains an optional `coverage: "owned" | "subset"`
    (default `owned`, omitted on the wire; `TsCoverage` in `ts_protocol.rs`). A `subset`
    engine returns `ids`-aligned cells for the units it ran, matched by `line`; core checks
    each id (known, sent with `owned: true`, not repeated) and skips the count equality. The
    count guard for marimo is the engine\'s `validateProjectionCount`; core cannot notice a
    cell a `subset` engine silently dropped. `subset` with `positional` alignment is a
    malformed notebook. This adds one optional field to EXR-7\'s wire; unknown keys are
    ignored, so an older core or engine is unaffected.

## Out of scope

- Freeze behavior; changing how islands hydrate; changes to the marimo
  compiler beyond what the wire needs; spans (marimo has no execution of inline expressions
  here, and the count covers `kind: cell` units only); multi-format records beyond
  tagging.

- **Header size.** About 52 KB per record is acceptable for now; if records
  multiply across a project, a shared-header reference is the obvious
  optimization (decide with the figure-sidecar work, not here).
- **Static figures are inline data URIs,** so static marimo records can be
  large (bd-sr73 is unmeasured); measure one fixture.
- **Interactive hydration offline** is unverified; if it needs network, replay
  output is no worse than live output.
- **Cross-engine order.** Marimo output between other engines\' cells relies on
  the multi-engine reconcile; keep one mixed-engine test.
- **Fork divergence.** The fork is two commits ahead of upstream\'s `0c24139` before
  this plan\'s changes; a rebase onto upstream is a recurring cost until upstreamed
