## Goal

Marimo produces an **engine execution record** like every other engine: one
unit per marimo-owned cell, in document order, each carrying the cell\'s
rendered output, plus the notebook-level header include the interactive mode
needs. A record must replay without launching marimo, `uv` or node.

## Background

Verified in code on 2026-10-28 unless marked otherwise. Paths under
`external-sources/quarto-marimo/` are the engine repo: Gordon\'s fork
`gordonwoodhull/quarto-marimo`, branch `q2/node-port` (upstream is
`marimo-team/quarto-marimo`; checked 2026-10-29: the checkout is at `8662e23`, the
commit q2\'s fixture pins, and its top commit makes the fork load release artifacts from
the fork). The q2 side is `crates/quarto-core`.

- **The engine runs the whole document and splices per cell.**
  `external-sources/quarto-marimo/src/engine/index.ts:159` `execute` passes the
  whole `options.target.markdown.value` to the Python compiler (`:170-182`),
  then re-splits the document with `breakQuartoMd` (`:183`) and walks the
  chunks: an owned cell becomes `projected[index++]`, every other chunk is
  copied verbatim (`:193-199`). So marimo is per cell and rendered, not
  document-level (the handoff said document-level).
- **Rendered per mode.** `interactive` is `isHtmlCompatible(format)`
  (`index.ts:160`). Interactive: `projectInteractivePage`
  (`src/engine/projection.ts:11`) turns each cell into a raw HTML fence holding
  a custom element with a base64url payload. Static: `projectStaticPage`
  (`projection.ts:17`) turns each cell into markdown (fenced code when the code
  is displayed, then a figure, paragraph, plain block, blockquote or raw table).
  Static figures are inline `data:` URIs unless the source is already a URL
  (`external-sources/quarto-marimo/_extensions/marimo/python/quarto_marimo/static.py:111-115`),
  and the engine returns `supporting: []` (`index.ts:211`).
- **Count validation already exists.** `validateProjectionCount`
  (`projection.ts:26-35`) throws if the compiler returned a different number of
  cells than the document has marimo-owned cells. This is the alignment
  assertion the record can reuse.
- **Ownership uses the negative projection.** `cellOwnedByMarimo`
  (`src/engine/authoring.ts:56-67`): every `.marimo`-tagged cell is marimo\'s;
  a bare `sql` cell is marimo\'s only when `handledLanguages` is defined and
  does not contain `sql` (`index.ts:163-164`). The wire doc comment at
  `crates/quarto-core/src/engine/ts_protocol.rs:366-391` records that this was
  once read backwards.
- **Header include, interactive only.** `index.ts:201-207` sets
  `includes["include-in-header"]` to a temp file written by `writeBrowserHeader`
  (`src/engine/browser-assets.ts:10`), which inlines the extension\'s browser
  script (`browser-v0.6.0.js`, 47,485 bytes in the q2 fixture) and stylesheet
  (5,054 bytes) as a `style` and a `script type="module"`.
- **`canFreeze: false`** at `index.ts:94`, forwarded at `:134`; q2 reads it via
  `ts_engine.rs:830-832` (`can_freeze`), and nothing consumes it yet (bd-mx5x609r).
- **The wire result has no per-cell outputs.** `TsExecuteResult`
  (`ts_protocol.rs:~403-430`) carries `markdown`, `supporting`, `filters`,
  `includes`, `html_dependencies`, `preserve`, `post_process` and the rest; no
  units or notebook.
- **Capture and splice today.** Marimo emits zero `.cell` Divs; each executed
  cell is one bare raw HTML block, and `capture_splice_seam.rs` SC22
  (`marimo_shaped_capture_splices`, `capture_splice_seam.rs:226`; the comment block above it
  is `:181-200`) pins that such a block splices.
  bd-5oyk1xce (open, P1) says preview drops the engine\'s `include-in-header`, so
  islands never hydrate (verified by reading the strand, not re-read in code;
  its text still mentions a CDN script, which the node-port engine no longer
  uses because it inlines the browser script).
- **Tests and gating.** `tests/integration/marimo_engine_e2e.rs` needs `node` and
  `uv` on PATH and runs when both exist (`:5-20`); `marimo_resolution.rs` needs
  neither; `marimo_fixture_fresh.rs` checks the synced fixture against recorded
  hashes. The fixture is `tests/fixtures/extensions/marimo` (`minimal.qmd`,
  `widget.qmd`), synced from the engine repo by `scripts/sync-marimo-fixture.sh`
  and pinned by `FIXTURE-SOURCE` (engine commit `8662e23`, version 0.6.0).
- **Ownership is by class, not by language alone.** `MARIMO_CELL_REGEX`
  (`authoring.ts:3-4`) claims `{python .marimo}`, `{.marimo}`, `{marimo}`, `{markdown.marimo}`
  and the like; a bare `{python}` cell is not marimo\'s. The resolver, in contrast, assigns
  ownership by language (`marimo_resolution.rs:147-198`: a document with only
  `{python .marimo}` cells gives `ownership["python"] == "marimo"`), and
  `view_for_engine` ([EXR-2](2026-10-28-exr-02-unit-scanner.md)) takes only a language
  predicate. In a document with both tagged and bare `{python}` cells, marimo\'s view would
  mark both owned although marimo runs only the tagged ones. The fixture
  `tests/fixtures/extensions/marimo/minimal.qmd` has `{python .marimo}` cells only, so a
  first test passes without exercising this. Resolution of a mixed document was not run
  (UNVERIFIED).
- **Not verified:** what the interactive compile does at build time (whether any
  cell code runs; `quarto_marimo/compiler.py` was not read), and whether browser

## Design decisions (from the epic; do not re-litigate)

1. **Unit = marimo-owned cell.** The set is exactly what `cellOwnedByMarimo`
   selects, in document order. The stage scans units once
   ([EXR-2](2026-10-28-exr-02-unit-scanner.md)), fills the ids with EXR-4\'s id function
   and gives marimo the same list as every other engine (epic decision 38: one list,
   re-located per engine). **Marimo validates `kind: cell` units whose own
   `cellOwnedByMarimo` rule holds; it locates them by `line`, not by the `owned` flag**,
   because the view\'s language-level `owned` cannot express marimo\'s class rule (a bare
   `{python}` cell in a view that marks `python` owned is not marimo\'s). Core re-locates
   each unit\'s `line` into the text marimo receives (EXR-2 `locate_units`, carried by
   EXR-7); marimo matches its own chunks to units by that `line`. The join to the
   engine\'s per-cell outputs is by order over those units, guarded by a count
   check over them only. A span unit that marimo\'s view marks owned gets nothing: marimo
   runs no spans, so it stays literal with no output and no record unit. The existing count
   assertion on the live markdown path is unchanged. For the record, a count
   mismatch follows the epic\'s alignment contract (EXR-7, decided with Gordon,
   2026-10-30): no record plus a diagnostic naming both counts, and the render
   succeeds while the record is additive (marimo has no flip in this plan, so that is
   the rule throughout it).
2. **Rendered, like knitr.** One `display_data` output per unit with
   `text/x-quarto-markdown` holding the projected markdown string, tagged with
   the output format in its output metadata. Presenting a marimo unit is
   placing that string.
3. **Includes fold into the record.** The header content (not the temp file
   path) is stored at notebook level and re-materialized as a header include on
   replay. It is the same for every marimo document at a given engine version
   (about 52 KB), so store it once per record.
4. **Per-engine metadata.** The engines list carries `quarto_can_freeze: false`
   for marimo, as provenance only; nothing reads it in this epic.
5. **Additive.** The engine returns per-cell outputs alongside the unchanged
   `markdown`; the core records them and a shadow test asserts
   `place(record) == result.markdown`. No flip in this plan; marimo leaves the
   legacy path at [EXR-17](2026-10-28-exr-17-legacy-removal.md).
6. **Engine changes land on the fork; no release is needed for q2.** Changes go on
   `q2/node-port` of Gordon\'s fork, then `dist` is rebuilt and the q2 fixture is
   re-synced with `scripts/sync-marimo-fixture.sh`, so `marimo_fixture_fresh.rs` stays
   green. q2\'s tests pin the fixture, not a published engine release. Upstreaming to
   `marimo-team/quarto-marimo` is a follow-up outside every plan.
7. **Hash definition, declared by the engine (epic decision 35).** Marimo cells are
   reactive across the document, so the declaration uses `granularity: document`: the
   execution-input hash is over all owned cells\' sources plus `eval`, `external-env`,
   `pyproject`, the bare-sql flag and the mode. This declaration is the single source
   of the marimo rule and is authoritative: EXR-4\'s marimo bullet points here and
   must not state a different rule (it once said per-cell source). The engine returns it
   as `recordInfo.hashDefinition` (EXR-7 wire, EXR-4 struct), core stores the full
   declaration in `quarto_engines[].hash_definition` and computes the hash. The
   Positron-style per-unit `quarto_content_hash` is still emitted for display matching.

## Out of scope

- Freeze behavior; changing how islands hydrate; changes to the marimo
  compiler beyond what the wire needs; spans (marimo has no execution of inline expressions
  here, and the count covers `kind: cell` units only); multi-format records beyond
  tagging.

## Risks and open questions

- **Header size.** About 52 KB per record is acceptable for now; if records
  multiply across a project, a shared-header reference is the obvious
  optimization (decide with the figure-sidecar work, not here).
- **Static figures are inline data URIs,** so static marimo records can be
  large (bd-sr73 is unmeasured); measure one fixture.
- **Interactive hydration offline** is unverified; if it needs network, replay
  output is no worse than live output.
- **Cross-engine order.** Marimo output between other engines\' cells relies on
  the multi-engine reconcile; keep one mixed-engine test.
- **Fork divergence.** The fork is two commits ahead of upstream\'s `0c24139` before
  this plan\'s changes; a rebase onto upstream is a recurring cost until upstreamed
  (a follow-up outside every plan).
