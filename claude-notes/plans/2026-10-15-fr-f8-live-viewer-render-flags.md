## Goal

`q2 preview foo.qmd` (the read-only viewer, the default `--ui`) accepts `--to`, `-M/--metadata` and `--profile` with the meaning they have for `q2 render`, so `q2 preview book/ --to typst`, `q2 preview ch1.qmd -M toc:true` and `q2 preview --profile print` work, also with `--share`. Configurations that have an editor (`--ui editor`) do not take them: the editor has its own UI for settings, and the combination is rejected, not silently ignored. `--profile` works as `QUARTO_PROFILE` does today: natively, with a startup notice that the browser's html preview ignores it. `q2 provide-hub` takes `-M` so a metadata option that changes how code runs reaches execution.

## Decisions

All from the epic; the plan-level ones:

- **F8-D1 Flags and where they are refused.** `Commands::Preview` gets `-M/--metadata` (repeatable) and `--profile` (comma-separated or repeated, as `render`), and `--to` stops requiring `--static`; **this plan rewrites the `requires = "static_mode"` that F5b put on `-M` and `--profile` (and the one `--to` already had, `main.rs:358`)** so that all three are accepted in `--static` and in the live viewer; `--no-watch` and `--no-navigate` keep their own `requires`. All three conflict with `--join` (the guest has no local project) and `--no-project` (no project to render). They also conflict with `--ui editor`: clap cannot condition on a value, so `main.rs` checks it before dispatch and exits with a message that names the flag and `--ui editor` (the editor has its own settings UI). **They are accepted with `--share`** (the default `--ui viewer` composes with `--share`): the guests receive the host's session and the host's `render` block with it (F8-D2, F8-D6); the refusals are `--ui editor`, `--join` and `--no-project`, not `--share`.
- **F8-D2 What travels, and how.** The server parses `-M` with F1's function into one JSON object (the overlay metadata) and keeps `--to` as the requested format, both held in state the config handler can read (the editor-boot `OnceLock` pattern, or a field of `PreviewConfig`, whichever 8.2 shows is cleaner). The SPA reads both from `/api/preview/config` (a new `render: { to?, metadata? }` block, absent when neither flag is given, so stale or new clients both work) and sends them on every render call: the overlay's metadata as `metadata` (F4's wire), the requested format as a new `to` string next to it **on a new trailing options argument of `render_page_for_preview` / `renderPageForPreview`** (`{ to?, metadata? }`; the wasm `.d.ts` at `:49`, **both** the `WasmApi` declaration in `wasmRenderer.ts:83-87` and the wrapper, `PreviewApp.tsx:~1202`), on the wasm request options of `render_pandoc_request` (beside F4's `metadata`) and on the extended `resolve_pandoc_formats` options object (F6-D1). The overlay is applied in all the wasm paths the SPA reaches: `render_page_for_preview`, `render_single_doc_to_response`, `render_project_active_page_to_response` and the preview AST renderer (F1-D4 lists the wasm entries; each wraps its own runtime). **`fetchAllowEdit` changes contract.** It fails closed to `false` today, and extending it naively to return the render block would make a transient config failure silently drop `--to` and `-M` (the preview would render as unflagged html while the server serves typst PDFs). It becomes `fetchPreviewConfig`, returning `{ allowEdit, render? }`: a failed fetch still yields `allowEdit: false`, but a session known to carry flags must not fall back silently, so a failed fetch is retried and, if it keeps failing, surfaces as an error state rather than as "no flags"; a server that answers successfully with no `render` block means no flags (stale or flagless servers change nothing). The function is private and called once (`PreviewApp.tsx:804`); `isTypstPdf` is used in a module-level closure (`:~618`), so it takes the render block as an argument or reads it from held module state. **Why `to` is separate from `metadata`.** The tempting alternative is to fold `--to x` into the overlay as a scalar `format: x`, which FR2 already makes select. It fails for the common `--to typst -M 'format:{typst:{toc:true}}'`: a runtime `format` is either the scalar that selects or the map that supplies settings, never both (the merge stage drops a runtime scalar's settings, `resolve_format_config`, `quarto-config/src/format.rs:72-129`), so folding would drop the settings. A requested format is not only metadata, which is also what the render path says (`cli_to` beside the runtime layer). (Inside Rust the requested format may ride in `RenderOverlay` as its own field, not as metadata, so the routes and wasm share one apply path; the wire stays `to`.) The native routes already carry an explicit format key per request (the PDF route is always `typst-pdf`), so they need only the `metadata`.
- **F8-D3 The pane's own scope wins.** The PDF pane sends `{ "book-scope": "chapter" }` (F4-D2); the SPA merges the CLI's overlay *under* it with a shallow spread (the key is top-level), so the pane's value wins and a CLI `-M book-scope:book` cannot turn a one-page preview into a whole-book PDF. The server prints a startup notice that `book-scope` is ignored by the live preview, which renders one page at a time. `-M book-scope:...` on `--static` is not a preview matter: it is the ordinary FR6 rule.
- **F8-D4 The servable gate runs at startup.** The same `check_servable_format` as `--static` (F5b-D4) judges `--to` and the project's resolved format (html, revealjs, typst are servable; epub, docx and pptx are refused, because there is no good way to preview them). Per-page formats that differ keep the existing "no live preview" message (`noLivePreviewMessage`, `PreviewApp.tsx:~285`). A document with `output-ext: typ` previewed with `--to typst` passes the gate but shows that same message, because its key is `typst`, not `typst-pdf`; the help text and docs say so.
- **F8-D5 `--to` and the pane.** The requested format wins over the document and the project (FR2), so `--to typst` makes a front-matter-less chapter and a chapter that says `format: html` both a PDF pane, and `--to revealjs` previews every page as slides, through the resolved format F6 already uses; no TypeScript decides it. `--to` is not validated against the pseudo-format names here: `q2-preview`, `q2-slides` and the like are accepted as before (a plain `--to q2-preview` behaves as it does for `q2 render` and `--static`), and what they should mean on a command line is the open question in `bd-pseudo-format-to-meaning-vxhyni3t`; the servable gate of F8-D4 is the only `--to` check.
- **F8-D6 `--profile` on the viewer works as `QUARTO_PROFILE` does today (FR20), through a runtime factory.** The server discovers its project with the selection and the **native** side honours it: the route project (`preview_out.rs`), the capture and re-execution paths, the config readers, the pre-render-script call, the startup readers in `commands/preview.rs` and the whole-book download. **Mechanism (decided): one factory builds the server's native runtime with an instance-scoped environment override**, not a process-global. `NativeRuntime` gains an instance-scoped override of environment reads (for example `with_env_override("QUARTO_PROFILE", value)`; `env_get` at `native.rs:314` reads `std::env::var` today), so `discover(path, runtime)`\'s fallback to `QUARTO_PROFILE` resolves to the flag's value on that runtime and on no other (tests build their own runtimes; nothing is set process-wide). The factory lives in a crate both `quarto-preview` and `quarto` can use (`quarto-system-runtime` for the override, a small constructor in `quarto-core` or `quarto-system-runtime`; 8.2 picks the home), is built once from the `--profile` selection, and is what every native site uses to obtain its runtime: **replace the inline `NativeRuntime::new()` in `quarto-preview` (`lib.rs:340, 425, 484, 576, 673`, `render_helper.rs:413`, `re_execute.rs:301`) and in the `quarto` preview commands (`commands/preview.rs:234, 246`, and `commands/preview_static.rs:315, 333, 340, 644`, which F5b gave `--static`\'s flags first; F8 moves them onto the same factory so both modes share one mechanism, and replaces whatever F5b used if it differs, recording that in the Handoff log).** Sites that already take a runtime parameter (`config.rs` readers, `preview_out.rs:55`, `capture_driver.rs:164, 276`) need no change of their own; `import_route.rs:162, 524` build runtimes for pandoc resolution only and stay. **The whole-book download** (`quarto-core/src/book_download.rs:147`) builds its own runtime, so `BookDownloadParams` gains a runtime (or the profile selection from which the function builds one through the factory); without that, whole-book downloads would ignore `--profile` while single pages honour it. **A lint test** fails if non-test code in `quarto-preview`, or the preview commands in `quarto`, calls `NativeRuntime::new()` directly (a grep-style test in the spirit of the repo's other lint tests), so a new site cannot silently bypass the profile. The blast radius is about fifteen edits across three crates (`quarto-system-runtime`, `quarto-preview`, `quarto`, plus the `book_download.rs` parameter in `quarto-core`). Engine children already receive the resolved profile explicitly (`project_profile.rs:86-94`). The round-5 spikes (research B6) found `single_file_render.rs:873, 1093`, `config.rs:575` and `import_route.rs:524` to be inside `#[cfg(test)]` modules (not sites), and three more non-test sites reachable from `q2 preview --static`, `commands/render.rs:914, 1068, 1159`, which take the profile through `RenderArgs.profile` and `discover_with_profile` and so need no factory change (the lint's scope excludes them on purpose); 8.2 re-confirms against the tree it has. **The browser does not honour it:** its VFS has no profile files and its runtime has no environment, and this plan does not add them (no sync of `_quarto-<name>.yml`, `_quarto.yml.local` or `_environment*`, no profile argument on the wasm entries, no profile-derived format shipped to the browser). When `--profile` is given to the viewer, the server prints a startup notice that the html preview, which the browser renders from the synced project, ignores it, and the docs (`profiles.qmd`, the preview page) say the same; a `--share` guest's browser ignores it in the same way, while the guest's native routes tunnel to the host and get it. The format a profile supplies is not sent to the browser either, so a profile that only supplies `format: typst` makes the native PDF routes typst while the browser sees html; this is the same behaviour `QUARTO_PROFILE` has today and is recorded as a known limitation, not fixed here. A browser-side profile would be a separate plan (a project-layer format input for the resolver plus syncing profile files, with the `--share` exposure of `.local` files to consider).
- **F8-D7 The help text states the limits**, once, shared with `render` and `--static` (F1-D5): first `=` or `:` separates key and value, YAML typing, no dotted keys, no path rebasing; `book-scope` is ignored by the live preview; `-M` and `--to` shape the rendered preview and downloads, not engine execution (F8-D8); `--to` of an unservable format is refused; `--profile` affects the native routes, not the browser's html preview; **with `--share`, the `-M` values and `--to` are served to every guest through `/api/preview/config` and applied by their browsers (guests can already view the whole project and re-run its code, so this is accepted), so do not put secrets in `-M`.**
- **F8-D8 `-M` and executed output in the live viewer (decided).** The server-side capture and re-execution paths run engines outside the browser render. In the live viewer `-M` and `--to` shape the rendered preview and downloads, not engine execution, and the help text says so (Gordon's decision). 8.2 still records which server paths build a render overlay, so the limit is stated accurately. (`provide-hub` is the opposite case, F8-D9.)
- **F8-D9 `q2 provide-hub` takes `-M` (decided, unconditional).** `provide-hub` (`quarto/src/main.rs:~622`, `commands/provide_hub.rs`) joins a hub session and executes documents on this machine; execution is its whole purpose, so a `-M` that changes how code runs (`-M execute:eval:false`, `-M jupyter:python3`) belongs there, unlike in the viewer. It takes `-M/--metadata` only: no `--to` (it renders no output format, so it would be redundant), and no `--profile` (hub discovery syncs only the six named config files, `quarto-hub/src/discovery.rs:116-123`, so `_quarto-<name>.yml`, `_quarto.yml.local` and `_environment*` never reach `materialize_project`; a `profile.default` in the synced `_quarto.yml` still applies). Round-5 reading found that the execution path reads `runtime_metadata()` (see "What exists"), so wrapping the provider's runtime in an `Arc<RenderOverlay>` at both construction sites (`execute.rs:267` and `:524`) is enough for `-M execute:eval:false` to take effect. The overlay is carried by a **setter or a separate constructor** on `Provider` (`Provider::new` has four callers; do not add a positional parameter). **Staleness interaction (checked in 8.3c, not assumed):** the capture's `input_qmd` is `serialize_ast_to_qmd` of the merged AST (`engine_execution.rs:537, 661`), so it embeds merged metadata, while the viewer's staleness check (`capture_driver.rs:226` `recompute_staleness`, `quarto-preview/src/cache.rs:162`, through `compute_input_qmd` with no overlay) could mark every provider capture stale when a `-M` changes serialized metadata. **Verified in the round-5 spikes (research C2) with a probe on the real code path: it is real.** `input_qmd` is the merged front matter, so a capture recorded through a runtime that returns metadata byte-differs from the viewer's overlay-free recompute (`capture_driver.rs:283`) and is marked stale; today the hazard is latent (the provider's `NativeRuntime` carries no metadata) and this plan's wrapping makes it live for any `-M` that changes serialized front matter. **Decided fix (default, implemented in 8.3c):** the staleness field describes the source, not the provider's execution settings, so the provider stores an `input_qmd` computed **without** the overlay (a `compute_input_qmd` call on the un-overlaid runtime, patched into the capture payload before it is stored), while execution and outputs still see the overlay; the viewer's recompute then matches. 8.3c picks the patch point (the capture payload is built at `engine_execution.rs:661`) and tests both halves.
