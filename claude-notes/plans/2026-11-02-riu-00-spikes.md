## Why spikes first

The epic was drafted from reading code and from the EXR-16 notes. Four independent surveys on
2026-11-02 (preview and provider internals, the Positron side, the record library, the writer
gate and release history) found that several load-bearing assumptions were either wrong or
unverified. The ones that matter are collected in the register below. A design review of
RIU-1 to RIU-6 is only useful if these are settled, so each gets a spike with a pass or fail
criterion, and the plans are finished from the results.

## Ground rules

- **Branches.** q2-side spike code goes on `spike/riu-<id>-<topic>` branches cut from
  `feature/records-in-use`. Positron-side spike code goes on branches in a separate
  `git worktree` of Gordon's fork, never in `/Users/gordon/src/positron`, because
  `external-sources/positron` links to that checkout and other plans cite line numbers in it
  (EXR-16 ground rules). S5 to S7 are cut from `spike/q2-s3-inline-exec`, not from
  `upstream/main`, on purpose: the demo ends by combining them with the S3 command, and the S3
  worktree already has a working dev build. EXR-16 set a cut-from-`upstream/main` rule for its
  spikes; this plan departs from it for that reason.
- **Positron conventions.** New files over edits; unavoidable edits to upstream files wrapped
  in `// --- Start Positron ---` and `// --- End Positron ---`; no `tsc` directly on the main
  project; vitest through `npm run test:positron`.
- **Real user data.** Positron cache files on this machine come from real documents. Copy a
  file into the scratchpad before using it, never modify Positron's own directory, and do not
  commit copies.
- **q2 binary.** `q2` on PATH (`~/.local/bin/q2`) is not this branch's build. Use
  `cargo run --bin q2 --` or `target/debug/q2`, and record the commit and profile at the top of
  each section. After any Rust change that preview serves, run the full chain in "Verifying
  Rust changes in `q2 preview`" of `AGENTS.md` (`npm run build:wasm`,
  `cargo xtask build-q2-preview-spa`, `cargo build --bin q2`).
- **Findings.** One note, `claude-notes/research/2026-MM-DD-riu-0-spikes-findings.md`, with a
  section per spike: the question, the method, the observed result with the exact invocation
  and an explicit statement of how the output was inspected (browser, file, HTTP, log), a go or
  no-go, the branch, and what was not tested. Render it with `q2 render --strict` before any
  push.
- **Say what was not seen.** A step that needed a browser or a human and had neither is marked
  "not run", never inferred from the absence of errors.

## S1: records through the real q2 preview and hub

This is the old RIU-1 (prove records in the real binary).

- **Question.** With the writer gate on, do execution records work end to end in `q2 preview`
  and through `provide-hub` and the hub client (U3 to U9)?
- **Background (from the surveys).**
  - The gate is `record_writing_enabled()` (`quarto-core/src/engine/capture_files.rs:266`),
    off by default; `QUARTO_ENGINE_RECORD_WRITE=1` turns it on. It is consulted by the preview
    writer (`capture_driver.rs:388`, inside `write_capture_doc`, reached from the eager driver
    and `re_execute.rs`) and by provide-hub (`execute.rs:361`). A plain `q2 render` does not
    consult it.
  - The cache is `<data_dir>/captures`; the CLI always passes `cache_dir: None`
    (`quarto/src/commands/preview.rs:368`) and the data directory is a `TempDir` deleted on
    exit unless `--data-dir` is given (`preview.rs:248-255`).
  - Policy `off` makes the eager driver return immediately (`capture_driver.rs:65-69`) and
    `recompute_staleness` a no-op, so an `off` preview creates no `CaptureRef`. The re-execute
    POST is not gated. Whether the SPA hides the button is not established.
  - `record_eager_captures` skips any path that already has a capture ref, so a persisted
    `--data-dir` store would not re-record.
- **Setup.**

```bash
export QUARTO_ENGINE_RECORD_WRITE=1
cargo run --bin q2 -- preview --no-browser --data-dir <scratch>/riu-s1-data -v <fixture>
```

- **Fixtures** (kept; new directory `crates/quarto-preview/tests/fixtures/records-in-use/`,
  read `claude-notes/instructions/testing.md` first):
  - `basic.qmd`: Python; a prose paragraph; a text cell; a matplotlib figure cell; a pandas
    table cell; an error cell with `#| error: true`; one inline span.
  - `echo.qmd`: one cell, for a presentation-only option edit.
  - `mixed.qmd`: Jupyter plus a second engine (a knitr chunk if R is usable per S0, else
    `{python.marimo}`).
  - `knitr.qmd` and a Julia document, if S0 allows.
  - `project/`: a `_quarto.yml` with `preview: {engine: manual}` and two documents.
- **Scenarios.** For each, record the exact invocation, the observed result, and how it was
  inspected.
  - B1 gate off: `<data-dir>/captures/` holds `<key>.bin` only (the control).
  - B2 gate on, first open: the engine runs once, every output shows (text, figure, table,
    error, span), and `captures/` holds `<key>.bin` and `<key>.record.bin`. Decompress the
    record and check it: nbformat 4.5, one cell per unit, content hashes, outputs.
  - B3 prose-only edit: stays fresh, no "Re-execute" button, no kernel run. Record whether the
    cache key changed and whether a second entry was written (the key is the input text, so it
    will change). Settles U4's first half.
  - B4 code edit: that cell stale or source, the others still showing outputs, the button
    present; click it and confirm refreshed outputs.
  - B5 presentation option edit in `echo.qmd`: the output stays, the code toggles, no re-run.
  - B6 inline span edit: the span goes stale and the cells stay fresh.
  - B7 restart: stop and restart with the same `--data-dir`: cache hit and no kernel start (U6).
    Restart without `--data-dir`: confirm the cache is gone.
  - B8 `preview.engine: off` with a persisted `--data-dir` and a pre-existing capture ref, then
    with a fresh one: are records shown, and does the SPA offer the button (U5). Also `auto`:
    an edit re-executes.
  - B9 `record: true`: `q2 render -M 'execute:{record:true}'` writes
    `.quarto/execution-records/<doc>.ipynb`; start preview and confirm it ignores the file
    (the known gap).
  - B10 gate on for knitr-only, Jupyter-plus-knitr, Julia and marimo documents; compare with
    the gate off. The EXR-15 note says an engine that builds no record loses its output in a
    mixed document and no test covers it (U7).
  - B11 failure modes (U8): an unwritable cache directory; a corrupt `<key>.record.bin`; a
    record with a future `quarto_record_version`; `<key>.bin` deleted with the record kept; and
    a `.quarto` that is a regular file under `q2 render` with `record: true` (the render is
    expected to fail today, because the write is propagated with `?` at
    `engine_execution.rs:864`).
  - B12 hub path (U9): a local hub (`q2 hub`, no auth), a project holding `basic.qmd`, then
    `q2 provide-hub <project> --file basic.qmd --token dev` once, answering the consent prompt.
    Open the hub client in a browser: outputs, then a prose edit and a code edit for
    staleness. Check the capture doc's MIME (`application/x-engine-record+gzip` expected).
  - B13 the hub client in B12 was built from this commit (stale-WASM check).
- **Defects.** Each defect found gets a failing test first, a verified failure, then a fix,
  following the repo's TDD rule. Prefer an integration test that drives the entry point the
  binary uses (`quarto-preview/tests/integration/`, as `eager_capture.rs` and `cache_hit.rs`
  do), registered in `tests/integration/main.rs`. A design question is not a defect: it goes
  to the note under "Handed to RIU-1" or "Handed to RIU-2".
- **Pass.** Every scenario has an observed result or a stated reason it was not run; each
  defect is fixed with a test or filed; the note says whether flipping the default is safe
  for the local preview.
- **Effort.** 1.5 sessions.

## S2: a record-only entry through the whole preview path

- **Question.** Is a record-only entry (no legacy capture) valid end to end, and how big is the
  change (U10, U11)?
- **Background (surveys).**
  - `write_capture_doc` has no emptiness check. The guards are in its callers:
    `capture_driver.rs:181` (`record_one`), `re_execute.rs:307` (`perform_re_execute`) and
    `quarto-hub-provider/src/execute.rs:338` (`run_and_store`).
  - `record_capture_run_cached` (`cache.rs:230`) writes only inside `if !run.captures.is_empty()`
    (`cache.rs:274`), writes `<key>.bin` first, and writes the record only when it has
    engines (`cache.rs:285`). A missing `<key>.bin` reads as a miss, so a record-only entry
    would re-run the engine.
  - `encode_capture_payload` already handles a record-only run when the gate is on; with the
    gate off it writes an empty legacy list.
  - `recompute_staleness` has a Legacy arm that assumes captures (`capture_driver.rs:264-272`).
  - No test covers a true record-only entry.
- **Method.** On `spike/riu-s2-record-only`, with the gate on:
  - (a) Change the `cache.rs:274` guard to captures non-empty or record with engines; skip
    `write_cached` when captures are empty and write the record file; decide hit or miss from
    either file; replace the three caller guards with "no captures and no record with
    engines".
  - Run `basic.qmd` in the real preview: first open, restart with `--data-dir`, prose edit,
    code edit. Confirm no `<key>.bin` is written or required.
  - Run the affected test suites and list every test that fails, with the reason (the
    surveys found: `gate_defaults_off_and_parses_overrides`; `eager_capture.rs`,
    `cache_hit.rs`, the provider `fetch_captures` helper, and several `capture_driver.rs`
    unit tests that read the default writer's output as legacy).
  - (b) Prototype a path-keyed pointer: `record_one` and `perform_re_execute` write
    `<cache>/by-path/<hash(rel_path)>` holding the last key; the preview looks the record up
    through it when the content key misses. Check that a prose edit then reuses the record in
    standalone preview and that a code edit shows stale rather than re-executing under
    `manual`. Compare with using the hub index `CaptureRef` alone (path-keyed, but it holds a
    samod doc id in a store that is ephemeral by default).
- **Pass.** A record-only entry is displayed through the real preview with no legacy file; the
  note lists every function and test that must change; and it states whether the pointer is
  needed and its smallest working form, or why the `CaptureRef` suffices.
- **Fail.** Something beyond the listed callers assumes legacy captures. Then the finding is
  the extra scope, and RIU-2 is resized.
- **Effort.** 1 session. Depends on S0 and S1's environment.

## S3: where record docs can be stranded, and consent

- **Question.** Which surfaces write capture docs that an older reader could be handed, and can
  an import-only provider skip the consent gate (U12, U13)?
- **Background.** The runbook's rule (readers first, flip later) exists because the hub
  exposes no version or capability. For the hosted hub, what counts is the deployed `q2_ref`,
  not a numbered release. No released tag contains the record reader (latest tag
  v0.39.0, 2026-10-29, checked 2026-11-02), so today the reader exists only on the epic
  branches.
- **Method.** Trace and then test each writer and its readers:
  - Local `q2 preview`: the embedded store in `data_dir`, read by the SPA embedded in the same
    binary (confirm the SPA's WASM is built from the same commit and that nothing else reads
    this store).
  - `q2 preview --share` with a guest using `--join`: whose store holds the capture doc, and
    which binary's SPA reads it. A guest on an older binary than the host is the case to
    check.
  - `q2 hub` plus the hub-client web app, and `q2 provide-hub` writing to a remote hub: which
    hub version is deployed and which hub-client version reads (a question for Gordon; record
    the answer).
  - Read `consent.rs` and the `execute_document` flow: the consent call sits after
    materialize and review-file, so an import path would branch before `review_file`. Confirm
    nothing else gates on consent (the beacon, the exec channel).
- **Pass.** A table, one row per writer: the store it writes, who reads it, whether a version
  mismatch can strand it, and the evidence. A yes or no on the consent skip with the code
  reference.
- **Effort.** 0.5 session. Mostly reading; the guest check needs two binaries.

## S4: a Positron cache spliced in the real preview

- **Question.** Does the design "convert the import to a `Record` with no engines and empty
  execution hashes, then splice as usual" work (U14 to U16)?
- **Background (survey).**
  - `match_units` skips cells whose `quarto_exec_hash` is empty in the execution pass
    (`matching.rs:112-115`) and then matches by content hash with the occurrence rule
    (`matching.rs:121-132`).
  - With `quarto_engines` empty the splice's `engine_for` returns `None`
    (`record_splice.rs:77`) and it falls back to a content-hash-only key
    (`record_splice.rs:156-162`). No engine entry is needed.
  - `record_is_stale` returns `Ok(false)` when there are no engines (`staleness.rs:88`), so an
    imported record would always look fresh; and `rehash_record` stamps a hash of an empty list
    (`overlay.rs:38-45`). Neither may be called for an imported record. Per-unit staleness comes
    from the `SpliceReport`.
  - `RecordBuilder` cannot produce an empty execution hash (`builder.rs:87-142`), so the record
    must be built by hand: `Record`, `RecordCell` and `CellMetadata` have public fields.
  - `DisplayOnlyOutputs` has private fields and the probe test
    `imported_outputs_convert_to_nothing_a_reuse_decision_takes`
    (`tests/integration/positron_conformance.rs:292`) forbids any `From` or `Into` to a unit
    result or a record cell. Reading `outputs()` and building a cell by hand is allowed.
  - The language gate needs the owner and the language token, and the owner is unknown inside
    the splice (the preview registry is empty in the tests; the record has no engines), so the
    gate must run at conversion with a caller-supplied owner function.
  - The occurrence must be counted per content hash across all units and the gate applied after
    it, as the demo harness does with its `seen` map, or a gated-out duplicate shifts the
    pairing.
- **Method.** On `spike/riu-s4-positron-record` (stacked on S2):
  - Write `record_from_positron(&PositronImport, &[Unit], &AuthorTexts, owner)` as a scratch
    function: cells with `quarto_engine: None`, `quarto_lang` from the unit, kind cell, the
    real content hash, and `quarto_exec_hash: ""`; provenance in the flattened `extra` map;
    `quarto_cache_version` left `None`; `quarto_record_version` 1.
  - Use a real Positron cache file from this machine (copy one to the scratchpad; confirm the
    source `.qmd` still exists, otherwise write a document whose cells match the cache's
    hashes). Convert, serialize, place it as the record-only entry from S2 in a preview data
    directory by hand, and open the document in the real preview with no kernel.
  - Check: outputs show for matched cells; an edited cell goes stale and the rest stay; a cell
    with a `python.marimo` token gets nothing; a duplicate-hash pair pairs by occurrence; an
    HTML output and an image output render; a Positron cell with no matching unit appears in
    `orphaned`.
  - `cargo check` the conversion and `import_positron_cache` for the WASM target
    (`wasm-quarto-hub-client`), since viewers run the splice there.
- **Pass.** A Positron cache shows in the real preview with no engine and no kernel, per-unit
  staleness is right, the gate behaves, and the conversion compiles for WASM. The note states
  the final signature, where the provenance marker lives, and what the viewer needs in order to
  show "outputs from Positron".
- **Fail.** The splice needs engine information after all; then the finding is the smallest
  addition (the survey's option ii, a second splice input, is the fallback).
- **Effort.** 1 session.

## S5: pushing outputs into an open Positron document

- **Question.** What is the smallest change that makes cached outputs appear in an
  already-open document, and where does the cache live (U17, U18)?
- **Background (survey).** There is no existing push path. `_loadCachedOutputs` is private and
  guarded by `_cachedOutputsLoaded` (`quartoOutputManager.ts:933`), and `loadCache` returns the
  in-memory entry for an open document instead of re-reading disk (`:240`). The cache service
  has no events and no file watcher. Public methods `clearCellOutputs` and `saveOutput`
  exist, and `saveOutput` marks the document dirty so it persists after one second. The
  contribution is reachable with `editor.getContribution<QuartoOutputContribution>`
  (`quartoCommands.ts:459`).
- **Method.** In a new worktree and branch cut from `spike/q2-s3-inline-exec`:
  - Add `reloadCachedOutputs()` to `QuartoOutputContribution`: clear the document's outputs,
    reset `_cachedOutputsLoaded` and `_contentHashByCellId`, call `_loadCachedOutputs`.
  - Add a command that, given a hand-made JSON of cells keyed by content hash, matches them to
    the open model's cells, calls `clearCellOutputs` then `saveOutput` per cell (taking
    `cell.id` and `cell.contentHash` from the model), and calls `reloadCachedOutputs`.
  - Try the alternative the survey suggested: an `importCachedDocument(uri, ipynbJson)` on the
    cache service that reuses the private `_ipynbToOutput`, and compare.
  - Add a debug command that shows `cacheService.getCachePath(uri).fsPath`.
  - In the dev build, with a document that was already run and open: confirm the outputs
    appear without closing the document, persist across a close and reopen, and that a dirty
    in-memory document does not overwrite them wrongly.
  - Locate the cache directory for this dev build (the survey's reading is
    `~/Library/Application Support/code-oss-dev/User/globalStorage/quarto-inline-outputs/`,
    not `.../Positron/...`, with the `User/globalStorage` segment unverified), and for an
    installed release build, and note how `--user-data-dir` or `POSITRON_APPDATA` change it.
- **Pass.** Outputs appear inline in an open document through the smallest change, the change
  is written down with file and function names, and both cache locations are verified.
- **Fail.** The view zones cannot be refreshed without a deeper change; then the finding is
  what Positron would have to add.
- **Effort.** 0.5 to 1 session. Needs the dev build (S0) and Gordon watching the window.

## S6: how a Positron command runs q2

- **Question.** What is the least-effort way for a Positron command to run `q2` and get a
  result back, and will the GUI app find `q2` (U19)?
- **Background (survey).** `positronQuarto` is a browser-layer contribution with no process
  spawning; extensions use `child_process` (`positron-supervisor` uses `execFile`); there is
  no Quarto extension in `extensions/`. Workbench code can register internal commands with
  `CommandsRegistry.registerCommand('_name', ...)` that an extension can call with
  `vscode.commands.executeCommand`. The layering rules for `INativeHostService` from the
  browser layer, and a precedent for an extension calling an internal `_` command with
  arguments, were not checked.
- **Method.**
  - Route A: `ITerminalService` from the workbench command (simple, but no completion
    callback).
  - Route B: a tiny spike extension (or a command in an existing extension) that does
    `execFile` on `q2`, then calls an internal workbench command with a JSON argument.
    Check the command argument marshalling for strings and objects.
  - In both, check that `q2` resolves: a macOS GUI app does not inherit the login shell PATH,
    so `~/.local/bin` may be missing. Look at `IShellEnvironmentService` and at how other
    extensions resolve tools, and settle on a setting or an environment variable for the `q2`
    path.
  - Run `q2 --version` and `q2 render` on a fixture from the command and show the result in a
    notification.
- **Pass.** A command runs `q2`, gets stdout and an exit code, and hands them to a workbench
  command; the note names the mechanism, the extension host, and the `q2` path setting.
- **Effort.** 0.5 session.

## S7: export for Positron

- **Question.** What does Positron actually display from an exported record, and what is the
  final transform (U20)?
- **Background (survey).** `write_record` emits outputs verbatim as the engine gave them
  (`record/writer.rs:22-36`): stream `text` as an array of lines, `text/plain` and `image/png`
  as strings, JSON mimes as objects, `execution_count` possibly `null`, many `quarto_*` keys,
  `quarto_source` project-relative. Positron needs `quarto_cache_version: 1`, an `outputs`
  array on every code cell, string `data` values, and keeps only `quarto_cell_id` and
