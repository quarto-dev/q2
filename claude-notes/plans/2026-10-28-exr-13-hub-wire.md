## Goal

Let the coalesced record from EXR-4 travel as the hub capture payload, with the
least change to everything that already moves capture documents:

- one new MIME type and `meta.kind` for record documents;
- one reader that decides legacy versus record by looking at the payload, used by
  every native, book and WASM reader;
- one writer helper next to `gzip_captures`, used by all three capture writers;
- `hub admin` still finds, ages and collects orphaned record documents;
- the capture reaches WASM and is parsed there, without any TS-side change to how
  bytes are fetched;
- the legacy path sits behind one seam (the `Legacy` arm of the payload enum), so
  removing it later is deleting an arm (decision 8).

Presenting a record (splicing its outputs into the preview AST) is EXR-14. This
plan ends when a record payload is read everywhere a legacy capture is read.

## Background (verified in code on 2026-10-28, workspace-1 at `2ee0bd966`)

**The document shape today.**

- `crates/quarto-hub/src/resource.rs:162` defines `CAPTURE_MIME_TYPE =
  "application/x-engine-capture+gzip"`. `create_binary_document` (`:136`) writes
  ROOT `content` (Bytes), `mimeType`, `hash` (SHA-256 hex).
- `create_capture_document` (`:201`, `_at` variant `:207`) calls
  `create_binary_document(gzipped, CAPTURE_MIME_TYPE)` (`:213`) and adds an
  uncompressed `meta` map: `kind: "engine-capture"`, `schemaVersion` (the constant
  `CAPTURE_META_SCHEMA_VERSION`, `:180`, value 1), `createdAt`, `sourcePath`,
  `engines`. Docs without `meta` stay valid. `read_capture_meta` reads it back.
- The index sidecar entry is `CaptureRef{captureDocId, staleness?, state?,
  lastError?}` in `ts-packages/quarto-automerge-schema/src/index.ts:40`.
  `CURRENT_SCHEMA_VERSION` is 3 (`:14`; V3 added `folders`), and the `captures`
  map has existed since V2. No index change is needed for a new payload.

**Writers (all native, all duplicated, all calling `gzip_captures`).**

- `gzip_captures` (`crates/quarto-core/src/engine/capture_files.rs:231`) serializes
  an `EngineCapture` array, gzips it, and logs `capture_doc_size_warning` above

- Its three callers each have their own `write_capture_doc`:
  `crates/quarto-preview/src/capture_driver.rs:331`,
  `crates/quarto-preview/src/re_execute.rs:336`, and
  `crates/quarto-hub-provider/src/execute.rs:493`. The provider's comment says it

**Readers: two copies of shape guessing.**

  `project/book/request.rs:82`, and the WASM wrapper `parse_capture_from`

  `quarto-hub` does not depend on `quarto-core`, so the hub side only ever sees bytes
  and the MIME. *Verified 2026-10-30.*

  in Rust. The TS layer needs no new knowledge of the format.

## Design decisions (from the epic, do not re-litigate)

1. **New MIME and kind.** `RECORD_MIME_TYPE = "application/x-engine-record+gzip"`
   next to `CAPTURE_MIME_TYPE`; `meta.kind: "engine-record"`. The envelope
   `schemaVersion` stays 1 (the envelope is unchanged); the record's own version
   is `quarto_record_version` inside the payload (EXR-4).
2. **Same document shape.** Binary doc with `content`, `mimeType`, `hash`, `meta`;
   same index `captures` sidecar and `CaptureRef`. No index schema bump.
3. **One reader, dispatching on the payload in Rust.** `parse_capture_payload` returns a
   `CapturePayload` (`Empty`, `Legacy(Vec<EngineCapture>)`, `Record(Record)`) and
   replaces both `parse_capture_gz` and the shape guess inside `read_capture_from_doc`.
   A top-level JSON object with an `nbformat` key is a record; an array, or an object
   with `engine_name`, is legacy; anything else is an error naming both shapes. It
   dispatches on the payload and never on the MIME, because the TS side never sees the
   MIME (`useActiveCaptureBytes` returns bytes only). Which wins, a hub payload or an
   on-disk record, is not a question this plan has to answer: nothing in the epic reads the
   on-disk record file (only EXR-4's reader and trace replay do), so the reader never sees
   two candidates (EXR-15 decision 8). `read_capture_from_doc` becomes a
   thin fetch of `content` plus a call to `parse_capture_payload`; `parse_capture_gz`
   survives only as the private body of the `Legacy` arm (decision 8).
4. **Immutable gzipped blob.** Same lifecycle as today: every execution writes a
   new doc and repoints the `CaptureRef`; orphans are collected by `hub admin`.
5. **One kind per path.** A `CaptureRef` points at a legacy capture or a record,
   never both. Old docs are never rewritten in place.
6. **Readers before writers.** This plan and EXR-14 ship in release N. Record
   writing is switched on in release N+1, or behind a flag until then. Once records
   have been written, reverting the reader (shipping a release N-1 reader again)
   strands them: that is the one one-way door in the epic's hub transition, so the gate
   flips only after the reader has been out for a release.
7. **Records are classified as the existing `DocKind::EngineCapture`.** `classify.rs`
   accepts both MIME types as `EngineCapture`, and `meta.kind` (`engine-capture` or
   `engine-record`) tells them apart for inventory counts. Otherwise an orphaned record
   would classify as `BinaryFile` and never be collectible. There is no new `DocKind`:
   the collector's safety allowlist is exactly `EngineCapture` (`scan.rs:374`,
   `collect.rs:341`) and `classify.rs` says never to guess, so a new kind would touch
   the safety-critical part, and the `DocKind::as_str` counters (`manifest.rs`) stay
   stable. The allowlist is unchanged. A doc with no `meta` counts as legacy in the
   inventory.

8. **The legacy path is one removable seam** (Gordon's decision on compatibility after
   legacy removal: old captures eventually degrade to "no capture", the window is open
   and undated, and the code must stay easy to remove; see EXR-17).
   - The `Legacy` arm of `CapturePayload` is the only code that may call
     `parse_capture_gz`, `apply_capture_splices` or `label_reinject::strip`.
   - New code in this plan, EXR-14 and EXR-15 must not import from
     `engine/capture_splice.rs`. Helpers it needs live outside that module (EXR-2
     moves `engine_cell_lang` out early). A grep-style unit test enforces both rules,
     as the repo already does for other invariants.
   - Tests that exist only for the legacy shape share the name prefix
     `legacy_capture_` (or one `legacy_capture` test module), so EXR-17's inventory is
     one search.
   - The behavior the `Legacy` arm will have after removal, "cannot present: show cells
     as source and log one notice naming the document", exists from the start behind a
     flag that is off while legacy payloads still present. Degrading later is then a
     one-line switch.

**13a implementation notes (2026-10-31).** Where the code differs from the wording above:

- `parse_capture_gz` is gone, not kept private. `parse_capture_payload` gunzips once and parses the
  JSON value; the private `legacy` module in `captures.rs` is the `Legacy` arm (`parse`, which does
  the array-or-single-object step, and `arm`, which applies the degrade flag). Deleting legacy
  support (EXR-17) is deleting that module and the `Legacy` variant. The seam test asserts the

- Call sites move to `parse_capture_payload(..).into_captures()`: a record yields no captures
  until EXR-14, so its cells render as source. The preview cache read (`cache.rs`) also moved, since

- `read_capture_from_doc` returns `CapturePayload`. The staleness check keeps the byte compare for
  `Legacy` and skips a record (per-unit staleness is EXR-14).
- The carrier is `HtmlRenderConfig::record` beside `captures`; `with_record` clears `captures` and

  with `..Default::default()`.
- Inventory: `ScanManifest::capture_inventory` (`#[serde(default)]`, so older manifests still

- The `read_capture_from_doc` parity test runs over a real samod repo document

- The WASM "tests" are hub-client `*.wasm.test.ts` (`recordPayload.wasm.test.ts`); the record is the

## Risks and open questions

- **Old deployed clients** fail on a payload they cannot parse (`Err("JSON parse failed")`);
  how the SPA surfaces that is not known. Mitigation is the release gating, plus the recorded-fixture test.
- **Two version numbers** (`meta.schemaVersion` for the envelope, `quarto_record_version`
  for the payload) can be confused. The doc comments on both must say which is which.
- **One-way door.** After record documents exist in a store, reverting the reader to a
  release that cannot parse them strands those documents (they keep their `CaptureRef`
  and show as source). Nothing rewrites them back. This is why writers wait a release.
- **Misleading parameter names** (`capture_gz_json`) remain until a follow-up rename.
- **Deployed index documents** are untouched, but the hub-client migration code
