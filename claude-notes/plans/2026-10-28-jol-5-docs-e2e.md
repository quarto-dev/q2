## Goal

1. A user can follow the docs to run a document with `ggsql` cells (or any language
   with an installed kernel) and understands the `jupyter:` key and the missing-kernel
   diagnostic (a warning in a single-engine document, an error in a multi-engine one).
2. CI proves kernel selection and ownership end to end without installing ipykernel or any
   real kernel, using the fake kernel from EXR-3 extended here.

## Background

Verified in the tree on 2026-10-28 (workspace-1, `origin/main` at `2ee0bd966`) unless marked.

- Existing Jupyter integration tests need a real kernel and are `#[ignore]` or skip when the
  engine is missing: `crates/quarto-core/tests/integration/jupyter_integration.rs`
  (`#[ignore = "requires ipykernel"]`, driving `get_or_start_session("python3", ...)`
  directly) and `jupyter_kernel_cleanup.rs` (skips when the engine is unavailable; isolates
  connection files with `JUPYTER_RUNTIME_DIR`). There is **no fake-kernel fixture yet**:
  EXR-3 builds the first one (a minimal kernel for the kernel-free unit-loop tests), and
  this plan extends it. *Verified.*
- `JupyterEngine` availability is a probe of a `jupyter` executable (`jupyter --version`
  must exit 0; memoized per path, `engine/jupyter/mod.rs:80-125`). Any test that goes
  through the engine registry therefore also needs a stub `jupyter` on `PATH`; a test that
  calls `execute_qmd` directly (a `pub` function in `text_execute.rs`) bypasses the probe.
  *Verified.*
- Kernel discovery uses `runtimelib::list_kernelspecs_with_jupyter_paths` and
  `find_kernelspec_with_jupyter_paths` (`engine/jupyter/kernelspec.rs:56,75`), so a
  kernelspec directory on `JUPYTER_PATH` is found. Whether the data-dir search reads the
  environment on every call or caches it was *not verified*; it decides whether tests can
  set `JUPYTER_PATH` per test or need a dedicated test binary.
- `runtimelib` and `jupyter-protocol` 2.0 are already dependencies
  (`crates/quarto-core/Cargo.toml:189-190`). Whether `runtimelib` exposes kernel-side
  connection helpers (shell, iopub, heartbeat sockets as a server) was *not verified*; it
  decides how much protocol code the fake kernel needs. EXR-3 Phase 1 answers it and
  records the answer there.
- Docs: `docs/guides/authoring/engines.qmd` already explains engine sequences and that a
  language no engine claims falls to Jupyter (line 44) and shows
  `engine: [{jupyter: {kernel: python3}}]` (lines 35-36). `docs/guides/authoring/notebooks.qmd`
  and `computations.qmd` mention Jupyter. No page covers non-Python kernels or the
  `jupyter:` key. *Verified.*
- ggsql specifics from the JOL epic research notes: the kernelspec is installed with
  `ggsql-jupyter --install` and uses a `{resource_dir}` argv entry (expanded by
  `expand_resource_dir` in `daemon.rs:454`); the PyPI install writes the same form.
  *Not re-verified.*
- Two items from the JOL epic were unverified and gate the user instructions. Both were
  tried on 2026-10-29 with the `q2` nightly 0.36.0-nightly.20261027 on PATH and the
  installed ggsql 0.5.2 kernelspec (venv from `~/docs/ggsql-user`): a plain `{ggsql}`
  document renders its plot with no `engine:` and no `jupyter:` key (also with either
  key or both), so neither key is needed; and a `{python}` document with no `engine:` key
  executes. A mixed `{python}` then `{ggsql}` document fails with a Python `SyntaxError`
  (the ggsql text goes to the Python kernel), with or without `engine: jupyter`, which is
  the case a multiplexing kernel (SoS, via the `jupyter:` key) addresses; JOL-3 (several
  kernels) is deferred. Phase 1 re-checks these when the docs are written.
- The SoS route is verified for q1 and not yet through q2. The installed `sos` kernelspec has
  `language: sos` (`~/Library/Jupyter/kernels/sos/kernel.json`, verified 2026-10-30);
  q1 with `jupyter: sos` was run (2026-10-31): a `{python}` fence stays display-only and only
  a `{sos}` fence ran, so JOL-2a (which sends every Jupyter-owned cell to that kernel) is a
  behavior change for q1 documents; the earlier q2 success (JOL epic, 2026-10-17) used a shim
  kernelspec named `python3`; JOL-2a is not built, so `jupyter: sos` has not been tried
  through q2; mixed-language documents
  need `%use <kernel>` lines in the cells; and plain `{ggsql}`-style fences on SoS
  would need q2 to send SoS\'s `cell_kernel` in the execute request (runtimelib\'s
  ability to add request fields is unverified). JOL-2a carries the manual check and
  the `cell_kernel` research item; the docs here describe only what that check shows.

## Design decisions

From the epic and the JOL epic; not to be re-litigated.

- ggsql is the worked example; the docs state plainly that owned languages execute
  because the resolver assigned them to Jupyter, and what to do when no kernelspec exists
  (the missing-kernel diagnostic from JOL-2b: an error in a multi-engine document, a
  warning in a single-engine one where the cell stays unexecuted).
- The e2e test uses the fake kernel that EXR-3 builds from dependencies already in the
  tree, extended here; no external install and no network.
- The docs describe the `jupyter:` key as it ships (scalar and `kernel:` map from JOL-2a;
  the per-language map only if JOL-3 is reopened) and say that the language ownership gate
  decides which cells run. For mixed-language documents the docs recommend a multiplexing
  kernel (SoS) selected with `jupyter:`.

## Out of scope

- The multi-kernel feature itself (JOL-3, deferred), execution of inline expressions docs
  ([EXR-3](2026-10-28-exr-03-jupyter-iee.md) and
  [EXR-18](2026-10-28-exr-18-docs-e2e.md) own those).
- Cell-option comment syntax for SQL-family languages: `comment_syntax_for` defaults an
  unknown language to `#`, wrong for ggsql (`--`). Record as a follow-up after checking
  whether Q1 has a ggsql entry; do not fix here.
- Vector (SVG or Vega-Lite) output for ggsql.

## Phase 2: extend the fake kernel (tests first)

EXR-3 builds the base fake kernel: it answers `kernel_info_request`, heartbeat and
`execute_request`; for `echo <text>` it emits `status busy`, one `stream` stdout message,
an `execute_result` with `text/plain`, `status idle` and a matching `execute_reply`; it can
emit an `error` message and an execution with no `execute_result`. This plan adds what only
the end-to-end tests need.

## Risks and open questions

- A hand-rolled fake kernel is protocol code to maintain; keep it to the minimum above.
  It is shared with EXR-3 and EXR-5, so a change here must keep their tests green. If
  `runtimelib` has no kernel-side helpers, EXR-3 weighs a thin ZeroMQ implementation
  against a Python fake that needs `pyzmq` (which violates "no external install").
- Env-var driven discovery makes tests process-global; a dedicated test binary or a
  serial group may be required.
- The user instructions may be wrong if the front-matter unknowns resolve badly; do Phase 1
  first.
