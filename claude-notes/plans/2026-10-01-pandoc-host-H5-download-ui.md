## Overview

The product surface: a "Download as" control next to the print button, a download-status channel, the three-class format classification with a `PreviewRouter` mode, accessibility, E2E and the changelog. docx first; the menu grows as request phases land.

## Decisions

- The menu comes from the Rust-owned format table; a click renders with the format overridden, on click only (D8.1, D8.3).
- Documents the preview cannot render get no preview, only a "Download <type>" button for the document's own format, rendering only on click (D8.2); three classes with `aria-disabled` explanation for "neither" (D8.4).
- A document with errors does not download; warnings still download (D8.5).

- **From R4 (landed):** `getPandocFormats()` rows have a `hidden` flag (`pdf` is hidden until H8): filter on it when building the menu. A typst request can carry a warning the menu should show: `Q-20-9` (R6: a remote image could not be fetched and its alt text is used instead; remote images are otherwise fetched in the browser, so only a failed download warns) (R8 retired `Q-20-10`: styled raw HTML tables are now CSS-inlined in the browser, so no warning). The `.typ` download names no images or brand assets, so say it may have dangling resource references (D8.6).

- **From R9 (planned; Gordon, 2026-10-02):** for a document in a book project (the resolver's `book` field, `{ chapter, chapters }`, `book.chapter === true`) whose format is typst, pdf or epub, the menu entry reads **"Download book as <format>"** and a second item **"This chapter only"** calls `render_pandoc_request` with `options.scope: 'chapter'`; docx and pptx keep one entry that downloads the active chapter silently. A page that is not a chapter (`book.chapter === false`) has the ordinary entries and downloads that page alone, with no mention of the book. While a book renders the status reads "Rendering chapter i of N: <file>" (from the export's `onProgress`, called before each chapter), and on success "Book downloaded (N chapters)" (from `stats.book.chapters`). For a book download the host collects the capture bytes of **every chapter** at click time (the `captures` sidecar's `captureDocId` for each path in the resolver's `book.chapters`, fetched in parallel with `getBinaryDocById`, as `useActiveCaptureBytes` does for the active file; keys are sidecar keys: `/`-normalized paths relative to the hub's VFS project root) and passes them as `options.capturesByPath` (R9, D-6; the export gains one optional trailing `options` object, `{ scope?, capturesByPath?, onProgress? }`; the Rust side yields to the event loop itself between chapters, so the host needs no timer trick for painting or abort); chapters with no capture are simply absent from the map, a failed fetch for one chapter degrades that chapter to source with a status note, and the click's cancel is checked between fetches (`getBinaryDocById` has no signal, but the sync client bounds each attempt with a deadline and retries). The PDF preview pane's controller passes `scope: 'chapter'` (Gordon, 2026-10-02: a whole-book recompile per edit is unworkable). In the native embed (`isPreviewEmbed()`), which renders one chapter natively, the menu keeps the plain chapter-alone entries: no "Download book as", no "This chapter only". `downloadService.ts` (`buildRequest`, which today passes no scope) is the wiring point: R9's default scope is `'auto'`, so the book entry, the per-chapter capture collection and the `capturesByPath` pass-through land in the same H5 change. Each is wired when R9 lands, as its own landing; the Close-out wire-up box for project downloads covers chapter-alone entries (R7) and book entries (R9) separately.
