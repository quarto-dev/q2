# Epic: Book projects (`ProjectKind::Book`)

**Date:** 2026-09-21 (revised after a critical review pass — see "Revision history" at the end)
**Status:** Design frozen after a multi-round research/design conversation; drafting per-phase plans.
**Design (authoritative):** [`../designs/book-projects-architecture.md`](../designs/book-projects-architecture.md)
**Integration branch:** `feature/book-projects`, stacked on `feature/pandoc-writer-hybrid` (that epic is substantially complete — single-document docx/pptx/typst/epub via Pandoc + vendored Q1 Lua — but not yet merged to `main`; this epic depends on its landed shape, not on the merge).
**Q1 references:** `src/project/types/book/*.ts`, `src/format/{typst,epub,pdf}/format-*.ts`, `resources/filters/crossref/sections.lua`, `tests/docs/smoke-all/typst/orange-book*` (the deepest numbering-correctness fixture in Q1's own test suite).

## The problem

`ProjectKind::Book` exists as an enum tag (`crates/quarto-core/src/project/mod.rs`) but dispatches to `DefaultProjectType` (`orchestrator.rs:627`) — a "not yet supported" stub (`bd-m1fzvpov`, `Q-5-18`/`Q-16-7`). This epic gives it a real implementation, reusing as much of the website-projects epic (sidebar, `ProjectType` trait) and the pandoc-writer-hybrid epic (single-document typst/epub rendering with correct crossref numbers) as possible, and building only the genuinely new pieces: chapter-aware numbering, single-file chapter merging, and project-wide cross-chapter crossref/bibliography resolution.

## Key architecture decisions (see design doc for full rationale)

- Book's Pass-2 dispatch is a concrete special case, not a new `ProjectType` trait method (revised by seventeenth-pass research — the original "one new overridable hook, `render_documents`" sketch wasn't `dyn`-safe, and turned out not to need to be generic in the first place). `ProjectPipeline<'a, RenderToFileRenderer<'a>>` gains `run_with_book_support()`, branching on `ProjectKind::Book` directly; `ProjectType`/`project_type_for` are untouched. `DefaultProjectType`/`WebsiteProjectType` are unaffected either way; the internal multi-pass machinery is entirely private, not shared/typed infrastructure.
- Single-file formats (Typst, EPUB, and — validated but not implemented — LaTeX/PDF) get book-wide numbering essentially free once chapters are merged into one AST *before* the Crossref phase runs — no cross-document registry needed there. Confirmed by reading Q1's `sections.lua` and Typst's vendored template, and empirically for HTML, Typst, and LaTeX (real `quarto render` renders inspected directly — see P2's and P4's appendices).
- Multi-file HTML needs a real, novel "Pass 3" *inside* `BookProjectType`: pause each chapter's transform pipeline after the `Navigation` phase (not, as an earlier draft of this epic imprecisely said, "between Crossref and Finalization" — `Navigation` sits between those two and must run per-chapter before the pause; see design doc §8), aggregate a project-wide crossref/citation registry, resume into `Finalization` — an AST-level replacement for Q1's DOM-postprocessing fixup, in-memory for now (disk persistence deferred until a freeze-style cache exists to make it cheap). The phase-bounded transform runner this needs was verified against the real pipeline code (`TransformPipeline::execute`'s loop holds no per-transform state; `RenderContext`'s only borrows are shared/immutable) — not just asserted from the phase enum's existence.
- Chapter-scoped numbering in multi-file mode reuses Q2's *existing* `CrossrefIndex.sections` counter (seeded with `chapter_number - 1`), not a new counter — mirrors Q1's own `number-offset`-into-Lua mechanism exactly, empirically verified, including the unnumbered-chapter case (an `.unnumbered` chapter consumes no chapter-number slot and its own floats number flat/unscoped, not chapter-scoped — verified against a real render).
- DOCX/PPTX book output: out of scope (see design doc §11). Manuscript: untouched.

## Definition of done

- A book project with `book.chapters`/`appendices`/`parts`/`references` renders correctly in both modes: multi-file HTML (per-chapter pages, correct sidebar, correct chapter-scoped numbering, cross-chapter refs resolved) and single-file merge (Typst compiled to one numbered PDF, EPUB with correct chapter splitting), verified end-to-end against real renders, not just unit tests.
- Numbering fidelity to Q1, verified empirically (not just by reading Q1's source) for every construct type `orange-book` exercises: figures, tables, equations, theorems/lemmas/definitions, listings, labeled callouts, sub-figure panels, and a custom `crossref.custom` kind — chapter-scoped (`N.M`), appendix-lettered (`A.M`), and correctly resetting/skipping for unnumbered chapters.
- Unified bibliography across chapters in both render modes — for single-file merge, via a review-pass-found fix that defers citeproc to one pass over the assembled document (not automatic, as an earlier draft assumed; see design doc §6), getting correct in-text numbers too; for multi-file HTML, via the project-wide registry (bibliography *list* only, matching Q1's own multi-file limitation).
- DOCX/PPTX/LaTeX book targets produce an explicit diagnostic or are simply not implemented — never a silent, wrong, unrelated-per-chapter-files fallback.

## Known limitations (v1)

- **No cross-chapter bibliography preview, and no single-file-merge preview.** P8 (added after the epic's original design was frozen) brings book-aware chapter numbering, title decoration, and an approximate, `StaticProjectAnalyzer`-based cross-chapter crossref resolution to `q2 preview`/hub-client — the "preview has zero book-awareness at all" gap this bullet originally described no longer applies once P8 lands. What P8 deliberately does not build: a merged-bibliography preview (no pre-engine analog exists to P6's per-chapter citeproc manifest — citation resolution isn't syntactically visible before engines run) or a single-file-merge preview (preview always renders as plain HTML regardless of the book's real target format; nothing to preview there). Deliberate, documented gap, not silence — P7's docs page should say so explicitly, and should reflect P8's scope precisely rather than the pre-P8 blanket statement.
- **No incremental rebuilds for books.** Pass 3's registry is held in memory for the duration of one render; nothing is cached across invocations. This is deferred until a freeze-style engine-result cache exists generally (see design doc §8) — persisting the registry without that cache would just move today's "engines never run twice" cost problem into a "sometimes engines run twice" one.
- **Both single-file merge (P2) and Pass 2 → Pass 3 (P4/P5) hold every chapter's data in memory simultaneously, for the duration of one book render — but not the same amount of data.** P2 holds every chapter's post-Normalization AST (the `Vec<Block>` body it merges) simultaneously, but not each chapter's `RenderContext`/`DocumentInfo`/`BinaryDependencies` — those can be dropped immediately after a chapter's body is extracted, one chapter at a time (see P2's plan). P5 is the heavier case: it holds every chapter's full `(Pandoc, RenderContext, DocumentInfo, BinaryDependencies)` checkpoint simultaneously across the Navigation→Finalization pause, since (unlike P2) it must resume each chapter's own `Finalization` independently rather than merging into one document. Same accepted-for-v1 posture either way: fine at `orange-book` scale, unverified at 50+ chapters. Revisit both together if it's a real complaint, not just the multi-file HTML case.
- **Pass 3's resume step is not parallelized in its first cut**, even though both halves (render-through-Navigation, resume-from-Finalization) look independently parallelizable per chapter, matching today's `render_batch_parallel` shape. Get the aggregation step correct serially first; parallelize as a deliberate follow-up once it's proven correct, not in the same change.
- **Pass 3's resume/write loop is not atomic across chapters — found by an eighteenth-pass review, resolved with the user as an accepted v1 limitation rather than a code fix.** Aggregation builds the whole-book crossref registry from every chapter's inventory *before* any chapter resumes into Finalization+write, so chapter A's already-written output can embed a resolved number/link into chapter B before B's own resume-and-write has happened. If B's write subsequently fails (disk full, permission error), the overall render still reports failure (the error propagates — this isn't silent), but A's file is left on disk referencing a chapter that was never produced, until the next full re-render. This sharpens a risk the codebase already accepts for ordinary multi-file project renders (some pages can already be written before a later one fails); the book-specific wrinkle is that a written sibling can *embed* a reference to the failed one. Accepted for v1 on the same terms as the limitations below — fine at fixture scale, revisit only if a real complaint surfaces. A cheap future mitigation, if needed: buffer all N chapters' resolved `RenderOutput`s in memory and defer every `write_rendered_output` call until all N resumes succeed (shrinks, not eliminates, the inconsistent-disk-state window) — see design doc §8.
- **Numeric citation styles renumber per chapter in multi-file HTML books** (`[2]` in one chapter, `[1]` for the same citation in another). Confirmed as a real, reproducible Q1 bug via a real render with an IEEE CSL, **and confirmed by reading `book-bibliography.ts` directly that Q1 has this identical bug too, silently** — its own DOM-postprocessing merge only ever rewrites citation hyperlink targets, never in-text marker text. Documented as inherited rather than fixed, since fixing it would make Q2 exceed Q1's own (undocumented) behavior. Author-date citation styles are unaffected. P6's bibliography-*list* merge (the part Q1 does do) is unaffected by this gap and ships regardless. **Single-file merge is not affected by this at all** — a composition-review pass found (and fixed) a related-but-distinct gap where Q2's own citeproc, unlike Q1's, was going to run too early (per-chapter, before merge) for single-file targets too; P2's fix defers it to one pass over the assembled whole, which gets correct in-text numbers for free, not just a merged list (design doc §6).
- **Per-chapter title-block metadata is not ported** — broader than "title/author overrides": Q1's `quarto-post/book.lua`/`title-block.md` mechanism renders a chapter's own subtitle, author affiliations, date, and abstract when its front matter sets them, not just an author/title override distinct from the book's. Q2 chapters use book-level title/author throughout and drop these fields silently. This is missing functionality, not an intentional design divergence — nothing architectural blocks porting it, and P4's chapter-title-decoration AST-insertion point is the natural seam. Tracked as `bd-ock6cyiy`, not this epic's job to build; P4 should leave that insertion point easy to extend (see design doc §7) without doing the work itself.
- **LaTeX/PDF book output is not implemented** — and this isn't really a book-specific scope decision: Q2 has no LaTeX/PDF Pandoc-hybrid output *at all* yet, for any project type (no compile stage exists in `quarto-core`), so there's no book-specific format-support gap here to diagnose or test. The abstraction (`top-level-division: chapter` + the already-vendored `book-numbering.lua`) was validated to generalize to it empirically anyway (see P2's appendix), for whenever LaTeX/PDF output exists in Q2 at all.
- **DOCX/PPTX book output is not implemented** — Q1's own book support there produces disconnected per-chapter files by default and isn't a real book feature even upstream.
- **No *general* bundled-extension auto-load mechanism — narrowed and resolved for the case that matters, by a fifteenth-pass decision with the user.** Q1 gives a Typst book chapter-scoped numbering/appendix-lettering for free, with zero config, by auto-loading the `orange-book` extension when no format extension is named (`render-contexts.ts`). Q2 has no equivalent *general* infrastructure — the closest related effort (`claude-notes/plans/2026-09-03-julia-engine-static-declarations-epic.md`) is a provisional, not-yet-started draft about bundling the Julia *engine*, not a general Typst-template mechanism — but this epic mirrors Q1's *specific* zero-config outcome for the one pairing it needs: a Typst book target with no explicit `format.typst` extension named now auto-resolves to the locally-vendored `orange-book` (P2, design doc §5), hard-coded to this one pairing rather than a general dispatch mechanism. **This closes the sharper, previously-open risk a taxonomy review found** — an appendix chapter silently rendering as an ordinary continuing chapter (no letter form, no error) for the *common*, no-extension-configured case — since that case no longer occurs by default. What remains a real v1 difference from Q1: a user cannot override the book default to a *different* Typst book extension without the general mechanism this epic doesn't build; document that narrower difference on P7's docs page, not the old, broader "you must explicitly reference an extension" framing.
- **P8's static preview sweep is uncached and adds a real, additional per-edit cost on top of Pass 1's existing (cached) sweep and the previewed document's own render — surfaced by design doc §12 but never promoted to this list, found by a taxonomy review.** Recompute on every preview call that touches a book project; no incremental/cached project-wide index in v1. This is a latency/UX cost, not a correctness gap (the approximation only affects displayed numbers, never link correctness — see design doc §12, item 2) — accepted for v1 on the same terms as the memory-scaling limitation above: fine at small scale, unverified at large scale, revisit if it's a real complaint. Document on P7's docs page alongside the other preview limitations.
- **Manuscript (`ProjectKind::Manuscript`) is untouched.** Its actual Q1 shape (one article + independently-rendered notebooks + MECA packaging) doesn't fit this epic's mechanism at all — see design doc §3.
