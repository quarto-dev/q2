## Overview

This is the **surface sibling** of the two mode plans (Plans 4/5). It extracts Plan 1's in-tree **`TextareaSurface`** — the reference `EditingSurface` impl (keystone §5, §12) — into a **bundled `editing-surface` extension** `editing-surface-textarea`, so the textarea becomes a *swappable* surface delivered like any other extension, on the same rail (keystone §6.1, Plan 2's delivery + `LOAD_CUSTOM_COMPONENTS`).

The decisive contract is the **two orthogonal axes** (keystone §2): **mode** (control/policy: when/where editing activates, navigation, commit policy) × **surface** (the widget that presents an active block's editable content and emits the edit). Plan 6 owns the **surface** axis for `textarea`. It is the dual of Plan 7 (`tiptap`), and it must work **unchanged** under *any* mode (`block-editing` ⊂ Plan 5, `nesting-cursor` ⊂ Plan 4) — the orthogonality proof (keystone §2: "any mode × any surface", §11 "active surface ❌ stackable — one widget renders an active block at a time").

> **CRITICAL FRAMING — this is a FAITHFUL EXTRACTION, not a redesign.** The textarea surface is today's textarea editing *behaviour* (the `EditTextarea` body + `renderMeasuredEdit` box-reproduction + `caretGeometry`'s visual-line/edge detection + caret placement) **relocated behind the `EditingSurface` contract** (keystone §5). **Do not change behaviour.** Every relocated test keeps its assertions; where an assertion's expected *value* must change because the seam moved (an import path; `ctx.X`/`mode.X` → an `EditingSurfaceProps`/`EditingSurfaceHandle` call), pre-validate the change with `prevalidating-test-seams` and bind it to a named revert hunk before writing code. The single most load-bearing DOM contract carried across the move is the active region `id="q2-active-edit-region"` (every `assertNoReflowOnActivation` caller, `ts-packages/preview-e2e-helpers/src/index.ts:28`) — it MUST survive byte-identical.

### The boundary this plan makes real (keystone §5)

The keystone's **hard boundary**: geometry/navigation (`onEdgeReached`, caret placement, first/last-visual-line, measure-and-set sizing) is the **surface's** responsibility, not the mode's. So **`caretGeometry` lives HERE** — it becomes the textarea surface's *internal implementation*, extracted out of today's `q2-preview/caretGeometry.ts` and out of the `EditTextarea` body (`dispatchers.tsx:137-484`). The mode delegates caret/edge to the surface via the `EditingSurfaceHandle`; it never assumes textarea (Plan 7's tiptap implements the same handle methods via ProseMirror selections).

### What stays mode-side (the boundary the extraction must NOT cross)

The textarea surface is **markdown string in, markdown string out** (keystone §5). It does NOT own:

- **`DocumentStore.commit` routing** — the surface fires `onCommit(text)`; the mode wraps prefixing containers + calls `commit` (keystone §3, §9). The §6 *delete-by-emptying* **commit policy** (the three-way `normalized===baseline`/empty guards) is the **mode's** decision about what an empty commit means — the surface just delivers the (possibly empty) text on commit. (The surface MAY pre-compute "is this dirty/empty" as a convenience the handle exposes, but the *policy* is the mode's.)
- **Activation / which block is active** — the mode's `ViewController.handleInput` decides; the surface only renders when the mode's `NodeOverride` selects it for the active block.
- **Cross-surface *navigation*** — the surface fires `onEdgeReached(dir)`; the mode resolves the landing surface and re-mounts. The surface owns the *edge detection*; the mode owns *where to go*.
- **`EditBufferCache` / clean-buffer generation** — the mode fetches `editableTextFor(node)` and hands the surface a clean `value` (keystone §3, §7.1). The surface never sees raw-vs-generated.
- **The `IME composition` gate, expand-on-edit policy** — judgement call, see "Open boundary questions" §. Default: the **mechanical** expand/auto-size (reading `scrollHeight`, clamping to `contentHeight`, the `overflow-y` clip rule) is *geometry* → surface-internal; the *decision* "this keystroke should expand" (the leave-key classification at `dispatchers.tsx:400-431`) is intertwined with edge detection (also surface) — so expand-on-edit is largely surface-internal, but **`s7-expand-on-edit` behaviour must stay byte-identical** and is pinned by a relocated test. IME composition gating (`isComposingRef`, `dispatchers.tsx:151,361-365`) is surface-internal (it gates the surface's own blur→`onCommit`).

**The Rust/WASM backend is unchanged.** Plan 6 is TypeScript-only (extension TSX + relocated TS tests + e2e). No `crates/` change is expected; if a task wants Rust, the scope was misread — STOP.

## Decision: extension packaging & location (consistent with Plans 4/5)

**Decision: ship `textarea` as a bundled editing-SURFACE extension at `resources/extensions/quarto/editing-surface-textarea/`** — the surface-axis **sibling** of Plan 4's `editing-mode-nesting-cursor/` and Plan 5's `editing-mode-block-editing/` — authored in TSX, delivered through Plan 2's discovery + the existing `customComponentsCode` / `LOAD_CUSTOM_COMPONENTS` rail.

This mirrors the mode plans' packaging decision verbatim, for the same grounded reasons, with the **one** axis difference that the manifest contributes an `editing-surface:` block (Plan 2's shape — `PLAN-2-KEY`) rather than `editing-mode:`:

1. **One rail, two front doors (keystone §6.1 / §8).** The delivery rail is `read paths → look up source → Babel-transpile → LOAD_CUSTOM_COMPONENTS → blob-import → merge`. Plan 2 adds extension-discovered `.tsx` as a second source feeding the same `customComponentsCode`. Author-style TSX discovered from an extension dir is the only artifact that flows through that rail — exactly the form the bundled `render-components` demos take. A `ts-package` would NOT be discovered, would NOT transpile through Babel-standalone, and would force a new path — contradicting "one rail."
2. **`resources/extensions/quarto/` is the established home for bundled, version-controlled extensions** (existing: `kbd/`, `lipsum/`, `placeholder/`, `version/`, `video/`, each with a `_extension.yml`). The External Sources Policy (CLAUDE.md) forbids `external-sources/`; bundling under `resources/` is the sanctioned pattern Plan 2's discovery already handles.
3. **`_extension.yml` is where the contribution is declared** (keystone §8). Co-locating the TSX + manifest in one extension dir is the only layout that satisfies the contract.

**Why a separate dir from the modes (and from `tiptap`).** Modes and surfaces are **two orthogonal axes** (keystone §2). At most one mode AND one surface are selected at a time (keystone §10, §11 "active surface ❌"). A dedicated surface dir keeps the **two-axis selection** (Plan 2) a clean one-of-N pick *per axis* and keeps the "any mode × any surface" matrix literal. `editing-surface-textarea` and `editing-surface-tiptap` (Plan 7) are independent surface tenants; the **shared primitives do not live in either surface** — `caretGeometry` is *this* surface's internal implementation (tiptap re-implements the same handle via ProseMirror), and the renderer-API primitives it imports (`byteLineMap`, `sliceSource`, the measure-and-set wrapper) live on Plan 1's surface.

**Boundary with Plan 1/2/3.** The *surface contract* (`EditingSurfaceProps`/`EditingSurfaceHandle`/`EditingSurfaceComponent`) and the in-tree `TextareaSurface` reference are **Plan 1's** (keystone §5; epic "Plan 1 produces"). The *manifest schema* (the `editing-surface:` contribution key, discovery of the dir's `.tsx`, two-axis selection) is **Plan 2's** (`crates/quarto-core/src/extension/{types.rs,discover.rs,read.rs}` + the host selection). This plan **extracts Plan 1's `TextareaSurface` into the manifest+TSX that conform to Plan 2's shape**, and marks the exact integration points (`PLAN1:` / `PLAN2:` / `PLAN-2-KEY`). If Plan 2's key name differs, a find-replace settles it (keystone §15.3).

Directory shape this plan creates (surface sibling of Plans 4/5):

```
resources/extensions/quarto/editing-surface-textarea/
  _extension.yml                 # editing-surface contribution (Plan 2 schema)  [PLAN-2-KEY]
  src/
    index.tsx                    # extension entry: exports the EditingSurfaceComponent (the surface)
    TextareaSurface.tsx          # the forwardRef EditingSurface impl (measure-and-set + handle)
    caretGeometry.ts             # MOVED from q2-preview/caretGeometry.ts — surface-internal now
    __tests__/                   # relocated surface-level vitest tests (see Phase 5)
```

> **NOTE — shared primitives import boundary (identical to Plans 4/5).** A discovered/transpiled extension cannot reach into `preview-renderer`'s source tree. So `editing-surface-textarea` imports React and the shared primitives + the `EditingSurface` contract **types** off the renderer API surface (`window.__Q2_PREVIEW_RENDERER__`): React (so the transpiled module shares the host React instance — see §"React boundary"), the measure-and-set textarea wrapper (`renderMeasuredEdit`), `byteLineMap`, `sliceSource`, and the `EditingSurfaceProps`/`EditingSurfaceHandle` **type contract**. **INTEGRATION POINT (Plan 1):** the exact accessor names + how the contract *types* are exposed to a transpiled extension are Plan 1's to publish (epic "Plan 1 produces"). Until known, import by the keystone names and mark `// PLAN1:`. **`caretGeometry` is the ONE thing this extension does NOT import — it OWNS it** (it is moved into the extension dir). Importing a duplicate of any *other* primitive (especially `renderMeasuredEdit`) is a plan failure.

### React boundary (surface-specific, not present in the mode plans)

Unlike a mode (which contributes a `ViewController`/`NodeOverride` that the framework calls), a **surface is a React component the mode renders** (`EditingSurfaceComponent = React.ForwardRefExoticComponent<…>`, keystone §5). A Babel-transpiled extension module must therefore use the **host's** React instance (hooks + `forwardRef` + context identity must match the renderer's), exactly as the existing render-components demos do (they read `React` off the renderer surface, `entry.tsx:107`). **Confirm in Phase 0** that Plan 1 exposes `React` (or the `forwardRef`/hook primitives) on `window.__Q2_PREVIEW_RENDERER__` such that a transpiled surface's `forwardRef` produces a handle the mode's `ref` can read. If Plan 1 does not yet expose React there, this is a **`PLAN1:` integration point** — file it; do not duplicate React into the bundle (two React copies break hooks). This is the single surface-axis novelty over Plans 4/5.

## Boundary with Plans 1, 2, 4, 5 (read before starting)

The plans touch overlapping code; the division is exact:

- **Plan 1** publishes the `EditingSurface` contract (`EditingSurfaceProps`/`EditingSurfaceHandle`/`EditingSurfaceComponent`, keystone §5), the in-tree `TextareaSurface` reference impl (with `caretGeometry` internal to it), and the renderer-API primitives (`renderMeasuredEdit`, `byteLineMap`, `sliceSource`, `caretGeometry` namespace). **In Plan 1, `caretGeometry` is internal to the in-tree `TextareaSurface`** (keystone §5 "caretGeometry becomes the textarea surface's internal implementation"). Plan 6 **extracts that in-tree `TextareaSurface` into the bundled extension** and **moves `caretGeometry` into the extension dir**, leaving (at most) a thin renderer-API re-export only if a non-surface consumer still needs it (Phase 5.1 audits — see the `caretGeometry`-ownership reconciliation below).
- **Plan 2** defines the `editing-surface:` manifest contribution + discovery + the **two-axis** selection that resolves the selected surface and feeds it to the mode as `ViewControllerProps.surface` (keystone §3.2: the mode renders the selected `surface`). Plan 6 authors the manifest+TSX that conform, and confirms the surface-axis selection installs this surface.
- **Plans 4/5 (modes)** render "the active surface" — they receive `surface: EditingSurfaceComponent` (keystone §3.2) and mount it for the active block; they **delegate** caret/edge to the surface handle and **never assume textarea**. Plan 6's surface is what they render. Plan 6 does **no mode work** and **owns no mode/nesting tests**.

## Risks & notes

- **`caretGeometry` ownership is the headline reconciliation.** Plans 1/4/5 all hedge ("if Plan 1 owns it"); Plan 6 makes it the surface's (keystone §5). Phase 0.4 records its current location; Phase 5/6.5 record the final ownership so the modes don't double-move. A mode importing `caretGeometry` after Plan 6 lands is a contract leak — route through the handle.
- **The active-region `id` is the single most load-bearing DOM contract** carried across the move (Phase 2.2). Every `assertNoReflowOnActivation` caller depends on `#q2-active-edit-region`. Verify by absence-of-regression: `edit-cell-sizing.spec.ts` is the backstop.
- **Geometry/no-reflow + visual-line detection are browser-only.** jsdom returns zero rects; `offsetTop`/`scrollHeight` are always 0 (documented in `caretGeometry.ts:13-18`). The sizing + edge-detection *correctness* is verified ONLY by Playwright (`edit-cell-sizing`, hub-client sizing specs). Do NOT declare Phase 2/3 done on vitest alone — gate on 5.3/5.4/6.2. jsdom tests verify structure (mirror cleanup, callback fired given a mocked edge), not pixels.
- **The surface is markdown-string-in/out — no commit-wire knowledge.** The biggest extraction error would be pulling `DocumentStore.commit`/`commitTextEdit` or the §6 delete *policy* into the surface. The surface fires `onCommit(text)`; the mode decides. If a relocated test asserts a *commit destination* or a *delete*, it is a mode test — leave it with the modes.
- **React boundary is the surface-axis novelty.** Two React copies break hooks. Confirm Plan 1 exposes React for transpiled extensions (Phase 0.2); this is the one thing a surface needs that a mode's `ViewController`/`NodeOverride` (called *by* the framework) does not.
- **Orthogonality is a real obligation, not a checkbox** (keystone §2). The demo (Phase 4) + its `fail-on-revert` (4.2) are the proof the mode↔surface boundary is complete. A surface that accidentally couples to one mode's shape is the subtle failure this plan exists to prevent.
- **Provisional names (keystone §15).** `EditingSurfaceComponent`/`EditingSurfaceProps`/`EditingSurfaceHandle` and the manifest key (`PLAN-2-KEY`) may be renamed by global find-replace; author against the keystone names and keep them greppable.
- **Reconcile with Plans 4/5 on vitest discovery + `caretGeometry` ownership.** Whichever runs second must not re-establish vitest discovery or re-claim `caretGeometry`. Phase 5.2 records the discovery choice; Phase 6.5 records `caretGeometry` ownership; the epic index is the reconciliation surface.
