## Goal

One resolver in `quarto-core` answers "which format, and which book scope was requested" from the same layers the merge stage uses, given the render's target. The per-document callers use it, and the orchestrator hands them the decision it made once for the render, so a whole html book renders every member as html even when one chapter says `format: typst`, while a website's pages keep their own formats. The old scope plumbing is still in place (F3b removes it); this plan does not change how the scope is *resolved* for the book dispatch, only how it is *requested* and how the format follows from it.

## Decisions

- **F3a-D1 Module and entry points** (`quarto-core/src/format_resolution.rs`):
  - `select_formats(inputs) -> FormatSelection { keys: Vec<String>, selected: String, source: LayerKind }`: pure, table-tested (FR1, FR2, FR4). Inputs: project keys, directory keys (taken from the **merged** `_metadata.yml` chain, not unioned per layer: FR1), document keys, `project_formats_only: bool`, the requested format (`cli_to`, then a runtime scalar `format`), fallback `"html"`. A runtime *map-valued* `format` is not an input. `null`/`false` entries skipped. List rule: `project_formats_only` → the project's keys; else document keys then directory keys, if non-empty, else the project's keys. The requested format may be undeclared and becomes `selected`; `keys` stays the declared list, so the Q-20-8 warning computes "skipped" as `keys` minus `selected`.
  - `requested_book_scope(value: Option<&str>) -> Result<Option<BookScope>, InvalidBookScope>` (FR5): the **one** function that interprets a `book-scope` value, over the scalar's string, so it has no dependency on `serde_json` or `ConfigValue` and compiles for wasm. Two thin adapters read the top-level `book-scope` key (never under `format.<x>:`) and call it: one over a `ConfigValue` layer (the resolver, through the collector) and one over a `serde_json::Value` object (the routes\' metadata; F4's captures pre-gate uses this one). An invalid value is reported to the caller (a diagnostic naming the layer) and yields `None`; a non-string value is invalid; `none` is invalid and its message says `none` is output only (FR5, FR9). No site compares the raw string.
  - `resolve_render_scope(project, target: &RenderMode, runtime) -> ScopeRequest { value: BookScope, explicit: Option<LayerKind>, diagnostics }`: reads top-level `book-scope` from the collector's layers (FR5): runtime > document > `_metadata.yml` > project, where document and `_metadata.yml` count only for exactly one active document (`ActivePage`, `Subset` of one) and never under `format.<x>:`; absent → the target's default (FR3: `Full` → `Book`; otherwise `Chapter`). `explicit` records which layer won (`None` for the default): F3b's Q-5-42 and Q-5-41 need it. Invalid value, `book-scope` under `format.<x>:`, a non-runtime `chapter` ignored in a `Full` render, and `book-scope` in a non-book project each emit a diagnostic (non-error); an invalid value is ignored and the next lower layer applies. **The project kind is checked first (FR6):** a runtime `chapter` with a `Full` target is the **error** "`book-scope: chapter` needs a file to render: name the chapter(s)" only for a **Book** project; for any other project, and for a standalone document, it is an info diagnostic and the request resolves as `chapter`.
  - `resolve_document_format(project, path, content_override: Option<&str>, request: &ScopeRequest, requested_format, runtime) -> FormatResolution { key, all_keys }` for one document; `resolve_project_format(project, request, requested_format, runtime) -> FormatResolution` for callers with no single document (the dispatch's project format, FR11). `project_formats_only` is computed here as "project is a Book and `request.value == Book`" (FR4). (`FormatResolution` is the result type's name; do not reuse the existing `ResolvedFormat` of `pandoc_request/formats.rs`.)
  - Request keys are normalised to the format key (`typst-pdf` → `typst`) through the existing mapping before `select_formats`.
- **F3a-D2 The orchestrator decides once, per-document callers follow.** The orchestrator computes the request through `resolve_render_scope` from its `RenderMode` (this is where the orchestrator first uses it; F3b-D3 reuses it for the dispatch). For a render of a **Book project** whose requested scope is Book, it computes the project format once and passes it to every per-document render through the existing `format_override`; so `render_document_to_file` (which calls `resolve_document_format` with the override as the requested format) renders every member in the project's format. **For any other project, even with a `Full` target, no format is forced** (a website's page with `format: revealjs` stays a deck: the override applies only when `project_formats_only` is true, which the resolver computes; the existing tests at `quarto-core/tests/integration/project_pipeline.rs:~719-803` exercise the format override and per-page behaviour, but on `type: default` projects (`:742`), not on a website or a book, so the website keep-the-deck test and the book keep-html test below are **new** work (3a.4)). For a Chapter render the override is only an explicit requested format (`--to` or a runtime scalar `format`) and otherwise `None`, so the document wins. `render_document_to_file` never learns the target: it always asks for a Chapter request, which is the right answer for every document the orchestrator did not pre-decide (a non-book project, a Chapter render). Tests (3a.4) pin: a `Full` render of an html **book** with a typst-saying chapter keeps it html through `render_document_to_file` and through Pass 3; a `Full` render of a **website** with a `format: revealjs` page keeps the deck; two named files each use their own format; an explicit `book-scope: book` with one file uses the project's.
- **F3a-D3 Callers migrated in this plan:** `render_to_file.rs` (~349), `multi_file_html.rs:182-192, 517`, `pandoc_request/formats.rs` (`resolve_formats` and `resolve_document_formats` call the resolver with chapter scope for the browser's classifier; the wasm-compiled module stays free of native-only code), `render_pandoc_request`. When `render_document_to_file` has a content override (`options.source_override`), the resolver's document layer and the `typst_output_ext` call (`render_to_file.rs:~375`) both read the **same bytes the render uses** (`input_bytes`, `~:320`), not a runtime re-read, or an editor-buffer render and its format would disagree. `format_key_from_frontmatter` and `format_keys_from_frontmatter` stay (the CLI's early guess and `preview_static.rs` still use them) and are deleted in F5b with `detect_single_input_format`; the wasm `detect_format_from_content` is deleted in F6. `frontmatter_format_keys` and `resolve_format_key` are deleted here.
- **F3a-D4 Diagnostics are catalogued.** Each new diagnostic gets a `Q-5-*` code, a catalog entry, a docs page and a sidebar entry in one commit (`error-docs-*` lint). They are warnings or info, never errors, except the FR6 `chapter`-needs-a-file error.
- **F3a-D5 The target mapping.** The resolver takes a `RenderMode`. For the CLI the argument classification (`RenderTarget`) maps onto it (`SingleDoc`/`Subset` of one → one active document; `FullProject` → `Full`); `Subset` of one and `ActivePage` are the same case for format and scope. A standalone document (`render_single_doc`, which sets no mode) is asked as `ActivePage(input)` without changing the pipeline's own mode (changing it would change `run_inner`). The orchestrator keeps its different dependency handling for `Subset` and `ActivePage` (graph augmentation). The CLI's "every file named is a whole-project render" collapse is a classification step, not the resolver's business: F5a skips it in `classify_inputs` for Book projects and re-applies it in the orchestrator, before the request is computed, only when every named file's format is non-consolidating (epic FR3); the resolver always sees the final target.

**Deviations from the plan text, and why.**
- `FormatSelection.source` is `Option<LayerKind>` (the layer that supplied the list; `None` = nothing declared) with a separate `requested` flag, because a requested format is not a layer. `FormatResolution::key_or(fallback)` exists because `render_document_to_file` and Pass 3 take the caller's `format` as the default for a document no layer gives a format (the preview pseudo-formats arrive that way); a bare `html` fallback would have changed them. The runtime scalar `format` is read by the resolver itself from the runtime layer; callers pass only `--to`.
- `resolve_project_format` takes `request` but does not use it yet (it is project keys plus the requested format either way). Kept for the signature F3b and F5a expect.
- The FR6 error is carried in `ScopeRequest.diagnostics` (kind `Error`, `Q-5-47`), not a `Result`. The orchestrator returns only the non-error notices in `project_diagnostics`; nothing raises the error until F3b (its interim check in `render.rs`). A non-book project with a runtime/other `book-scope` gets one `Q-5-46` info and the value resolves as asked.
- A `_metadata.yml` at the **project root** is not in the chain (existing `directory_metadata_paths_for_document` starts at the first subdirectory), so a root `_metadata.yml` `format:` is not seen by the resolver either; the merge stage has the same limit. Not changed here.
- `resolve_render_scope` reads the one active document's front matter from disk through the runtime (there is no content override on the scope path).
- The `QUARTO_PROFILE` environment route is not re-tested through a spawned binary here (quarto-core has no binary): `--profile` (`discover_with_profile(Some)`), `_environment`, and `profile.default` are tested through the resolver; the env var route reaches the same project layer and is covered by the `quarto` crate's `get_config_env_var_selects_overlay`.
- `render_pandoc_request` (listed in F3a-D3) takes its format key from its caller and never decided it from front matter, so nothing there needed migrating; the wasm `resolve_document_formats` (the classifier) goes through the resolver via `resolve_formats`.
