# Plan: Pass 3 — project-wide crossref registry (book-projects P5)

**Date:** 2026-09-21 (revised after a critical review pass; renumbered from a prior draft's P6 — see the epic doc's revision history)
**Epic:** [`2026-09-21-book-projects-epic.md`](2026-09-21-book-projects-epic.md)
**Design (authoritative):** [`../designs/book-projects-architecture.md`](../designs/book-projects-architecture.md) §8
**Prior art:** `crates/quarto-core/src/crossref/index.rs`'s own module doc (*"per-file indices can be persisted... and merged into a project-wide index... see Phase 4 of the design plan"*) and `claude-notes/plans/2026-04-15-crossref-design.md`'s "Phase 4 — Multi-file foundations" section, whose own O8 explicitly deferred appendix numbering "to the book-projects session" — this epic.
**Q1 reference (for the problem shape, not the mechanism — Q1's DOM-postprocessing approach is explicitly not being ported):** `book-crossrefs.ts`'s `bookCrossrefsPostRender`.

## Overview

This is the epic's most novel piece: resolving a cross-chapter `@ref` (one chapter references another's figure/table/theorem) without DOM postprocessing, which this repo's architecture policy prohibits. The replacement is an AST-level transform consulting an in-memory, project-wide registry — the same pattern `crates/quarto-core/src/transforms/link_rewrite.rs` already established for cross-document *link* rewriting in the website epic, extended from explicit hrefs to crossref ids.

## Decisions

- **"Pass 3," not "Pass 2a/2b."** The pause point is a real, fixed, already-existing seam — but a precise one, not the loose "Crossref/Finalization boundary" an earlier draft claimed. Grepping every `TransformPhase::Navigation` implementor (`sidebar_generate/render`, `navbar_generate/render`, `toc_generate/render`, `footer_generate/render`, `page_nav_generate/render`, `breadcrumbs_render`, `listing_generate/render`, and others) confirms all of it is page-local, config- or local-heading-structure-driven, and must run **before** the pause — Pass 2 runs Normalization, Crossref, *and* Navigation per chapter, then pauses immediately before Finalization. Confirmed against the actual precedent this design copies: `link_rewrite.rs` (cross-document link rewriting) has `phase() -> TransformPhase::Finalization`, not Navigation — Finalization, after Navigation, is where cross-document resolution has always belonged in this pipeline. Book rendering pauses there, aggregates, and resumes — it does not re-run engines a second time (that would double the actual expensive part of rendering; ruled out explicitly during design).
- **Mechanism, redesigned by a sixteenth-pass "step back and consider alternatives" conversation: the pause side is `execute_range` as before; the resume side is a second, previously-missing mechanism, not just a mirror-image `execute_range` call.** The pause (`..=Navigation`) reuses P2's `AstTransformsStage::for_range`/`build_html_pipeline_pause_stages` exactly as before — `TransformPipeline::execute_range` itself needs no new pipeline-construction machinery, and there's no new `PipelineData` enum variant, since this pause is between two `AstTransform` phases operating on the same `(Pandoc, RenderContext)` signature throughout.

  **The resume is not "the same call with a different range" — it needs a real stage list of its own, and a real story for how the output reaches disk, neither of which existed in any earlier draft of this plan.** `AstTransformsStage::run()` only ever runs *inside* the larger stage list `build_html_pipeline_stages_with_options` builds; there is no existing way to start a *fresh* stage-list call mid-way through it. The fix: reuse P2's `build_html_pipeline_finishing_stages(lower_bound)`/`run_pipeline_from_ast` — a general mechanism P2 builds first (it needs its own instance, `Crossref..`, for its merge step) — called here with `Finalization..`. This starts directly with a range-bounded `AstTransformsStage`, then the real, unchanged tail (`UserFiltersStage::post → ResourceReportStage → CodeHighlightStage → MathJsStage → RenderHtmlBodyStage → ApplyTemplateStage`), and returns a real `RenderOutput`.

  **Getting that `RenderOutput` onto disk is this phase's own new work, not reused from P2.** P2's targets (Typst, EPUB) write inside their finishing pipeline's own tail stages (`PandocWriteStage`/`TypstCompileStage`) — P2 never needs a separate write step. This phase's target is HTML, where writing is *not* a stage — it's the external `OutputSink` glue in `render_document_to_file` (`render_to_file.rs:453-472`, entirely outside `run_pipeline`). **Split `render_document_to_file` into its two already-implicit halves for real**: a "render" half (unchanged — resolve paths, build context, call the pipeline, return `RenderOutput`) and a new `write_rendered_output` function (build `OutputSink`, drain `ctx.artifacts`/`resource_copies`/`resource_report`, `sink.write`, `sink.flush`) that existing single-shot callers call right after the render half — byte-identical behavior, a refactor not a redesign. This phase's resume step then: reconstructs `RenderContext<'_>` from the held owned struct → calls `run_pipeline_from_ast(ast, ctx, build_html_pipeline_finishing_stages(Finalization..))` → gets a `RenderOutput` → calls the *same* `write_rendered_output`, once per resumed chapter.
- **P5's per-chapter owned struct — held simultaneously, one per chapter, in a book-scoped `Vec`.** Traced end to end against real code (design doc §6): the pause-side entry point takes `ctx: &mut RenderContext<'_>`, so **the caller constructs `RenderContext`, not the entry point** — nothing ever needs to hold a *constructed* `RenderContext<'a>` across the pause. P5's book orchestrator holds one plain owned struct per chapter (`doc_info`, `binaries`, plus copies of `RenderContext`'s owned fields — the **full** audited list, unlike P2's shorter one; see the checklist below and design doc §6 for why P5 needs every field P2 doesn't), built up front and kept alive until each chapter resumes; `RenderContext<'_>` is reconstructed fresh, borrowing from that struct, for the pause-side `execute_range(..=Navigation)` call and again for the resume-side `run_pipeline_from_ast(Finalization..)` call, then discarded. **Also recompute, don't carry, four more per-chapter values at resume time**: `resolver`, `output_path`, `resource_paths`, `project_type` — all cheap, deterministic functions of `input_path`/`format`/`project` in today's `render_document_to_file`, needed by `write_rendered_output` but not worth adding to the carry-list.
- **`run_with_book_support()`'s multi-file-HTML branch is where this lives, not a general orchestrator concept — and not a `ProjectType` trait method at all, resolved by a seventeenth-pass research round (design doc §3).** `ProjectType` gains nothing new; `run_with_book_support()` is a concrete method on `impl<'a> ProjectPipeline<'a, RenderToFileRenderer<'a>>`, branching directly on `ProjectKind::Book`. No `Checkpoint` associated type, no `Pass3Renderer` trait, no `needs_pass_three()` flag anywhere. `DefaultProjectType`/`WebsiteProjectType` are unaffected. If Manuscript ever needs a multi-step render, it gets its own seam in its own shape — not this one, since Manuscript's actual Q1 shape (independent article + notebooks + MECA packaging) doesn't fit this mechanism at all.
- **In-memory now; keep types serializable for later.** The crossref-design plan's own Phase 4 sketch proposed disk persistence (`.quarto/xref/<file-id>.json`). That's the right shape once a freeze-style engine-result cache exists (so re-deriving a chapter's AST for Finalization is a cache hit, not a re-execution) — Q2 has no such cache yet. Define `ChapterCrossrefInventory`/`ProjectCrossrefIndex` as `Serialize`/`Deserialize` (matching `CrossrefIndex` already being so) even though nothing serializes them in this phase, so the upgrade path is a drop-in later, not a redesign — and actually test the round-trip, not just declare the derive.
- **Shape the merge type so it directly serves P8's `StaticProjectAnalyzer` (preview) consumer too — no longer a hypothetical, P8 is now a real phase in this epic.** Same `ProjectCrossrefIndex` type, same `RenderContext` field (see the new Decision below), built from a cheaper pre-engine sweep instead of Pass 2's post-engine one. This phase builds the real producer; P8 only needs to populate the same field from a second, cheaper source and confirm the consuming transform doesn't care which produced it.
- **The registry entry shape**: id → `{owning_chapter_href, resolved_number (formatted string, e.g. "2.3"), caption_inlines, ref_type}`. Built from each chapter's `ChapterCrossrefInventory` (its own `CrossrefIndex.entries`, harvested at the pause point). **Correction, found by an eighteenth-pass review: `resolved_number` is not "already computed by the existing `CrossrefIndexTransform`" — the aggregation step must compute it itself.** `CrossrefIndexTransform` (Crossref phase, before the pause) only populates each entry's *raw* `Order` (the `order.order`/`order.section` counters); the *formatted* string is produced exclusively by design doc §7's `format_crossref_number(order, chapter_seed)` helper, called from `CrossrefRenderTransform`'s display functions — a **Finalization**-phase transform that hasn't run for any chapter yet at this phase's pause point (immediately after Navigation). The aggregation step must call `format_crossref_number` itself, once per harvested entry, using that chapter's raw order data plus its own `ChapterSeed` (both already present in the paused checkpoint) — this is real, previously unstated aggregation work, not "just aggregation of what P4 already produces per chapter."
- **How the transform reaches the registry — a new `RenderContext` field, not a book-only pipeline splice (a real gap found by a review pass: this plan previously stated the transform's phase and position but never said where it's registered).** `CrossChapterCrossrefResolveTransform` is registered as an ordinary member of the shared `build_transform_pipeline` (Finalization phase, before `CrossrefRenderTransform`) — not spliced into some book-only pipeline construction — and no-ops (leaves `CrossrefResolvedRef` nodes exactly as `CrossrefResolveTransform` left them) whenever its `RenderContext` field is absent. That field — **`cross_chapter_crossref_registry: Option<Arc<ProjectCrossrefIndex>>`** — follows the same builder idiom as `chapter_seed`/`project_index` (`with_cross_chapter_crossref_registry(...)`), populated by this phase's resume orchestrator right before each chapter's `execute_range(Finalization..)` call. Because the transform only ever touches nodes already marked unresolved by `CrossrefResolveTransform`, it cannot clobber a chapter's own correct local resolution — resolution precedence (local wins, the registry is fallback-only) is safe by construction, not something the transform needs to check explicitly. Registering it unconditionally in the shared pipeline (rather than book-only) is what makes it a true no-op for every non-book render **and** what lets P8 reuse it verbatim for preview, feeding the same field from a cheaper, pre-engine-only producer instead of this phase's real post-engine aggregation.
- **Deliberately serial in this first cut — stated explicitly here, not only in the epic doc's Known Limitations** (added by a review pass: this fact previously existed nowhere in this plan itself, so an implementer working from this file alone had no signal it was intentional). Both halves of the pause/resume round-trip (render-through-Navigation, resume-from-Finalization) look independently parallelizable per chapter, matching `render_batch_parallel`'s shape — but get the aggregation step correct serially first; parallelize as a deliberate follow-up once proven correct, not in the same change. Contrast P4, which explicitly keeps `Pass2Renderer`'s existing parallel `render_batch*` machinery for its own (non-paused) per-chapter renders — this phase's *aggregation/resume* step is the part that's serial, not chapters' initial Pass 2 render through Navigation.
- **Accepted v1 limitation, resolved with the user (eighteenth pass): the resume/write loop is not atomic across chapters.** Because aggregation builds the whole-book registry from every chapter *before* any chapter resumes, chapter A can be written (embedding a resolved link/number into chapter B) before chapter B's own resume-and-write happens; if B's write then fails, A's already-written file references a chapter that was never produced, until the next full re-render. The overall render still reports failure (the error propagates) — this isn't silent, just undocumented until now. Document as a Known Limitation (epic doc), not a blocker; see design doc §8 for the full analysis and the future-mitigation sketch (buffer all N `RenderOutput`s, defer every write until all N resumes succeed) if this ever becomes a real complaint.
- **Forward-compatibility note for P6**: P6's bibliography merge wires a new `ChapterCitationManifest` into "P5's per-chapter held struct/`Vec`... the same way `ChapterCrossrefInventory` does" (see P6's plan) — build the held-checkpoint type so a field can be added later without restructuring the pause/resume mechanism itself (e.g. don't hard-code it as a fixed-arity tuple `(BookRenderItem, Pandoc, RenderContext, ChapterCrossrefInventory)` that's awkward to widen; a struct with named fields extends more easily). Whichever of P5/P6 lands first should leave this room, not assume the other will restructure it later.
- **One dependency on P4, both now resolved by research but still a real sequencing requirement.** This phase's aggregation step reads whatever chapter-scoped numbers P4 actually produces for figures/tables/equations. P4's `order.section`-vs-`order.order` gap (design doc §7) now has a concrete fix (read `ctx.chapter_seed.chapter_number` directly in `crossref_render.rs`'s display functions) — confirm P4 has actually *landed* that fix before relying on its output here; a resolved design isn't a shipped implementation. (The `render_documents`/`Box<dyn ProjectType>` object-safety dependency this bullet used to name is fully resolved, not just designed — `run_with_book_support()` is a concrete method, so there's no trait signature to wait on; see design doc §3.)

## Checklist

### Tests first
- [ ] Unit test: aggregating 3 chapters' `ChapterCrossrefInventory` (each with distinct crossref ids) into a `ProjectCrossrefIndex` produces the expected id → (href, number, caption) map, with no chapter needing to know about any other during its own local pass.
- [ ] Unit test: `ChapterCrossrefInventory`/`ProjectCrossrefIndex` round-trip through `serde_json` (serialize, deserialize, compare) — proves the "serializable from day one" decision is real, not just a derive that's never been run.
- [ ] Unit test: a duplicate id across two chapters produces a diagnostic identifying both locations (mirrors the existing single-document duplicate-id diagnostic's shape and O7's resolution in the crossref design plan), not a silent last-wins overwrite.
- [ ] Integration test: chapter 1 references `@fig-x` defined in chapter 3 — after the full render, chapter 1's HTML contains the correct number and a working relative link into chapter 3's actual output file. Verified by reading the rendered HTML file from disk, per this repo's end-to-end verification rule — not by inspecting the AST alone.
- [ ] Integration test: an id that exists in *no* chapter still produces the P4-established "unresolved" placeholder (not a crash, not a silently-wrong number) — confirms P5 is additive over P4's contract, not a replacement of its error handling.
- [ ] Integration test: the pause/resume round-trip is verified to *not* re-run engine execution — instrument a test fixture with a counter-incrementing code cell and assert it executes exactly once per chapter across the full P4→P5 flow.
- [ ] Integration test: sidebar/navbar/TOC output (Navigation phase, run before the pause) is unaffected by anything the aggregation step or the resumed Finalization phase does — confirms the phase split didn't leak Navigation-phase work across the boundary.
- [ ] Regression test: a non-book (or single-file-merge) render never populates `cross_chapter_crossref_registry`, and `CrossChapterCrossrefResolveTransform` is a true no-op in that case — output byte-identical to today's pre-P5 behavior. This is the guard that makes registering the transform in the *shared* `build_transform_pipeline` (rather than a book-only pipeline) safe.
- [ ] Unit test extending P2's owned-struct/reconstruction round-trip test to P5's harder case: build 3 chapters' owned structs simultaneously (not one at a time, per P2's drop-immediately pattern), call the pause-side entry point on each with `..=Navigation`, then resume each independently via `run_pipeline_from_ast(Finalization..)` — assert each chapter's own owned fields (**the full, audited list — unlike P2's, which needs only a short subset, this phase genuinely needs all of it**: `artifacts`, `diagnostics`, `crossref_index`, `ref_type_registry`, `project_index`, `resource_resolver`, `options`, `includes`, `pipeline_profile`, `observer`, `user_grammar_provider`, `resource_report`, `resource_copies`, `code_block_decorations`, `attribution_provider`, `attribution_data`) come back correctly attributed to *that* chapter, not cross-contaminated with another chapter's held state. This is the regression guard specific to P5's "N structs alive at once" requirement, which P2's own version of this test (a single struct, used and dropped) can't exercise. `attribution_data`/`code_block_decorations`/`crossref_index` are the sharpest cases here specifically: all three are read only in the *resumed* Finalization phase (or, for `crossref_index`, by this phase's own aggregation step before the resume), so a bug that drops them during the pause wouldn't surface until later, not immediately.
- [ ] **Resolved before implementation, per the user's explicit ask**: confirm `AttributionGenerateStage` (populates `RenderContext.attribution_data`, if a provider is installed) genuinely cannot double-fire across this phase's two calls. It's a plain `PipelineStage`, not a `TransformPipeline`/`AstTransform` member (`pipeline.rs:5202`'s `t6_3_attribution_generate_is_stage_only_not_a_transform_pipeline_member` pins this structurally) — it runs once, in the initial pre-pause stage-list call, entirely outside what `execute_range` iterates over and entirely outside the resume-side finishing pipeline (which starts fresh at `Finalization..`, never re-running it). No new mechanism needed; the only real risk this surfaced was the `attribution_data` carry-list gap above, not a control-flow one. See design doc §8 for the full trace.
- [ ] Integration test: `run_pipeline_from_ast(Finalization..)`'s own `RenderContext↔StageContext` bridge round-trips this phase's full field list correctly, both in (at the resume call) and out (before `write_rendered_output` reads `ctx.artifacts`/`resource_copies`/`resource_report`) — this is the concrete fix for the bridge-completeness gap an implementability review found (`run_pipeline`'s existing bridge only carries ~8 of 16 fields, because no existing caller ever needed more); confirm it's actually complete for *this* phase's needs, not just declared so.
- [ ] Integration test: `write_rendered_output`, called from this phase's resume step, produces a real HTML file at each chapter's own (recomputed, not carried) `output_path`, with artifacts/resource copies/resource report correctly drained — and confirm the *existing* single-shot `render_document_to_file` callers are byte-identical after being split into "render" + "write" halves (regression guard on the refactor itself).

- [ ] P4's `order.section`-vs-`order.order` figure/table numbering fix (design doc §7, resolved: `crossref_render.rs`'s display functions read `ctx.chapter_seed.chapter_number` directly) is actually implemented, not just designed — confirm before relying on P4's per-chapter numbers in this phase's aggregation.
- [ ] P1's `run_with_book_support()` (design doc §3, resolved) exists on `ProjectPipeline<'a, RenderToFileRenderer<'a>>` — this phase's multi-file-HTML branch lives inside it.

### Implementation
- [ ] `ChapterCrossrefInventory`/`ProjectCrossrefIndex` types (serializable from day one, per the decisions above).
- [ ] Split `render_document_to_file` into a "render" half (unchanged) and a new `write_rendered_output` function (the existing `OutputSink`/artifact-drain/`sink.write`/`sink.flush` tail, `render_to_file.rs:453-472`) — existing callers call both back-to-back. **This phase builds the split; P2 doesn't need it** (its targets write inside their own finishing-pipeline tail stages).
- [ ] `run_with_book_support()`'s multi-file-HTML branch, extended: Pass 2 (P4) now stops after `Navigation` via P2's `AstTransformsStage::for_range`/pause-stage constructor instead of finishing; a new aggregation step builds the registry; a resume step, per chapter, reconstructs `RenderContext`, calls `run_pipeline_from_ast` with `build_html_pipeline_finishing_stages(Finalization..)` to get a `RenderOutput`, recomputes `resolver`/`output_path`/`resource_paths`, then calls `write_rendered_output`.
- [ ] New `CrossChapterCrossrefResolveTransform` (`Finalization` phase, before the existing `CrossrefRenderTransform`, registered unconditionally in the shared `build_transform_pipeline`): reads `ctx.cross_chapter_crossref_registry`, no-ops when `None`; otherwise finds unresolved `CrossrefResolvedRef` nodes, looks them up in the registry, resolves them in-AST — modeled directly on `link_rewrite.rs`'s existing pattern for cross-document link resolution.
- [ ] New `RenderContext` field `cross_chapter_crossref_registry: Option<Arc<ProjectCrossrefIndex>>` + `with_cross_chapter_crossref_registry(...)` builder, matching the `chapter_seed`/`project_index` idiom.
- [ ] `cargo clippy -p quarto-core --all-targets -- -D warnings`; `cargo nextest run -p quarto-core`; phase-boundary `cargo nextest run --workspace` with delta reported.

## Details

This phase is where "fidelity to Q1" is weakest by necessity — Q1's DOM-postprocessing approach is architecturally prohibited here, so the *mechanism* is genuinely new even though the *observable result* (a correct cross-chapter reference) must match. Keep the observable-behavior fixtures (the multi-file HTML equivalent of `orange-book`'s cross-chapter assertions, e.g. "Dinosaur 2.1 referenced from chapter 3 shows 2.1, not renumbered") as the actual acceptance bar, not a structural resemblance to Q1's implementation.
