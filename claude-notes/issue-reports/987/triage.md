# Issue #987 — q2 mcp: full-size screenshots cannot be uploaded because bytes travel through the conversation

- **GitHub**: https://github.com/quarto-dev/q2/issues/987
- **Reporter**: @midleman (Marie Idleman), 2026-10-30
- **Triage date**: 2026-10-30
- **Worktree**: none, at the maintainer's request: topic branch `issue-987` in the main checkout, based on `main` @ `ad262fde8`
- **Braid strands**: bd-llklgl70 (feature), bd-jiwob9g7 (incidental bug)
- **Scope**: uploading local files to a hub project through `q2 mcp`. Excludes the read direction (getting large binaries out of a project) and URL sources (see below).

## Summary

The report is accurate, and the title is the clearest statement of it. `edit` with `action: "write"` and `encoding: "base64"` already writes an image to any project path. The limit is how the bytes reach the server: they are a tool-call argument, so the model has to emit the whole base64 string as output. A 5 MB screenshot is about 7 million characters, which no model can practically emit. The reporter wants the server to read the bytes itself. This is a real feature gap, and the fix is small. Triage also found a separate bug: base64 writes above about 3 MB fail with a stack overflow.

## Reproduction

There are two parts, and neither needs a live hub.

**The conversation limit** follows from arithmetic. Base64 output is 4/3 of the input size, and every character must be generated by the model:

| Screenshot | `content` length |
| ---------- | ---------------- |
| 1 MB       | 1.4 M chars      |
| 5 MB       | 7.0 M chars      |
| 10 MB      | 14.0 M chars     |

**The server is not the limit, apart from the bug.** `large-write-probe.test.ts` drives the real server with an in-memory client and test hub. To run it, copy it to `ts-packages/quarto-hub-mcp/src/` and run `npx vitest run <file> --disable-console-intercept`.

| Payload | As shipped                                 | Validation regex bypassed     |
| ------- | ------------------------------------------ | ----------------------------- |
| 1 MB    | ok                                         | ok, synced, 97 ms             |
| 5 MB    | `Maximum call stack size exceeded`         | ok, synced, 545 ms            |
| 10 MB   | same error                                 | ok, synced, 1076 ms           |
| 25 MB   | same error                                 | ok, synced, 2640 ms           |

So once the bytes are in the server process, the write path handles full-size images in about a second.

`repro.mjs` isolates the bug to the regex: on Node 24, 3 MB passes and 3.5 MB throws `RangeError`. The exact threshold depends on the engine and stack size.

## Localization

- `ts-packages/quarto-hub-mcp/src/tools.ts:1099` `decodeBase64`: the regex with the repeated `{4}` group that overflows.
- `ts-packages/quarto-hub-mcp/src/tools.ts:2019` `handleWriteFileBinary`: create or replace, with dangling-entry refusal, `expected_hash`, `create_only`, and `synced`. It decodes `content` as its first step, so splitting that off lets a new arm reuse the rest unchanged.
- `ts-packages/quarto-hub-mcp/src/tools.ts:2957` `inEdit`: the discriminated union that gains the new arm.
- `ts-packages/quarto-hub-mcp/src/tools.ts:3320`: `edit` is not registered under `--read-only`, so the new arm inherits that gating.
- `hub-client/src/services/resourceService.ts:167` `FILE_SIZE_LIMITS`: the 10 MB per-file limit for uploads in the web client. The MCP write path has no equivalent, which is why 25 MB was accepted.

## Open questions — resolved during triage

**New tool, or an arm on an existing one?** An arm. The maintainer's first instinct was a new tool, and the capability is right, but `claude-notes/plans/2026-10-13-mcp-tool-consolidation.md` makes "a new arm on an existing tool" the default answer to capability requests. The result shape and guards match `write`, so `edit` is the natural home. It should be a separate `action: "upload"` arm because `write` requires `content`.

**Can the server see the file?** Today yes, in the usual case: `q2 mcp` and `npx @quarto/hub-mcp` are stdio-only and run on the user's machine. Two cases do not work:

- Sandboxed hosts, where the agent's filesystem differs from the server's. The error for a missing file has to say so, rather than only "not found".
- The planned in-hub HTTP mount (`claude-notes/plans/2026-10-07-hub-mcp-streamable-http-design.md`). A path there would name a file on the hub machine, so the arm must not exist over HTTP. It joins the §8 exceptions alongside `render`. Browser-hosted agents would need their own upload channel, which is a separate design.

**Is it safe to let the server read local paths?** Not without limits, and this is the main design point. The server reads project text written by people the user may not know, and that text can carry prompt injection. A general `local_path` would let such text ask for `~/.ssh/id_rsa` to be uploaded to a shared project, and that read would bypass the file permissions of the host. The first version therefore:

- accepts only PNG, JPEG, GIF, and WebP, verified by magic bytes rather than the extension (SVG is excluded because it is text and cannot be verified this way);
- caps size at 10 MB, matching the web client;
- requires an absolute path and checks the resolved target, so a symlink named `x.png` pointing at a non-image is refused by the same check.

This meets the reported need, screenshots, with default-on behaviour. An image can still contain private content, so this reduces the exposure rather than removing it. Non-image files are left for a later opt-in flag on the `--allow-render` model if someone asks.

**Should URLs be supported too?** Not in the first version. The issue offers them only as an example, the reported case is local, and fetching URLs adds SSRF handling.

**Does the bug block the feature?** No. The new arm does not decode base64, and it is unreachable for most model-driven calls anyway. The bug is filed separately because it gives a misleading error to any scripted client sending more than 3 MB. A linear check passed on 70 M chars during triage.
